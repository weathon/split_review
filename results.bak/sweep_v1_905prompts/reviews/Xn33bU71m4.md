## Summary

This paper systematically evaluates nine open-source LLMs (CodeLlama, Llama 2, DeepSeek-R1, etc.) on two reverse engineering tasks — name recovery and type inference — using a dataset of 40,000 stripped binary functions across four architectures (x86-64, x86-32, ARM, MIPS) at multiple optimization levels. The study finds that current LLMs perform poorly on both tasks, with most F1 scores below 0.10 for type inference even after fine-tuning, though variable name recovery shows some improvement (up to 0.33) after LoRA fine-tuning. The paper's main contribution is the large-scale systematic benchmarking and the automated evaluation pipeline.

## Strengths

1. **Large-scale systematic benchmarking across diverse conditions.** The paper evaluates 9 LLMs on a 40,000-function dataset spanning 4 architectures and 4 optimization levels (Section 4.1). The result tables (Tables 2–6) provide concrete evidence that current mid-sized LLMs perform poorly on type inference (all F1 < 0.10) and modestly on variable name recovery (best F1 = 0.33 after fine-tuning), supporting the paper's main negative finding.

2. **CodeWordNet-based evaluation provides fairer measurement of name recovery.** The paper adopts the SYMLM method using CodeWordNet to assign partial credit for semantically equivalent names (Section 3.4). Figure 1 demonstrates that without CodeWordNet, F1 scores drop sharply (e.g., Qwen3 from ~0.25 to ~0.08), confirming that the low absolute scores reflect genuine task difficulty rather than strict string-matching artifacts.

3. **Fine-tuning analysis reveals nuanced, task-dependent results.** The paper fine-tunes all models with LoRA and reports per-task results (Tables 2–4). Finding 1 highlights that improvements are inconsistent — e.g., DeepSeek-V2's variable name recovery F1 drops from 0.10 to 0.05 after fine-tuning on O1 (Table 3). This goes beyond a simplistic "fine-tuning helps" narrative.

4. **Real-world firmware evaluation with two decompilers provides practical grounding.** Table 6 reports near-zero F1 scores on stripped firmware binaries, confirming that the findings hold in a realistic setting. The comparison between Ghidra and IDA Pro outputs (e.g., CodeLlama type inference: 0.10 for IDA Pro vs. 0.03 for Ghidra) adds practical insight.

## Weaknesses

### Fatal

None.

### Major

1. **The abstract and introduction claim an F1 score of 0.37 for fine-tuned DeepSeek-R1 that does not appear in any result table.** Both the abstract and introduction (line 23) state: *"after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37."* Yet the highest F1 score for DeepSeek-R1 across all tables in the paper is **0.17** (variable name recovery, O0, Table 3). For function name recovery the best is 0.05; for type inference it is 0.01; for assembly it is 0.00; for firmware it is at most 0.07. The 0.37 figure is the strongest positive claim in the paper, presented as a headline result, but it is entirely unsupported by the data shown. This is not a minor imprecision — it is a factual inconsistency that undermines the credibility of the reported results. Until the authors clarify which task, metric, architecture, and optimization level produced this number, or correct it if it is an error, the reader cannot rely on the paper's quantitative claims.

2. **The auxiliary-LLM post-processing pipeline is never validated.** The paper uses an auxiliary LLM to normalize heterogeneous model outputs into a uniform schema (Section 3.2). This is a practical approach, but the accuracy of this step is never evaluated — no human validation, no synthetic test with ground-truth outputs, no error analysis. If the auxiliary model mis-parses, omits, or alters predictions, the reported F1 scores could reflect the auxiliary model's formatting ability rather than the target model's reverse engineering ability. This affects all quantitative results in the paper.

3. **No variance, confidence intervals, or statistical significance reported.** All results are point estimates (single F1 values). Given the randomness inherent in LLM generation and the random sampling of the dataset, it is impossible to gauge whether observed differences between models or between fine-tuned and original variants are meaningful or simply noise. For a benchmark paper whose primary output is comparative performance numbers, this is a basic omission.

4. **No comparison against specialized reverse engineering baselines.** The paper's motivation (Section 2) explicitly discusses SYMGEN, RESYM, and VARBERT as prior work, yet the experiments include only general-purpose LLMs. There is no comparison to published results from these specialized models. Without this context, the conclusion that *"current LLMs remain fundamentally limited"* lacks a benchmark against the actual state of the art in the field.

### Minor

1. **Internal inconsistency between Table 2 and Figure 1.** Table 2 reports CodeLlama O0 function name recovery F1 as 0.04 (original model), while Figure 1 reports CodeLlama O0 function name recovery "with CodeWordNet" as ~0.15. Both claim to measure function name recovery on x86-64 via decompiled code. The paper does not explain this ~3-4x discrepancy, making it unclear which values are authoritative.

2. **Prompt sensitivity is not explored.** The paper uses a single fixed prompt (from a prior ChatGPT study) for all models. The authors state they avoid prompt optimization to prevent bias, but this choice could systematically disadvantage models with different instruction-tuning styles. A sensitivity analysis with 2-3 prompt variants on a subset of models would clarify whether results are robust to prompt wording.

3. **Strict type inference metric inflates difficulty.** The paper acknowledges that type inference uses strict equality (Section 3.4), but does not discuss whether partial credit (e.g., matching base types for `unsigned int` vs. `int`) would yield more informative results. Given that all type inference scores are below 0.10, the strictness likely contributes to the floor effect.
