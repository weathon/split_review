## Summary

ToolLLM presents a comprehensive framework for enabling open-source LLMs to use real-world APIs. The paper contributes: (1) ToolBench, a dataset of 126k instruction-solution pairs covering 16,464 real REST APIs across 49 categories; (2) DFSDT, a depth-first search-based decision tree reasoning strategy that outperforms ReACT; (3) ToolLLaMA, a fine-tuned LLaMA-2 model that achieves performance comparable to ChatGPT on tool-use tasks; (4) ToolEval, an automatic evaluator with strong human correlation; and (5) a neural API retriever. The scale of the dataset, the breadth of real API calls (469k+), and the systematic evaluation across three generalization levels represent a significant step forward in tool-use research.

## Strengths

- **Large-scale, real-world multi-tool dataset**: ToolBench collects 16,464 real REST APIs from RapidAPI and generates 126,486 instruction–solution pairs covering single-tool **and** multi-tool scenarios, far exceeding prior datasets in scale, realism, and complexity (Table 1). The inclusion of 469,585 real API calls during annotation grounds the data in actual execution outcomes rather than simulated responses — a distinguishing feature from works like APIBench and ToolAlpaca.

- **DFSDT significantly outperforms prior reasoning strategies**: Across all instruction types, DFSDT achieves an average pass rate of 63.8% vs. 35.3% for ReACT and 44.5% for ReACT@N (Table 3, evaluated using ChatGPT). The improvement is largest on the hardest multi-tool settings (I2 and I3), where DFSDT nearly doubles the pass rate of ReACT@N. The ReACT@N control is a fair baseline that matches total inference cost.

- **ToolLLaMA achieves performance comparable to ChatGPT**: Using DFSDT, ToolLLaMA reaches a pass rate of 66.7% and win rate of 60.0%, outperforming Text-Davinci-003 (43.1% pass, 46.3% win) and Claude-2 (22.6% pass, 43.5% win), while ChatGPT+DFSDT obtains 64.8% pass and 64.3% win (Table 4). This demonstrates that a fine-tuned 7B open-source model can match a much larger closed-source teacher model on this task distribution.

- **Neural API retriever substantially outperforms baselines**: The trained retriever achieves 78.0% NDCG@1 and 84.9% NDCG@5, far exceeding BM25 (18.5%, 17.0%) and Ada embeddings (49.6%, 45.4%). Notably, when integrated with ToolLLaMA, retrieval sometimes surpasses the oracle API set (e.g., I1-Inst. pass rate 64.0% with retriever vs. 57.0% with ground-truth APIs), showing the retriever can find functionally superior APIs.

- **Systematic evaluation across three generalization levels**: The paper tests on unseen instructions (Inst.), unseen tools from seen categories (Tool), and unseen tools from unseen categories (Cat.) — a rigorous design that cleanly measures how well the model adapts to novel APIs from documentation.

- **Automatic evaluator with validated human correlation**: ToolEval achieves 87.1% agreement on pass rate and 80.3% on win rate with human annotators, providing a scalable evaluation method for tool-use tasks where ground-truth solution paths are hard to pre-specify due to temporal API variability.

## Weaknesses

### Fatal
None.

### Major

- **Evaluation distribution is confounded with the training distribution, weakening the headline "on par with ChatGPT" claim.** Both ToolBench's training data (instructions, solution paths) and its test sets (I1/I2/I3 across all generalization splits) are generated by the same ChatGPT model. Consequently, ToolLLaMA's reported pass rate of 66.7% vs. ChatGPT's 64.8% largely measures how well the student distills the teacher's output distribution rather than emergent generalization to independently-written queries. The APIBench OOD experiment partially addresses this concern, but APIBench is a simpler single-tool, single-domain benchmark that does not test multi-tool reasoning. This structural issue does not invalidate the dataset contribution (ToolBench is valuable regardless) but means the "on par with ChatGPT" framing gives a misleading impression of the evidence. The paper's own three-level generalization splits (unseen instructions/tools/categories) are a step in the right direction because they at least test held-out *compositions*, but the underlying queries still come from the ChatGPT distribution.

### Minor

- **ToolEval uses the same model family (ChatGPT) as both the solution-path generator and the evaluator, introducing potential stylistic bias.** While the paper reports solid human agreement (87.1%/80.3%), known LLM-as-judge bias toward outputs resembling the judge's own style could inflate win rates for methods whose outputs are ChatGPT-derived. This concern applies most to the win-rate metric; pass rate is less affected since it measures objective execution success.

- **OOD generalization claims on APIBench are overstated relative to the evidence.** The paper asserts "remarkable OOD generalization performance" (Section 3.3), but Table 5 shows mixed results: on HuggingFace, ToolLLaMA+Our Retriever achieves only 16.77% AST (vs. Gorilla-RS+BM25 at 15.71% — a tiny gap of 1 point), and on TensorHub it underperforms Gorilla-RS+BM25 (40.59% vs. 41.90%). Only TorchHub shows a clear lead (51.16% vs. 50.00%). With the oracle retriever, ToolLLaMA+Oracle is competitive but often slightly behind Gorilla-RS+Oracle (e.g., HuggingFace: 88.80% vs. 89.27%). The low absolute AST on HuggingFace (16.77%) also suggests significant domain difficulty that is not discussed.

- **No analysis of failure modes or error patterns.** The paper reports aggregate pass/win rates but does not break down where models fail — whether from API unavailability, planning mistakes, parameter hallucination, or irrelevant API retrieval. A failure taxonomy would materially improve the paper's utility for future work.

- **No statistical significance or confidence intervals reported.** Table 4 reports point estimates without error bars. Given that several comparisons are close (e.g., ToolLLaMA-DFSDT 57.0% vs. ChatGPT-DFSDT 54.5% on I1-Inst.), it is unclear whether observed differences are meaningful. The test set sizes are also not reported in the main table, making it hard to assess estimate reliability.

### Trivial

- The paper notes that API filtering criteria are deferred to the appendix; a brief summary in the main text would improve self-containedness.
- The claim that generated instructions "have a high diversity" (Section 2.2) is asserted without quantitative evidence (e.g., n-gram diversity or embedding coverage); the reference to an Atlas visualization is not shown.
- The average reasoning trace length (4.0 steps) is stated, but the distribution (e.g., min, max, variance across I1/I2/I3) would be more informative.

## Nice-to-Haves

- A human-written evaluation set (even 100–200 instructions) would transform the evaluation from a within-distribution distillation measurement to a true generalization test and address the most central concern about the paper's claims.
- Deeper analysis of why retrieval sometimes beats the oracle API set — the paper attributes this to the retriever "finding more appropriate APIs" but provides no case studies or quantitative breakdown.
- Reporting the inference cost of DFSDT (average API calls per instruction) for practitioners who need to weigh performance against budget.
- Ablation on the sensitivity of instruction generation to the number/choice of human-written seed examples.

## Removed Points

These points were considered but removed from the main weaknesses list:

- **"A stronger baseline would be fine-tuning Ada or using a domain-adapted retriever"**: Speculative; the comparison against Ada (general-purpose) and BM25 is standard and sufficient to demonstrate large improvements.
- **"No analysis of temporal variability in API responses"**: The paper explicitly discusses temporal API variability as motivation for ToolEval's design. A full analysis is beyond the paper's scope.
- **"Incomplete comparison to concurrent work through cross-dataset evaluation"**: Cross-dataset evaluation is a nice-to-have, not a required weakness. The paper provides a comprehensive comparison table (Table 1).
- **"API retriever training data comes from the same ChatGPT-generated pairs"**: This is an inherent consequence of the automated pipeline and is already captured by the distribution concern in Major weaknesses.
- **"DFSDT is not a novel method; it's just DFS with backtracking"**: The paper acknowledges similarity to ToT in Related Work and positions DFSDT as an adaptation, which is reasonable. The empirical improvement over ReACT is well-demonstrated regardless of the method's novelty.
- **"The evaluation lacks rigorous comparison with Reflexion and ToT"**: The paper compares against ReACT with a cost-matched @N control and demonstrates large improvements, which is sufficient. The claim is about DFSDT's empirical effectiveness, not novelty over every possible baseline.

## Novel Insights

None beyond the paper's own contributions. The two reviewers' analyses are largely convergent on the paper's main strengths and weaknesses, with the distribution-confound issue being the most substantive cross-cutting critique. The interesting finding that the neural retriever sometimes outperforms the oracle API set (Table 4) warrants deeper investigation but is noted by the paper.

## Suggestions

1. Temper the "on par with ChatGPT" claim and explicitly discuss the distribution overlap as a known limitation — acknowledge that the evaluation measures within-distribution distillation effectiveness, with OOD generalization only tested on the simpler APIBench.
2. Add a failure-mode analysis section (e.g., classification of errors into API unavailability, planning mistakes, hallucination, retriever failure) across at least 50–100 failure cases.
3. Report bootstrap confidence intervals for pass/win rates in Table 4, and include test-set sizes in the table.
4. Provide the average number of DFSDT API calls per instruction alongside the main results so practitioners can assess the cost-performance trade-off.
