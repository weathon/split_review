## Summary

This paper evaluates nine open-source LLMs (CodeLlama, Llama 2, DeepSeek-R1, Qwen 2.5/3, WizardCoder, Phi4, Gemma3) on two reverse engineering tasks — function/variable name recovery and type inference from stripped binaries. Using a 40,000-function dataset spanning four architectures and multiple optimization levels, the authors find that all models achieve very low zero-shot F1 scores (typically ≤0.06) and that fine-tuning produces inconsistent and often modest improvements. The paper provides a useful empirical baseline for the community.

## Strengths

- **First systematic large-scale evaluation across multiple LLMs on two core RE tasks.** The paper evaluates nine LLMs on name recovery and type inference using a 40,000-function dataset spanning x86-64, x86-32, ARM, and MIPS across multiple optimization levels (§4.1, Tables 2–4). This directly addresses the gap identified in §2 that prior work selected models arbitrarily (SYMGEN uses CodeLlama-34B, RESYM uses StarCoder-3B) without comparative rationale.

- **CodeWordNet-based evaluation captures semantic similarity.** The paper adopts the SYMLM method with CodeWordNet to give partial credit for semantically equivalent names, and Figure 1 empirically demonstrates that removing CodeWordNet causes a sharp performance drop (§3.4, Figure 1). This is more appropriate than strict string matching for name recovery.

- **Real-world firmware evaluation with two decompilers.** Table 6 shows that the limitations extend beyond synthetic benchmarks to real firmware binaries, and the comparison between Ghidra and IDA Pro outputs provides practical insight into decompiler influence.

- **Controlled analysis of model size vs. training quality.** Figure 2 compares CodeLlama 7B/13B/34B and finds little difference, while the comparison of Qwen2.5 vs. DeepSeek-R1 (same architecture, different training) shows data quality matters more than parameter count (Findings 4–6).

## Weaknesses

### Major

- **Inconsistency between the claimed evaluation metric and the reported numbers (§3.4 vs. Table 2 vs. Figure 1).** Section 3.4 states that name recovery uses the SYMLM method with CodeWordNet to compute semantic distances. However, the F1 scores in Table 2 (e.g., CodeLlama O0=0.04, Llama2 O0=0.01, DeepSeek-V2 O0=0.01) are close to the "without CodeWordNet" values in Figure 1 (0.05, 0.06, 0.07) and far from the "with CodeWordNet" values (0.15, 0.18, 0.20). The paper never addresses this discrepancy, leaving readers uncertain which metric was actually used for the main results. This needs to be clarified — if strict matching was used, the paper should say so; if CodeWordNet was used, the numbers in Tables 2–3 should be different.

- **No validation of the auxiliary LLM used for response extraction (§3.2).** The paper relies on an auxiliary LLM to normalize heterogeneous model outputs into a standardized format, noting that "a single parsing algorithm cannot robustly handle the degree of variation across models" and that "no LLM consistently adhered to the required structure" (Finding 8). Yet the paper provides no evaluation of this extraction step: no accuracy metrics, no human spot-checks, no discussion of failure cases, and does not even name which LLM was used. If the auxiliary model mis-parses, hallucinates, or selectively drops content, all downstream F1 scores could be corrupted.

### Minor

- **No comparison to specialized non-LLM baselines.** The paper only compares LLMs against each other. Prior work such as SYMLM, VarBERT, and Debin report measurable performance on similar tasks. Including even one such baseline would contextualize how far LLMs are from specialized approaches and significantly strengthen the negative result.

- **Narrow dataset domain (§4.1).** The dataset is drawn primarily from GNU software. The paper does not discuss how well this generalizes to other code domains (embedded systems, kernel code, malware, IoT). The firmware experiment (§4.3) partly addresses this but uses only two firmware images.

- **Exclusion of ChatGPT/GPT-4 limits practical relevance.** The paper excludes ChatGPT and GPT-4 for being "charged" and "not adequate for comparison" (§4.2), but these are the most commonly used LLMs in practice. Readers who want to know whether to use GPT-4 or open-source models get no answer.

- **Prompt sensitivity not explored.** The paper uses a single prompt template and acknowledges that prompt design affects fine-tuning time by up to 4× (Finding 7). The same sensitivity likely affects zero-shot performance, yet no ablation is conducted. The low scores may partially reflect prompt incompatibility rather than inherent inability.

- **No statistical testing.** With 40,000 samples, standard errors are tiny, but confidence intervals or significance tests would prevent overinterpreting small differences (e.g., 0.04 vs. 0.05) that may be noise.

### Trivial

- Table 5 reports "0.00" for assembly code function name recovery. The text notes these are rounded to three decimal places, which is fine, but a note on the actual number of correct predictions would be helpful context.

## Nice-to-Haves

- Validate the auxiliary extraction LLM with human evaluation on a few hundred samples (report precision/recall of extraction).
- Test at least one alternative prompt template to disentangle model capability from prompt compatibility.
- Add a simple specialized baseline (e.g., CodeBERT fine-tuned on the same dataset) to sharpen the negative result.
- Ablate the placeholder normalization (§3.1) — does raw decompiled code yield different results?

## Removed Points

- *"Table 6 claims near-zero but some entries are 0.09–0.12"* — The paper's "near-zero" characterization is reasonable in context (compared to F1=1.0) and the text discusses the values clearly. Not misleading.
- *"9 models is a small sample"* — 9 is adequate for a systematic evaluation and the paper's selection criteria are transparent.
- *"No analysis of why fine-tuning helps some cases but hurts others"* — The paper provides case examples (Table 8) and identifies prompt sensitivity as one factor. Deeper analysis would strengthen the paper but its absence is not a weakness.
- *"Fine-tuning only 200 steps may be insufficient"* — While 200 steps is not full convergence, the paper's goal is comparative analysis under uniform conditions, not absolute performance.
- *Missing related works* — The paper covers relevant prior work (SYMGEN, RESYM, SYMLM, Yang et al., VARBERT). Removal per instructions.

## Novel Insights

None beyond the paper's own contributions. The main empirical finding — that all nine LLMs perform poorly on these RE tasks and fine-tuning gains are inconsistent — is the paper's core contribution and is well-supported by the data (pending resolution of the metric inconsistency).

## Suggestions

1. **Clarify the metric**: State explicitly whether Tables 2–3 use CodeWordNet or strict matching. If the former, reconcile with Figure 1 values. If the latter, update §3.4 to reflect the actual methodology.
2. **Validate the extraction pipeline**: Report accuracy of the auxiliary LLM on a human-annotated sample of model outputs. Disclose which LLM was used.
3. **Add at least one non-LLM baseline** (e.g., a BERT-sized model fine-tuned on the same data) to anchor the results against specialized approaches.
