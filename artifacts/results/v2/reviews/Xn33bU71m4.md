## Summary
The paper presents a systematic evaluation of nine open-source mid-sized LLMs on two core reverse engineering tasks — name recovery (function and variable) and type inference — using decompiled and assembly code inputs across four architectures and four optimization levels. The authors also assess LoRA fine-tuning and real-world firmware. The central finding is that current LLMs achieve low F1 scores, with fine-tuning providing inconsistent and often marginal improvements.

## Strengths
1. **First systematic large-scale multi-LLM comparison in this domain.** The paper fills a clear gap in the reverse-engineering literature, where prior work selects models without rationale (e.g., SYMGEN uses CodeLlama-34B, RESYM uses StarCoder-3B). Evaluating 9 models on a shared dataset with a standardized pipeline is a useful contribution.

2. **Comprehensive experimental scope.** The dataset spans 40,000 functions across 4 architectures (x86-64, x86-32, ARM, MIPS) and 4 optimization levels, with both decompiled and assembly inputs. The evaluation includes original and fine-tuned models, real-world firmware, and two different decompilers (Ghidra, IDA Pro).

3. **Non-trivial findings that challenge assumptions.** The paper surfaces several evidence-grounded insights: (a) fine-tuning helps inconsistently and can even decrease performance, (b) larger model size does not guarantee better performance (e.g., CodeLlama 13B ≈ CodeLlama 34B), (c) training data quality matters more than architecture (DeepSeek-R1 underperforms its base Qwen2.5), and (d) function name recovery from assembly code yields uniformly 0.0 F1.

4. **Real-world validation.** The evaluation on stripped firmware with two commercial decompilers confirms that the near-zero scores persist outside synthetic benchmarks, lending practical relevance.

## Weaknesses

### Fatal
None.

### Major
1. **Unresolved inconsistency in the name-recovery evaluation metric.** Section 3.4 states that name recovery uses the SYMLM method with CodeWordNet to give partial credit for semantically similar sub-words. However, the values in Table 2 (function name recovery) are an order of magnitude lower than what Figure 1 reports for the same models *with* CodeWordNet, and instead align almost exactly with Figure 1's *without* CodeWordNet (strict matching) values. For example, CodeLlama at O0 is 0.04 in Table 2, while Figure 1 shows ~0.15 with CodeWordNet and ~0.05 without. The same pattern holds for every model where comparison is possible. The paper never clarifies which metric the main tables use, making the central quantitative story uninterpretable. If Tables 2–3 use strict matching, then Section 3.4 is wrong; if they use CodeWordNet, the numbers are inconsistent with the ablation experiment. Either way, the reader cannot trust the reported scores.

2. **Underspecified fine-tuning protocol.** The fine-tuning results in Tables 2–4 are central to the paper's claims about improvement, yet the experimental setup is critically underdocumented: (a) LoRA rank, alpha, target modules, learning rate, batch size, and optimizer are not stated; (b) it is unclear whether the training data consisted of decompiled code, assembly code, or both — the description "10,000 functions per architecture and optimization pair" does not specify input representation, yet Table 5 evaluates assembly-code recovery after fine-tuning; (c) training runs for only 200 steps on 160,000 functions, which is suspiciously short unless the batch size is extremely large, but no epoch count or convergence evidence is provided. Without these details, the surprising finding that fine-tuning sometimes *decreases* performance (e.g., several models drop to 0.00 in Table 4) could reflect an ill-tuned training setup rather than a genuine property of the models.

3. **Unvalidated auxiliary LLM in the measurement pipeline.** The paper uses an auxiliary LLM to normalize heterogeneous model outputs into a standard format before computing scores (Section 3.2). This auxiliary model is never identified (not even by family), and its extraction accuracy is never evaluated. Since different base models produce different response styles, the auxiliary model could introduce systematic bias that differentially affects the reported F1 scores. Without validation, every reported score is contaminated by an unknown amount of measurement error, undermining the reliability of the comparative claims.

### Minor
4. **No variance or confidence intervals.** All reported results are point estimates from single runs. LLM generation is stochastic, yet the paper provides no error bars, no repeated trials, and no discussion of variance. For a paper whose central message is comparative ("model X scores Y, model Z scores W"), the absence of any uncertainty quantification weakens the findings.

5. **The abstract's headline 0.37 for DeepSeek-R1 is not traceable in the main paper.** The abstract states that after fine-tuning, DeepSeek-R1 "reaches an F1 score of 0.37." The highest fine-tuned DeepSeek-R1 value visible in the main tables is 0.17 (variable name recovery, O0, Table 3). The 0.37 presumably comes from an appendix result (other architectures). Cherry-picking the best result from non-primary-condition data in the abstract, without context, is misleading.

6. **The strict type-inference metric is acknowledged but its consequences are underexplored.** The paper correctly notes that exact matching for types is harsh, especially for user-defined types. However, it does not report any relaxed metric (e.g., base-type-only matching) that would reveal whether models capture "type flavor" even when exact names are wrong. This limits the insight the type-inference data can provide.

### Trivial
7. The presentation is fragmented: the six experiments in Section 4.3 are described in prose blocks without a clear mapping to which table/figure each produces. A summary table or flowchart would help.

8. The paper states results are "rounded at the third decimal place" for assembly-code scores (0.00 in Table 5), but does not clarify rounding for other tables.

## Nice-to-Haves
- **Cross-domain fine-tuning evaluation.** Fine-tuning on the GNU dataset and testing on the real-world firmware would strengthen the generalization claims considerably.
- **Comparison to non-LLM baselines.** Contextualizing the reported F1 scores against traditional decompilers or specialized ML models (e.g., from cited prior work) would help readers interpret "low" — are these scores typical for the task, or do LLMs underperform classic methods?
- **Quantification of under-generation.** The paper notes that models often output fewer names than requested; a systematic analysis of missing-identifier rates would clarify whether F1 scores are depressed by under-generation vs. incorrect generation.

## Novel Insights
The review process surfaces one observation beyond the paper's own contributions: the metric inconsistency (Major #1) is not just a clarity issue — it suggests the authors may have run the main evaluation with strict matching while describing CodeWordNet in the methodology, perhaps because they developed the CodeWordNet ablation later or because the paper was assembled from separate experiments without cross-checking. If confirmed, this points to a systemic lack of careful verification between the methodology description and the results that should be scrutinized by the authors regardless of which metric is ultimately correct. The core finding (LLMs are limited) survives either way, but the specific numbers, the "0.03" framing in the abstract, and the claimed improvement from fine-tuning all shift materially depending on which metric was actually used.

## Suggestions
1. **Resolve the metric inconsistency transparently.** Pick one evaluation regime (CodeWordNet or strict matching), apply it consistently across all tables and figures, revise Section 3.4 to match, and recompute the abstract's numbers. If both are reported, clearly label each table.
2. **Document all fine-tuning hyperparameters** (LoRA rank, alpha, target modules, learning rate, batch size, optimizer, schedule, number of epochs). Specify the input representation used in training. Show at least training loss curves to demonstrate convergence.
3. **Identify the auxiliary LLM and report its extraction accuracy** on a human-annotated sample of at least 200 outputs. If accuracy is poor, consider replacing it with a deterministic parser or a more robust few-shot pipeline.
4. **Add confidence intervals** via repeated runs (at least 3 seeds) for a representative subset of conditions, or at minimum acknowledge the absence of variance estimates as a limitation.
5. **Trace the abstract's 0.37 claim** to a specific experimental condition and caveat it appropriately.
