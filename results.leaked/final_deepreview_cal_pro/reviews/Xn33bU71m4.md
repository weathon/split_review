## Summary

This paper presents the first systematic, large-scale evaluation of nine open-source LLMs on two reverse engineering tasks — function/variable name recovery and type inference from stripped binaries. The evaluation spans 40,000 functions across four architectures (x86-64, x86-32, ARM, MIPS), four optimization levels, and includes both zero-shot and LoRA-fine-tuned settings. The authors find that all models achieve low F1 scores (typically ≤ 0.1), that fine-tuning helps inconsistently, and that training data quality matters more than model size. Real-world firmware experiments with Ghidra and IDA Pro outputs corroborate the difficulty.

## Strengths

- **First systematic benchmarking of LLMs for these RE tasks.** The paper evaluates nine models under a standardized protocol across multiple architectures, optimization levels, input representations (decompiled code, assembly), and two tasks — filling a genuine gap where prior work selected models without empirical justification. (Evidence: Tables 2–6, experimental design in Section 4.3.)

- **Multiple analysis dimensions.** The study isolates key factors: fine-tuning (Finding 1), model size (Finding 4, Figure 2), training data quality vs. architecture (Finding 5), and the role of CodeWordNet in evaluation (Figure 1). These provide actionable insights beyond simple model rankings. (Evidence: Figures 1–2, Findings 1, 4–6.)

- **Real-world validation.** Evaluation on stripped firmware binaries with outputs from two different decompilers (Ghidra and IDA Pro, Table 6) strengthens the ecological validity of the conclusions and reveals decompiler-quality effects.

- **Automated evaluation pipeline.** The auxiliary-LLM-based post-processing (Section 3.2) addresses a practical challenge in benchmarking models with heterogeneous output formats, enabling scalable and consistent comparison.

## Weaknesses

### Fatal

None.

### Major

- **Internal inconsistency in reported results.** The introduction highlights a fine-tuned DeepSeek-R1 F1 score of 0.37, yet no table in the main body reports a value remotely close to this (the highest DeepSeek-R1 fine-tuned score visible in Tables 2–6 is 0.17 for variable name recovery at O0). Even if this 0.37 figure originates from the appendix (other architectures), the introduction presents it without qualification about which task, architecture, or optimization level it refers to, and the reader cannot verify it from the main results. More concerning: Figure 1 reports F1 scores on function name recovery (with CodeWordNet) that are 2–5× higher than the corresponding values in Table 2 for the same task and x86-64 architecture. For example, Qwen3 shows ~0.05–0.06 in Table 2 (Orig) but ~0.15–0.25 in Figure 1 (w/ CodeWordNet). While the "wo CodeWordNet" bars in Figure 1 (~0.05–0.08) roughly align with Table 2, Section 3.4 states that CodeWordNet-based evaluation is the standard metric for name recovery. The paper provides no explanation for why its main results table and its dedicated CodeWordNet experiment disagree so sharply. These discrepancies undermine confidence in the empirical findings until resolved.

- **No baselines or external reference points.** The paper reports absolute F1 scores without comparing against random baselines, frequency-based heuristics, or established specialized methods such as SYMLM (whose evaluation metric the paper adopts) or Debin. Without any reference point, a reader cannot judge whether an F1 of 0.03 represents near-random performance or a meaningful signal. A benchmark paper that omits baselines fails to provide the context that would make its measurements interpretable.

### Minor

- **No validation of the auxiliary LLM post-processing step.** The automated pipeline (Section 3.2) uses a second LLM to normalize heterogeneous model outputs into a uniform format. The accuracy of this extraction step is never quantified. Systematic parsing errors could artificially depress reported F1 scores, yet the paper treats the post-processed outputs as ground truth for evaluation.

- **Strict exact-match metric for type inference is acknowledged but not critically discussed.** Section 3.4 applies strict equality for all types including user-defined types, which guarantees near-zero scores and masks any partial progress models might make (e.g., correctly inferring primitive types within a struct). The paper notes the difficulty but does not report alternative metrics that would reveal more nuanced performance.

- **Dataset description is too vague for reproducibility.** The dataset is described only as "mostly from GNU software" (Section 4.1), with no project-level breakdown, no explicit guarantee that training and test sets are disjoint at the project level, and no distributional statistics. This makes it impossible to assess whether fine-tuning gains reflect genuine generalization or memorization of project-specific patterns.

- **Limited analysis of why fine-tuning fails.** Finding 1 correctly notes that fine-tuning gains are inconsistent, and several models regress after fine-tuning (e.g., DeepSeek-V2 variable name F1 drops from 0.10 to 0.05 at O1 in Table 3). The paper does not analyze these failure cases or explore whether a different adaptation objective would help, leaving an open question about whether the problem is the task difficulty or the fine-tuning method.

### Trivial

- The CodeWordNet experiments in Section 4.3 are described as "restricted to the x86-64 architecture to illustrate general trends," but it is unclear whether these experiments use the same 2,500-sample test set as Table 2 or a different subset, contributing to the confusion noted under Major weaknesses.

## Nice-to-Haves

- Providing the model with additional context commonly available in real reverse engineering (e.g., imported library names, string constants) would make the task more realistic and could reveal whether current LLMs become useful with modest additional signal.
- Adding a frequency-based baseline (e.g., always predicting the most common function name like `main` or `malloc`) and a replication of one published specialized method would immediately contextualize the LLM scores.
- Reporting per-CWE or per-type-category breakdowns for type inference would show whether models succeed on primitive types even when they fail on user-defined types.
- Quantifying the auxiliary LLM's extraction accuracy on a manually annotated subset would strengthen confidence in the automated pipeline.

None beyond the paper's own contributions. ## Suggestions

- **Resolve the number discrepancies.** This is the single most important fix. Either (a) confirm that Table 2 uses strict matching (not CodeWordNet) and update Section 3.4 to clarify when each metric is used, or (b) explain why the Figure 1 and Table 2 experiments differ. Also, either include the 0.37 result in a main-body table with full context, or remove it from the introduction.
- **Add at least one baseline.** A simple frequency-based predictor and/or a replication of SYMLM on the same data split would immediately give readers a meaningful reference frame.
- **Validate the auxiliary LLM parser.** Report extraction accuracy on a small hand-labeled subset.
- **Report alternative type-inference metrics** (e.g., primitive-type-only accuracy, structural compatibility) alongside strict exact match.
- **Describe the dataset more precisely**, including project-level train/test split guarantees and at minimum a list of source projects.
