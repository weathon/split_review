## Summary

The paper presents a systematic evaluation of nine open-source LLMs (CodeLlama, Llama 2, WizardCoder, DeepSeek-V2, DeepSeek-R1, Qwen2.5, Qwen3, Phi4, Gemma3) on two core reverse engineering tasks: **name recovery** (function and variable names) and **type inference** from stripped binaries. Using a dataset of 40,000 functions across four architectures (x86-64, x86-32, ARM, MIPS) and four optimization levels (O0–O3), plus a 160,000-function fine-tuning set, the paper finds that: (1) all un-fine-tuned LLMs achieve F1 scores below 0.1 on both tasks, (2) fine-tuning yields inconsistent gains (best: 0.33 on variable names), and (3) type inference is particularly challenging. The paper also evaluates name recovery from assembly code and on real-world firmware.

## Strengths

1. **Systematic, multi-dimensional evaluation across 9 models, 4 architectures, and 4 optimization levels.** The dataset construction is substantial (40k test + 160k training samples), and evaluating every model on every architecture×optimization combination provides a comprehensive picture that prior work in this area has not delivered at this scale (Tables 2–6).

2. **Semantic evaluation of name recovery via CodeWordNet.** Adapting WordNet-based semantic distance (from SYMLM) to measure partial credit for semantically similar identifiers is methodologically appropriate for this task. Figure 1 convincingly shows that removing CodeWordNet causes scores to drop sharply, validating its necessity and distinguishing this work from exact-match baselines.

3. **Real-world firmware validation with two decompilers.** Testing on stripped firmware using both Ghidra and IDA Pro (Table 6) adds ecological validity. The finding that IDA Pro pseudocode slightly improves scores over Ghidra is a practically useful observation for practitioners.

4. **Automated response-normalization pipeline.** Using an auxiliary LLM to standardize heterogeneous model outputs (Section 3.2) enables fair, large-scale comparison that would otherwise be infeasible. This is a practical contribution that addresses a genuine challenge in benchmarking LLMs with varying output formats.

5. **Documentation of model failures to follow formatting instructions.** Finding 8 (models fail to adhere to required output format unless assisted by fine-tuning or post-processing) is well-observed and valuable for practitioners building RE pipelines with LLMs.

## Weaknesses

### Major

1. **Assembly fine-tuning experiment is ambiguously specified, undermining a core finding.** The paper reports zero F1 for both original and fine-tuned models on assembly-based function name recovery (Table 5), but never states whether fine-tuning was performed using assembly code or only decompiled code. The fine-tuning description (Section 4.3, "Performance Evaluation with Fine-Tuned Models") says a training set of 160,000 functions was prepared, but does not specify the input representation format. If the models were fine-tuned on decompiled code and then evaluated on assembly, the near-zero scores are expected and convey no information about fine-tuning's effect on assembly tasks. Finding 3 ("both original and fine-tuned LLMs struggle with function name recovery from assembly code") is partially supported by the original-model results, but the fine-tuned component is uninterpretable. The authors must clarify this setup or retract the fine-tuned column.

2. **Critical fine-tuning hyperparameters are missing, compromising reproducibility.** The paper uses LoRA but reports none of the key hyperparameters: rank, alpha, learning rate, batch size, optimizer, number of epochs/steps beyond "200 steps" (Table 7), or hardware configuration. There is no training loss curve, validation curve, or convergence evidence. Without these, the fine-tuning results cannot be independently reproduced or properly interpreted — modest gains or even performance drops could reflect insufficient training or suboptimal hyperparameters rather than genuine model properties.

3. **No comparison with existing specialized models' reported performance.** The paper cites SYMGEN (Jiang et al.), RESYM (Xie et al., 2024), VARBERT (Pal et al., 2024), and Debin (He et al., 2018), all of which report non-trivial performance on these tasks, yet never compares its own fine-tuned numbers against those prior results. Without this context, readers cannot determine whether the low F1 scores are a general property of LLMs or a consequence of the particular dataset, prompt, and fine-tuning choices made here. The paper's contribution as a "systematic benchmark" is diminished when it cannot situate its numbers relative to the state of the art.

### Minor

4. **Zero-shot evaluation uses a single, unvalidated prompt.** The paper adopts a single prompt from a prior ChatGPT-based RE study (gpt, 2023) "rather than optimizing prompts" (Section 3.2). No prompt sensitivity analysis is conducted across models. Given that models differ substantially in instruction-following behavior and preferred prompt formats, the near-zero zero-shot scores may partially reflect prompt–model mismatch rather than pure capability limitations. While unlikely to reverse the paper's main conclusion (all models perform poorly), this concern undermines finer-grained claims about relative model rankings and the zero-shot ceiling.

5. **No error bars, confidence intervals, or variance reporting.** All results are point estimates (Tables 2–6), even though the paper acknowledges randomness from both data sampling and LLM output generation. The reproducibility statement ("similar, but not identical") does not quantify expected variance. For a benchmarking paper, this omission is significant — differences between models (e.g., Qwen3's 0.06 vs. Llama2's 0.01 on function name recovery) may be within noise.

6. **Type inference metric asymmetry is acknowledged but not analyzed.** Name recovery uses CodeWordNet (partial semantic credit), while type inference uses strict exact matching (including user-defined types). The paper correctly notes that "strict evaluation criteria" contributes to low scores (Section 4.4), but does not analyze how results would change under a more relaxed or categorized metric (e.g., primitive vs. user-defined types separately). Finding 2 ("type inference proves even more challenging") may partly be an artifact of this asymmetric evaluation.

7. **Auxiliary LLM extraction pipeline is not validated.** The response-normalization step (Section 3.2) uses an auxiliary LLM to extract structured outputs, but no validation of its accuracy is provided. Extraction failures could systematically deflate scores or introduce bias favoring models whose outputs are easier to parse.

8. **Abstract highlights a result (DeepSeek-R1 F1=0.37 after fine-tuning) that is not clearly present in the main paper's tables.** The best DeepSeek-R1 fine-tuned scores visible in the x86-64 tables are 0.17 (variable names, O0) and 0.05 (function names). The 0.37 may come from the appendix (which was stripped by the parser), but presenting it as an unqualified headline result without anchoring it to a specific task, architecture, or optimization level in the main paper is misleading.

### Trivial

- "Reproducibility" statement says numbers will be "similar, but not identical" without operationalizing this.

## Nice-to-Haves

- **Prompt sensitivity analysis:** Testing each model with 3–5 diverse prompt templates would strengthen confidence that the zero-shot results reflect genuine capability limitations rather than format sensitivity.
- **Relaxed type inference metric:** Applying a compatibility-based or categorized metric for types would help separate model capability from metric stringency.
- **Cross-architecture summary in main paper:** A compact summary table of cross-architecture results would strengthen the claim of systematic evaluation without relying entirely on the appendix.
- **Convergence analysis for fine-tuning:** Showing loss curves or evaluating at multiple checkpoints would clarify whether 200 steps is sufficient.

## Novel Insights

The most interesting insight from the reviews is that the paper's core problem — arbitrary model selection without rationale — is genuinely important and well-motivated, but the paper's own methodological gaps (especially the assembly fine-tuning ambiguity) mirror the very problem it criticizes: it is difficult to draw reliable conclusions from an evaluation when critical experimental details are underspecified. This creates a meta-level tension: a paper arguing for principled model selection would benefit from being more rigorous in its own experimental design.

## Suggestions

1. **Clarify the assembly fine-tuning setup explicitly.** State clearly whether the fine-tuned models in Table 5 were trained on assembly or decompiled code. If trained on decompiled code, remove the "Fine" column from the assembly table or add a separate assembly fine-tuning experiment.
2. **Report all LoRA hyperparameters** (rank, alpha, learning rate, batch size, optimizer, gradient steps) and include convergence evidence (loss curves or validation at multiple checkpoints).
3. **Add a prompt sensitivity analysis** by testing at least 3 prompt templates on a subset of models and reporting whether rankings or absolute scores change substantially.
4. **Add variance estimates** by running each experiment 3 times with different seeds and reporting means ± std. Focus this on a representative subset (e.g., x86-64, O0/O2) if full replication is too costly.
5. **Contextualize fine-tuned results against prior specialized models** by citing and comparing with the numbers reported in SYMGEN, RESYM, and VARBERT — even if datasets differ, a qualitative comparison would help.
6. **Anchor the DeepSeek-R1 F1=0.37 claim** to a specific task, architecture, and optimization level in the main paper, or qualify it if it appears only in the appendix.
