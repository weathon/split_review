## Merged Review

### Summary
The paper proposes GNSVR, a generative neuro-symbolic visual reasoning system that grows and reuses a library of neural modules via LLMs. Given a small training set for a vision-language task, GNSVR first checks if existing modules can solve the task; if not, it uses an LLM to propose a new module signature and I/O specification. It then prompts the LLM to generate Python code for that module, tests it on few-shot examples, and adds it to the library if it passes. At test time, the augmented API is used to produce and execute programs. The method achieves competitive performance on GQA, RefCOCO, and shows promising transfer to image editing and knowledge tagging, as well as few-shot generalization on Raven and MEWL. Reviewers generally find the direction compelling but raise concerns about novelty, ablation analysis, experimental comparisons, and missing details.

### Strengths
- The idea of augmenting a fixed API with task-specific modules discovered via LLMs is sound, compelling, and opens interesting future directions (R3).  
- The division of labor between module initialization (proposing a new function) and module generation (authoring its code) is a neat insight; it allows the LLM to create its own test cases and verify module correctness (R3).  
- The paper makes a clear case for its contribution, and the value of code reuse is well motivated (R1).  
- Empirical performance is impressive: GNSVR outperforms VisProg and ViperGPT across tasks, and the transfer results (image editing, knowledge tagging) are particularly compelling (R2, R3).  
- Few-shot generalization on Raven and MEWL is notable given the limited training data (R3).  
- The method of continuously growing a verified library of modules is innovative, simple, and elegant (R4).  
- The paper is well written, with a healthy split of information between the main paper and supplementary (R2).  

### Weaknesses
**Novelty and contribution scope**  
- The core contribution appears to be the orchestration of existing APIs (VisProg, ViperGPT) rather than new visual reasoning techniques; the ratio of the authors’ insights to those of the API authors seems insignificant (R1).  
- The paper does not clearly delineate its novel aspects beyond iterative prompting, and there is minimal engagement with visual modalities beyond pre-built modules (R1).  
- Reviewer disagreement: one reviewer (R2) rates contribution 2 (fair) and questions novelty, while others rate contribution 3 (good); R2 also recommends replacing RAVEN with i-RAVEN due to shortcut flaws in RAVEN (R2).  

**Insufficient ablation and analysis**  
- No detailed analysis of the importance of each component of the framework is provided (R2).  
- Key design choices are not ablated: the role of module initialization, the definition of correct input/output formats, the selection of few-shot samples (the paper states “extracted 300 examples from GQA … based on experimental experience” without justification—potential cherry-picking), the influence of LLM capability, and the prompt design (R2, R4).  
- Without such analysis, the paper is limited to presenting a method and empirical results; it is hard to understand what works and why (R2).  
- Potential overfitting: the method may overfit to the small training set of a given task, creating modules that are not useful for new tasks (R4, W1).  
- The stage 2 verification with few test cases could lead to a bad implementation that only works for those examples and harms overall performance (R4, W2).  

**Experimental comparisons and baselines**  
- GNSVR uses a base API that combines VisProg and ViperGPT, so the proper baseline is GNSVR without module learning (w/o ML) using only the original API. This ablation is only reported on a subset of RefCOCO, not on all tables (Tables 1–5). The improvement over VisProg/ViperGPT could partly come from the improved base API, not solely from discovered modules (R3).  
- It is unclear whether the GNSVR w/o ML baseline is allowed arbitrary Python logic (ViperGPT style) or only API calls (VisProg style); the former would be fairer. The baseline’s performance on Raven and MEWL is not reported, so it is unknown if the baseline can solve those tasks without module discovery (R3).  
- VisProg and ViperGPT are not given the same few-shot training examples or error correction loop; including those would help disentangle the source of improvement (R4, W4).  

**Lack of critical details on method and reproducibility**  
- Module generation details are unspecified: can modules be hierarchical (call other generated modules)? What is the pass-rate threshold for accepting a module? How many times and how is error correction performed? How many modules are created per task and how often are they used? (R3)  
- The selection of in-context examples for LLM prompts is not described. The prompts shown always use COMPARE_SIZE and LOC; how are inference examples chosen? (R3)  
- For the Raven task, how are images turned into a question? What are the internals of the SOLVER module? (R3)  
- Error correction is only vaguely described (“incorporate error information into the prompt”); a detailed mechanism is needed (R4, Q2).  
- The process for selecting training examples in stages 1 and 2 is not clarified (R2, R3, R4).  
- GNSVR requires more training data than VisProg/ViperGPT because I/O pairs are used for both in-context examples and module evaluation; this trade-off should be explicitly acknowledged (R3).
