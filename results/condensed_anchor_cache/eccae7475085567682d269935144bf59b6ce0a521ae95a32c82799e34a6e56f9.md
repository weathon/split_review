## Merged Review

### Summary

AgentHarm is a benchmark of 110 malicious agentic tasks (expanded to 440 via synthetic variations) covering 11 harm categories (fraud, cybercrime, harassment, etc.). It evaluates LLM agents on refusal rate and task success (multi-step tool use) under both direct prompts and jailbreaks. The benchmark uses synthetic tool calls, manual grading conditions with limited LLM judges, and includes 110 paired benign tasks to measure capability degradation. Evaluations of leading LLMs find: (1) many models show surprisingly low refusal without jailbreaking; (2) simple universal jailbreak strings effectively reduce refusal; (3) jailbroken agents maintain high task competence comparable to benign settings; (4) best-of-n sampling increases success; (5) refusal and performance vary across harm domains and prompting strategies (CoT, ReAct). The dataset is implemented in the UK AISI Inspect framework, designed to be cheap, side-effect-free, and quick to run.

### Strengths

- **Timeliness & Significance**: The problem of LLM agent misuse is highly relevant and important for the community (Reviewers 1,4). The benchmark convincingly shows current models are vulnerable to jailbreaks for malicious agentic behavior (Reviewer 3).
- **Clear exposition**: Well-structured, easy to understand, with helpful examples and a clear limitations section (Reviewers 1,3,4).
- **Thorough evaluation**: Covers a broad range of state-of-the-art LLMs (Reviewers 1,2). Experiments provide valuable insights (Reviewer 2).
- **Benchmark design strengths**: 
  - First dataset focusing on *multi-step, agentic* misuse scenarios, not just single-turn QA (Reviewer 3).
  - Broad coverage of 11 harm categories makes cross-model comparisons more meaningful (Reviewer 3).
  - Self-contained, quick, cheap, and side-effect-free execution facilitates follow-up work (Reviewer 3).
  - Building on the Inspect framework is a good choice (Reviewer 3).
  - Inclusion of both malicious and benign varieties allows capability degradation analysis (Reviewers 2,3).
  - Thoughtful use of LLM judges only for narrowly defined sub-assessments, with manual conditions for core scoring, making results more robust (Reviewer 3).
  - Anti-leakage measures (canary strings, withheld test set) are laudable (Reviewer 3).
- **Metric innovation**: Attention to capability degradation (distinguishing successful jailbreak from trivial model failure) is valuable (Reviewer 2).

### Weaknesses

- **Realism and complexity of tasks**: Several reviewers question whether the synthetic, pre-defined toolset tasks are sufficiently realistic. The tasks are described as "toy tasks" significantly simpler than real-world open-ended agentic behavior (Reviewer 3). Specific examples (e.g., "hire a hitman" task, absurdly small tweet IDs in Figure 17) make it obvious the setting is fake, undermining credibility of both safety and capability results (Reviewer 4). This limits the informativeness of findings about jailbroken agent competence (Reviewer 4). Even the authors note the tasks are "relatively easy," which creates a tension with the conclusion that jailbreaks do not harm agentic competency—empirical support on more complex tasks is needed (Reviewer 3). One reviewer notes that single-prompt, fixed tools cannot capture unpredictable harmful behaviors in open-world multi-turn interactions (Reviewer 1). A minority reviewer (Reviewer 2) does not raise this concern, but the majority (Reviewers 1,3,4) see it as a major limitation. 
- **Lack of comparison with existing benchmarks**: The paper does not demonstrate what new insights the benchmark provides over existing evaluations (Reviewer 2). It fails to clarify the main difference between general LLM robustness and LLM-agent robustness beyond tool integration—specifically, whether attacks on general LLM task planning also succeed on agents (Reviewer 2). In contrast, Reviewer 3 praises the benchmark as the first for multi-step agent misuse, suggesting a disagreement on novelty.
- **Questionable definition of malicious behavior**: Some examples (e.g., Apple privacy, "2nd best athlete harassment") appear borderline; the paper lacks a clear, grounded definition of maliciousness, which could inflate reported refusal rates if some tasks are not actually harmful (Reviewer 3). This makes the benchmark's validity questionable (Reviewer 3).
- **LLM judge reliability and vulnerability**: The use of LLM judges (even if limited) is not thoroughly validated for reliability (Reviewers 1). This also introduces a potential vulnerability: a malicious entity could attack the judge to escape detection (Reviewer 1). The authors should discuss this risk in the limitation section (Reviewer 1). (Reviewer 3 is less concerned because judges are limited to sub-assessments.)
- **Evaluation methodology concerns**:
  - **Happy path enforcement**: Grading assumes specific tool call sequences; creative agents that solve tasks via alternative valid paths may be incorrectly scored as failures, making the benchmark a lower bound (Reviewer 3). No analysis is provided on how often such alternative traces occur (Reviewer 3, question).
  - **Multi-turn interactions missing**: Real agents would typically ask for clarification or confirmation; the single-prompt setup does not model this (Reviewers 1,3).
  - **Forced tool calling inconsistency**: For Gemini and Llama (queried via DeepInfra), the authors copy values from direct requests because forced tool calling is not supported, which may be misleading (Reviewer 3).
  - **Table formatting**: Bolding in Table 3 is confusing—what counts as best? (Reviewer 3).
- **Missing citations and discussion**: 
  - No citation of prompt injection threat models (e.g., Greshake et al., 2023) (Reviewer 3).
  - No citation of test data contamination issues (e.g., Haimes et al., 2024) despite using anti-leakage measures (Reviewer 3).
  - No discussion of trade-offs between broad coverage vs. deeper single-domain evaluation (Reviewer 3).
  - No explanation for why safety training techniques seem not to transfer to the agent setting (Reviewer 3, question).
- **Lack of code availability**: No source code or full benchmark is provided in the supplementary material (Reviewer 1). Third-party augmentation process and community contributions are not described (Reviewer 1, question).
- **Refusal rate discrepancy**: One reviewer (Reviewer 4) finds results surprising—simple copy-paste prompts without jailbreak always led to refusal on GPT-4o-mini, contradicting the paper's reported low refusal rates. The authors should explain this discrepancy, possibly due to the agent scaffold or prompt differences (Reviewer 4, question).
