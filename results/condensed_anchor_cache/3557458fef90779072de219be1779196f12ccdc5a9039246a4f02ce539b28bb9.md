## Merged Review

### Summary

The paper proposes Chain-of-Table, a framework that extends chain-of-thought (CoT) prompting to tabular data by explicitly using tabular data as a proxy for intermediate reasoning steps. It uses in-context learning to iteratively generate predefined atomic operations and update the table, forming a tabular reasoning chain. The method is evaluated on WikiTQ, FeTaQA, and TabFact, achieving state-of-the-art performance. The approach is simple, effective, does not require fine-tuning, and provides explainable step-by-step reasoning. However, reviewers identify several weaknesses: limited operation set, missing experiments on diverse tasks and open models, high computational cost, lack of scalability for large tables, and insufficient comparison with relevant baselines (Tab-CoT, Dater, Binder under equal query budget).

### Strengths

- The problem of leveraging structured tabular data in reasoning chains is important and practical, and existing LLMs struggle with it.
- The proposed chain-of-table is a novel adaptation of CoT to table tasks, using step-by-step tabular operations (atomic operations) that are independently reasonable and well-designed.
- The method is training-free (no fine-tuning), relying only on in-context learning.
- The reasoning process is step-by-step, explainable, and effective, with clear presentation and helpful figures; several case studies are provided in the appendix.
- Empirical results on three real-world benchmarks (WikiTQ, FeTaQA, TabFact) show clear improvement over a broad range of baselines, including single-turn methods and other program-aided methods (e.g., Binder).
- The method highlights the value of decomposing reasoning in tabular tasks and improves understanding of intermediate results via evolving tables.

### Weaknesses

- **Limited operation set and flexibility**: The five predefined atomic operations may not cover all needed operations (e.g., aggregations like SUM, MAX, MIN). It is unclear how such aggregations are performed and why these five suffice. The framework’s reliance on a fixed set of operations could limit adaptability to complex or dynamic reasoning scenarios, and its ability to integrate external knowledge or contextual information is not addressed. *(Reviewer 2, 4)*
- **Missing comparison with key related works**: The paper does not discuss Tab-CoT (Jin and Lu, 2023), which modifies CoT to leverage tabular structure. A comparison and clear distinction are needed. Dater (Ye et al., 2023) is considered the most important baseline; the paper should provide in-depth methodological comparison (e.g., one-step vs. multi-step reasoning). *(Reviewer 1, 3)*
- **Computational and query cost**: The method queries LLMs twice per operation (once for operation type, once for arguments), leading to significantly more LLM calls than baselines like CoT and Binder. No comparison is provided under equal query budget (e.g., using self-consistency for baselines). The repeated processing of the (potentially large) table at each reasoning step substantially increases computational overhead and latency; scalability to large tables and large-scale data is unaddressed. *(Reviewer 2, 3, 4)*
- **Marginal improvements on some metrics**: On TabFact and ROUGE-1/2/L, improvements are only marginal; the reasons are not discussed. Also, Figure 4 shows that longer chains do not consistently improve accuracy—the underlying reasons need explanation. *(Reviewer 3)*
- **Missing evaluation on diverse tasks and models**: The benchmarks cover QA and fact verification, but not table summarization, column type annotation, row augmentation, etc. Evaluation with open-source models (e.g., Llama-2) is missing to test generalizability across architectures and sizes. *(Reviewer 1, 2)*
- **Ignoring table structure and semantics**: The method treats tables as a set of tokens, ignoring structure beyond the defined operators. No mechanism to encode table structure or semantics is discussed. *(Reviewer 1)*
- **Table size and context length**: The entire table must fit within the model’s context length; the paper does not evaluate on larger tables or discuss handling tables that exceed the limit. *(Reviewer 1, 2)*
- **Lack of clarity in argument generation and operation details**: The description of argument generation is unclear—specifically, `add_column` directly generates the new column via LLM, while other operations generate arguments for a programming language. The number of reasoning steps, total input/output tokens compared to baselines, and the number of examples used in Figure 2 are not specified. *(Reviewer 2, 4)*
- **Difference from Binder’s added API calls**: Binder also adds columns via API calls; the paper should clarify how Chain-of-Table differs from that approach. *(Reviewer 4)*
