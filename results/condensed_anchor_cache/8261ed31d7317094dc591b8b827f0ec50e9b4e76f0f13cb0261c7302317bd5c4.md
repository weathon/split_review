## Merged Review

### Summary
The paper introduces Activation Beacon, a plug-in module for transformer LLMs that compresses activations (keys and values) per layer via progressive chunk-wise compression. Interleaved beacon tokens accumulate contextual information, and training uses randomly sampled compression ratios. The method reports 2× inference speedup and 8× KV cache memory reduction while maintaining performance on long-context tasks (up to 128K inputs despite training on only 20K). Evaluations on LongBench, Needle-in-a-Haystack, and few-shot learning show it outperforms soft-prompt and KV-cache compression baselines and is competitive with full fine-tuning.

### Strengths
- **Efficiency**: 2× inference time reduction and 8× KV cache memory cost reduction (all reviewers). Pre-training requires only 1B tokens (R4).
- **Method design**: Chunking at each layer avoids recomputation and gradient back-propagation issues found in prior recursive-dependency baselines (R1). Progressive fine-grained compression preserves quality and handles contexts beyond the model’s window (R3). Interleaved beacon tokens are straightforward and intuitive (R1, R4).
- **Flexibility**: Training with random compression ratios enables adaptive ratios at test time (R1, R2). Maintains short-context capabilities (R2, R3).
- **Strong empirical results**: Outperforms KV cache compression and soft-prompt baselines on LongBench and Multi-Needle-in-a-Haystack (R1, R4). Competitive with full fine-tuning (R4). Table 2 shows strong accuracy at good latency (R4). Ablations in Table 4 examine design choices (R4).
- **Presentation**: Figures 1 and 2 clearly explain the method (R4). Paper is generally well written (R4).

### Weaknesses
- **Missing comparisons and baselines**:
  - No evaluation on newer challenging benchmarks like RULER (R1).
  - Missing baselines: CEPE, LLoCO (R1); KIVI (R3); CacheGen, LM-Infinite (R3). A comparison with KIVI would highlight trade-offs between numerical KV-cache compression and sequence-length compression (R3). Also need comparisons along other compression dimensions (layer, head, channel) (R3).
  - Unclear fundamental difference from ICAE and AutoCompressor: both use soft tokens; the paper claims their workflow lacks fine-grained handling, but simply decreasing chunk size might achieve similar effect (R4). Would that massively improve ICAE/AutoCompressor? (R4)
- **Scalability and model size concerns**:
  - Evaluations are on medium-sized models (7B); no validation on larger models (e.g., 70B) (R2, R3). Not addressed how compression ratio and beacon token size scale with model size (R2). Generalizability to different architectures/parameter counts is uncertain (R2).
  - Training a 7B model requires 8 A800 GPUs; scaling to 70B may be prohibitive. Need analysis of memory footprint and training time scaling (R3).
- **Implementation overhead and efficiency details**:
  - Added complexity of beacon tokens and compression ratios increases end-user implementation overhead; process of selecting optimal compression ratio not clearly defined (R2).
  - Impact of added parameters (self-attention projections for beacon tokens) on VRAM and latency not quantified. Could LoRA fine-tuning be effective? (R1)
  - No latency breakdown of prefilling vs. decoding for specific workloads (e.g., 32k/128k context, 128 decoded tokens) compared with flash-attention full-context baseline (R1). No report of GPU training/inference time, including time for beacon token generation and compression (R3). Lack of detailed analysis of compression/decompression computational overhead that could become a bottleneck on certain hardware (R2).
  - Table 1: latencies not obviously comparable because compression ratio is not mentioned (R4). Table 2: latency units missing (R4). Effect on fine-tuning throughput not compared with Full-FT (R1).
- **Technical questions**:
  - How are rotary embeddings managed for beacon tokens? Relative positions vary across chunks (R1).
  - Why is adaptive compression used for LLaMA2 and uniform compression for Qwen? (R4)
  - What window size is used? Line 184 suggests 1024 as common, but model context length is 32k (from Table 1). How much is the window logic actually used given LongBench has few examples above 32k? (R4)
- **Minor typos**: line 47 “it it”, line 53 “alternamtive”, line 371 “highligh”, line 483 “scope” (R4).

- **Contrast between reviewers**: Two reviewers (R1, R2) rated the paper 6 and raised concerns about missing comparisons, implementation overhead, and scalability. Two reviewers (R3, R4) rated it 8 but also highlighted missing baselines (especially KIVI), scalability, and unclear differentiation from prior work (R4). R1 is open to adjusting rating if concerns are addressed.
