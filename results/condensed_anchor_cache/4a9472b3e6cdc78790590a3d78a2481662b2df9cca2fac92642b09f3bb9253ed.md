## Merged Review

### Summary

This paper explores using feedback to improve LLM code generation. The proposed architecture mimics human debugging by logging runtime variable values, providing feedback on code accuracy, test case results, and local variable states, and generating pseudo test cases for iterative refinement. The approach is evaluated on HumanEval and MBPP, claiming up to 7% improvement over existing state-of-the-art methods. Additional experiments examine feedback granularity, iteration count, and temperature. However, multiple reviewers note significant concerns about novelty, missing comparisons, methodological vagueness, and evaluation rigor.

### Strengths

- The problem of debugging for code generation is interesting and relevant.
- The idea of mimicking human debugging to improve code generation is interesting.
- The method is described as simple and easy to integrate into other frameworks.
- One reviewer (Rating 5) notes that the method achieves SOTA performance compared to current baselines and includes an ablation study showing component contributions.
- Additional experiments on feedback granularity, iteration number, and temperature are provided.

### Weaknesses

1. **Lack of novelty and missing comparisons**: Several reviewers identify that the core idea of logging runtime variable values as debugging feedback has been explored in LDB (Zhong et al., ACL 2024). Yet no comparison to LDB is made. Moreover, the paper overlooks other important debugging / refinement methods in both the experiments and related work, such as Self-Debug (Chen et al., ICLR 2024), Self-Refine (Madaan et al., NeurIPS 2024), Reflexion (Shinn et al., NeurIPS 2024), AutoCodeRover (Zhang et al., ISSTA 2024), Cycle (OOPSLA 2024), Coffee, SelfEvolve, and MapCoder. This omission weakens both the technical contribution and the evaluation.

2. **Vague methodology and lack of reproducibility**: The description of the five components (code generator, pseudo test case generator, executor, debug module, feedback module) is too vague. Key details are missing: the exact prompts used for each step, how runtime values are stored and formatted for feedback, and how pseudo test cases are validated. No workflow figure is provided for the architecture. These gaps raise concerns about soundness and reproducibility. One reviewer questions the feasibility of using an LLM to validate pseudo test cases.

3. **Evaluation rigor issues**:
   - **Inconsistent SOTA numbers**: The reported pass@1 for GPT-3.5 (56.4) and GPT-4 (66.1) on HumanEval differ substantially from values reported in other papers (e.g., 76.2% and 84.1% in DeepSeek-Coder). Similarly, Self-Debug’s reported numbers (60.1 and 80.6) conflict with the Self-Debug paper (72.8 and 80.2 on MBPP when using program traces).
   - **Rounding inconsistencies**: On HumanEval (164 problems), a reported 97.2% with GPT-4 does not correspond to any integer count (159/164 = 96.95%, 160/164 = 97.6%). Similar issues exist in other table results.
   - **Iteration count**: The analysis uses 8 iterations in Figure 3 but only 5 iterations in Figure 5; the exact maximum iteration setting is not stated for the main results (Section 4.3), and it is unclear whether baselines use the same count.
   - **Temperature experiments**: For non-zero temperature, experiments should be repeated multiple times and averages reported. Greedy decoding (T=0) should also be included.
   - **Debugging experiments (Section 4.5)**: How “debugging accuracy” is measured is unclear. No statistics about the buggy codes (e.g., count, bug type distribution) are provided. No comparison with other debugging methods (e.g., Self-Debugging, LDB) is given.

4. **Dataset choice**: HumanEval and MBPP are relatively easy benchmarks. Evaluation on more challenging datasets (e.g., BigCodeBench, APPS) is needed to demonstrate robustness.

5. **Writing and presentation deficiencies**:
   - Numerous grammar issues and typos throughout the paper.
   - Incorrect citation formatting (e.g., “AgentCoder Huang et al. (2023)” instead of proper parenthetical citations; missing \citep usage).
   - The appendix is disorganized and difficult to read.
   - Table 1 is not clear/intuitive.
   - Line 62 appears incomplete.
   - Direct examples (e.g., of pseudo test cases) should be included in the Appendix for clarity.
   - The paper’s structure needs improvement (e.g., punctuation, citation consistency).

6. **Missing details on automation**: It is unclear whether the entire architecture is fully automated (e.g., pseudo test case generation and validation).
