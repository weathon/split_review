## Merged Review

### Summary

Reviewers uniformly praise Spider 2.0 as a significant advance in Text-to-SQL benchmarking, moving from simple queries to real-world enterprise workflows. The benchmark comprises 595–632 tasks derived from actual projects and tutorials, with databases having (often >1,000) columns across diverse SQL dialects (BigQuery, Snowflake, DuckDB). Tasks require multi-step SQL (often >100 lines), schema linking, dialect understanding, and interaction with project-level codebases and documentation. Evaluations show even state-of-the-art LLMs achieve at best 15–17% success, underscoring large gaps. The dataset is publicly available with source code, and the analysis provides clear insights into limitations (dialect errors, schema linking, etc.). Reviewers note the benchmark’s originality, quality, and potential to drive progress toward autonomous data analytics agents. While all rate the paper highly (scores 8), several note missing aspects for full enterprise realism: multi-turn agent process definition, more granular difficulty classification, support for Python/scripting, business context, schema complexity details, and realistic question generation.

### Strengths

- **Benchmark originality and significance**: Fills a critical gap by going beyond existing benchmarks (Spider 1.0, BIRD, WikiSQL, GeoQuery), which either focus on simple single‑table queries or multi‑table tasks without real‑world complexity. Spider 2.0 introduces enterprise‑level challenges: large schemas (>1,000 columns), multiple SQL dialects (DuckDB, Snowflake, BigQuery), and complex multi‑step workflows that often involve nested queries and advanced SQL functions (e.g., ST_DISTANCE, CORR). This redefines the text‑to‑SQL task to align with practical enterprise applications.

- **Dataset quality and realism**: Tasks are derived from actual enterprise projects and tutorials, not synthetically generated. Each database is selected to have a minimum of 200 columns, ensuring sufficient complexity. The inclusion of project‑level codebases and SQL dialect documentation as context is a first in text‑to‑SQL benchmarks, reflecting a crucial part of a data engineer’s workflow (marking an advancement over BIRD’s simple evidence). The dataset is publicly available and solidly curated.

- **Insightful evaluation and analysis**: The paper provides a thorough error analysis (e.g., dialect function errors, schema linking failures) and shows that even top‑performing models (o1‑preview) solve only 17.0% of tasks, compared to 91.2% on Spider 1.0 and 73.0% on BIRD. This clearly highlights current LLM limitations in enterprise settings. All reviewers consider this analysis valuable for guiding future research.

- **Reproducibility and community value**: Source code, baseline models, and data are all released, enabling easy reproduction and extension. The benchmark is seen as essential for both academic research and industrial adoption of LLM‑based text‑to‑SQL solutions.

### Weaknesses

- **Undefined multi‑turn agent process**: The benchmark lacks a clear definition of the ideal multi‑turn interaction sequence (number of turns, types of actions, strategy). While execution results are used as the metric, this aspect is crucial for evaluating agent efficiency and reasoning and should be emphasized more. (Reviewer 2, confidence 5)

- **Incomplete difficulty classification**: The current difficulty metric (SQL length) is not comprehensive. Tasks may involve complex joins, nested schema, ambiguous queries, or need for external knowledge. A more granular tagging system (e.g., data complexity, join count, ambiguity) would better characterize specific challenges. (Reviewer 2, confidence 5)

- **Only SQL allowed; no scripting flexibility**: Restricting execution to SQL limits LLMs’ ability to leverage other languages (e.g., Python/Pandas) for data transformation or cleaning. A more realistic enterprise setting should allow the model to choose the best tool for each sub‑task. (Reviewers 2 and 3, confidence 5 and 4 respectively)

- **Missing business context**: Enterprise workflows often rely on page‑long documentation or formulas to define metrics (e.g., DAU, retention). Spider 2.0 includes codebase and SQL docs but lacks such business‑specific documentation, which is essential for real‑world SQL generation. (Reviewer 4, confidence 5)

- **Schema complexity not fully captured**: The reported minimum of 200 columns does not guarantee intricate table relationships; 200 columns might be in a single table. Information on the number of tables per database and typical join counts is needed to assess schema complexity. (Reviewer 4, confidence 5)

- **Question source and realism**: Questions were generated by authors from SQLs crawled from forums/tutorials, which may not reflect real BI questions (e.g., trends, patterns). Involving real data engineers in the creation or audit process would increase the benchmark’s realism. (Reviewer 4, confidence 5)

- **Discrepancy in average query length**: The abstract claims queries “often exceeding 100 lines,” but the average query length is 144 tokens, which seems unlikely to correspond to >100 lines. Clarification is needed. (Reviewer 4, confidence 5)

- **Missing token count for context**: The paper does not report the total token count of (Codebase + DB Info + Documents) per task, which is an important parameter for selecting appropriate LLMs for agent construction. (Reviewer 3, confidence 4)

- **Schema linking datasets not open‑sourced**: While schema linking results are shown, the corresponding datasets are not released. Making them available would help extend research on LLM‑based schema linking. (Reviewer 3, confidence 4)

- **Unanswered model‑training detail**: For the CodeS‑15B baseline, it is unclear whether the model was fine‑tuned on Spider 2.0 or used directly from its existing checkpoint. This distinction affects interpretation of results. (Reviewer 2, confidence 5)

- **Request for error‑type breakdown**: Among dialect function usage errors, the ratio between simple syntax errors and completely incorrect function choices would be informative for understanding model behavior. (Reviewer 2, confidence 5)

- **Need for comparison with MLE‑Bench**: The authors should clarify the difference between Spider 2.0 and OpenAI’s MLE‑Bench to help position the contribution. (Reviewer 3, confidence 4)

- **Administrative**: The proper JSON files for Spider 2.0 and Spider 2.0‑Light should be clearly indicated in the repository. (Reviewer 3, confidence 4)

**Note on reviewer confidence and disagreement**: All reviewers rated the paper highly (8/8) with confidence 4–5. One reviewer (Reviewer 1) explicitly noted no major weaknesses, while the others provided the specific limitations listed above. The contrast is mild; the overall assessment is that the benchmark is a strong contribution but can be further enriched on several dimensions to better capture real‑world enterprise complexity.
