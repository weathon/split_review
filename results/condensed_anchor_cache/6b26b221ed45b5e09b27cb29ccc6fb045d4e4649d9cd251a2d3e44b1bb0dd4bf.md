## Merged Review

### Summary
This paper introduces FlashDP, a cache-friendly method for efficient DP-SGD training of LLMs. It fuses gradient norm calculation and gradient rescaling into a single backward pass to reduce memory movement (by up to 50%) and redundant computations (by 20%) compared to prior methods like GhostClip and Opacus. Experiments on GPT-2, TinyLLaMA, and a custom LLaMA-3B and LLaMA-13B show FlashDP achieves ~90% throughput of non-private training on four A100s without increasing memory, while matching standard DP-SGD precision. The reviews are mixed: one reviewer (score 6) finds the empirical results impressive but the novelty limited; another (score 3) strongly criticizes the lack of implementation details and absence of discussion about per-layer gradient norm computation; a third (score 6, low confidence) praises the problem importance and results but finds the method unclear; the fourth (score 5) values the empirical comparisons and technical contributions but notes the omission of JAX baselines.

### Strengths
- **Problem importance**: Improving DP-SGD performance is critical for adoption of differential privacy in ML, especially for large foundation models. (R1, R2, R3, R4)
- **Impressive empirical results**: FlashDP matches the memory footprint of non-private training and achieves 70-90% of its throughput, outperforming existing DP-SGD implementations (Opacus, GhostClip, BK) in speed while using only slightly more memory than GhostClip. (R1, R3, R4)
- **Comprehensive experimental evaluation**: Comparisons against non-private baselines and multiple DP-SGD implementations (Opacus, GhostClip, BK) across different models (GPT-2, TinyLLaMA, LLaMA-3B, LLaMA-13B) in various setups. (R2)
- **Careful presentation**: Nice figures, line-by-line breakdown of the hardware algorithm, explanations accessible to DP experts not familiar with GPU details. (R4)
- **Significant technical contribution**: Solving clipping during block-wise gradient computation (which a priori seems to require a multi-pass algorithm to learn the norm before clipping) is a nontrivial problem. (R4)  [Note: Reviewer 1 disagrees, calling the techniques "standard engineering techniques" with little novelty; see below in Weaknesses.]

### Weaknesses
1. **Insufficient implementation details and missing code** (major weakness – R2): The paper lacks a complete implementation or detailed pseudocode. Algorithm 1 is too high-level, especially for the Block-wise All-Reduce operation, which the authors acknowledge as a key challenge (line 356). For an engineering-focused paper, source code availability is essential. (R2)  [R1 also notes the subscript T in Algorithm 1 line 7 is undefined; R3 asks whether Algorithm 1 only describes an MLP layer.]

2. **Failure to address the fundamental challenge of computing per-example gradient norms across all layers** (major weakness – R2): Prior work (e.g., Section 4 of [1]) shows that DP-SGD requires the full gradient norm across layers for per-example clipping, forcing either recomputation or buffer storage. This work does not discuss how FlashDP handles this requirement or avoids additional recomputation/memory overhead. The substring "layer" appears only in the supplementary material and in different contexts. (R2)  [R1 similarly asks "How do you exactly match the performance of DP-SGD?" given that noise and subsampling create variance not reflected in Table 2; R4 asks if the losses in Table 2 are exactly the same due to possible numerical stability differences.]

3. **Missing baselines in figures and omissions of competitive methods** (minor weakness – R2): GhostClip is omitted from Figure 4, and both GhostClip and BK are omitted from Figure 5, without justification. These methods were more competitive with FlashDP than the retained Opacus baseline; indeed Table 3 shows GhostClip outperformed FlashDP in memory usage. (R2)

4. **Clarity issues with the proposed method** (R1, R3):
   - The intuition for memory savings is not straightforward: per-sample gradients for all weights still appear to be saved before block-wise synchronization, yet FlashDP claims lower memory than Opacus, which also explicitly stores per-sample gradients. (R3)
   - Figure 1 is not informative—how does eliminating the buffer help throughput? (R1)
   - Definitions like GEMM and HBM are used without expansion, limiting accessibility. (R3)

5. **Lack of novelty concern** (R1): Most techniques appear to be standard engineering optimizations for accelerating deep learning, rather than fundamentally new ideas.  [This contrasts with R4’s positive view of the technical contribution; the minority view of R1 is that novelty is low.]

6. **Missing comparisons to JAX implementations** (limited weakness – R4): All empirical comparisons are PyTorch-only. The original Opacus paper (Appendix E, arxiv:2109.12298) shows that JAX-based DP-SGD can be more scalable (lower per-iteration runtime after a large compilation cost). It is unclear whether FlashDP’s techniques work in JAX or how it compares to JAX implementations. (R4)

7. **Sequential-loop inconsistency in Algorithm 1** (minor – R2): Lines 8-10 describe an All-Reduce between blocks for gradient norm computation, but all *for* loops in the pseudocode are executed sequentially, so there are no multiple blocks to reduce. Clarification is needed. (R2)

8. **Subsampling and implementation details** (R1):
   - How is Poisson subsampling performed? In the reviewer’s experience, Poisson subsampling itself can slow training even without gradient clipping.
   - When fixing batch size, does that mean using subsampling rates that yield that batch size in expectation?

9. **Custom model architecture**: The paper evaluates on a LLaMA-like 3B model, but the official LLaMA release does not include a 3B variant. The authors should clearly state that this is a custom architecture and provide its full description. (R2)

10. **Applicability questions** (R3): Can FlashDP be applied to other architectures (e.g., CNNs for vision)? Is it possible to package the method for easy use with transformer variants? (Not criticisms per se, but missing ablation/discussion.)

11. **GhostClip memory efficiency vs. NonDP** (R3): Why is GhostClip's memory usage even more efficient than NonDP (Table 3)? (A request for explanation of an observed comparison.)
