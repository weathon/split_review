## Merged Review

### Summary
The paper proposes Agent-G, a unified framework for Graph Retrieval-Augmented Generation (GRAG) that combines an agent, a retriever bank, and a critic module to handle queries requiring both unstructured documents and structured graph knowledge bases. The agent uses self-reflection to improve actions, and the critic evaluates answer reliability. Experiments on STaRK and CRAG datasets show relative Hit@1 improvements of 47% (STaRK-MAG) and 55% (STaRK-Prime), and 35% accuracy increase with 11% hallucination reduction (CRAG). Reviewer 3 was notably more positive (score 5, confidence 4) than the other reviewers (scores 3, confidence 2–3), citing stronger significance and clarity of the Critic Module.

### Strengths
1. **Novel task setting**: Addresses RAG with both unstructured documents and structured graph knowledge bases, a relevant and under-explored scenario (Reviewer 1, Reviewer 4).
2. **Promising performance**: Achieves significant improvements over baselines on two real-world benchmarks (Reviewer 1, Reviewer 2, Reviewer 3).
3. **Unified framework with agent and critic**: Automatically retrieves from multiple sources, uses self-reflection, and includes a Critic Module for robustness and interpretability (Reviewer 2, Reviewer 3). The critic also enables evaluation of answer reliability (Reviewer 3).
4. **Clear presentation**: Well-organized structure, clear explanation of motivations and challenges, easy to follow (Reviewer 2, Reviewer 4).

### Weaknesses
1. **Task definition and scope unclear**:
   - The GRAG task is not formally defined: what are the exact inputs? Does the knowledge base consist of a knowledge graph, or documents with relational data? Figure 1 suggests the latter but is ambiguous (Reviewer 1, Reviewer 4).
   - The distinction between textual and relational query types lacks formal definitions. Example: "What is Bob’s mother’s name?" – under which category? (Reviewer 4).
   - The paper does not report the proportion of hybrid, textual, and relational queries in the datasets, making it hard to assess the necessity of handling hybrid queries (Reviewer 4).

2. **Insufficient implementation details**:
   - Missing details on the retrieval module (retriever and ranker), including how graph retrieval is implemented, which embedding model and ego-graph retriever are used, and the design of the validator (binary classification) and its performance (Reviewer 1, Reviewer 4).
   - The LLMs used for the agent, validator, and commentator are not specified (Reviewer 4).

3. **Limited originality and novelty**:
   - The approach appears to be a straightforward compilation of existing methods: the critic module is essentially self-reflection (Reviewer 2). The method closely resembles ReAct, with only the Action function modified and a critic added—no fundamental difference is demonstrated. No code is provided, only prompts (Reviewer 3).
   - The Critic Module is an intuitive idea common in agent systems, and its effectiveness heavily depends on the underlying LLM capability (Reviewer 3).

4. **Insufficient experiments and comparisons**:
   - Missing comparisons with state-of-the-art Graph RAG methods such as Microsoft’s GraphRAG (Reviewer 3, Reviewer 4). Also missing other relevant RAG baselines like IRCoT, Adaptive-RAG, REPLUG, and Trace (Reviewer 1).
   - The method is not evaluated on traditional graph tasks (e.g., KBQA, GrailQA) to support the claim of adaptability (Reviewer 2).
   - No experiments with different LLM backbones (e.g., GPT-3.5, GPT-4, LLAMA3-8B) to test generalizability (Reviewer 2, Reviewer 3).
   - The claim of interpretability is not backed by quantitative metrics (e.g., readability, faithfulness); only a single qualitative case is provided (Reviewer 2).
   - The paper does not report or compare the number of LLM calls or token consumption per query, which is important given the multiple invocations required (Reviewer 3, Reviewer 4).
   - STaRK dataset: the knowledge graph is derived from the documents—why not directly use the documents? (Reviewer 4). CRAG dataset: contains only 50 web pages, which is too small for reliable RAG evaluation (Reviewer 4).

5. **Cost and efficiency concerns**:
   - Handling graph queries through multiple model invocations per query is expensive, and the queries addressed are relatively simple, raising questions about cost-effectiveness (Reviewer 4).

6. **Writing and presentation issues**:
   - Line 048 mentions "tool-use methods" without clarification or justification (Reviewer 1).
   - Experimental section lacks essential settings details (Reviewer 1).
   - Table 4 baselines use mixed backbone architectures, and the meaning of baseline categories (e.g., Cot LLM, Text-only RAG, Text & Graph RAG) is not clearly explained (Reviewer 1).
   - The method description is unclear, especially how the model decides which knowledge base to query (Reviewer 3).
