## Merged Review

### Summary
DynamicRTL introduces a Graph Neural Network (GNN) that learns circuit representations by incorporating both static structure and multi-cycle dynamic execution. It models RTL circuits as operation-level Control Data Flow Graphs (CDFGs) and proposes DR-GNN, a heterogeneous GNN that handles non-commutative operations via parameterized attention per operation type and node position. The work contributes a new dataset of over 6,300 Verilog modules and 190,000 simulation traces and evaluates DR-GNN on branch prediction and assertion prediction tasks. While reviewers acknowledge the importance of exploring circuit dynamism and the creation of a benchmark, they raise significant concerns about the evaluation’s simplicity (binary classification only), the small circuit sizes (mostly 10–500 nodes), limited novelty (heavy reliance on Heterogeneous Graph Transformer [1] and GRU [2]), missing comparison with stronger/recent circuit GNN baselines, unconvincing over-smoothing claims, poor reproducibility (no code/dataset/hyperparameters), and lack of analysis on scalability, variance, depth, speed, and comparison with commercial tools or human evaluation. Reviewer scores vary from 3 to 6, indicating disagreement on the strength of the contributions and the experimental validation.

### Strengths
- First comprehensive dynamic circuit dataset, containing over 6,300 Verilog modules and 190,000 simulation traces. (R1, R3, R5)
- Novel approach that combines operation-level CDFGs with a circuit-aware GNN to capture dynamic runtime behavior, an underexplored dimension in circuit representation learning. (R1, R2, R5)
- Addresses the over-smoothing problem in GNNs (R3; though R4 contests the evidence).
- Well-written and clearly organized; technical steps (CDFG construction, DR-GNN architecture) are easy to follow. (R4, R5)
- Builds a benchmark for dynamic circuit modeling. (R3)
- Extensive experiments showing effectiveness on branch prediction and transfer learning to assertion prediction. (R1, R2)
- Tackles an important and underexplored problem with potential impact on hardware verification, optimization, and EDA. (R2, R4, R5)

### Weaknesses
- **Limited evaluation scope:** Only branch prediction and assertion prediction (both binary classification) are used; the paper does not evaluate on typical dynamic metrics such as timing, power, glitch, or PPA estimation. (R1, R3)
- **Task simplicity:** Binary classification tasks are insufficient to validate the quality of the learned representation; more complex/intelligent tasks are needed. (R2, R3)
- **Circuit sizes too small:** Most circuits have 10–500 nodes; scalability to larger, real-world circuits is untested, and the accuracy drop in Table 2 is not fully explained. (R2, R3, R5)
- **Limited novelty:** The DR-GNN architecture is largely based on Heterogeneous Graph Transformer [1]; the use of GRU has been explored in prior works (e.g., [2]); several recent circuit representation learning methods (e.g., [3-5]) are not compared. (R4, R5)
- **Unconvincing over-smoothing claim:** Figure 4 shows a significant accuracy drop at 30 layers, and prior over-smoothing works [6] are discussed but not compared. (R4)
- **Poor reproducibility:** Source code and dataset are not provided; hyperparameter settings for DR-GNN and baseline GNNs are missing; it is unclear if a validation set was used for tuning. (R4)
- **Lack of statistical rigor:** No variance reported for accuracy scores in Tables 1 and 3; test set size and class balance are not provided, making it possible for data to be biased. (R2, R4)
- **No depth analysis:** Accuracy across different circuit depths (in contrast to sizes in Table 2) is not examined. (R4)
- **Training/inference speed not reported.** (R2)
- **No comparison with human evaluation or existing commercial/pre‑existing tools** (e.g., RTL simulators or formal verification). (R2, R5)
- **Generalizability unexplored:** Model is only tested on RTL-level CDFGs; applicability to netlists or higher abstraction levels (layout optimization) is not addressed. (R5)
- **Dynamic features not clearly defined:** The paper focuses on branch and multi-cycle execution, but other dynamic aspects (e.g., iterative algorithms where iteration count depends on input and affects runtime/power) are not modeled; a formal definition of “dynamic behavior” is needed. (R3)
- **Input sequence selection details missing:** Robustness would benefit from an explanation of how input sequences were selected for testing. (R5)
- **Abstract improvement:** Including quantitative results in the abstract would give a clearer overview of performance. (R5)
