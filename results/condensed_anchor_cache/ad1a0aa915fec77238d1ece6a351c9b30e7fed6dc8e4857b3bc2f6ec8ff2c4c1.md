## Merged Review

### Summary
The paper proposes ToolDec, a finite-state machine-guided decoding algorithm for tool-augmented LLMs that eliminates syntactic errors by ensuring valid tool names and type-conforming arguments. It is designed to work with any tool-augmented LLM and removes the need for fine-tuning or in-context documentation by enabling tool selection based solely on tool names. The method is validated by applying it on top of ToolLLM, ToolkenGPT, and RestGPT across tasks involving math functions, knowledge graph relations, and real-world RESTful APIs, showing zero syntactic errors and improved performance.

### Strengths
- The FSM-guided decoding method is intuitive, simple, and suitable for solving syntax errors in tool calls. [R1, R2]
- The method is compatible with existing LLM tool-use schemes, including both fine-tuning and in-context learning. [R2]
- Empirically eliminates syntactic errors entirely, leading to significantly better performance. [R1, R2]
- Validated across several different LLMs (ToolkenLLM, RestGPT, ToolLLM), and appears to improve the in-context learning ability of the LLMs. [R3]
- Maintains levels of accuracy even with increasing numbers of unseen tools in the test set (Figure 5). [R3]
- Demonstrates that LLMs still require external knowledge to constrain the search space for tool use and that existing methods (fine-tuning, in-context learning) are insufficient to address syntax errors. [R4]
- The type of errors (syntax errors) is shown to be addressable by a simple FSM for the settings tested. [R4]

### Weaknesses
- The switching between language mode and tool mechanism is unclear. The effectiveness of the switching and whether the `<T>` token can be appropriately decoded should be evaluated. [R1]
- The reported zero error count may be due to the existing tool-learning benchmark being too easy. The claim of zero error rate should be carefully qualified. [R1]
- FSM construction may require careful curation: how to decide the best naming for a tool, robustness to name changes, and the process for constructing FSMs for a large collection of tools (e.g., via parsing tool documentation) need more discussion. [R2]
- It is unclear how ToolDec enables generalization to new tools beyond syntactic correctness. The FSM does not provide information on when to invoke a tool, so generalization depends only on the LLM's language prior and proper naming. [R2]
- Would like to see an experiment testing robustness by assigning tool names that are not semantically meaningful. [R2]
- Need more explanation why ToolDec is faster at inference compared to ToolkenGPT. [R2]
- The paper claims the general machinery of FSM is not necessary (“any grammar checker that tells the set of valid next tokens suffice”), so better motivation for using FSM is needed. [R3]
- The approach seems like a step backwards to expert-based AI, as improvements largely result from hand-crafting decoding constraints. It is unclear if the hand-crafted constraints were tailored to perform on the test data. [R3]
- Table 4 timing results: were all methods equally optimized? [R3]
- The term “fine-tuning” is confusing because ToolDec involves no parameter fine-tuning; does it refer to evaluating the LLM+ToolDec only on unseen tools? [R3]
- Novelty is limited: constraining the search space of a language model by a grammar is a known technique (though possibly not applied to LLMs for tool use before). Deeper discussion is needed on why LLMs have limitations without such external knowledge, and whether a much stronger LLM would still exhibit the same problem. [R4]
- The technique goes against the simplicity of LLMs (plain text input/output). It may not always be possible to automatically construct FSMs for more complex tools; manual definition is tedious and error-prone. Decoding with an external FSM adds system complexity. [R4]
- Would like to see the list of tools and their signatures used in experiments, as well as the prompts used for both baselines and the proposed method (could be in appendix). [R4]

*Note: Reviewer 1 (score 8, confidence 4) is notably more positive overall, while Reviewers 3 and 4 (scores 5, confidence 5 and 4 respectively) raise stronger concerns about novelty and complexity.*
