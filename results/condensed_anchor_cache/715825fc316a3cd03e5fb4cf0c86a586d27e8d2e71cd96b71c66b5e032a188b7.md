## Merged Review

### Summary
The paper introduces GitChameleon, a manually curated benchmark of 116 Python code completion problems, each conditioned on specific library versions and accompanied by executable unit tests. The benchmark aims to evaluate LLMs' ability to generate version-specific code that is syntactically correct and functionally accurate. The paper evaluates state-of-the-art LLMs, finding that even GPT-4o achieves only 39.9% pass@10 (43.7% with error feedback), highlighting the difficulty of version-switching. The benchmark is intended to advance adaptable code generation models.

### Strengths
- Novel focus on version-specific code generation, addressing a critical gap in existing benchmarks that largely ignore library version dynamics (Reviewer 1, 2, 3, 4).
- Execution-based evaluation using unit tests provides a robust measure of functional correctness beyond static analysis (Reviewer 1, 2).
- Meticulous manual curation of the dataset, with executable unit tests, enhancing reliability and offering a concrete resource for future research (Reviewer 2, 3, 4).
- Well-organized and clear presentation, making the motivation and methodology accessible (Reviewer 2, 4).
- Includes evaluation of multiple state-of-the-art LLMs (GPT-4, CodeLlama, DeepSeek-Coder), providing insights into current limitations (Reviewer 4).
- Underscores the need for LLMs to adapt to rapidly changing libraries, which is practically important (Reviewer 1).

### Weaknesses
- Small dataset size (116 samples) limits generalizability and stability of results; many libraries include only a few API changes, increasing randomness (Reviewer 1, 2, 3, 4). One reviewer noted the benchmark will soon be saturated (Reviewer 1).
- Limited to Python, which oversimplifies version-switching challenges (e.g., type changes in Java are a significant aspect) and reduces broader applicability (Reviewer 2). Also, dataset focuses only on Python machine learning libraries (Reviewer 3).
- Missing critical baseline methods: RAG and few-shot learning were not included as baselines, despite being common approaches for addressing knowledge gaps in LLMs (Reviewer 2). Also, no experiments with prompt engineering (e.g., chain of thought), prompt-tuning, or parameter-efficient fine-tuning (Reviewer 4).
- The role of unit tests is questioned: interpreters already catch deprecated API usage, and passing tests does not guarantee the model actually used the target API (it could use alternative implementations or make non-API errors) (Reviewer 3).
- The benchmark currently offers evaluation only, without investigating methods to improve LLM version-switching ability; this is a thin contribution, especially given existing benchmarks in this domain (Reviewer 3). Some reviewers considered it an incremental improvement (Reviewer 1).
- Maintaining and expanding GitChameleon is non-trivial; it will require continuous updates as libraries evolve, and adding new languages/libraries will be difficult (Reviewer 1, 4).
- Manual dataset construction introduces potential bias (Reviewer 3).
- Omitted relevant related work on API learning, such as Zan et al. (2022) and Zhang et al. (2023), which could better contextualize the problem (Reviewer 2).
- Several specific issues: (a) The classification of change types (Line 177) lacks distribution counts; (b) Performance in 2023 being better than 2022 (Line 322) is unexplained; (c) Figure 3.4 should be Figure 5; (d) Wang et al. reference is not properly linked (Reviewer 3).
- The evaluation does not consider more mainstream LLMs like Claude (Reviewer 4).
- The benchmark's focus on software engineering libraries may make it more suited to specialized SE venues rather than general AI/ML conferences (Reviewer 4).

**Note on reviewer disagreement:** While three reviewers assigned a score of 3 (weak reject/neutral), one reviewer (Reviewer 4) assigned a score of 5 (accept) and was more positive about the benchmark's novelty and clarity. This contrast is reflected in the strengths acknowledging the unique focus and well-structured presentation, while weaknesses include concerns about thin contribution and incremental nature noted by other reviewers.
