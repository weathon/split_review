## Merged Review

### Summary
The paper introduces a dataset of correct and incorrect solutions for math and code reasoning tasks, generated by multiple LLMs (Mistral, Phi3, InternLM2-Math, MAmmoTH2-plus, LLaMA-3-8B, GPT-4o). It trains verifiers using outcome-reward models (ORM) and preference optimization (SimPO, DPO, ORPO), and proposes a collaborative verification strategy (CoTnPoT) that filters solutions by checking consistency between Chain-of-Thought (CoT) and Program-of-Thought (PoT) outputs before ranking with the verifier. Experiments on GSM8k, MATH500, and MBPP show improvements, achieving state-of-the-art results (e.g., outperforming GPT-4o with Qwen-72B-Instruct as reasoner).

### Strengths
- Compilation of a large dataset with both correct and incorrect solutions from multiple LLMs, offering a valuable resource for training verifiers.
- The CoTnPoT verification framework is intuitive and leverages complementary strengths: CoT provides step-by-step reasoning, PoT provides executable, error-sensitive validation.
- Thorough exploration of verifier training methods (ORM, SimPO, DPO, ORPO) with several generators, including weighted majority voting and hyper-parameter search.
- The method is simple and effective, with good analysis on verifier success (Table 4) and relevant ablations (Section 3.4).
- Achieves state-of-the-art performance on GSM8K and MATH (e.g., outperforming GPT-4o with Qwen-72B-Instruct as reasoner).
- Authors commit to releasing code and data, beneficial for reproducibility.
- Tackles an important topic (improving LLM reasoning via verification) with a sensible motivation.

### Weaknesses
- **Limited novelty**: The approach largely follows established directions: scaling inference-time compute via multiple reasoning paths and verifiers has been widely explored; comparing CoT with a formal version (PoT) also builds on prior work [1,2,3]. The primary novelties are data volume, data variety, and minor training variations. The paper’s tone overstates novelty (e.g., framing “scaling inference-time computation” and “develop inference-time verifiers” as novel solutions).
- **Unfair compute comparison**: CoTnPoT doubles inference-time compute by generating additional PoT solutions. For fair comparison, other methods should be given a matched budget (e.g., best-of-2K or sampling twice the number of solutions). The paper does not provide such a baseline.
- **Unclear adaptation to code tasks**: The method is not clearly explained for coding problems. Equation (2) and surrounding text are hard to understand. In code reasoning, many works assume access to test cases; it is questionable whether the verification setting (without test case usage) is appropriate. The authors did not compare with verification using, e.g., 50% of test cases.
- **Marginal improvement over strong baselines**: The gain of CoTnPoT over SimPO in Table 1 is relatively small. Since SimPO is already strong, the necessity of the collaborative step is not fully justified.
- **Missing ablation**: The paper lacks an ablation isolating the verification method from the benefits of using diverse model outputs for training. Simply merging knowledge from six models (Mistral, Phi3, InternLM2-Math, MAmmoTH2-plus, LLaMA-3-8B, GPT-4o) might itself boost reasoning; the contribution of the verification filter alone is unclear.
- **Performance imbalance between CoT and PoT**: CoT often has significantly lower accuracy than PoT. This imbalance undermines the collaborative verification step (which relies on CoT output) and raises concerns for more difficult benchmarks (e.g., AI Mathematical Olympiad). The method may sacrifice recall and degrade the upper bound of reasoning performance.
- **Lack of domain generality**: The method is only tested on math and code reasoning. Other reasoning domains are not assessed.
- **Inconsistent experimental settings**: The number of candidate solutions k varies across experiments (e.g., 64 vs. 100 in Figure 4). Figure 2 compares Maj@k without verifiers to verification-based approaches, but that comparison is not clearly stated.
- **Contradictory reliance argument**: The paper claims that using the same LLMs for code and description reduces over-reliance on external LLMs (line 256), yet for math tasks the method relies on an external LLM to generate PoT solutions (S_{PoT}).
- **Missing analyses and experiments**: The paper does not report performance improvement from fine-tuning the base model on the generated dataset. The performance curve with varying sample sizes is not shown. There is no analysis of which solution types the verifier handles better or worse.
- **Presentation issues**: “Recall rate” (Figure 1) should be renamed to Pass@64. “Sample-then-rank” should be replaced with “best-of-N”. Line 219: “reference-tuning” should be “preference-tuning”. Line 128: grammatically awkward phrase. Figure 3 explains the method only for math, not for code.
