- Decision: Accept
- Scores: 1, 6, 3, 6

## Merged Review

### Summary
The paper proposes ToolEVO, a framework that uses Monte Carlo Tree Search (MCTS), self-reflection, and tool-update mechanisms to adapt large language models (LLMs) to dynamic external environments where APIs/tools may change. It also introduces ToolQA-D, a benchmark derived from ToolQA by randomly mutating API usage. The paper evaluates ToolEVO on this benchmark and reports improvements over static and proprietary baselines. Reviewer scores are 1, 6, 3, 6, indicating strong disagreement: two positive (6,6), one moderately negative (3), and one strongly negative (1, high confidence=5).

### Strengths
1. **Important research problem.** The paper addresses the real-world challenge of LLMs adapting to evolving APIs/tools, which is a practical and underexplored area. (Reviewers 1, 2, 3, 4)

2. **Novel methodological components.** The self-reflection and tool-update mechanisms are considered novel contributions, grounded in the MCTS literature. (Reviewer 2)

3. **Strong empirical results on the curated benchmark.** ToolEVO is reported to outperform a wide range of baselines including proprietary LLMs (e.g., GPT-4, Claude-3.5-Sonnet) and supervised fine-tuned models, demonstrating adaptation capability. (Reviewers 2, 4)

4. **Useful benchmark release.** The ToolQA-D benchmark can facilitate future research on adaptation to dynamic tool environments. (Reviewer 2)

5. **Comprehensive baseline comparison.** The paper includes many strong baselines (closed and open-source LLMs) and extensive experiments, which is useful for the community. (Reviewer 3)

### Weaknesses
1. **Computational inefficiency and unrealistic design (Reviewer 1, high confidence).** The MCTS-based method is computationally heavy and not practical in real-world settings. A simpler proxy-based approach that accesses APIs through an intermediary could achieve the same adaptation at much lower cost. Moreover, the paper overlooks existing literature on design patterns for evolving environments, leading to a method that is cumbersome and likely impractical. (Minority strong negative view: Reviewer 1 states the design is flawed.)

2. **Misguided adaptation target (Reviewer 1).** The LLM itself should not be adapted; instead, the adaptation module (a small interface) should be updated. The paper does not separate the core LLM from the adaptation mechanism.

3. **Contrived evaluation setting (Reviewer 2, Reviewer 3).** The APIs in the benchmark are static within each evaluation episode; they do not change continuously. Therefore, strong performance does not demonstrate adaptation to a constantly evolving environment. Furthermore, the MCTS Q-values are not adaptive, so the method would not work in a truly dynamic setting. (Reviewer 2)

4. **Unfair comparison due to privileged reward signal (Reviewer 2).** ToolEVO receives a 0/1 reward at the end of each episode, while baselines only get API outputs/error messages. The paper does not compare against methods that also use the reward, making the evaluation potentially biased.

5. **MCTS may not be the source of performance gain (Reviewer 2).** Ablation results (Table 5) show that removing self-reflection and tool-update yields performance similar to supervised fine-tuning, suggesting MCTS alone contributes little. A direct comparison with a “Static-SFT + self-improve + tool-update” variant is missing to isolate MCTS's effect.

6. **Unconvincing problem setup (Reviewer 3).** The paper restricts the LLM to using only the outdated static prompt (\(P_C\)) and forbids updating the prompt with recent API data before each task. This seems artificially limiting, as a separate process could continuously optimize the prompt. A baseline that allows proprietary LLMs to update their static prompt with the latest API invocation data before each task is missing.

7. **Unclear MCTS implementation and lack of computational details (Reviewers 2, 3).** The state includes the full history, so tree nodes are rarely revisited; it is unclear whether this still constitutes effective MCTS. No illustrative example is provided. The paper omits discussion of inference-time overhead (time, tokens), sample complexity, hyperparameters, and standard MCTS implementation choices like rollouts and caching.

8. **Weak motivation and construction of ToolQA-D (Reviewers 3, 4).** The paper states that GPT-4 “randomly modifies” API usage but does not specify how (e.g., parameter names, descriptions, or whole API changes). It is unclear whether the same mutation is applied uniformly across all examples in \(P_{S_{in}}\) and \(P_{S_{ood}}\) or varies per instance. Using actual API version histories might be more realistic. The degree of difference between \(P_{S_{in}}\) and \(P_{S_{ood}}\) is not quantitatively described.

9. **Unclear result presentation and interpretation (Reviewers 3, 4).** Tables 2–4 use bold formatting inconsistently: ToolEVO’s score (e.g., 30.3) is bolded even when a higher score (Claude-3.5-Sonnet, 45.3) appears on the same line. The “Average-Hard” column suggests that proprietary LLMs (Claude-3.5-Sonnet) often outperform ToolEVO; if so, the baseline proprietary LLM would be the best method. The caption does not explain bold/underline notation. Results are reported with decimal points (e.g., “Coffee hard” has non-integer values) without explanation; no statistical significance tests or multiple run information is provided.

10. **Poor presentation and insufficient detail (Reviewers 2, 3, 4).** Key algorithmic details and explanations are deferred to the appendix, making the paper hard to follow. Hand-wavy phrasing (“stereotypes induced by Static SFT”, “lazily focus on how to use APIs”) is used without empirical support. Abbreviations like SFT are not defined initially. Figure 2 shows no drop in performance for ToolEVO while others drop, but this is not explained.

11. **Missing generalization to truly out-of-distribution APIs (Reviewers 3, 4).** The method is tested only on predefined mutated versions (\(P_{S_{in}}, P_{S_{ood}}\)) of the same base APIs. It remains unclear whether the approach can adapt to entirely new APIs not seen during training or to real-world API version changes.

12. **Missing comparison to online RL adaptation (Reviewer 2).** The paper does not compare to an online RL approach that directly optimizes the policy using the reward signal, which could be a natural competitor.
