## Merged Review

### Summary
This paper proposes instruction tuning for code language models using git commits, which pair code changes with natural-language instructions via commit messages. The authors compile CommitPack, a 4TB dataset of permissively licensed commits across 350 programming languages, and then filter it to produce CommitPackFT, a 2GB subset of high-quality, imperative code instructions. For evaluation, they extend HumanEval into HumanEvalPack, covering three tasks (code fix, explanation, synthesis) across six languages (Python, JavaScript, Java, Go, C++, Rust). They fine-tune StarCoder and CodeGeeX on a 5000-sample subset of CommitPackFT combined with OASST and achieve state-of-the-art performance among permissively licensed models on HumanEval Python (46.2% pass@1). The resulting models, OctoCoder and OctoCodeGeeX, are released.

### Strengths
- **Permissively licensed data and models**: The collection and tuning are permissively licensed and avoid proprietary data, making a significant contribution to the open-source research community (Reviewer 3, confidence 4).
- **Large-scale dataset creation**: CommitPack (4TB) and CommitPackFT (2GB) provide a large, reproducible resource of code instructions across 350 languages, which will benefit future research (Reviewers 1, 3).
- **Careful decontamination and benchmark construction**: The authors go to substantial effort to decontaminate HumanEvalPack (e.g., removing solution overlap between code and generated explanations), lending credibility to the results (Reviewer 3).
- **Comprehensive and well-written presentation**: The paper is well-organized, with clear motivation, detailed discussion, nice figures, extensive supplementary material, and thorough comparisons (Reviewers 1, 2). The ablation studies and qualitative analysis yield many interesting conclusions (Reviewer 3).
- **Useful and extended benchmark**: HumanEvalPack extends beyond a single task and language, representing a substantial improvement over the standard HumanEval set (Reviewer 2).
- **Ablation insights**: The combination of CommitPackFT with OASST yields the best performance on HumanEvalPack, demonstrating the complementary value of the dataset (Reviewer 3).
- *Minority view (Reviewer 1, score 6, confidence 3):* While agreeing on these strengths, Reviewer 1 is less convinced about the models’ performance without further explanation, and rates the paper lower (6 vs. 8) compared to Reviewers 2 and 3.

### Weaknesses
- **Scale of CommitPack vs. actual usage**: The paper leads with the enormous 4TB size of CommitPack, but the version actually used for instruction tuning is only 2GB (0.05% of the original). No experiments or validation on the full set are provided, and the text does not always clarify this distinction (e.g., abstract, contributions on page 2). This creates the impression that the larger set is very noisy; the 2GB subset should be the primary concrete contribution (Reviewer 2, confidence 5).
- **Lack of justification for fine-tuning data choices**: (i) Only 5,000 samples from CommitPackFT are used for fine-tuning, with no explanation of why this number was chosen or whether more data would help (Reviewers 2, 3). (ii) OASST uses nearly twice as many examples (~8.5K), without ablation or discussion of the ratio. (iii) StarCoder receives 3 extra samples; this change is not well motivated (Reviewer 2). These decisions are not defended, and the fact that CommitPackFT is never used alone—only in combination with OASST—raises questions about its standalone quality (Reviewer 2).
- **Evidence for CommitPackFT’s value is limited**: In the HumanEvalPack results, CommitPackFT + OASST mainly boosts the “Fix” task; on “Sync” and “Explain” it performs about even or worse than OASST alone (Tab. 13). This suggests CommitPackFT may not be high-quality but simply adds more coding examples to OASST (Reviewer 2). An ablation to test more data from CommitPackFT could clarify its usefulness (Reviewer 3).
- **HumanEval argument insufficiently supported**: The paper argues that building on HumanEval is a strength because the dataset is commonly filtered from training data, but this is hard to verify given limited insight into LLM training data and evidence that pretrained models perform worse on newer problems (e.g., CodeContests). A more cautious discussion acknowledging this as a potential limitation is recommended (Reviewer 2).
- **Missing evaluation on explanation task**: Reviewer 2 suggests that StarCoder’s poor performance on the explanation task might be an artifact of prompt design; the model could be prompted to predict a docstring/javadoc using its Fill-in-the-Middle capabilities, which would give it a fairer chance. Also, reporting BLEU/METEOR scores on explanation generation could provide a complementary view to the automated metric proposed (Reviewer 2).
- **Low token limit for inputs**: Appendix C shows inputs are filtered to 768 tokens (before-code + message + after-code). This is very low by modern standards and results in very short programs compared to the natural commit distribution (Tab. 8). The motivation and downstream impact are not discussed (Reviewer 2).
- **Unexplained model differences**: OctoCoder and OctoCodeGeeX both achieve best performance among permissive models, but no detailed comparison of their architectures, training data, or behavior is given. Specifically, why does OctoCodeGeeX perform better on Go and Rust for the explanation task? (Reviewer 1, score 6, confidence 3)
- **Minor issues**: (i) Figure 3’s center panel is visually unclear—it looks like the model is prompted with code, predicts, then is prompted with more text and predicts again; a blank space between tasks and a clearer arrow would help (Reviewer 2). (ii) The statement that GPT-4’s accuracy varies by only 2% when sampling 1 vs. 20 samples is not backed by experiments; sampling 2–5 samples would balance cost and precision (Reviewer 2). (iii) The naming “CommitPackFT” is confusing because only a 5000-sample subset is used for fine-tuning, not the full 2GB (Reviewer 3). (iv) Some odd details in the appendix: why is “can’t you see i’m updating the time?” used as a commit message filter (Tab. 5)? Why is data limited to 2016 when more recent GitHub archives exist? (Reviewer 2)
