## Merged Review

### Summary
Three reviewers (scores 3, 3, 3) concluded that the evidence is insufficient to support the claimed benefits of Fusion Token, while one reviewer (score 5) was more positive, though noting the performance gap is smaller than described. All reviewers agreed that the method adds 1024 n‑gram tokens to a 51K BPE vocabulary, expands token groups to 10‑grams, and improves compression and inference speed on code data. However, they raised serious concerns about experimental validity, missing natural‑language (NL) evaluations, lack of necessary baselines, and unclear tokenization details.

### Strengths
- The method achieves faster inference because it produces shorter tokenized sequences (Reviewers 1, 4).
- It yields noticeable improvements on code generation benchmarks (Reviewers 1, 2, 4; e.g., Table 4 results).
- The paper clearly motivates the importance of tokenization by analyzing bits‑per‑word and bits‑per‑byte, and presents the algorithm in an understandable way (Reviewer 2).
- One reviewer (score 5) found the motivation strong and the method straightforward, noting that expanding to 10‑grams for higher compression is justified and should outperform naive BPE in practice, though the observed performance gap is smaller than described.

### Weaknesses
- **Insufficient and potentially biased experimental setup.**  
  - The only downstream task evaluated is code generation (Reviewers 1, 2, 4). The added tokens are derived from a specific code dataset, and evaluation datasets are similar in distribution; this raises concerns about overfitting and inflated performance (Reviewer 2). The bias is visible in Table 1 and Figures 2(a)/(c), where the improvement is mostly in the code portion (Reviewer 2).  
  - Only two model sizes (125M and 650M parameters) are tested, which is too small to support the claim that “BPE for large models with Fusion Token is superior to standard BPE” (Reviewer 2).  
  - No evaluations on standard NL benchmarks (e.g., PG‑19, WikiText103, or the Pile official GPT‑2 setups) are provided, despite the method being presented as general‑purpose (Reviewers 1, 3, 4). Code data has more patterns and a limited vocabulary, making token fusion more likely to succeed there; NL is more complex and may suffer semantic confusion (Reviewers 3, 4).  
  - The improvement on code is only about 10%; recent neural compression methods achieve 2–4× compression; the paper should discuss and compare with those (Reviewer 4).

- **Missing crucial baselines and ablations.**  
  - No comparison is made with adding the same number of tokens via simple bi‑gram merging (standard BPE) to isolate the effect of the Fusion Token method (Reviewer 2).  
  - The paper does not vary the number of added tokens (e.g., 500, 2K, 4K) to show how performance changes and to justify the choice of 1K (Reviewer 3).  
  - How “Bytes per token” in Table 1 is calculated is not explained (e.g., whether it is the average length E[ℓ]) – Reviewer 1.

- **Unclear tokenization details.**  
  - It is not specified whether Fusion Token merges tokens across whitespace. Standard BPE and SentencePiece do not merge across whitespace. If the proposed method does merge across spaces (e.g., “go_to” as one token), the comparison with conventional BPE is unfair (Reviewer 4). The authors should clarify and, if so, evaluate against BPE applied under the same crossing‑whitespace setting (Reviewer 4).  
  - The composition of the 1K added tokens is not described (Reviewer 2).  
  - It is unclear how to decide which fusion tokens to add for a given corpus and whether the method crosses whitespace (Reviewer 3).
