## Merged Review

### Summary
EditRoom is a two-module framework for language-guided 3D room layout editing. It uses GPT‑4o as a command parameterizer to break natural language commands into sequences of six edit types (rotate, translate, scale, replace, add, remove) and a graph diffusion model as scene editor to generate the edited layout. The paper introduces EditRoom-DB, a large-scale dataset of 83k editing pairs derived from 3D‑FRONT. Quantitative and qualitative results demonstrate effectiveness. The framework supports multi-operation commands without explicit training. (Reviewers 1–3)

### Strengths
- The paper is well-written (R1).
- The idea of decomposing a command into multiple steps is interesting and enables multi-operation editing without explicit training – useful for interior designers (R1, R2).
- The problem of language-driven 3D scene layout editing is important for real-world applications (R2).
- EditRoom-DB, with 83k editing pairs from 3D-FRONT, is a valuable contribution to the community (R1, R2, R3).
- The graph diffusion model is tailored to layout editing and outperforms the adapted DiffuScene (R3).
- The use of GPT‑4o as command parameterizer and graph diffusion as scene editor forms a reasonable, state-of-the-art pipeline (R3).

### Weaknesses
- **Motivation for the diffusion model is insufficiently justified.** For operations like rotate, translate, scale, add, remove, and replace, one could directly manipulate the source scene graph (e.g., rotate an object analytically, add/remove a node, retrieve an object from a database) – a diffusion model seems unnecessary for layout editing and is more appropriate for generating new scenes from scratch. The paper misses a relevant reference: *Language-Driven Editing of 3D Scenes from Scene Databases* (SIGGRAPH 2018). (R1, R3)  
  - *Minority: Reviewer 2 is more favorable (score 8) but still asks for complexity analysis; this contrast suggests that even a positive reviewer sees this as an open question.*
- **Missing comparisons with alternative approaches.**  
  - Only one baseline (DiffuScene‑N) is from existing work; the other is a variant of the proposed method. The paper should also compare with modified versions of InstructScene (ICLR 2024) and EchoScene (ECCV 2024) (R1).  
  - No comparison with LLM-based in-context learning methods (e.g., LayoutGPT) that could be adapted for layout editing by defining the task and conditioning on examples from EditRoom-DB. The examples should be selected based on edit type, not at random (R2).  
  - No comparison with heuristic methods: directly parsing breakdown commands to modify the scene graph, or using simulated annealing to resolve collisions – these would alleviate the need for a training dataset and provide a strong lower bound (R3).
- **Missing complexity analysis.** Training and inference time are not reported (R2).
- **Dataset construction and evaluation issues.**  
  - Test set size is only 500 samples vs. 83k training samples; the dataset is heavily biased toward bedrooms (∼50k train vs. 500 test) compared to dining rooms (∼18k train vs. 500 test). This imbalance may explain the higher performance on bedrooms in Table 2. The train:test ratio should be equalized across categories (R1).  
  - It is unclear whether the editing is one-shot (all commands at once) or progressive (one command at a time) (R1).
- **Lack of motivation for the language-based editing setting.** The paper does not discuss when a user would prefer a vague language instruction over direct interactive manipulation. The provided examples are straightforward; a more challenging setting would involve complex intended edits. For example, Figure 4 second row shows a user wanting to “rotate the bed” and expecting the companion nightstand to also rotate – but the method only edits explicitly specified objects and produces an unreliable layout (R3).
- **Insufficient analysis of the command parameterizer (GPT‑4o).**  
  - There is no in-depth analysis of the LLM’s spatial reasoning ability – when it fails and how to improve it. Figure 5’s example (making two nightstands symmetric) appears to have an incomplete LLM response (R3).  
  - Minor unclear details: whether the point cloud of each object includes RGB or only locations (line 227), and how “concatenate each element of source scene graphs into noisy target scene graphs” (line 241) is performed – is it attribute concatenation or node list merging? (R3)
