## Merged Review

### Summary
The paper introduces two datasets: M²CRB, a multilingual code retrieval evaluation benchmark with queries in Spanish, Portuguese, German, and French paired with Python, Java, and JavaScript code snippets (~7,700 points, curated via AST parsing, language identification, and human verification), and an additional paired English/code dataset similar to CodeSearchNet. The authors hypothesize that a model can map from non-English languages to code if it can map from English to code and from other languages to English. They train models using a contrastive loss for embedding similarity plus an autoregressive loss, combining their English/code data with existing translation datasets (e.g., TATOEBA, CodeXGlue). They evaluate on the new tasks, English code search, and code-to-code search (Java/Python) across model classes including CodeT5, CodeBERT, and CodeGen (60M–360M parameters). Results suggest generalization to unseen language pairs, and the paper discusses the influence of model size and architecture.

### Strengths
- Introduces a new multilingual natural language to code evaluation dataset (M²CRB) and an additional English/code paired dataset, addressing the scarcity of non-English code retrieval data. Multiple reviewers note the utility for non-English-speaking developers.
- Extensive evaluation across multiple model classes (CodeT5, CodeBERT, CodeGen), sizes (60M–360M), and language combinations (NL–code and code–code), confirming the proposed training hypothesis that models can generalize to unseen language pairs indirectly observed during training.
- Clear presentation of the dataset filtering pipeline (AST parsing, language identification, human verification), training methodology, and results, making the work easy to follow.
- The training setup (using paired NL–NL data to bridge between English and code) is noted as a practical approach given the scarcity of direct non-English code data, and could be extended to generative settings (code generation, summarization) in future work.
- Provides a path for future research on multilingual code retrieval and contributes to understanding generalization behavior.

### Weaknesses
- **Absence of baselines and ablations**: No baselines are provided for English code search (e.g., CodeBERT achieves MRR 0.7603—it is unclear what the auMRRc would be) or for Python–Java code search (e.g., from existing multilingual pre-trained models). Ablation studies are missing to disentangle the role of each training component (TATOEBA, CodeXGlue, English/code data) and to verify the claim of learning through an anchor language. Several reviewers note this as a significant gap (R1, R3, R4).
- **Missing comparison to alternative approaches**: The paper does not compare against a straightforward alternative: using the paired NL–NL data to train a translation model and then translating English queries to create large synthetic (Spanish, code) training corpora. Reviewers ask why the proposed objective is better than this translation-based method (R1, R3).
- **Limited language coverage and generalizability**: M²CRB only covers four natural languages (es, pt, de, fr) and three programming languages (Python, Java, JavaScript), omitting languages with different paradigms (e.g., Haskell, Prolog) or less common natural languages. This limits assessment of generalizability (R2). Potential biases from specific programming language styles or non-English docstring quality are not analyzed (R2).
- **Exploration of model scale is limited**: Experiments are restricted to the 60M–360M parameter range. The impact of larger models (e.g., GPT-3, Megatron-LM) on generalization is not investigated, leaving open the question of scaling behavior in this multilingual setting (R2). Reviewer 1 also questions the claim that “scaling up model size will not necessarily improve performance.”
- **Unclear role of additional datasets and pre-training exposure**: The purpose of adding TATOEBA and CodeXGlue to the training mix is not clearly articulated, weakening the anchor-language claim because another factor is introduced. Moreover, it is uncertain whether pre-trained models already have multilingual exposure in their training data, and whether the near-zero auMRR figures reflect task alignment issues rather than a lack of generalization (R4).
- **Writing clarity issues**: Several sentences are long or poorly constructed, hindering comprehension (R4). Examples include: Section 3.1 last paragraph (unclear purpose of discussing data realization), Section 4.1 second paragraph (“models able to generate train…”), and Section 4.1 after Equation 3 (“define translation auxiliary tasks”). The “decoder-only model” in Section 4.3.2 should be explicitly named (CodeGen) to avoid back-and-forth (R4).
- **Minority negative assessment**: One reviewer (R1, score 3) found the paper lacking scientific or technical contribution, arguing that the research question is already known from multilingual LMs learning a shared embedding space, the experiments are not well-motivated, and the value/need of the dataset is not convincingly demonstrated. This contrasts with the more positive views (scores 5, 6, 6) from other reviewers.
- **Additional reviewer questions that highlight weaknesses**: 
  - Why not simply use NMT to translate existing English docstrings into other languages? (R1, R3)
  - Is the “less compute-intensive” argument sufficient motivation for studying code search? (R1)
  - Why train a retriever model to generate (autoregressive loss) when large language models already excel at generation? (R1)
  - What is the purpose of the AST parsing phase in dataset creation? (R4)
  - Will the data and evaluation code be open-sourced? (R4)
