## Merged Review

### Summary

The paper proposes Code Execution Simulation (CES), a framework for evaluating LLMs’ code reasoning by having them predict output and intermediate states (branch conditions, loop variables, predicates, return values) for HumanEval Python programs. CES defines valid/invalid reasoning processes and measures reasoning consistency (strong, weak, random) across test cases with same or different prime-path coverage. Thirteen models (GPT-4 Turbo, Gemini-1.5 Pro, CodeLlama, DeepSeekCoder, Magicoder-S, SemCoder-S, StarCoder2) are evaluated. Results: 82.32% valid reasoning (30.79% correct outputs, 51.53% incorrect), but most reasoning is random (55.59%) or weak (41.69%).

### Strengths

*   Introduces an important research question: whether LLMs can emulate code execution for general software engineering tasks. (R1)
*   Provides a thorough investigation of LLMs’ code execution capability with a strong/weak framework and detailed error analysis across >10 models (small to large, closed to open). (R2)
*   Unique contribution: the concept of “invalid reasoning path” (incorrect intermediate state but correct final answer or branch selection), revealing that models may not follow exact instruction execution yet still arrive at a correct result. (R2)
*   Examines consistency of code execution ability across different test inputs covering different paths, showing that even when test cases go through the same path, models often still get them wrong. (R2)
*   Well-written, nicely structured; figures and tables are legible. (R3)
*   The story is engaging and the topic interesting. (R3)
*   CES improves on prior work by pinpointing errors in LLM reasoning at a lower inference cost. (R3)
*   Novel CES framework; diagnostic design detects suspiciously correct outputs under invalid reasoning. (R4)
*   Reasoning consistency metric (strong/weak/random) via multiple tests with same or different prime path coverage is a valuable benchmarking tool. (R4)

### Weaknesses

**Conceptual and definitional issues**

*   The choice of which intermediate states to predict (branch-taking, predicates, return values) is not justified; the exclusion of assignment statements is not supported by evidence (e.g., no ablation study comparing the chosen subset with a comprehensive set including assignments). The claim that predicting assignment values would confuse the model lacks experimental backing. (R3)
*   The definition of “invalid reasoning” (Equation 4) is ambiguous: (i) a compound property containing both correct and incorrect predictions is labeled invalid, but the example (loop variable `o` and loop iterable `zip(evens, odds)`) does not belong to the same property per Section 3.1. (R4) (ii) When an intermediate state (predicate) is wrong but the consequence (branch) is correct, this is called invalid, yet it could be _consistent_ (e.g., “if p or not p:” yields correct branch regardless of p). No evidence is given that such cases in the dataset are always truly incorrect reasoning. (R3)
*   “Valid reasoning” includes (by definition) all cases where the output is incorrect. This naming is confusing and lacks evaluation of consistency, which would be a better indicator of reasoning. (R3)
*   Using code execution simulation as a direct measure of code reasoning is debatable. Execution requires precise computational skills (e.g., multiplication, indexing) that are distinct from logical understanding of code logic. A model might compute simple operations correctly yet struggle with complex inputs without lacking reasoning ability. This distinction is not sufficiently discussed. (R4)

**Evaluation and benchmark limitations**

*   RQ4 results are underwhelming: no correlation between an LLM’s ability to emulate code and its performance on the same programming task. This does not support the paper’s hypothesis. Alternative explanations (e.g., humans also find bugs via pattern-matching, not deep emulation) are not explored. (R1)
*   Weak performance on CES may indicate suboptimal benchmark design: the format may be unnatural for LLMs, and free-form natural language reasoning allows correct derivation even when CES predicts wrongly. Appendix A.6 strengthens this suspicion, as strong models (GPT-4, Gemini 1.5 Pro) perform well on bug localization/repair but show no correlation with CES. (R3)
*   The lack of correlation with other coding tasks (Sec 5.5) is left unanalyzed—whether CES or bug tasks inadequately represent code reasoning, or measure different aspects. No other code comprehension tasks (e.g., summarization) are used. (R4)
*   Several “why” questions remain unanswered: why predictions differ from ground truth, why suspiciously correct outputs occur. Analysis relies only on case studies without quantitative data. (R4)
*   No control for test coverage per program is established; detailed Figure 6 partially compensates. (R3)
*   Restriction to HumanEval Python programs is a limitation; exploring other languages (C/C++ with bitwise ops, pointer arithmetic, security vulnerabilities) might better test the hypothesis. (R1)

**Experimental details and reporting issues**

*   Equation 1 notation is unclear (CES and GT symbols should be differentiated from variables). (R1)
*   Figure 7 radar plot and legend are very difficult to parse; grouping choices are confusing. (R1, R3)
*   Figure 8 instruction says “output” but the model is clearly given _input_ below; likely a typo affecting interpretation of results. (R3)
*   Typo: line 362 reports 83.32% valid reasoning, line 20 reports 82.32%. (R2)
*   In Sec 5.2 the statement “LLMs with good performance in valid reasoning also make more invalid reasoning” is contradictory because valid + invalid sum to constant; clarification needed. (R3)
*   The impact of variable values (large intermediate integers, long lists) on CES results is not discussed. (R2)
*   Whether the same prompts were used for all LLMs, how in-context examples affect performance, and the contribution of Chain-of-Thought are not addressed. (R4)
*   Sampling multiple outputs (pass@k) to account for hallucination variability is not explored. (R4)

**Contrast between reviewers**

*   Reviewer 2 (score 6) was notably more positive, commending the thoroughness, error analysis, and consistency insights. Other reviewers (scores 3,3,3) rated the paper lower, citing conceptual issues, insufficient justification, and limited benchmark design. (All)
