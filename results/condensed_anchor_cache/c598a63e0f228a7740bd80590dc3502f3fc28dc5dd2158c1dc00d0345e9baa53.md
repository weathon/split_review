## Merged Review

### Summary
This paper presents WasmTest, a generate-then-test methodology for testing WebAssembly binaries without source code. It leverages LLMs to generate equivalent C++ code from high-level descriptions of Wasm functionality, then creates test cases via LLMs and type-aware mutations to detect bugs. The approach is evaluated on the HumanEval-X and MBXP benchmarks, reporting compile rates, code coverage, and bug detection on manually injected bugs.

### Strengths
- **Novel approach to a relevant problem:** The generate-then-test methodology for black-box testing of Wasm binaries is novel and addresses an important, underexplored problem. Reviewers noted that the paper is the first to combine LLM-based binary lifting and automatic test generation in an end-to-end pipeline for Wasm, and the approach may extend beyond Wasm to other binary testing scenarios.
- **Clarity and presentation:** The paper is clearly written, well-organized, and easy to comprehend. All four reviewers praised the presentation and readability.
- **High coverage on selected benchmarks:** WasmTest achieves high code coverage on the simple, single-program benchmarks used (HumanEval-X, MBXP). One reviewer also highlighted that the evaluation across multiple LLMs demonstrates robustness to the choice of LLM.
- **Interesting and impactful problem domain:** Testing Wasm binaries is a relevant and difficult task; the paper’s focus on this area was appreciated.

### Weaknesses
- **Limited comparison with existing approaches:** The paper lacks a comprehensive comparison with existing Wasm test generation tools (e.g., WASMaker, wasm-smith, Wasm-mutate), binary-lifting tools (e.g., wasm2c), general fuzzing techniques (AFL, libfuzzer), and other LLM-based test generation/fuzzing works (CODAMOSA, ChatUniTest, MuTAP, TitanFuzz, FuzzGPT, Fuzz4All). Without such baselines, the effectiveness of the generate-then-test pipeline over simpler alternatives (direct Wasm input generation, direct fuzzing, or using a traditional reverse engineering tool) is not demonstrated. Multiple reviewers considered this a critical omission.
- **Dubious oracle correctness:** WasmTest uses LLM-generated C++ code as the test oracle. The paper does not guarantee functional equivalence between the C++ code and the original Wasm binary. Passing example tests and majority voting do not eliminate the risk of non-equivalence, leading to potential false positives (disagreement attributed to a bug when it is actually a semantic difference). One reviewer noted the LLM oracle has “approximately 50% accuracy” (from the paper’s data), further undermining confidence in bug detection. The false positive rate is not reported.
- **Insufficient evaluation of the core translation step:** The paper does not evaluate whether the LLM-generated C++ code is semantically equivalent to the Wasm binary beyond pass rates on example tests. An ablation replacing the LLM with a traditional tool like wasm2c is missing, as is a comparison of LLM-based translation to a simpler reverse engineering approach. The reliance on natural language descriptions of Wasm functionality introduces a bottleneck: the approach cannot be used without such descriptions, and no validation of description quality (e.g., accuracy, completeness) is provided. One reviewer raised that the translation of high-level descriptions into executable code is itself a difficult problem and the paper does not convincingly show its efficacy.
- **Unclear use cases and intended audience:** The paper does not clearly state who would use WasmTest. For attackers, functional bug detection is less interesting than security bugs, and they may not have access to natural language descriptions of the Wasm binaries. For developers, source code is usually available, making direct source-level testing more efficient. This ambiguity reduces the practical significance of the work.
- **Limited evaluation scope and benchmarks:** The evaluation is restricted to two small, single-program datasets (HumanEval-X, MBXP) that are originally source code compiled to Wasm – creating an artificial scenario tailored to the methodology. Real-world Wasm binaries are often much larger and more complex (e.g., from C/C++ applications, game engines). The paper does not test on complex, real-world Wasm binaries, nor does it evaluate the approach when no natural language description is provided (a common case in practice).
- **Limited novelty in mutation component:** The type-aware mutation techniques are not new; many existing mutation testing tools for C/C++ (e.g., CCmutator) and LLM-driven mutation tools (e.g., LEAM) have explored similar ground. The paper does not compare or distinguish WasmTest’s mutation step from these.
- **Insufficient details on bug detection experiments:** The manual injection of bugs lacks detail: fault types, the background of the engineers who crafted them, and the number of bugs per benchmark are not clearly described. Without this information, the bug detection results are difficult to interpret.
- **Minority opinion on originality:** One reviewer noted that while the combination of binary lifting and test generation is novel, the individual components (LLM-based binary lifting, LLM-based test generation, mutation testing) have been previously explored, limiting the overall technical contribution of the paper.
