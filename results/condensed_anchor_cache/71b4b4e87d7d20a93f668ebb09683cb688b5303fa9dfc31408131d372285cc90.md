## Merged Review

### Summary
The paper introduces ActionFiller, a framework for OS agent task automation that uses fill-in-the-blank prompting to handle long-horizon tasks with multiple application interactions. It includes a Foresight Optimization Agent (FOA) and Action Template Agent (ATA) to generate task flows and action sequences, leveraging past experiences. The CohesiveFlow method optimizes unexecutable action prompts based on environmental state. Experiments on the newly introduced EnduroSeq benchmark and WinBench show improvements over GPT-4o and GPT-o1 baselines. Reviewers find the topic interesting but raise substantial concerns about novelty, experimental rigor, clarity, and the claimed efficiency gains.

### Strengths
- The paper addresses an interesting and practical problem: minimizing reliance on frequent observations for foundation model agents in long-horizon OS tasks, thereby aiming to improve efficiency.
- The ActionFiller framework demonstrates practical potential for complex task automation by leveraging LLMs to interpret and convert natural language commands into feasible actions.
- The introduction of the EnduroSeq benchmark, designed to evaluate OS agent performance on long-horizon instructions, is a valuable contribution that could benefit future research if further developed.
- The method keeps planning flexible by representing planned action sequences in three formats: executable actions, non-executable actions requiring parameters, and pure text descriptions, only converting them to actions at execution time.
- The paper presents interesting results of an OS agent solving long-horizon tasks.
- The straightforward construction of the LLM-based agent may appeal to newcomers to the field.

### Weaknesses
- **Novelty and contributions are not clearly distinguished from recent work.** The fill-in-the-blank strategy and task decomposition are fairly standard in LLM applications. No comparison is made with relevant prior methods such as MobileGPT, AutoDroid, Mobile-Agent, Voyager, AutoGuide, and RAP, which also use LLM-based planning, skill libraries, or retrieval-augmented planning for agent tasks. The CohesiveFlow method appears to be a straightforward application of masked language modeling without significant innovation. Many components seem to be combinations of existing techniques.
- **Experimental comparisons are limited and potentially unfair.** The only baselines are GPT-4o and GPT-o1; other state-of-the-art OS agent frameworks (e.g., UFO, the cited methods above) are excluded. There is no mention of which LLM is used within ActionFiller itself—if GPT-4 or another model is used for FOA/ATA/CohesiveFlow, results should be reported separately (e.g., ActionFiller(4o) and ActionFiller(o1)). Moreover, Structural Memory (SM) appears to be accessible to ActionFiller but not to the baseline agents, creating an unfair advantage. The paper does not compare against agents that utilize similar resources as skill libraries (Voyager), state-aware guidelines (AutoGuide), or retrieval-augmented planning (RAP), which would test ActionFiller’s merits more rigorously.
- **Insufficient evaluation and missing metrics.** The EnduroSeq benchmark has only 30 samples, which is too small for meaningful conclusions, and no statistical significance tests are provided. The claimed reduction in number of environment observations is never directly measured or compared against baselines. No experiments on more common benchmarks like VisualWebArena are included. The evaluation appears insufficient to validate the effectiveness of the proposed method.
- **Efficiency claims are unsupported and contradictory.** ActionFiller requires multiple LLM calls (for FOA, ATA, and CohesiveFlow), which inevitably increases total computation time and token usage. The paper focuses only on reducing environment observations while ignoring this computational overhead, effectively trading one form of inefficiency for another without clear justification. No runtime performance metrics, latency measurements, or data on the number of LLM calls per task are provided. Direct efficiency comparisons (e.g., total input tokens or execution time) with baselines are missing.
- **Lack of ablation studies.** There is no analysis isolating the contribution of individual components (e.g., memory without FOA, memory size impact, the role of the three action prompt types). The effect of LLM size on ActionFiller’s performance is not investigated; experiments with smaller models are needed.
- **Insufficient explanation of key components.** Many elements are unclear or undefined:
  - In Figure 2, the roles of Planner, Observer, Actor, and Reflector are not explained; the Reflector appears without prior introduction; a loop between action generation and observation is missing.
  - The generation of subtask prompts and action prompts is inadequately described: the meaning of “reference steps” and “operational steps” is not defined; the inputs to the planner and how it produces its two outputs are unclear; the mechanism by which ATA distinguishes and generates the three action classes is not specified.
  - Memory usage is poorly explained. It is unclear whether predictions use the entire memory \( M \) (with \( L(q, M, o_i) \)) or retrieve specific examples; the retrieval mechanism (similarity measure, number of examples, memory construction) and the role of Structural Memory (\( SM \)) are not detailed.
  - CohesiveFlow’s parameter update mechanism is not clearly described.
  - Both the input and output of the LLM are referred to as “prompts,” making the operation of ActionFiller confusing.
- **Adaptability and scalability concerns.** The method’s reliance on template-based prompting may limit its adaptability to tasks deviating significantly from predefined structures. The assumption that executable action sequences are directly grounded to the environment is unrealistic—unexpected environmental changes could fool the algorithm. Scalability may suffer as memory of past experiences grows and slows retrieval.
- **Dataset and task definition issues.** The paper should clarify what makes EnduroSeq more challenging than WinBench and address concerns about its limited size. The description of “open tasks” and “dynamic tasks” appears identical; the distinction should be explained. The method for assessing whether an action successfully achieves its intended goal (L298-299) is not described.
- **Presentation and completeness.** Figure 3 largely overlaps with Figure 4; a unified diagram showing all components (FOA, ATA, Memory, CohesiveFlow agent) with detailed information would improve comprehension. Most figures are abstract and lack specific details (e.g., Figure 1 should clarify the difference between left and right sides and their impact on the OS environment). There is a typo in lines 41-48 (missing space or parentheses for citations). Citation style needs correction. The conclusion does not address limitations or suggest future work. The appendix should include actual prompts used and ActionFiller’s outputs to aid understanding.
