## Merged Review

### Summary
The paper introduces FALCON, a framework for automated code generation that combines long-term memory (retrieval of similar examples from a memory bank) and short-term memory (immediate compiler/AI feedback) within a meta-reinforcement learning (MAML) formulation. Four rewards are defined—correctness, code style, complexity, and error-type statistics—and jointly optimized via policy gradient and supervised fine-tuning losses. Experiments on APPS, HumanEval, MBPP, CODAL-Bench, SciCode, and AgentBench using CodeT5 770M and DeepSeek Coder 6.7B Instruct report pass@1/pass@5 results, claiming state-of-the-art performance over prior RL methods.

### Strengths
- **Novel combination of RAG and MAML for code generation.** The general idea of applying meta-RL to the LLM domain is interesting and timely (R2). The framework integrates long-term memory (via retrieval) and short-term memory (immediate feedback) with meta-RL (R1, R3).
- **Incorporation of four non-differentiable rewards beyond functional correctness** (correctness, code style, complexity, error-type statistics) into the RL pipeline, aiming to generate code that also meets real-world programming standards (R1, R3).
- **Empirical evaluation is comprehensive in scope** (six benchmarks: APPS, HumanEval, MBPP, CODAL-Bench, SciCode, AgentBench) with two model sizes (R1). The inclusion of CODAL-Bench for non-functional metrics and a complete ablation of each reward term is appreciated (R1). FALCON demonstrates state-of-the-art performance relative to previous RL-based methods (R3).

### Weaknesses
- **Novelty and methodological contribution.** The novelty lies mainly in the *combination* of RAG-like long-term memory and MAML, but each component is directly applied without significant algorithmic modification. The long-term memory is retrieval augmented generation, yet no literature review of RAG for code generation (e.g., classic code generation/summarization, SWE-Bench) is provided, nor is the differentiation clarified (R1). The MRLF algorithm (Sec 4.2, Algorithm 1) appears to be a direct application of MAML (Finn et al. 2017, Algorithm 3 for RL) to code generation with limited difference/novelty; the paper does not state whether it is a direct application or contains additional algorithmic changes (R1). Reviewers disagree: one finds the idea interesting (R2), but another calls novelty modest (R1).
- **Clarity, motivation, and presentation are severely lacking.** The paper is very hard to read and understand; a major rewrite is needed (R2, R3). Motivation is unclear: Section 3 defines the optimization as finding the most likely completion (standard LLM objective), but the goal should be code correctness (R2); the role of long- vs. short-term memory is touted but revealed piecemeal, and it is unclear why MAML helps when the use-case is not adaptation to new tasks (R2). The problem setting and methodology section lack a solid foundation (R3). Four assumptions for FALCON’s effectiveness (lines 125–130) are presented without justification; they may not hold (e.g., task-order independence contradicts recency effects, feedback signals overlap, rewards are too coarse-grained for parameter optimization) (R3). Presentation issues include: no pointer to Table 3; Eq(2) and Eq(8) are identical; symbols undefined or collide (𝒟, 𝒳, F_i, T_i, ω vs. ω̂, φ); reward definition R(W,F) does not depend on F on the RHS; optimization objective differs between sections (R1, R3). Grammar/style issues: past tense in abstract, unused abbreviation (CLM) (R2). The roles of short- and long-term memory buffers remain unclear—Algorithm 1 suggests they contain few-shot samples, but experimental results imply inference-time use, and it is never explained how historical tasks provide long-term memory feedback (R2, R3).
- **Experimental evaluation is insufficient and poorly described.** The data used for training in each experiment is not stated (R2). Baselines (CodeRL, PPOCoder) are outdated—their numbers are very low compared to current models; need comparisons with up-to-date models (R2). Missing critical baselines: an SFT baseline when using a custom dataset, and a standard RL (without MAML) baseline to justify the MAML component (R2). All hyperparameters are omitted (reward coefficients, optimization HPs like batch sizes), severely hurting reproducibility and making results hard to judge (R1, R2). While one reviewer found the experiments comprehensive and appreciates the CODAL-Bench ablation (R1), the issues raised by others regarding incomplete baselines and lack of clarity are major weaknesses.
- **Missing details and clarification requests that overlap with criticism/insufficient analysis.** The following points were raised as questions but indicate missing explanations, experiments, or ablation: (i) How is the long-term memory collected? On-the-fly during evaluation or a separate dry-run? (R1). (ii) What is the definition of “task” in Algorithm 1: a problem instance or a benchmark? (R1). (iii) Is the reward answer-level (reward placed at last token, zero elsewhere) or token-level? (R1). (iv) Is there a weight to balance the SFT and PPO losses? (R1). (v) What is the embedding function φ (L282)? (R1). (vi) Interpreting ablation in Table 6: do rows without short-term memory correspond to no training, while the last two rows with training? (R1). (vii) How are the four assumptions satisfied, especially task-order independence and handling of overlapping feedback? Provide theoretical or empirical justification (R3). (viii) How are the feedback rewards designed to be sufficiently fine-grained for effective parameter optimization? (R3). (ix) Reward coefficient details in Eq(8) are missing (R1, R3).
