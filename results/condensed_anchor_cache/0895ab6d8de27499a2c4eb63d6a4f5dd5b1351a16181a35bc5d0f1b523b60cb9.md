## Merged Review

### Summary
The paper formalizes Model Equality Testing as a two-sample test to determine whether a black-box API serves a distribution identical to a reference model, using Maximum Mean Discrepancy (MMD) with a Hamming-distance-based string kernel. Experiments on LLaMA-family models show a median 77.4% power against various distortions with an average of 10 samples per prompt, and an audit of 31 commercial endpoints finds 11 serve different distributions. Reviewer opinions range from 6 to 8; most find the problem timely and the method well-presented, but concerns remain about significance, evaluation diversity, kernel choices, generalizability beyond LLaMA, computational cost, and specific failure cases.

### Strengths
- The paper is well-written, well-organized, and easy to follow (Reviewer 1, 2, 3, 4).
- The problem is timely and valuable: verifying API model integrity is important for practitioners who depend on black-box APIs (Reviewer 2, 3, 4).
- The application of two-sample testing with MMD to distributions from language models is novel and methodologically sound (Reviewer 1, 2, 4).
- The proposed method is simple, intuitive, and empirically effective with a reasonably small number of samples (Reviewer 2, 4).
- Public release of generated samples is a valuable resource for the community and future API change tracking (Reviewer 3).
- The framework provides a novel way to analyze APIs on non-classification tasks (Reviewer 3).
- One reviewer (Reviewer 4, score 8) is particularly positive, expecting high impact; the method is characterized as "simple but effective" and the experiments as "sound enough to support the claims."

### Weaknesses
- Significance of the problem: one reviewer doubts the need for a technical test, suggesting the issue might be solvable via policy and provider disclosure (Reviewer 1). (Contrast: other reviewers consider the problem very timely.)
- Reference distribution acquisition requires the user to set up the reference LLM, which may be inconvenient or infeasible in many practical scenarios (Reviewer 3).
- Evaluation diversity is limited:
  - Tests are primarily on Wikipedia-based data (English, German, Spanish, French, Russian); more diverse tasks such as coding are recommended to broaden applicability (Reviewer 1).
  - Wikipedia content is highly factual and may underestimate output diversity; potential data contamination is a concern, partially addressed by HumanEval but more analysis is needed (Reviewer 3).
- The claim of high power with an average of 10 samples per prompt and 20–25 prompts lacks sufficient analysis regarding:
  - Effect of temperature (e.g., zero temperature) (Reviewer 1).
  - Effect of prompt topic homogeneity vs. diversity (Reviewer 1).
  - Performance with even smaller sample sizes, which is likely in real-world scenarios (Reviewer 2).
  - Whether the method detects no changes when samples come from the same model, and how detection power varies with different sampling temperatures (Reviewer 1).
- Kernel choices and understanding:
  - Limited baselines (only string kernels); no comparison with Levenshtein distance or other edit-distance-based kernels (Reviewer 4). Hamming distance performing best is surprising and lacks discussion or intuition (Reviewer 4).
  - The Hamming kernel’s bias-variance tradeoff with respect to window length L is not discussed; as L → ∞ it approaches a one-hot kernel, as L → 0 it biases toward first tokens; implications for creative tasks are unclear (Reviewer 1).
  - L is set to 50 and studied only up to 50; reviewer recommends studying at least up to 10× that (e.g., 500 tokens) because 50 tokens is low for many LLM applications (Reviewer 1).
  - Effect of different tokenizer vocabularies on L is not studied (Reviewer 1).
  - No semantic equivalence kernel is considered; the current kernel checks token equivalence only (Reviewer 1).
  - Effectiveness for open-ended/creative generation tasks is questionable; high-variance outputs may cause significance tests to miss quality differences (Reviewer 3).
- Low detection power for certain distortions: in Llama3.1 8B vs. int8 quantization (0.07) and vs. watermarking (0.32) (Figure 3 lower left) – these are very low, yet detecting such changes is a premise of the method (Reviewer 1).
- Generalizability beyond LLaMA is not demonstrated; further validation on models with different architectures, training methodologies, or training distributions is needed (Reviewer 2). The paper only tests LLaMA-family models; inference algorithms may also differ beyond weights (Reviewer 4).
- No discussion of two common customizations: system prompt customization and generation-time safety interventions; the method’s behavior under these is unclear (Reviewer 3).
- Computational cost of MMD may be high in large-scale scenarios; more detailed complexity analysis and discussion of potential optimizations (e.g., dimensionality reduction, sampling) are requested (Reviewer 2).
- Technical issues and missing details:
  - Line 081: extra article “a” before “an API” (Reviewer 3).
  - Equation (4): should z and z' be different? (Reviewer 4).
  - Line 162: what does “accurate completion” mean? (Reviewer 4).
  - Line 210: is the only difference in weights, or can generation algorithms also differ? (Reviewer 4).
  - Figure 2: a sentence is not readable (“Curves first median power ...”) (Reviewer 4).
  - Line 312: 1.1M Unicode characters – how computed? (Unicode 16.0 has 155,063 unique characters) (Reviewer 4).
  - Line 326: “significantly different training data” – is “significantly” used in a statistical sense? (Reviewer 4).
  - Line 337: missing citations for semantic caching and quantization (Reviewer 4).
  - Figure 4 (right): colors are not defined (Reviewer 4).
  - L (the number of tokens for the Hamming kernel) should be explicitly defined (Reviewer 1, nit).
  - How kernels are computed when the model generates a sentence shorter than the maximal length (Reviewer 4).
- Figure 4 compares absolute task accuracy difference with MMD; using non-absolute difference would be more informative because interventions are not always harmful to accuracy (Reviewer 3, question).
