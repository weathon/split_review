## Merged Review

### Summary
DIESEL is a lightweight inference guidance technique that reranks tokens during decoding based on their cosine similarity to predefined negative concepts, using the miniLM sentence embedding model. It operates without retraining, adds minimal overhead (1.4–1.6× slower), and can be integrated with existing safety measures. Evaluated on Llama 3, Mistral, and Vicuna using AdvBench and TruthfulQA, compared against RAIN. Automated safety evaluation uses GPT-4o as judge.

### Strengths
- Addresses an important problem; paper is clearly structured. (R1, R4)
- The approach of using semantic embeddings for real-time safety filtering is **novel** – one reviewer states it is the first paper to use semantic similarity to judge safety of LLM outputs. (R2)
- *Contrast:* Another reviewer notes that similarity-based decoding control is a **very common idea**. (R1)
- Use of a set of negative concepts is innovative and user‑friendly; allows users to plug in their own bad cases. (R2)
- Lightweight and efficient: only 1.4–1.6× slower than standard decoding; easily combined with other safety methods. (R2)
- Comprehensive evaluation across three backbones (Llama‑3‑8B, Mistral‑7B, Vicuna‑7B). (R2, R4)
- Strong empirical validation includes automated metrics, human evaluation, clear ablation studies, runtime analysis, and testing against jailbreak attacks. (R2)
- Effective on AdvBench across all three backbones. (R3)

### Weaknesses
- **Limited generalizability to long‑form output** – no quantitative analysis of performance degradation with output length. (R2)
- **Core assumption unvalidated:** There is no rigorous validation that semantic similarity reliably identifies undesired content. Semantic similarity does not always indicate toxicity (e.g., information leakage, implicit bias). Controlled experiments are needed to demonstrate the relationship between semantic similarity and different types of unsafe content. (R2)
- **Coverage of negative concepts R is unclear and not scalable.** It is infeasible to predefine all possible negative responses. Reviewers ask for concrete examples (words or sentences) and where they are stored. (R2, R3, R4)
- **Too many hyperparameters** (e.g., b=20 tokens, α=0.98); sensitivity analysis is missing. (R2)
- **Limited comparisons:**
  - Only one baseline (RAIN) compared, and its description is insufficient. (R1)
  - Missing comparison to other state‑of‑the‑art methods like Llama Guard (R2) and representation‑steering approaches (e.g., https://openreview.net/pdf?id=dJTChKgv3a). (R4)
  - No evaluation of how the technique performs at different model sizes. (R4)
- **Insufficient evaluation scope:**
  - Only one adversarial dataset (AdvBench, 500 prompts) – insufficient to demonstrate robustness. Larger and more diverse adversarial datasets are needed. (R1, R3, R4)
  - General LLM performance measured only on TruthfulQA; broader benchmarks like MMLU are necessary to confirm no degradation. (R3)
- **Evaluation methodology concerns:**
  - Using GPT‑4o as an automated judge may inherit its limitations; human judges or external metrics should be employed. (R3)
  - One reviewer notes that no insight is provided into failure cases. (R4)
- **Presentation issues:** Algorithm block variables are undefined (e.g., r_e) and do not match the main‑text equations. (R4)
- One reviewer notes that the technique could improve instruction‑following (e.g., on IFEval) by encoding instructions as concepts – this extension is not explored. (R4)
