## Merged Review

### Summary

Four reviewers gave scores of 3, 5, 6, and 1 (mean 3.75), reflecting strong disagreement. The positive reviewers (R2, R3) praise the relevance of studying diversity and the empirical insights from the code-based methodology. The negative reviewers (R1, R4) raise serious concerns about limited scope, uncontrolled comparisons, outdated metrics, and lack of generalizability. R3 (score 6) finds the insights fresh and the metric valuable, while R4 (score 1) considers the contributions very limited and the setups flawed. The main points of contention are the choice of 21 problems, the use of different base models for SFT vs PT, the appropriateness of CodeBERTScore, and the lack of correctness evaluation. R2 notes the findings are not conclusive and the contribution is more suitable for a shorter piece.

### Strengths

1. Figure 1’s temperature plot suggests that T=0.9 or T=1.0 may yield higher semantic diversity than CodeT’s default T=0.8, a finding deserving further elaboration. (R1)
2. The research addresses a relevant, underexplored question: there are few evaluation frameworks for LLM output diversity. (R2)
3. The study includes several empirical demonstrations providing tangible evidence. (R2)
4. Semantic diversity and other diversity metrics are crucial for open‑ended tasks (creativity, randomness). (R3)
5. The metric devised by the authors is useful for measuring model output diversities. (R3)
6. Insights from the experiment results offer fresh arguments for open‑ended code generation diversity. (R3)
7. The overall structure is clear and easy to follow. (R4)
8. The authors conduct experiments on several Llama models. (R4)
9. Diversity is evaluated from multiple dimensions (semantic, lexical, syntactic, neural). (R4)

### Weaknesses

1. The experimental results are limited to 21 competitive programming problems, raising concerns about generalizability. The problem descriptions are vague, making functional correctness hard to evaluate; they require manual abstraction and lack constraints on expected outputs (e.g., random word sequences are not valid answers). (R1, R4)
2. The comparison between CodeLLama (based on Llama2) and Llama3(.1) for SFT vs PT uses distinct model versions, so observed diversity differences may be confounded. A controlled experiment using Llama3(.1)-based SFT would improve reliability. (R1)
3. Instruction‑tuned LLM diversity could be influenced by the training set’s diversity. A controlled comparison of LLMs without instruction tuning and LLMs with tuning that vary training set or trajectory diversity is missing. (R1)
4. The finding that execution‑based diversity differs from lexical/syntactic diversity is unsurprising. Prior work (APPS) has documented similar discrepancies. Section 4.2 replicates results from counterfactual code augmentation research. The statement (lines 327‑338) that program semantics may be harder to model than natural language is problematic because BERTScore itself is not robust; there is no reason CodeBERTScore should accurately reflect program correctness. (R1, R4)
5. CodeBERTScore is outdated. More current options include UniXCoder, CodeExecutor, or LLM‑based evaluators like ICE‑Score (which shows CodeBERTScore is weak compared to LLM‑as‑Judge) or CHASE‑SQL’s fine‑tuned code‑pair verifier. (R1, R4)
6. Representative correctness benchmarks (e.g., HumanEval, BigCodeBench) are not included. (R4)
7. The open models evaluated are not diverse; other Code LLMs such as StarCoder2 and CodeQwen should be included. (R4)
8. Training setups are not documented, making results questionable. (R4)
9. Experiments are Python‑only; evaluations on more programming languages are needed. (R4)
10. There is no related work on Code LLMs, code generation, or coding benchmarks. (R4)
11. The dataset construction lacks detailed explanation (e.g., the 21 handcrafted abstractions from CodeNet and test cases from AlphacaCode are inadequately described in the appendix). (R2)
12. The overall presentation needs improvement: a stronger Background/Related Work section in the main paper, a flowchart figure for dataset creation, and proofreading for typos (e.g., ‘the the’ line 389, ‘We’ line 296). (R2)
13. The study’s findings regarding the research question “Does instruction tuning reduce diversity?” are not conclusive. (R2)
14. The contribution appears insufficient for a full paper; it could serve as the basis of a shorter piece (e.g., a research agenda). (R2)
15. Why is this work presented as a case study? (R2) 
16. The meaningfulness of studying diversity for LLM open‑ended generation is not fully discussed. It could contribute to more effective solution searching when scaling inference computation (like o1), but that connection is not made. (R3)
17. Code generation is a special case with a “correct” output. Why does semantic diversity matter if only one generated program is correct? Do we only care about covering the correct output? (R3)
18. Whether conclusions generalise to general‑domain open‑ended generation is questionable; the answer may be no. (R3)
19. What is the benefit of higher response diversity beyond applications like creative writing? (R3)
20. The motivation for using code generation over text generation is insufficiently explained. (R4)
21. What does column “N” in the tables represent? (R4)
