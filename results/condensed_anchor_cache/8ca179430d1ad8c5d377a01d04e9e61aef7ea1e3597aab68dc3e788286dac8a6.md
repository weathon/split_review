## Merged Review

### Summary

The paper introduces a test-driven development (TDD) benchmark for LLMs where test cases serve as both instruction and verification. The benchmark consists of 1000 JavaScript/React tasks designed to be solved with short code snippets. 18 proprietary and open-source models (mostly tested with 10 runs each) are evaluated. The authors find that reasoning models like OpenAI’s o1 achieve state-of-the-art performance. They analyze failure types (e.g., missing imports, deprecated libraries) and show that longer prompts with more test cases increase failure rates. They also propose a multi-feature version merging two tasks.

### Strengths

- The topic is timely and the benchmark is novel. (Reviewer 1, 2, 4)  
- The first fully-blown benchmark using test cases as instructions, which prevents the gap between specification and test cases (cf. Programming Puzzles focused on algorithmic puzzles). (Reviewer 2)  
- Analyses are of good quality: many models tested, failure cases are analyzed with concrete examples, and categories of errors are identified. (Reviewer 2)  
- The paper is straightforward and easy to follow. (Reviewer 2)  
- TDD is relevant to real-world software development and could be useful for studying developer productivity tools. (Reviewer 2)  
- Benchmark generation is costly, so the current dataset is useful. (Reviewer 1)  
- The benchmark has a good distribution of task difficulties. (Reviewer 1)  

### Weaknesses

- **Focus on React is poorly motivated.** The authors claim React is popular and produces brief code, but Python is more popular and can also produce short solutions. This choice needs better justification. (Reviewer 1)  
- **Learning from the paper is limited.** Most findings are obvious: LLMs make mistakes from missing libraries, ignoring instructions, and training on legacy code. The conclusions should be clarified and focused. (Reviewer 1)  
- **Lack of clarification on how increasing test cases hurts LLM performance.** Does the same happen to human coders? Adding two issues is not the same as lengthening the prompt with four test cases; the framing needs clarification. (Reviewer 1)  
- **Benchmark may be too easily saturated.** A public release should use the multi-feature version and validate with human software engineers to ensure tests are satisfiable. (Reviewer 2)  
- **No discussion of differences from SWE-bench-verified.** More discussion is needed (e.g., following Section 6.4). (Reviewer 2)  
- **Data collection is left in the dark.** Where do the 1000 tasks come from? Are they scraped from GitHub or learning websites? How close are they to pretraining data? Could contamination explain high scores? (Reviewer 2, 3, 4)  
- **Lack of comprehensive statistical analysis of the dataset.** No details on data distribution, balance, or biases. (Reviewer 4)  
- **Limited test cases can be “hacked” by LMs.** Models often generate incorrect code that still passes tests. (Reviewer 3)  
- **Poor paper writing and formatting.** References and tables are in incorrect format. Many redundant sentences (e.g., line 161). Duplicated content: both Section 2.2 and Section 4.1 are named “Task Formulation”. Weird structure: Section 4 is merely a case study of o1. (Reviewer 3)  
- **Introduction is unclear.** Motivation needs a concrete example of the TDD task. Contributions should be summarized concisely in the introduction. (Reviewer 4)  
- **Presentation of tables and figures needs improvement.** Use color fonts or symbols to highlight critical code in Tables 1, 2, 3. Clarify what the horizontal axis represents in Figure 1. (Reviewer 4)  
- **Evaluation section is verbose and lacks clarity.** Why was pass@k chosen? Is one metric sufficient? Provide evaluation setup details and compare with existing benchmarks. (Reviewer 4)  
- **“Incomplete manual examination” is vague.** How many solutions were manually inspected, and is the sample sufficient to support conclusions? (Reviewer 4)  
- **No discussion of using agents with execution feedback.** This could easily correct some error categories (version mismatch, uninstalled modules). (Reviewer 2)  
- **Need more dataset visualizations and statistics.** Additional examples in the appendix would be useful. (Reviewer 2)  
- **Performance stability between pass@1 and pass@10 is interesting but unexplained.** Why do LLMs not improve much with more attempts? (Reviewer 1)  

**Note (minority view):** Reviewer 3 scores this paper very low (1/10), citing poor writing, lack of benchmark details, and potential for overfitting to tests. Other reviewers find contributions moderate but note significant missing information.
