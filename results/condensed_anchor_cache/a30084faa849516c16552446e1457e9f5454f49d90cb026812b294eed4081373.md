## Merged Review

### Summary

This paper presents MMQA, a multi-table, multi-hop question-answering benchmark. The dataset is constructed by sampling 45 SQL templates from the Spider dataset, converting them to natural language questions using GPT-4-Turbo, and then having human experts verify the resulting questions and answers. MMQA includes tasks for Multi-Table Retrieval, Text-to-SQL, Multi-Table QA, Primary Key Selection, and Foreign Key Selection, with splits for questions requiring 2 or 3 tables. The authors also propose a new multi-table retrieval method (MTR) that uses question decomposition and a combination of question-table and table-table relevance scores; MTR achieves SOTA retrieval performance on MMQA. Experiments across several open and proprietary LLMs (GPT-3.5, GPT-4, Gemini-pro, O1, TableLLaMA-7B, Mistral-7B) show a large gap between LLMs and human performance (humans achieve 80–90% while O1 achieves ~50%), with performance degrading rapidly as table length increases. The paper is well motivated by the real-world need for multi-table reasoning, and the benchmark is considered a valuable resource for future research.

### Strengths

- **Novel and important task:** Multi-table QA is a realistic, underexplored setting that closes a gap in existing single-table benchmarks. Reviewers agree this is a well-motivated and high-impact contribution.
- **Comprehensive benchmark design:** MMQA includes multiple subtasks (retrieval, text-to-SQL, QA, key selection) that cover different reasoning steps, as well as different difficulty levels (2-table vs. 3-table) and table lengths. This enables fine-grained evaluation.
- **High dataset quality:** The dataset contains 3,312 expert-verified tables, an average of 7.61 reasoning steps, and diverse question categories including “list/count all answers,” which are often overlooked. Human performance is high (80–90%), confirming the quality of the annotations.
- **Strong baseline:** MTR significantly outperforms existing LLMs on the multi-table retrieval subtask (around 10–15% improvement), providing a useful reference for future work.
- **Thorough experimental analysis:** A good mixture of open and closed LLMs is evaluated, and ablation studies examine the effect of table length. The paper identifies a clear performance gap between LLMs and humans, with O1 being the best but still far behind.
- **Well written and easy to follow:** The logic flow is clear, and the supplementary material (dataset samples) is helpful.

### Weaknesses

- **Synthetic dataset and limited diversity:** MMQA is constructed from only 45 SQL templates from the Spider dataset, then translated to NL by GPT-4-Turbo. This limits the diversity of query types (e.g., complex aggregations, nested subqueries, join patterns) and may not reflect the distribution of real-world user questions. Reviewer 2 notes that questions often use column names and SQL keywords (e.g., “distinct,” “creation years”) that a real user would not know, making the task less realistic than claimed. Reviewer 3 raises concerns about overfitting to the synthetic style and potential biases, information loss, or noise introduced by GPT-4-Turbo as a translator. These risks are not discussed in the paper, and no analysis of annotation disagreement patterns (e.g., whether disagreements stem from ambiguity, translation errors, or annotator mistakes) is provided.

- **Evaluation metrics are not fully appropriate:**
    - Using ROUGE and BLEU for the Text-to-SQL task is inappropriate. Standard metrics like exact match (as used in the original Spider paper) or, better yet, execution accuracy (comparing execution results of predicted and gold SQL) should be used. More advanced metrics (e.g., from [2],[3]) could also be considered.
    - The partial match metric for QA relies on GPT-4, but no validation of its quality (e.g., correlation with human partial match judgments) is provided (noted by Reviewer 1). This makes the QA results less reliable.
    - Exact match and partial match for QA may underestimate model performance, especially for list and count questions (order sensitivity; a miss-by-one should get partial credit). Reviewer 2 suggests using an LLM judge for comparison or adopting a generalized execution accuracy.
    - No unified subtask that allows systems to answer either via SQL or direct reading and have the final answer evaluated against the gold answer is included, which would enable fair comparison between text-to-SQL and table QA approaches.

- **Baseline models are not SOTA for table QA:** The evaluated models are mostly general-purpose LLMs plus the small TableLLaMA-7B. Reviewer 3 recommends including more recent, specialized table QA agentic systems (e.g., from the Spider leaderboard) that incorporate iterative query refinement, dynamic schema linking, and sophisticated reasoning modules. Without such comparisons, the true difficulty of MMQA and the significance of the observed gaps are hard to assess.

- **Missing details in method and experiments:**
    - Algorithm 1 does not specify that a single-table retriever is used, only that GPT-4-Turbo is used for question decomposition. (Reviewer 2)
    - It is unclear what unit “question length” in Table 1 uses (characters?). (Reviewer 2)
    - Line 199: How is the number of reasoning steps measured? (Reviewer 2)
    - For the Table QA, Text-to-SQL, Primary Key Selection, and Foreign Key Selection tasks, is the input the gold (ground-truth) tables? This should be stated. (Reviewer 2)
    - In Table 4, what is the difference between, e.g., “TableLlama-7b” and “MTR (TableLlama-7b)”? Is it just the question decomposition step or does training data differ? (Reviewer 2)
- **Bias, information loss, and noise from GPT-4-Turbo:** Reviewer 3 notes the risk that the NL translations may overrepresent certain wording patterns, lose SQL semantics, or introduce hallucinations. The paper should discuss these caveats, possibly in an appendix, and explain how they were mitigated.
