## Merged Review

### Summary
The paper proposes MAGE, a framework that uses a domain-specific language (DSL) and reinforcement learning to guide LLMs (GPT-4o) in generating task-to-processor and data-to-memory mappers for parallel programs. The DSL provides a high-level abstraction over C++/Legion APIs. An RL-like agentic loop iteratively generates, tests, and corrects mapping code based on performance and syntax/execution errors. Evaluated on three benchmarks (circuit simulation, stencil computation, Pennant) and a matrix multiplication study, the generated mappers outperform expert-written mappers by up to 34% and reduce development time from days to minutes.

### Strengths
- The DSL simplifies mapper generation by constraining LLM outputs to a structured, syntax-restricted language, which reduces hallucination and improves the rate of valid code generation (Reviewers 1, 2, 3).
- The RL-based agentic workflow automates iterative tuning, achieving expert-level performance with much less human effort (Reviewers 1, 2).
- Experimental results demonstrate concrete speedups (up to 34% on benchmarks, up to 31% throughput improvement on parallel matrix multiplication) and drastically reduced development time (from days to minutes) (Reviewers 1, 4).
- Ablation studies (Figure 7) qualitatively confirm that the DSL helps produce functional code and that agentic feedback loops improve performance (Reviewer 2).
- The paper is generally easy to follow (Reviewer 4).

### Weaknesses
- **Limited experimental scope** (Reviewers 1, 3, 4): Only three applications (circuit simulation, stencil computation, Pennant) are used; well-established GPU benchmark suites such as Parboil or Rodinia are absent. The benchmarks do not represent the complexity of real-world distributed applications like deep learning model training, and there is no discussion of scalability to larger systems with intricate communication patterns (Reviewer 3).
- **Lack of novelty** (Reviewer 3 is notably more critical): The work is described as “incorporating an LLM into an existing reinforcement learning framework” without introducing new techniques. The contribution is incremental rather than fundamental.
- **Insufficient justification of DSL design** (Reviewers 1, 3, 4): The paper does not explain why the specific keywords and grammar (Figure 3(a)) are well-suited for task mapping or LLM generation. Alternative designs (e.g., C++ templates with fill-in-the-blank prompts, or exposing tuning parameters directly) are not compared. The assertion that DSL improves LLM generation is not fully proven – LLMs may perform equally well with C++ constraints or few-shot prompting (Reviewer 3). Reviewer 1 asks whether the high-level abstraction loses low-level C++ details essential for performance.
- **Missing analysis of failure cases and strategy choices** (Reviewer 1): Success cases are emphasized, but no analysis is given for cases where generated mappers failed. The impact of different mapping decisions (e.g., task selection, memory allocation) on performance under various scenarios is not explored in Section 4.2.
- **Insufficient evaluation details** (Reviewers 1, 3, 4): The evaluation platform (GPU cluster, number of nodes, GPU driver, CPU details) is not fully specified. How the benchmarks are implemented (CUDA? which kernels?) is unclear. There is no comparison to classical tuning frameworks like OpenTuner or CompilerGym, despite the optimization space consisting of only a few parameters (processor type, data placement, data layout) (Reviewer 4). Why not simply expose these as tunable parameters?
- **No explicit correctness guarantees for LLM-generated mappers** (Reviewer 3): The paper states “Mappers do not change correctness” but some mapping strategies (e.g., tensor parallelism) require inter-device communication (e.g., all_reduce) for correctness. The paper assumes the runtime handles all communication, yet no verification or formal guarantees are provided.
- **Missing baselines and ablations** (Reviewer 2): The agentic flow is compared only to baselines that already provide performance feedback; a more fundamental baseline (single/few-shot prompting without iterative feedback) is missing. Additionally, the term “RL” is used in a non-standard way (agentic flow, not gradient-descent-based RL) and should be clarified early (Reviewer 2).
- **Figure 7(c) interpretation and error explanation impact** (Reviewer 1): In Figure 7(c), “Perf+Err” and “Full Feedback” alternate in performance over 10 iterations – more iterations may be needed to confirm consistent superiority. The large impact of error explanations (vs. performance-only feedback) on throughput is not explained.
- **Generalizability concerns** (Reviewers 1, 3, 4): The DSL may be tied to the Legion runtime; effort to support other frameworks (e.g., TaskFlow) is unclear. Would the DSL need adjustments? How would the approach apply to distributed LLM training (e.g., comparison to Alpa)? Would hardware changes (e.g., A100 vs. P100) require rerunning the RL pipeline from scratch? (Reviewers 3, 2 ask similar.)
- **Comparison to prior RL-based task mappers** (Reviewer 3): Early work [C] (Mirhoseini et al., ICML 2017) on RL-based device placement is not discussed. Why does adding LLMs produce better results than direct RL optimization?
- **Correctness of generated programs** (Reviewer 3): Can the two errors shown in Table 1 for the DSL be avoided by simply improving the prompt? This questions the necessity of the full RL pipeline for correctness.
- **Missing clarification of scope** (Reviewer 2): The paper should state earlier that the mapping is at the task/processors level, not kernel level (people may misinterpret “matrix multiply” as CUDA kernels rather than distributed GEMM).
