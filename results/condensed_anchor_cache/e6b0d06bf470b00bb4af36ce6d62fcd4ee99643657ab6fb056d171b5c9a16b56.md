## Merged Review

### Summary

The paper proposes a variable-length AutoML framework using Tree of Thoughts (ToT) with LLM-driven code generation. The method avoids a fixed pipeline structure by dynamically determining the number and order of ML components, and uses GPT-4 to sequentially generate executable Python code. Experiments are conducted on ten datasets from OpenML and clinical tasks, comparing against Auto-Sklearn, TPOT, H2O, and fixed/variable-length versions of random search, Bayesian optimization, and LLM-based approaches. Reviewer 1 (score 8, confidence 4) finds the approach novel, well-executed, and significant. Reviewers 2 and 3 (both score 3, confidence 4 and 5 respectively) are highly critical of the experimental design, missing state-of-the-art comparisons, lack of reproducibility, unsubstantiated claims, and methodological flaws.

### Strengths

- **Novel formulation**: First method to integrate Tree of Thoughts for AutoML pipeline design, treating AutoML as a variable-length optimization problem (R1, R3). This enables flexible pipeline lengths based on task complexity (R2).
- **LLM-driven code generation**: Using prompted LLMs as AutoML agents with code generation provides a fully flexible search space, even if the prompt constrains operators (R1, R3).
- **Agentic AutoML with ToT**: The ToT approach fits the problem well, allowing structured decision-making to navigate the expanded search space efficiently (R2, R3).
- **Experimental breadth**: Tested on multiple OpenML and clinical datasets against established baselines (Auto-Sklearn, TPOT, H2O), including a maximum step length analysis (R1).
- **Clarity and presentation**: Figures and tables effectively illustrate key concepts and results; paper is well-organized and logically structured (R1).

### Weaknesses

- **Experimental design and reproducibility**:
  - No code provided to reproduce experiments (R2).
  - Manual intervention: the paper states "if after several iterations, the program still does not perform satisfactorily, we manually code the pipelines" (Line 234). This invalidates the evaluation, and the frequency of such manual coding is not reported (R1, R3). Reviewer 3 notes this should never occur in an automated system.
  - Repeated train-test splits are used instead of 10-fold cross-validation, which is more appropriate for tabular data (R3).
  - Only ten datasets are used; claims of state-of-the-art cannot be made on such a small set (R3).
  - Max step size hyperparameter appears to have been tuned on the test data (Table 5 shows drastic performance differences), and the best value likely used for the main results; this requires an independent study (R3).
- **Comparisons and state-of-the-art**:
  - Baselines are outdated: Auto-WEKA (2013), Auto-Sklearn (2019), H2O (2020). Missing recent SOTA methods like AutoGluon, MLJAR, LightAutoML, FLAML (R2, R3, referencing AutoML Benchmark and Kaggle AutoML Grand Prix). The paper incorrectly calls these "mainstream" and "state-of-the-art" (R3).
  - No differentiation from evolutionary search (e.g., TPOT), which also varies pipeline structure via predefined components. The main difference is code generation (R3).
  - No comparisons with methods from 2022–2024 (R2).
- **Methodological clarity**:
  - The Tree of Thoughts decision-making process is unclear; how thought paths are evaluated and pruned is not explained. Adding a flow diagram or pseudocode is needed (R1).
  - Code generation transparency lacking: details on code validation, error handling, and how often manual coding is required are missing (R1).
  - Sections 3.3 and 3.4 (HPO and variable-length optimization) lack critical details: what HPO method (grid/random?), search space, model library, validation strategy (split type), and optimization metric (the paper says classification/regression metrics but later uses ROC AUC; user should be able to specify target metric) (R3).
  - Prompt examples for in-context learning (Line 210) come from the same task; an ablation study is needed to assess their impact (R3).
  - Dataset descriptions used in prompts (Line 273) are created manually, risking evaluation bias; they may be uninformative or incorrect on OpenML (R3).
- **Statistical and table concerns**:
  - Table 1 bolding error: LLM-F performs best on Task 8, not ToT; all results need verification (R2).
  - Identical results for RS-V and BO-V on Tasks 1,2,10, and RS-F/BO-F on Task 8 (Table 1). The paper does not clarify whether parentheses show variance or standard deviation (R2).
  - "NAN (NAN)" in Tables 2 and 4 is unexplained. It likely indicates timeout (1 hour limit), but hardware and environment are not specified. Is it across all five trials or some? Why does fixed-length LLM-F produce NAN for Task 2 while variable-length ToT does not? (R2)
  - RS-V standard deviation of 0 on Task 4 (Table 2) is implausible given its other SDs (0.0167, 0.0268, 0.0098). More data needed (R2).
  - Auto-Sklearn scores 0.5 (0.0) on Task 1 (Table 4), far below other methods (>0.93) and with zero variance; unexplained (R2).
  - Internal inconsistency: LLM-F is called a fixed-length method (Line 306–308) but later referred to as variable-length (Line 342–344) (R2).
  - NAS-Bench-201 experiments show identical scores across all metrics, which is implausible, and memorizeability of best pipelines is a concern (R3).
- **Transparency and claims**:
  - Claim that the method "enhances efficiency" is unsupported; no runtime or resource analysis is provided (R1, R3). R1 suggests an efficiency analysis with comparisons.
  - Claim of "improves transparency" is not new; the shown optimization trace (Figures 2, 4) is equivalent to what any AutoML system can produce (R3).
  - Claim "outperforms traditional AutoML systems" is unjustified given experimental flaws (R3).
  - Motivation is unclear: the abstract claims fixed pipelines "limit adaptability to diverse task complexities," but fixed pipelines with HPO are by definition adaptable. No example shows failure of traditional AutoML due to inflexibility (R3).
- **Memorization and LLM-specific issues**:
  - No memorization tests were conducted; datasets may be memorized by GPT-4, especially OpenML datasets (citing Bordt et al., 2024). Many of the used datasets are known to be memorized (R3).
  - How were dataset descriptions created without biasing evaluation? (R3)
- **Minor issues**:
  - Typos: "feature trnasformation" (Line 48), "dataset dataset" (Line 195) (R2, R3).
  - Equation 1: \(x_i \in \{Op_1, Op_2, Op_3\}\) should use a union, not a set (R3).
  - Figure 5 has overlapping tick labels for accuracy, precision, recall, F1 (R1).
  - OpenML is referred to as a single dataset, not a collection platform (R1).
  - The paper lacks a proper related work section; the short appendix literature review is insufficient and should be in the main text (R3).
  - Many technical details on comparative methods are missing—methods are named only without description (R2).
