## Merged Review

### Summary
This paper presents SecCodePLT, a unified platform for evaluating security risks of Code GenAI across two tasks: insecure code generation (IC) and cyberattack helpfulness (CH). For IC, the authors manually created 153 seed tasks covering 27 CWEs (Python only) and used LLM-based mutators to scale to 1345 samples, each with ~5 functionality and security test cases. For CH, they built a simulated e-commerce network environment covering 7 MITRE ATT&CK categories (though “weaponisation” and “infiltration” are not MITRE categories). They evaluate CodeLlama-34B-Instruct, Llama-3.1-70B, Mixtral-8×22B, GPT-4o, and the code agent Cursor. Comparisons with CyberSecEval show SecCodePLT outperforms in security relevance and prompt faithfulness. Review scores range from 3 to 6; one reviewer (rating 3, high confidence 4) was notably more critical, raising fundamental concerns about language coverage, metric validity, lack of ablation, and limited CH generalizability.

### Strengths
- Tackles important and timely problems at the intersection of LLMs and cybersecurity (R1, R4).
- Benchmark includes both security and functionality unit tests per code example, enabling simultaneous evaluation that is lacking in most existing benchmarks (R4).
- Proposed LLM-based scaling of benchmark dataset development is promising (R4).
- Controlled real-environment simulation for cyberattack helpfulness with dynamic metrics; tracking refusal rates provides insight into safety mechanisms (R1, R4).
- Outperforms CyberSecEval in security relevance and prompt faithfulness (R3).
- Applied to four SOTA open-/closed-source models (CodeLlama-34B-Instruct, Llama-3.1-70B, Mixtral-8×22B, GPT-4o) and the advanced code agent Cursor, revealing non-trivial security risks (R3, R4).
- Integrates two distinct security tasks into a unified platform; dynamic evaluation through test cases enables real-time assessment (R2).

### Weaknesses
- **Scope and positioning**: Combining insecure code generation and cyberattack helpfulness into a single conference-length paper restricts depth; the logical connection is unclear beyond following CyberSecEval’s structure. The two tasks have fundamentally different objectives, infrastructure, and audiences (R4). The minority reviewer (rating 3) also found the paper weak overall due to these and additional issues.
- **Missing comparisons and related work**:
  - Overlooks LLMSecEval (MSR 2023), which covers 18 Python CWEs, contradicting the claim that existing benchmarks cover only 8 Python CWEs (R4).
  - BigCodeBench is not discussed (R1).
  - Several SOTA code generation methods not mentioned or experimented: He & Vechev (CCS 2023), CodeGen (ICLR 2023), InCoder (ICLR 2023), SantaCoder (CoRR 2023) (R3).
  - For the cyberattack task, no comparison with existing cyber ranges/frameworks: MITRE Caldera, Metasploit, IBM Cyber Range, VulHub, HackTheBox, OWASP Benchmark, VulnHub (R4). No gap analysis justifying why a new simulation range was needed (R4).
- **Data generation and test suites**:
  - Unclear how test suites for mutated IC samples are generated. If using LLMs, how is quality assured? If reusing original suites, can they adapt to new contexts? (R2).
  - Code mutator types and the dynamic methods used to check correctness after mutation are not specified (R3).
  - “Instruction generation” task is confusing—it appears to ask for code generation, not instructions (R4).
  - The role of context in reducing false positives is not ablated; experiments set context to None (R1).
  - Rule-based metrics introduced for cases without standard test cases lack provenance or citation (R1).
- **Security testing and evaluation details**:
  - No breakdown of security test cases per CWE, no code-coverage-like metric to demonstrate exhaustiveness (R4).
  - Unclear how vulnerable and patched code examples are used to evaluate test correctness or generated output (R4).
  - The “security relevance” metric is confusing: it appears to assess prompts, not LLMs, and the Security-relevancy Judge (GPT-4) includes the security policy reminder as part of user input fed to the LLM, potentially biasing the evaluation (R2).
  - Missing ablation study on the security policy reminder; rationale for prompt design (system templates, user templates, role-playing wording for CH) is not justified or compared with alternatives (R2, R4).
  - No specific ASR metric for end-to-end attacks in CH; unclear whether evaluation is fully automated or requires human input (R2).
  - No discussion of defenses (firewalls, IDS) in the simulated CH environment; insights on LLM performance with defenses would be valuable (R2).
- **Cyberattack helpfulness scenario limitations**:
  - Scenario generalizability is limited; practical attacks vary and the strong assumption that internal users click on malicious links reduces relevance (R2).
  - Attacker capabilities and tools are not specified (R2).
  - Lateral movement—a known gap in LLM-driven red teaming—is not addressed (R4).
  - Table 2 claims “weaponisation” and “infiltration” as MITRE categories, but these are not part of MITRE ATT&CK (R4).
  - Multi-stage attacks (kill chain) are not considered (R1).
- **Programming language coverage**: Only Python is used; C/C++ and Java, which constitute a significant portion of recent CVEs, are missing, making the benchmark inadequate for a comprehensive large-scale evaluation (R2).
- **Prompt quality and bias**: Using GPT-4 as the Security-relevancy Judge introduces potential bias since the same model type is used in prompt construction. Diverse judges or a user study would be more objective (R4).
- **Lack of ablation studies**: The boundary between user control and benchmark-provided components is unclear; prompts and instructions are not ablated to measure their effect on evaluation (R2). Diversity analysis across the 10 samples per seed and 5 test cases per sample is missing—there may be redundancy (R4).
- **Typos and errors**:
  - Missing period after “security-critical scenarios” (line 76); period placement issue in “security is required.)” (line 253) (R1).
  - Missing word: “our automatic and validate process” (page 2) (R4).
  - Repeated phrase: “not even not even vulnerable” (page 3) (R4).
  - “MITER” should be “MITRE” (page 4) (R4).
  - Figure 2 caption: ‘worn’ should be ‘worm’ (R4).
  - “active domain (AD) server” likely “Active Directory” (R4).
  - Section 4.2 says Figures 8 and 9 are about CyberSecEval but captions say SecCodePLT (R4).
  - Multiple instances of “cursor” should be “Cursor” (R4).
  - “Not that we consider cursor” should be “Note” (R4).
