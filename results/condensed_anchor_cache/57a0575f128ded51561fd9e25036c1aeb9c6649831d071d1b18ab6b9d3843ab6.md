## Merged Review

### Summary
ProTrain is a training system that automates memory management for LLM training by abstracting strategies (ZeRO, parameter/activation offloading, activation checkpointing, persistent GPU parameters, optimizer-in-backward) into a small set of tunable configuration parameters. It builds cost models from runtime profiling (latency, memory, I/O bandwidth) to search for the optimal policy. Evaluations on single-node (4 GPUs) and two V100 nodes show ProTrain supports models up to 1.64× larger and improves throughput by 1.43×–2.71× over state-of-the-art (vanilla FSDP). Reviewers generally find the problem important and the system well-organized, but raise concerns about technical novelty, experimental scale, baseline fairness, missing comparisons (e.g., LoRA, PyTorch’s native selective activation checkpointing), lack of pipeline parallelism support, and insufficient analysis of overlap efficiency and configuration details. One reviewer (score 6) is more positive, highlighting the dual-chunk design and profiling system as promising contributions, while the other three (scores 5) see limited novelty and practical scope.

### Strengths
1. **Important problem and clear exposition (R1, R4)**: Reducing memory consumption in LLM training is important and challenging. The paper is well-organized and easy to follow, though one reviewer (R4) notes some key concepts (offloading, activation recomputation) are not well introduced.
2. **Broad search space (R2, R3)**: Covers a wide spectrum of memory techniques: ZeRO, parameter offloading, activation offloading, activation checkpointing, GPU-persistent parameters, and optimizer-in-backward. The dual-chunk design for model states and interleaved organization for activation management effectively reduce memory overhead (R3).
3. **Runtime and peak memory estimators (R2, R3)**: The cost model building blocks (latency, memory, I/O bandwidth estimators) are fundamental and useful for OOM prevention and offline simulation. They enable automated memory management without manual intervention (R3).
4. **Promising results across models and hardware (R3, R4)**: ProTrain shows tangible gains in both trainable model size (up to 1.64×) and throughput (1.43×–2.71×). Evaluations cover various LLMs and different hardware platforms (R4). Integration into existing platforms could enhance training efficiency (R3).

### Weaknesses
1. **Limited technical innovation (R1, R2)**: The approach relies on applying ZeRO, offloading, and activation checkpointing; their combination is not sufficiently novel. The large search space is not well justified and could be easily pruned (R1). Stronger justification of the challenge in combining these techniques is needed (R1, R2). *Minority view (R3 score 6) finds the dual-chunk heuristics and profiling system a meaningful contribution, but this is not shared by other reviewers.*
2. **Insufficient experimental scale and configuration detail (R1, R2, R3)**: Experiments use at most 4 GPUs on a single node (plus two V100 nodes) – too small to demonstrate scalability for billion-scale LLM training (R1). Missing details on how each baseline is configured: which offloading is used, which activation checkpoints, how parameters are grouped for all-gather/reduce-scatter (R2). For maximum trainable model size, the explanation of why baselines fail is vague (R2). The exact combination of tricks that achieves best memory and throughput should be summarized (R2). Overlap between memory transfers and computation is not analyzed with varying batch sizes and parallel scales; a detailed micro-benchmark is needed (R3).
3. **Unfair or incomplete baseline comparisons (R1, R4)**: Only vanilla FSDP (ZeRO-3) is compared, but PyTorch already supports selective activation checkpointing; the paper should compare with PyTorch’s combination of FSDP, offloading, and activation checkpointing (R1). Additionally, LoRA could achieve similar performance with much lower training overhead, yet is not considered (R4).
4. **Lack of pipeline parallelism support (R3)**: ProTrain primarily addresses data parallelism. Many modern LLMs are too large to fit on a single GPU, requiring pipeline parallelism. The current design does not extend to that setting, significantly restricting practical applicability.
5. **Potential incompatibility with real-world training (R4)**: Because the system includes offloading, it is argued to be usable only for fine-tuning, not full pre-training of large LLMs (R4). *Note: This is a strong criticism from one reviewer; others did not raise this issue.*
6. **Missing analysis of gradient norm clipping with optimizer-in-backward (R2)**: Performing the optimizer step per gradient/layer without knowing total gradient norms may conflict with gradient norm clipping, which is critical for LLM training. The paper should discuss this.
7. **Portability to existing frameworks (R3)**: ProTrain is built on PyTorch, but many developers use DeepSpeed or Colossal-AI. How can they integrate ProTrain without rewriting their codebases?
8. **Unclear difference from LRU caching and persistent chunk design (R3)**: The persistent first-chunk heuristic needs justification – why not evict and swap back like other chunks? How does it differ from a computation-aware LRU caching strategy? Finer granularity (e.g., 1/3 of a transformer block) might achieve better throughput than the current block-level management (R4).
9. **Motivation and overhead (R1, R4)**: The paper claims existing frameworks depend on manual tuning but does not show how poor their performance is (R4). Search overhead and the resulting configurations should be reported (R1). The design overhead of ProTrain itself is not quantified (R4).
