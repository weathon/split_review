## Merged Review

### Summary
The paper proposes RLEF, an end-to-end reinforcement learning method that teaches code LLMs to leverage execution feedback (error messages, unit test results) across multiple turns. The method frames code generation as an interactive RL task where the LLM agent iteratively refines its solution based on unit test outputs. The authors benchmark on competitive programming tasks (CodeContests) using Llama 3 models (8B and 70B) and report state-of-the-art solve rates with an order-of-magnitude reduction in required samples. They also show generalization to HumanEval+ and MBPP+. The core contribution is using execution feedback as textual input across turns within an RL (PPO) training loop.

### Strengths
- The method is intuitive and the formulation of code generation as an interactive RL task is reasonable. (R3)
- The results demonstrate general improvement on CodeContests across Llama 3 model sizes and achieve new state-of-the-art performance. (R1, R2, R3, R4)
- The approach significantly reduces the number of samples needed (order of magnitude) while maintaining or improving accuracy. (R1, R2)
- The trained models (especially Llama 3.1 70B) generalize to held-out datasets HumanEval+ and MBPP+, suggesting broader applicability. (R2)
- Behavioral and error analysis post-training (fewer repetitions, more targeted edits, reduced reliance on random sampling) provides empirical support for improved multi-turn robustness. (R2)
- The paper is well-written and the results are clearly presented. (R4)
- The method addresses a critical limitation of current LLMs—inability to effectively use execution feedback for iterative improvement. (R1)

### Weaknesses
- **Limited novelty.** Multiple reviewers note that the core idea of using unit test / compiler feedback as a reward signal for RL has been proposed before. Specifically, RLTF [1] uses unit test feedback in an online RL framework; Anthropic's work on iterative code correction and DeepMind's adaptation of self-correction in RLHF also explore similar directions. RLEF's primary advancement is extending this to a multi-turn setting where feedback is included as input text, making it more of an empirical extension than a conceptual breakthrough. One reviewer (R3) found the innovation particularly limited, noting that prior methods also used specially designed reward functions. Direct comparisons with RLTF, CodeRL, StepCoder, B-Coder, and related works are missing. (R1, R2, R3)
- **Missing ablations and insufficient experiments on broader benchmarks.**
    - The experiments are limited to CodeContest (with small validation/test splits). Evaluation on APPS (commonly used in RLHF+compiler feedback research) is needed. (R1)
    - No ablation on the reward function is provided, which is important for understanding the method. (R3)
    - The method is only validated on Llama 3 models; experiments on other model families (e.g., CodeLlama, StarCoder) to verify generality are needed. (R3)
    - The claim that multi-turn SFT performs significantly worse than RL (as stated in the appendix) should be validated by releasing both SFT and RL code, as self-improvement via critic+SFT has proven effective. (R1)
- **Practical applicability concerns.** The method relies on high-quality unit tests for feedback. Generating such tests for arbitrary prompts is often as hard as solving the problem, which constrains the method to OJ-style problems with pre-existing tests. The paper does not study sensitivity to unit test quality (beyond "random feedback"), e.g., incomplete tests or tests covering only trivial cases. An analysis or discussion on generating or selecting high-quality tests in real-world settings is missing. (R2, R4)
- **Presentation and methodological clarity.**
    - The Method section is overly condensed; key PPO implementation details and task-specific adjustments are packed into dense paragraphs, making reproduction difficult. (R2)
    - The primary results table compares models across n@k metrics with varying n and k, which is not intuitive without clearer explanation or a consistent comparison framework. (R2)
- **Advantage computation and value estimation.** The authors claim token-level action space but use the same advantage for all tokens in a turn. The justification for this hybrid approach (response-level value estimation, token-level policy optimization) and how the critic is updated is unclear. An intuitive or empirical explanation is needed. (R4)
- **Effectiveness of multi-turn feedback vs. iterative structure.** It is ambiguous whether the iterative nature of the algorithm or the specific content of execution feedback (error messages, expected outputs) drives the improvement. An ablation study should compare detailed feedback vs. only numerical signals (e.g., fraction of tests passed) with smaller turn-level rewards and a larger episode-level reward. (R4)
- **Several open questions remain unaddressed.**
    - What is the effect of incorporating feedback (e.g., compiler errors) on incorrect code before the next iteration? (R1)
    - How robust is RLEF to varying quality/amounts of execution feedback? Is there an optimal type or amount of feedback? (R2)
    - What is the impact of a fixed turn limit vs. a dynamic turn limit based on problem complexity or feedback content? Does performance saturate after a certain number of turns? (R2)
