## Merged Review

### Summary

The paper introduces CRAFT, a framework for creating and retrieving task-specific toolsets to augment LLMs. It generates code solutions via GPT-4, validates, abstracts, and deduplicates them into reusable code snippets, then retrieves relevant tools at inference time to assist generation. Experiments on vision-language, tabular processing, and mathematical reasoning tasks show substantial improvements over strong baselines. Analysis demonstrates scalability with tool count and backbone capability, and that created tools are low-complexity and atomic. Two reviewers assign 6, one assigns 8, with the higher-rated reviewer particularly valuing the toolset contribution and the proposed “pseudocode library” future direction.

### Strengths

1. **Originality and Flexibility.** CRAFT combines tool learning, code generation, and retrieval in a novel way, moving beyond general-purpose APIs by reusing task-related tools (R1, R2, R3). It adapts off-the-shelf LLMs to new domains/modalities without finetuning (R1, R2).

2. **Rigorous Validation and Strong Results.** The framework is validated across diverse tasks (VQA, tabular, math) with substantial improvements over baselines; the process ensures tool correctness and reusability (R1, R2, R3). Experiments are comprehensive and the results are promising (R3).

3. **Clarity and Structure.** The paper is well-structured and clearly written, presenting the framework, applications, and experiments effectively (R1).

4. **Important Practical Contribution.** The created toolsets themselves are a valuable contribution to the LLM community (R3). The future direction of a “pseudocode library” is considered cool and meaningful (R3).

5. **Addresses Key Challenges.** CRAFT tackles the limitation of fixed general-purpose APIs and provides a plug-and-play solution for augmenting LLMs (R1, R2).

### Weaknesses

1. **Limited Experiment Setting and Baselines.** The evaluation does not cover broader agent benchmarks (e.g., MINT, AgentBench) needed to verify problem-solving capacity as agents (R2). Comparisons with existing tool-augmented methods (e.g., LATM) are limited; further comparison with SOTA in specific tasks (e.g., VQA) is missing (R1). The paper does not clearly distinguish its approach from related methods (e.g., Figure 1 resembles LATM), and a table comparing tool-augmented methods would help (R3).

2. **Unfair Comparison with LATM.** CRAFT’s toolset is created by GPT-4, whereas LATM uses an inferior model for tool creation, making the comparison potentially unfair (R2). Reliance on GPT-4 also raises concerns about biased tool creation and fairness across diverse datasets (R1).

3. **Lack of Failure Case and Transferability Analysis.** The paper does not discuss scenarios where CRAFT might fail, e.g., tool abstraction failing to generalize across input formats or edge cases (e.g., date format variations) (R1). The transferability across tasks is unclear: toolset for VQA vs. reasoning are not the same; an experiment creating a general toolset for all tasks is suggested (R2). More analysis on where and how the created toolsets can be applied/generalized is needed (R3).

4. **Insufficient Analysis of Tool Creation and Retrieval.** The contribution of different tool types to performance is not detailed. The retrieval mechanism’s handling of ambiguous queries and tool prioritization is not explained (R1). The process of abstraction and deduplication criteria (e.g., how “bug-free” is ensured) needs elaboration (R1, R3). The handling of descriptive LLM responses (which can underestimate performance) is not fully described (R1).

5. **Scalability Evidence Missing.** The paper claims scalability but lacks quantitative analysis of how performance changes with toolset size or task complexity (R1).

6. **Missing Experiments with Alternative Backbones.** The authors mention that CodeLlama shows near-random performance, but do not report results of different LLMs (e.g., GPT-3.5-turbo, CodeLlama) in creating and using tools (R3). It is also unclear whether CRAFT can be adapted to programming tasks like HumanEval (R3).

7. **Lack of Real-World Validation.** No user study or real-world application examples are provided to demonstrate practical effectiveness beyond controlled settings (R1).

8. **Underexplored Pseudocode/In-Context Learning Distinction.** The proposed “pseudocode library” future direction needs more discussion: e.g., whether a natural language library is possible and how it differs from standard in-context learning (R3).
