## Merged Review

### Summary
The paper introduces VisualAgentBench (VAB), a benchmark to evaluate Large Multimodal Models (LMMs) as visual agents across diverse, realistic scenarios: embodied (VAB‑OmniGibson, VAB‑Minecraft), Graphical User Interface (VAB‑AndroidLab, VAB‑WebArena‑lite), and Visual Design (VAB‑CSS). VAB provides standardized environments, a function‑calling‑based action space, and a hybrid trajectory collection strategy (program‑based solvers, LMM agent bootstrapping, human demonstrations). The benchmark includes 746 test cases and 4482 training trajectories across five tasks. The paper benchmarks 18 LMMs (both proprietary and open‑source) and conducts ablation studies on input image prompting, reflection, and planning (ReAct). The authors also perform supervised fine‑tuning (SFT) on open LMMs using the collected training trajectories. Key insights include challenges in visual grounding, planning, and error recovery.

### Strengths
- **Comprehensiveness and Diversity**: The benchmark covers a wide range of real‑world application scenarios (embodied, GUI, gaming, visual design), making it a thorough evaluation tool for LMMs as agents.
- **Standardization**: VAB provides a unified function‑call action space and standardized environments with good consistency and reproducibility across different task domains.
- **Extensive Experiments**: Rigorous benchmarking of 18 LMMs (both proprietary and open‑source) and solid ablation studies on input prompting (labels, SoM), reflection (error injection), and planning (ReAct with & without Thought).
- **Training Trajectories**: The paper provides additional training trajectories for SFT, promoting improved performance through behavior cloning.
- **Insightful Analysis**: Reveals specific limitations in visual grounding, action planning, and error handling, providing practical direction for future LMM development.
- **Interactive and Multi‑turn Nature**: The benchmark emphasizes interaction through text/vision‑based environment feedback, an important aspect for agent evaluation.

### Weaknesses
- **No Clear Advantage Over Existing Benchmarks**: There are existing benchmarks for embodied robot manipulation (RoboVQA) and GUI agents (Webshop‑V, VisualWebArena); it is unclear what novel contribution VAB provides beyond a combination of these domains. *Note: One reviewer (rating 8) disagrees, finding VAB a good complement to current benchmarks.*
- **Low Quality of Training Trajectories**: For GUI agent tasks, VAB‑WebArena‑lite uses script‑based trajectory collection, which is known for limited diversity compared to real‑world human web browsing actions. The human‑annotated and LMM‑bootstrapped methods similarly do not guarantee high diversity; careful task space design is needed but not detailed.
- **Function‑Calling Action Space Bias**: The function‑calling action space biases toward LMMs with strong coding ability, leading to unfair low scores for models like Qwen‑VL‑Max and Gemini‑1.0‑Pro, which perform well on pure VQA benchmarks. A reviewer questions why a model without function calling ability cannot be a good VLM agent (e.g., Qwen‑VL could perform well in driving, robotics, UI tasks when fine‑tuned as a VLA model without function calling).
- **Questionable Physical Realism in VAB‑OmniGibson**: Most robot arms have a workspace of 700–1000 mm, but the environment allows grasp within 1.2 m, which is unrealistic. The grasping is simplified into a rule‑based text environment (if robot has hand and is within 1.2 m, grasp succeeds), violating the golden design rule for evaluating real grasping. Additionally, a reviewer questions whether the physical dimension of the robot arm is given in Gibson (e.g., grasping a banana on a far countertop may be infeasible).
- **Unclear Role of Visual Information in Some Tasks**: For tasks like Minecraft, actions such as “Teleport” do not inherently require visual information since they can execute without reference to the visual state. The benchmark should clarify how each action necessitates visual input, to justify the use of VL models over text‑only approaches.
- **Insufficient Explanation for Poor Model Performance**: Some vision–language models achieve low scores without adequate explanation; the paper does not explore why certain models failed.
- **Limited Training Data and Scalability**: The number of training trajectories is limited; the paper does not show whether scaling up training data in these environments is feasible.
- **No RL Training Analysis**: There is no experiment to verify whether the environments can be effectively used for RL training; the reward structure and its impact on learning are not discussed.
- **No Non‑LLM Specialist Baselines**: The paper lacks performance baselines from non‑LLM specialist models (e.g., trained via RL or imitation learning) in each environment, which would help assess task difficulty.
- **Catastrophic Forgetting Not Addressed**: After fine‑tuning LMMs with collected training data, the paper does not evaluate general multimodal abilities on other benchmarks, nor explore whether original abilities can be maintained while improving benchmark performance.
- **Ambiguities in Figures and Process Flow**: Figure 2 has multiple input/output connections but lacks a clear process flow or sequential dependency indicators, making agent behavior difficult to follow.
- **Missing Detailed Analyses**:
    - Quantitative evaluation of grounding vs. reasoning; a systematic metric separating these abilities is requested.
    - Analysis of which “prototypes” or subtasks cause failures, and whether failure patterns correlate across models.
    - Evaluation of interaction rounds (e.g., average steps to recover from error) rather than only final success rate.
- **Clarification Requests**:
    - How are task descriptions, action spaces, few‑shot demonstrations, and notices formatted as prompts? How are visual outputs of the environment passed as text in interaction rounds for embodied and GUI agents?
    - When training open LMMs, the paper says they only use the vision input of the latest turn. Does this mean each turn in the training trajectory is treated as an independent sample (with previous turns provided in context) instead of training as a multi‑turn conversation?
    - For evaluating LMM APIs, what does “Vision Input image won’t be kept in the dialog” mean? Wouldn’t previous turn images automatically be kept?
    - Clarify the role of bounding boxes and object tags in Figure 7: must objects be visible in input images for the simulator to recognize them? How does the agent operate when no label/tag is provided?
    - What practice does VAB provide for ease of use (e.g., unified API or modular code)?
