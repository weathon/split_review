## Merged Review

### Summary
The paper proposes the Cascaded Learned Bloom Filter (CLBF), a learned Bloom filter architecture that alternates multiple machine learning models and Bloom filters in a cascade. It uses dynamic programming to automatically select configurations to optimize memory usage and reject time. Experiments on two real-world datasets show memory reductions up to 24% and reject time reductions up to 14× compared to the state-of-the-art PLBF. Reviewers are divided: one (score 6) finds the work novel and thorough; two (scores 3, 3) see an incremental contribution with significant theoretical and practical gaps; one (score 1, confidence 5) considers the approach far too complex for adoption.

### Strengths
- **Cascaded architecture**: CLBF uniquely combines sandwiched learned Bloom filters and partitioned learned Bloom filters with classical Bloom filters as branch filters (R1).
- **Novel structure and optimization**: The cascade of multiple ML models and Bloom filters, optimized via dynamic programming, reduces manual parameter tuning and improves memory–reject time trade-offs (R2). The structure allows flexible balance by adjusting hyperparameters (R2).
- **Clear exposition and theory**: The paper provides a clear description of CLBF with thorough theoretical analysis (R2). It effectively summarizes prior learned Bloom filter work and explains how CLBF differs (R3).
- **Experiments**: Extensive experiments on multiple real-world datasets and baselines give a well-rounded view of CLBF’s effectiveness and limitations (R2, R3).
- **Weak-learner assumption**: The assumption that ML models are weak learners is important because strong patterns are often absent in Bloom filter keys, making high accuracy difficult (R4 – minority positive point from the most negative reviewer).

### Weaknesses
- **Critical theoretical gaps** (R1, high confidence):
  - The claim that dynamic programming yields an *optimal* balance is unsubstantiated. Eq. (4) lacks an explicit relation between a learned filter’s false positive rate \(f^{(t)}_i\) and the model size, making the optimization meaningless without such an expression.
  - The overall false positive rate of CLBF is not \(\prod f^{(t)}_i\); this equation is unjustified. Most of Section 3.3 is unclear.
  - The optimality of the dynamic programming solution is not formally established.
  - The effect of cascade depth \(d\) on the model–filter size balance is not analyzed.
- **Missing baselines** (R4, confidence 5):
  - The paper does not compare against two important competitors of PLBF that measure memory: (1) Ada-BF by Dai and Shrivastava (NeurIPS 2020) – only cited, not compared; (2) Data-aware Hash Functions for Bloom Filters by Bhattacharya et al. (VLDB 2022), which shows improved memory over both Vaidya (PLBF) and Ada-BF.
- **Incremental contribution** (R3, R1): The design largely combines existing techniques (sandwiched BF and PLBF) into a cascade, yielding an incremental rather than groundbreaking contribution (R3). The approach lacks novelty beyond this combination (R1).
- **Practical complexity and construction cost** (R4, confidence 5; R3):
  - The multi-layered structure with many ML models and Bloom filters adds enormous coding complexity, making adoption in real file systems unlikely (see Fig. 1 vs. 2) (R4).
  - Construction time is massively increased over a simple Bloom filter (Fig. 6). This is unacceptable for distributed filesystems that require periodic rebuilds (R4). Even without rebuilds, the initial construction time is high, limiting scalability and practicality in time-sensitive applications (R3).
- **Reject-time motivation and query-time costs** (R3):
  - The emphasis on reject time is not grounded in real-world use cases; there is no discussion of applications where reject time is critical or where it is less relevant.
  - The cascade structure may *increase* query time for elements in the set (present keys). The paper does not report average query time across different query types for a fair comparison.
- **Limited machine learning exploration** (R2):
  - Only XGBoost is used. Comparisons with other models (SVM, Random Forest, logistic regression) are needed to show versatility and robustness across algorithmic approaches (R2, moderate confidence).
  - It is unclear whether fine-tuning hyperparameters of XGBoost (learning rate, regularization, tree depth) or varying cascade Bloom filter parameters (hash functions, bit-array sizes) could yield similar or better results; the source of gains (cascade vs. optimization) is not isolated (R2).
- **Unexplored memory–learning tradeoff** (R4): No experiment investigates the tradeoff between memory and learning in terms of model size. Mathematical quantities (e.g., “reject time”) are not properly defined (e.g., is it clock time?) (R4, confidence 5).
- **Additional missing analyses/questions overlapping with weaknesses**:
  - How would the method perform in dynamic cases where set-membership structures must be reconstructed periodically? (R4, Q1)
  - How is memory split between Bloom filters and ML models decided? (R4, Q2)
  - Could hyperparameter tuning of the ML model within a standard learned Bloom filter achieve similar performance? (R2, Q1)
  - Could embedding a multi-layer deep learning model or using a hierarchical Bloom filter (e.g., a coarse BF then a precise BF) provide similar optimization? (R2, Q2, Q3)
  - Can the design be generalized beyond Bloom filters to other learning-augmented applications? (R3, Q1)
  - In what real-world applications is reject time prioritized over query time for present keys, and how should cascade depth be controlled? (R3, Q2)
  - How adaptable is CLBF to ML models with diverse size/query-time profiles? Would the structure require major adjustments? (R3, Q3)
- **Minor issue**: Line 266 has an extra quote (“) (R3).
