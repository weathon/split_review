## Merged Review

### Summary
The paper proposes RLCF (Coarse-Tuning Models of Code with Reinforcement Learning Feedback), which further trains a pre-trained code LLM via reinforcement learning using feedback from a grounding function. The grounding function combines (i) compiler-derived feedback on whether generated code passes correctness checks (including the location of compile errors) and (ii) feedback from a CodeBERT-based discriminator that compares generated code to a reference. The approach is model- and language-agnostic. Empirical evaluations on MBJP and MathQA tasks (Java) show that RLCF improves the odds of generating compilable, executable, and correct code, often allowing LLMs to match 2x-8x larger models. Experiments use CodeGen (up to 1.5B parameters) among others.

### Strengths
- The idea of using compiler (static analysis) feedback to fine-tune an LLM for code generation is novel, and the hybrid grounding function (compiler + discriminator LLM) is an innovative combination that enhances reliability and relevance.
- The approach is model- and language-agnostic, making it potentially applicable to many programming languages and models.
- The writing is clear, well motivated, and the method is presented clearly. The potential impact for code generation applications is significant.
- The experimental results are relatively comprehensive, including a slate of baselines for comparison on MBJP and MathQA tasks for Java, showing promising improvements.
- Using compiler/static analysis tools mirrors how human programmers learn from environment feedback, and many languages support such tools, so the method appears general.

### Weaknesses
- Novelty concern: Prior works (e.g., CodeRL, RLTF [1], [3] combining RL with AST/dataflow-graph metrics) have used static/dynamic analysis as RL reward for fine-tuning LLMs for code generation, limiting novelty. The paper should discuss these in related work and provide quantitative comparisons with them, especially CodeRL (mentioned as baseline but not compared) and RLTF.
- Weak generalization evidence: The paper evaluates only on two Java tasks (MBJP, MathQA). Both benchmarks were originally in Python and transpiled to Java; CodeNetJava also has a Python equivalent. The compiler error location feedback should be available for Python as well, but experiments are not done in Python. This makes comparisons with existing works (which almost universally use Python) difficult. For example, RLTF achieves 30.4 pass@1 on MBPP (Python) using 770M CodeT5, while RLCF achieves 6.6% on MBJP (same base model starts ~4% pass@1). The limited scope may not be representative of other languages or models. Missing comparison with state-of-the-art LLMs like GPT-3/GPT-4 is also a gap.
- Insufficient compute-controlled baselines: Experiments compare against pre-trained models that use zero additional compute (except incidental rehearsal). A more informative baseline would use the same amount of compute as RLCF but with the standard LM loss. The “+Mono” baseline in Table 7 goes in this direction but does not match RLCF’s compute budget. The ablation comparing to CodeRL is also questioned as unfair because CodeRL includes additional components (e.g., critic network); renaming the ablation is suggested.
- Discriminator concerns: The method requires a separate discriminator LM (pre-trained CodeBERT). It is unclear why this specific model was chosen and how it impacts results. Pre-training the discriminator has a large effect (Table 4 appendix), but this raises the question of whether performance gains are largely due to distilling “Java code knowledge” from CodeBERT rather than the RL coarse-tuning itself. The paper should evaluate how well CodeBERT performs on the tasks and test sensitivity by swapping in other discriminators (e.g., a dataflow-graph-based metric from [3]).
- Need for more robust RL baselines: Comparisons with standard RLHF/RLAIF frameworks (using binary compiler success as reward) would help isolate the contribution of RLCF’s specific grounding function design. Similarly, an RLHF baseline with CodeBERT as the reward model should be run to test the distillation hypothesis.
- Missing ablation of compiler localization feedback: The compiler feedback includes the location of the error; the benefit of this localization over a simpler -1/0 for compile errors should be ablated.
- The approach is limited by CodeNetJava’s design, which does not consider dependencies on user-defined packages or libraries, potentially limiting applicability to larger datasets.
- Practical implementation challenges: Using both a compiler and an additional discriminator model may present significant obstacles for integration into developer tools.
- Compiler variability: Different compilers may have different strictness or feature support, potentially leading to inconsistent evaluation of generated code.
- Missing analysis on how RLCF works with existing pre-trained code-specific LLMs (e.g., CodeT5, CodeBERT) and not just CodeGen.
- One reviewer suspects the labels for pre-trained vs. not pre-trained in Table 4 (appendix) might be mixed up; authors should clarify.
