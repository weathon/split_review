## Merged Review

### Summary
The paper proposes IDS-Agent, the first LLM-powered agent for intrusion detection in IoT networks. It features a reasoning-followed-by-action pipeline where a core LLM decides optimal tools for data extraction, preprocessing, classification, knowledge retrieval (RAG), and results aggregation. A memory and knowledge base (long-term and short-term) supports reasoning. Experiments on ACI-IoT and CIC-IoT datasets report F1 scores of 0.97 and 0.75, and zero-day attack recall of 0.61.

### Strengths
- IDS-Agent is the first LLM agent designed specifically for intrusion detection.
- The design pipeline is clearly presented.
- The reasoning-followed-by-action pipeline and use of RAG for external knowledge are well-motivated.
- IDS-Agent offers capabilities for explanation, customization, and zero-day attack detection.
- It outperforms existing ML-based IDSs and an LLM+prompt engineering baseline on two benchmarks.
- The paper is well-written and addresses the hot topic of LLM application in security.

### Weaknesses
**1. Limited contribution of the LLM beyond ensembling and explanation**  
- The core detection capability still comes from the ML models in the toolbox; the LLM essentially acts as an ensemble aggregator with natural-language explanation.  
- In Table 1, Majority Vote (without LLM) achieves very close performance on CIC-IoT and even higher on ACI-IoT. This raises doubt whether the LLM adds value beyond the ensemble of ML models, especially when using GPT-3.5.  
- Most components (pipeline, long-term memory, RAG) are existing approaches with no substantial adaptation to the IDS scenario.

**2. Missing comprehensive related work and baselines**  
- The paper does not survey state-of-the-art IDS methods from top security conferences (e.g., CCS, NDSS, USENIX Security) or recent ML/DL/pretrained/LLM works. Relevant references include:  
  [a] Realtime Robust Malicious Traffic Detection via Frequency Domain Analysis, CCS 2022  
  [b] Detecting Unknown Encrypted Malicious Traffic in Real Time via Flow Interaction Graph Analysis, NDSS 2023  
  [c] HorusEye: Realtime IoT Malicious Traffic Detection Framework with Programmable Switches, USENIX Security 2023  
  [d] ET-BERT, WWW 2022; [e] NetGPT, arxiv 2023; [f] Yet Another Traffic Classifier, AAAI 2023  
  [g] HuntGPT, arxiv 2023; [h] ChatIDS, arxiv 2023  
- No comparison with traditional rule-based IDS tools (Zeek, Suricata, Snort) that are effective on standard attacks.  
- No comparison with traditional deep learning methods for zero-day detection (unsupervised anomaly detection).

**3. Evaluation weaknesses**  
- Only two IoT datasets (ACI-IoT and CIC-IoT) are used; the field commonly uses many more (e.g., CIC-IDS 2017, CSE-CIC-IDS 2018, UNSW-NB15, BoT-IoT, ToN-IoT).  
- Test set is very small: 200 benign samples and 20 per attack category. The authors should justify why this small set was used – if due to API cost, why not use local open-source LLMs like LLaMA?  
- The false alarm rate (FAR) is 3–5%, while many SOTAs achieve FAR < 1%. In practice, even 1% FAR on benign-dominant traffic would create an excessive number of false positives.  
- Table 1 shows no big improvement over majority vote (especially for GPT-3.5), suggesting the ensemble of ML models, not the LLM analysis, provides primary detection capability.  
- The zero-day attack analysis uses ACGAN-generated CAN protocol samples; the paper focuses on IoT networks, but CAN is not an IoT protocol. The relevance and analogy to IoT attacks are unclear.  
- Performance evaluation lacks a breakdown of the 8.65-second processing time per sample across preprocessing, LLM reasoning, RAG, and inference stages. Practical real-time feasibility is not addressed – a DDoS attack could cause extensive damage during such delay.  
- Missing quantitative analysis of false classifications (e.g., confusion matrices for multi-class).  
- The threshold of 0.7 for binary classification is not analyzed; a performance curve across thresholds would be informative.  

**4. Issues with RAG and interpretability**  
- Retrieved knowledge may be inconsistent with dataset features. For example, knowledge about ARP spoofing may point to MAC addresses, but many datasets omit such environment-specific fields to prevent overfitting. How does knowledge help when features are not present?  
- The claimed interpretability is limited: the LLM only analyzes score distribution from classifiers, not which attributes are most important for the decision. Readers expect attribute-level explanation (e.g., [j]), especially since external knowledge is available but not used for that purpose.  

**5. IoT-specific justification is weak**  
- The paper’s title and claims focus on IoT networks, but no design elements are specific to IoT (e.g., traffic patterns unique to IoT devices, as in [i]). The authors should explain the added complexity or challenges of IoT vs. general networks (lines 297–299).  
- The argument that understanding rationale is “particularly critical” in IoT (line 56) is not substantiated with examples or distinctions from other network types.  

**6. Unclear design choices and missing details**  
- If data extraction, preprocessing, and classification are always executed, what does the LLM’s reasoning add over a fixed program? The authors should report how often the LLM jumps over or triggers conditional actions like knowledge retrieval (KRM) or long-term memory (LTM).  
- The use of timestamps in long-term memory is unexplained: LTM is initialized by running the agent on a validation dataset, which is not correlated with execution timestamps.  
- “FlowID” is used repeatedly but never formally defined; its meaning varies across sources.  
- The knowledge base is constructed from 50 online blogs and 50 research papers; criteria for selecting these sources are not given, leaving reliability and relevance unclear.  
- Feature selection per dataset and the exact attack types in training vs. testing sets are not specified. Random selection may cause similar attacks (e.g., flood attacks) to appear in both sets, skewing results.  

**7. Real-time and resource concerns for IoT**  
- IoT devices are resource-constrained; applying a heavy LLM agent seems contradictory to the typical lightweight (e.g., TinyML) approach. Practical examples of how the system could be deployed beneficially in IoT are missing.  
- The system is not real-time (8.65 sec/instance). The authors should discuss architectural and hardware challenges for real-time deployment and the impact of such latency (e.g., DDoS mitigation).

- Figure 1: “traffics” → “traffic”.
