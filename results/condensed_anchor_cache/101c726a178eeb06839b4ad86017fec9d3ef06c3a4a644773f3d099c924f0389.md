## Merged Review

### Summary
All four reviewers acknowledge the importance of the LLM selection problem and recognize the novelty of reformulating it as a graph-based edge prediction task. They agree that GraphRouter is well-motivated, leverages contextual information effectively, and shows strong empirical performance across multiple cost-performance scenarios and inductive settings. However, reviewers raise concerns about the realism and scope of the evaluation, the justification of the graph design and edge features, limited scalability analysis, and missing ablations. One reviewer (score 8) is notably more positive, emphasizing the conceptual generalizability and convincing empirical results, while the other three (score 6) point out more substantial methodological and evaluation gaps.

### Strengths
- The paper tackles a challenging and important problem—generalizable LLM selection with performance-cost trade-offs—and is the first to reformulate it as a graph-based edge prediction problem (R1, R2, R3, R4).
- GraphRouter constructs a heterogeneous graph with task, query, and LLM nodes, capturing contextual interactions that prior router methods neglect (R1, R2, R3).
- The framework adapts to new LLMs and tasks without retraining (inductive setting), which is critical for the rapidly evolving LLM landscape (R2, R3, R4).
- Comprehensive experiments across three cost-performance weight scenarios demonstrate substantial improvements (≥12.3% in standard settings, ≥9.5% in new LLM settings) over existing routers (R1, R2, R3, R4).
- Evaluation includes four diverse tasks (Alpaca, GSM8K, SQuAD, Multi-News), ten LLMs, and multiple metrics; ablation studies on GNN layer count and embedding size provide useful implementation insights (R2).
- The paper is well-structured and easy to follow, with illustrative figures that aid comprehension (R3, R4).

### Weaknesses
- **Evaluation realism and scope are limited.** The experimental tasks are mostly reasoning and QA, overlooking specialized domains like code generation or complex multi-hop QA, which are critical for assessing generalizability (R3). Only ten LLMs are tested, with nearly half from the LLaMA family, so the range of architectures and capabilities is not representative of the broader LLM ecosystem (R3). The setting assumes per-query LLM switching, which is unrealistic in practice due to model loading overhead, latency, and session consistency—these costs are not accounted for in the evaluation (R1). The cost metric (likely based on API pricing or token counts) does not reflect actual hardware-dependent costs (e.g., inference time on CPU vs. GPU), making results hard to generalize to diverse deployments (R1).
- **Methodological justification and feature design are insufficient.** The paper lacks a rigorous explanation of why edge prediction directly translates to optimal LLM selection: the connection between predicted edge weights and actual routing performance is not formally established (R2). LLM-query edge features are only performance and cost concatenations, ignoring other potentially valuable signals like response length, generation time, or latency (R2). Task-query edges are initialized uniformly to 1, which is overly simplistic given the rich relationships that could be captured (R2). The initial LLM node features rely on text embeddings, which are ill-suited for representing numerical attributes like token pricing or context length—subtle but important numerical differences (e.g., $0.0001 vs $0.0002 per token) may be lost (R4).
- **Scalability and dynamic update mechanisms are not addressed.** Experiments only go up to 10 LLMs, leaving open questions about performance at larger scales (R2). There is no discussion of how to incrementally update the graph when new LLMs emerge or existing ones are fine-tuned—whether the entire graph must be rebuilt or if partial updates are possible (R2, R3). The effect of temporal dynamics (e.g., newer models like GPT-4o vs. GPT-o1 becoming best at different times) is not considered (R3). The paper does not analyze how different LLM architectures (e.g., transformer-based families, correlated models in the same series) affect routing decisions or how to leverage shared knowledge among related models (R2, R3).
- **Missing analyses and ablations.** The ablation study (Table 4) only varies GNN layers and embedding size, but does not explore alternative edge feature designs or the impact of different edge feature combinations—a critical omission since edge features directly affect the GNN’s representational power (R2). The paper does not examine how GraphRouter distinguishes between LLMs with similar architectures but different sizes (e.g., LLaMA3-7B vs. LLaMA3-8B) (R2, question). The framework assumes a single universally optimal LLM per query, ignoring that optimal selection depends on user-specific constraints (e.g., latency budget, strict cost caps) that vary per application (R4).
- **Related work attribution is incomplete.** The discussion omits key references: the original label propagation work (Zhu & Ghahramani, 2002), the first heterogeneous GNN (R-GCN), and early attention-based heterogeneous GNNs (e.g., HAN) (R4).
- **Minor presentation issues.** Figures 2–4 lack sufficient explanation: the notation \( t \) in Figure 2, the term “effect” (should be clarified as performance), and why some LLMs appear as multiple dots in Figures 3 and 4 are not explained (R3). There is an unfinished sentence in Line 138 (R3). Hyperparameters beyond GNN layers (e.g., embedding dimension, learning rate) are not thoroughly explored (R2). The purpose of separate task nodes is unclear; task information could potentially be encoded within query node features to simplify the graph (R1). The reward function used in Table 5 is not defined, hampering reproducibility (R1). The paper does not discuss whether a training-free GNN (e.g., SGC, LightGCN) could be adapted for the link prediction task, and what fraction of training samples is required for satisfactory performance (R3, question).
