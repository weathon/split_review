## Merged Review

### Summary
ShortcutsBench is a large-scale benchmark for API-based agents, constructed from real iOS Shortcuts data comprising 88 applications, 1,400 APIs, and an average of 21 actions per API. The authors synthesize tasks using GPT‑4o, with human‑annotated action sequences by shortcut developers. They evaluate 5 open‑source (≥57B) and 4 closed‑source LLMs (e.g., GPT‑4o, Gemini‑1.5‑Pro, GPT‑3.5) on API selection, parameter filling, and requesting necessary input from system/user. Results show that models struggle with multi‑step reasoning, complex API selection, and identifying when external input is needed. The majority of reviewers rated the paper 6 (accept), while one reviewer rated it 8 (strong accept), creating a contrast in enthusiasm.

### Strengths
- The benchmark is comprehensive, covering real APIs from Apple, diverse task types, multi‑dimensional difficulty, and human‑verified action sequences. It addresses gaps in prior benchmarks like ToolBench and ToolLLM.
- The data source (Shortcuts) is novel and previously untapped for agent benchmarks; extracting real‑world APIs and action sequences is a practical and scalable approach.
- Evaluation includes both open‑source (e.g., Qwen‑2‑70B, LLaMA‑3‑70B) and closed‑source models, with detailed analysis of failures in reasoning, planning, and parameter filling (Sections 4.2–4.3).
- The provided example instances in the appendix help clarify task types.
- Artifacts are well‑organized and available.
- One reviewer (score 8, confidence 4) particularly highlighted the benchmark’s focus on agents’ ability to request necessary input and the diverse difficulty levels as strong contributions.

### Weaknesses
- Annotator details are insufficient: the paper only states “shortcut developers are our annotators”; further information on their background, selection, and verification process is needed (Reviewer 1).
- The process of simulating user queries with GPT‑4o (Section 3.2) lacks steps for verifying correctness and ensuring diversity (Reviewer 1).
- The methodology in Section 3 is unclear, e.g., “after duplicating based on iCloud link…” — what is duplicated and why is unclear (Reviewer 2).
- Evaluation scope is limited: only assesses action selection and parameter filling against ground‑truth sequences, not end‑to‑end task success rate (as done in AppWorld). Linking these two aspects is missing (Reviewer 3).
- No human performance (upper bound) reference is provided; given the synthetic task generation, it is uncertain whether all tasks are truly solvable or how hard the benchmark actually is (Reviewer 3).
- The paper does not evaluate GPT‑4o’s structured output capability (OpenAI’s “Structured Outputs” feature), which could affect parameter‑filling performance (Reviewer 4).
- No comparison with other agent frameworks beyond ReACT (e.g., CodeAct); all tested agents use ReACT, so generalizability to other architectures is unknown (Reviewer 2).
- Missing comparisons with specialized agent models such as AgentLM (70B) and xLAM (8x7B or 8x22B); such models might yield different insights (Reviewer 1).
- The source of numbers in Table 1 is unclear: e.g., whether Qwen‑2.5‑7B and LLaMA‑3‑8B consistently achieve >90% on ToolBench or >80% on ToolLLM, and how MetaTool’s metrics were verified given missing code/details (Reviewer 1).
- Paper uses emotional language (“We made great efforts to evaluate…”) that appeals to emotion rather than stating scientific value (Reviewer 4).
- Several references are outdated (e.g., ToolLLM cited as arXiv although already published at a conference) and excessive repetitive citations affect readability (Reviewers 2, 4).
- One reviewer (score 6, confidence 2) argues the work is a technical report lacking scientific hypothesis or contribution beyond engineering, and suggests it belongs to software engineering venues (ICSE, ASE) or dataset benchmarks tracks, not ICLR. This reviewer notes >2/3 of references are web pages rather than scientific studies (Reviewer 4).
- Reviewer 3 asks for quantitative details on dataset construction time and manual effort to assess scalability; Reviewer 2 asks why all tested agents are ReACT‑based. These questions overlap with missing experiments/ablations and are listed here as weaknesses.
