## Merged Review

### Summary
The paper introduces CoLM (Coresets for Training LLMs), a memory-efficient training method that constructs small mini-batch coresets approximating the gradient of larger batches. CoLM addresses three challenges in LLM training: imbalanced data sources by including all examples from small sources, Adam optimizer compatibility via historical gradient normalization, and high gradient dimensionality through zeroth-order gradient estimation and sparsification. Empirical evaluation on fine-tuning Phi-2, Phi-3, and Zephyr (main tables report Phi-2) with LoRA on MathInstruct and SuperGLUE shows 2x memory reduction while matching or outperforming 4x larger mini-batches.

### Strengths
1. **Clear motivation and well-structured paper** (R1,R2,R3,R4). The paper systematically frames the three key difficulties of applying coreset methods to LLMs, making the presentation easy to follow.
2. **Innovative data-selection perspective** (R1). Unlike typical memory-efficient methods (e.g., gradient checkpointing), CoLM focuses on data selection and batch size reduction.
3. **Strong empirical performance** (R1,R3,R4). CoLM consistently outperforms baselines, often matching or surpassing full-batch training with 2x to 4x larger mini-batches.
4. **Thorough ablations** (R3,R4). The authors validate each proposed component’s importance (e.g., small-source inclusion, Adam normalization, zeroth-order estimation) with detailed ablation studies.
5. **Low memory overhead** (R3,R4). The method uses less memory than representative baselines (e.g., LoRA, full fine-tuning) while achieving competitive accuracy.

### Weaknesses
1. **High computational overhead** (R1,R2). Figure 2(b) shows CoLM doubles training time in some cases, whereas typical memory-efficient methods incur only 5–20% overhead. A memory vs. computational overhead vs. performance comparison with other methods is needed. (R3 notes overhead is “reasonable,” creating a minority opinion that the overhead may be justified.)
2. **Missing comparisons and settings**:
   - No explicit comparison to gradient accumulation + LoRA (R3). CoLM’s speed and memory advantage over this trivial baseline remain unquantified.
   - Main results (Tables 1 and 7) only report Phi-2; include Phi-3 and state-of-the-art models like LLaMA-3 8B/3.1 (R2).
   - No pre-training or continual pre-training experiments (R1). Activation memory could become dominant with very large batches.
   - No experiment with large vocabulary (e.g., 128k as in LLaMA-3) (R3).
3. **Insufficient memory and time quantification**:
   - No quantitative breakdown of memory cost for LoRA, other low-rank methods, and CoLM (R2,R3).
   - No wall-clock time vs. accuracy plot alongside training iteration vs. accuracy plots (R2). The convergence plot (Figure 3) does not include LoRA or perplexity/training loss over iterations (R2).
4. **Clarifications needed**:
   - **Handling small data sources**: Algorithm 1 suggests including all examples from small sources in the coreset. However, Figure 4 shows small sources can have >1000 examples, making full inclusion implausible when batch sizes are limited. Is there sampling or a representative subset selection? (R4)
   - **Boundary between small and large sources**: The paper uses average count as a cutoff, but this is not rigorously justified for skewed distributions. Clustering is mentioned as an alternative, but its sensitivity to algorithm choice and number of clusters is not explored (R4).
   - **Adam gradient normalization**: The novelty versus prior work [1] (renormalization with mini-batches) needs clearer distinction (R2).
   - **Low-dimensional gradient estimation (Section 4.2)**: How does this differ from Espace and Galore? Advantages over these existing methods should be articulated (R2).
   - **Hyperparameter sensitivity**: The number and size of small/large sources, and the cost of tuning these, is undeclared. Are hyperparameters sensitive to data structure? (R1,R4)
   - **Motivation clarity**:
     - Memory cost calculation: fine-tuning Phi-2 (2.7B parameters) with batch size 128 is claimed to require 44 GB, but model weights + optimizer states approximate 22 GB (R2).
     - Comparison to LoRA: LoRA reduces trainable parameters and speeds up training. CoLM has similar wall-clock time to full fine-tuning but is slower than LoRA; the motivation for using CoLM over LoRA needs clarification (R2).
5. **Title inconsistency**: Submission title differs from manuscript title (R2).
6. **Typo**: “to iteratively selecting small mini-batches” should be “to iteratively select” (R3).
