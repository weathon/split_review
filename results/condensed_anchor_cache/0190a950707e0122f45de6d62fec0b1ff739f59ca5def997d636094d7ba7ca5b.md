## Merged Review

### Summary

The paper proposes a GPU-accelerated implementation of Counterfactual Regret Minimization (CFR) by reformulating the algorithm as a sequence of dense and sparse matrix and vector operations, replacing recursive tree traversal. The approach leverages GPU parallelism at the cost of higher memory usage. Several reviewers note that the core idea of level-by-level computation and GPU acceleration has been explored in prior work (e.g., Reis thesis, Weng report, DeepStack), but the paper presents a specific matrix-operation formulation. Benchmarks against OpenSpiel (Python and C++) show substantial speedups, though the games tested are extremely small and include a perfect-information game (tic-tac-toe). The paper does not include exploitability results, does not compare with other performant CFR implementations (e.g., Cepheus), and does not address advanced CFR variants (CFR+, MCCFR, discounting). Concerns about wasted computation in deeper games, GPU unfriendliness due to sparse operations, and lack of memory-scaling analysis are raised.

### Strengths

- **Originality of reformulation**: The creative restructuring of CFR as matrix operations for GPU parallelization is novel and underexplored, representing a solid step toward using GPUs for game solving (R1, R2, R5).
- **Efficiency by avoiding recursion**: By eliminating recursive tree traversal, the design achieves substantial speed gains, especially as game size grows (R1, R4).
- **Thorough empirical evaluation against OpenSpiel**: Benchmarks are performed on a diverse set of games with varying complexity, comparing against both Python and C++ baselines (R1). 
- **Reported speedups**: R1 reports up to 352.5× faster than OpenSpiel’s Python and 22.2× faster than C++ (note: the abstract claims up to 401.2× and 203.6×; reviewer 3 also acknowledges the acceleration as significant). R4 notes the speedup grows with game size, and open-source code is provided (R4).
- **Clear presentation**: The paper is well-written with clearly defined notations, and the code is made available (R4).
- **Interesting dual motivation**: Attempting to represent CFR via a GraphBLAS-like semiring approach and to bring GPU acceleration to game solving beyond neural-network calls (R2).

### Weaknesses

- **Limited novelty and insufficient contextualisation**:
  - Several reviewers note this is not the first GPU implementation of CFR; prior work (Reis thesis, Weng report, DeepStack) uses similar level-by-level parallelization, yet the paper does not compare or discuss these works (R4). This undermines the claim of originality.
  - The approach covers only vanilla CFR, not modern variants like CFR+, MCCFR, or discounting techniques, which significantly limits its applicability to state-of-the-art game solving (R1). The paper does not explain how matrix operations would handle dynamic per-node regret adjustments or sampling-based trajectories (R1).
  - R3 and R5 describe the work as engineering-driven with little new algorithm/methodology/theory; R3 suggests it might be more suitable for a systems venue than ICLR.

- **Benchmark and baseline concerns**:
  - OpenSpiel is designed for generality, not performance; comparisons with more efficient CFR implementations (e.g., Cepheus for Leduc, other codebases) are missing (R2, R5). It is also unclear whether OpenSpiel’s implementation is parallelized (R5).
  - The tested games are extremely tiny: the largest (tic-tac-toe) takes under 3 seconds in pure Python and is a perfect-information game (R2). The inclusion of a perfect-information game is questionable (R2). The benchmarks do not inspire confidence in scalability to larger, complex games.
  - R5 questions the source of the performance benefit and R2 notes that batched updates become wasteful as depth increases: with a branching factor of 10, at depth 5 ten times more nodes are updated than needed, suggesting speedups may diminish in deeper games.

- **Missing evaluations and metrics**:
  - No exploitability results are provided, which is a standard convergence metric for CFR; their absence makes it difficult to assess the algorithm’s effectiveness relative to existing implementations (R2).
  - No error bars are shown on time measurements (R2).
  - Tree setup time is not reported (R2).
  - The float precision used (32- vs 64-bit) and whether tensor cores were enabled is not stated (R2).
  - R1 notes no threshold for when the GPU approach becomes advantageous over CPU, and no analysis of CPU-GPU data-transfer overhead.
  - R4 asks for the space complexity of the method.

- **High memory usage and limited analysis**:
  - The matrix-based reformulation leads to high memory consumption, especially for larger games, but the paper does not thoroughly analyse memory scaling (e.g., wrt number of game states or branching factor) nor explore mitigating techniques like sparse matrix representations or memory-mapping (R1).
  - R5 challenges the claimed memory–computation trade-off, arguing that storing matrices in sparse format should not incur extra memory; an explanation is lacking.

- **GPU unfriendliness and wasted computation**:
  - The heavy reliance on sparse matrix operations may cause significant thread divergence on GPUs, wasting FLOPS; no profiling is provided to identify bottlenecks (R2).
  - The computational pattern (batched masked updates) becomes increasingly inefficient with game depth (R2).

- **Inflexibility and implementation difficulty**:
  - Modifying the algorithm (e.g., switching from simultaneous to alternating CFR) appears extremely expensive and cumbersome (R2, referencing line 515). R1 and R2 also note that integrating sampling or discounting would require major effort.
  - Pruning the tree is also expensive (R2).

- **Claims unsupported by evidence**:
  - The statement that the approach is “easier (and likely more efficient) to be run on supercomputers” is not backed by any experiment or analysis (R2).

- **Presentation and correctness issues**:
  - The abstract is repeated in the introduction (R2).
  - “GPU” is defined twice (R2).
  - The nature player is assigned information sets, which is nonstandard and philosophically questionable (R2).
  - Notation is sometimes inflated (e.g., “\(l\in [1,D]\cap \mathbf{Z}\)”) (R2).
  - The Hadamard product is used without definition (R2).
  - The purpose of Figure 1 is unclear (R2).
  - The reported number of infosets for liars_dice (24583) appears wrong; should be 24576 or 12288 without single-action infosets (R2).
  - Minor suggestions: add a symbol table, an example figure, and keep symbol descriptions consistent with CFR literature (e.g., \(I\) for infoset, \(h\) for history) (R4).

- **Narrow applicability**:
  - The GPU implementation is unsuitable for small games, where CPU may be faster due to overhead, limiting its practical scope (R1). R3 also notes the selected games (OpenSpiel) are less known and suggests showing improvements on more common benchmarks.
