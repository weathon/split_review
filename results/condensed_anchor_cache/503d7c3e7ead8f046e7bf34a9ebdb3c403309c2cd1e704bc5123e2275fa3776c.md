## Merged Review

### Summary

This paper identifies and evaluates insider and outsider threats in LLM-integrated applications (e.g., an online shopping chatbot using GPT-3.5/4) that can bypass OpenAI’s safeguards to inject bias, toxicity, privacy risks, and disinformation. The authors define four key properties (integrity, source identification, attack detectability, utility preservation) and propose a lightweight defense called Shield that combines cryptographic signing/verification (RSA-based) with LLM-based detection to mitigate both threat types. Experiments show Shield detects attacks while preserving utility. Two reviewers rated the paper 6, while two rated it 3 – a clear minority strongly criticizes novelty, writing quality, and defense clarity.

### Strengths

- Addresses an important and timely problem as LLM-integrated applications rapidly expand; results are valuable for building secure applications and for industry practitioners unaware of these risks. (R1, R2, R4)
- Provides extensive experimental results across multiple vulnerability types (bias, toxicity, privacy, disinformation) using GPT-3.5 and GPT-4. (R1)
- Clearly characterizes four key properties (integrity, source identification, attack detectability, utility preservation) that can guide solution development. (R1)
- The threat model is well articulated: focuses on insider (malicious developer) and outsider (database manipulation) threats that bypass OpenAI’s restrictions, distinct from typical LLM risks like hallucination. (R2)
- Shield is a simple, novel, and industry-adoptable defense that uses cryptographic signing/verification and LLM-based detection to guard against upstream/downstream manipulation. (R2)
- The service scheme of LLM-integrated applications (Figure 1) is clearly presented. (R4)

### Weaknesses

- Novelty vs. existing prompt injection attacks is unclear; the analysis and results are already widely known in the community. (R1, R3) – *One minority reviewer (R3) is absolutely certain that the paper contributes little new.* (Confidence 5)
- The paper is poorly written and extremely difficult to follow: the problem setting and attack surfaces are not well-defined, and the defense mechanism is not explained until the end. (R3)
- Shield’s dependence on the LLM’s own capability to detect maliciousness is not evaluated; results from different LLMs would provide insight into this dependency and overall effectiveness. (R1)
- When an attack is detected and the response from the user’s raw query is returned, there may be degradation in response quality compared to using the application’s refined prompt – this is not evaluated. (R1)
- Shield requires an additional prompt per user query, increasing cost per query; cost analysis is only in the supplementary material, not the main paper. (R1, R2)
- The defense method does not involve ML/DL and uses only cryptographic techniques (RSA); scientific contribution beyond the detection strategy is limited. (R2)
- The evaluation lacks real-world case analysis – only a generic online shopping chatbot is considered without detailed information; multiple real-world applications should be included. (R4)
- Sending user messages directly to the LLM (as part of Shield) may break the business model of the application (Figure 1) and could increase the attack surface rather than reduce it; it is unclear how this prevents the described threats. (R4)
- It is not clear what Shield actually verifies: the description suggests only signature verification (confirming the message originates from the user) without semantic analysis. However, the threat model (Figure 4) shows an attacker manipulating the system prompt (not the user’s message); how signature verification addresses such manipulations is not explained. (R4)
- It remains unclear how generic the proposed threat evaluation and defense are for other application domains (e.g., legal chatbots). (R2)
- No comparison to existing defenses for LLM-integrated applications is provided. (R3)
