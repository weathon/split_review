## Merged Review

### Summary
This paper proposes AgentBench, a benchmark of 8 distinct environments (3 categories) to evaluate LLMs as agents in multi-turn interactive tasks. The authors evaluate 27 API-based and open-source LLMs, finding that top commercial models significantly outperform open-source ones, and that poor long-term reasoning, decision-making, and instruction following are key failure modes.

### Strengths
- The benchmark is comprehensive and multi-dimensional, covering 8 environments in 3 categories (code, game, web) with a well-designed HTTP evaluation interface. [Reviewer 2, 3, 4]
- Extensive evaluation over 27 LLMs (both API-based and open-source) provides a useful reference for LLM development. [Reviewer 2, 4, 5]
- The work is timely and significant given the growing need to benchmark LLMs as agents in interactive environments. [Reviewer 5, 3]
- The authors release the code, datasets, and an integrated evaluation package, enabling easy reproducibility and addition of new agents. [Reviewer 4]
- A weighting scheme is provided for each environment to enable fair comparison across tasks. [Reviewer 4]
- The analysis identifies useful insights (e.g., code and multi-turn alignment data improve agent performance). [Reviewer 4]
- The paper is well-written and easy to follow. [Reviewer 2]
- One reviewer (3) highlights that this is a unique type of benchmark with profound implications for LLM-as-agent research.

### Weaknesses
- **Limited novelty and technical insight**: The paper applies existing LLMs to pre-existing environments without introducing new technical methods or insights. [Reviewer 1] Conclusions (e.g., “code training helps”) are already well-known, and the overall trend is simply that more capable LLMs perform better. [Reviewer 1] The analysis does not offer actionable guidance for improvement (e.g., if a model fails on web-browsing, what should one do?). [Reviewer 3]
- **Prompt fairness and leakage**: The same prompt is used for all models, which may give an unfair advantage to the model for which the prompt was optimized. [Reviewer 2] Data leakage from internet pretraining is possible for tasks from existing datasets. [Reviewer 2]
- **Dataset generation bias**: Many datasets were generated using LLMs, including GPT-3.5-turbo for database tasks; GPT-3.5-turbo outperforms GPT-4 on that exact task, raising possible correlation. [Reviewer 5]
- **Claims about OSS vs closed-source overreached**: The claim that open-source LLMs fall behind closed-source ones is unfair because the authors only considered OSS models with ≤70B parameters. [Reviewer 5]
- **Task selection and quantification issues**: Task complexity is not objectively quantified (e.g., computational complexity, filesystem size). The scoring depends on current LLM abilities rather than an intrinsic hardness measure. [Reviewer 5] The tasks are mostly coding-based, so non-coding LLMs that could still be good agents will underperform. [Reviewer 3] Embodied tasks (especially AlfWorld) are contrived: AlfWorld drops all 2D/3D aspects and can be mastered by a fine-tuned GPT-2 [1]. [Reviewer 3]
- **Missing important related work**: DB task references are outdated (2017/2017/2021); recent multi-turn SQL approaches (DIN-SQL, DIAL-SQL, TPTU) are not cited. [Reviewer 4] The related work omits multiagent reasoning approaches (e.g., multiagent debate), and some citations are misattributed (e.g., Reed et al. 2022 does not use an LLM for embodied policy; Ahn et al. 2022 uses a real robot, not a simulator). [Reviewer 1]
- **Lack of task-specific fine-tuning and ablation**: No experiments with few-shot demonstrations or fine-tuning per domain. [Reviewer 1, 5] The paper does not discuss sensitivity to prompts or how they were chosen. [Reviewer 1] Prompt omission is surprising: for fully observable cases, a summarized state might be more appropriate than full history. [Reviewer 5]
- **Clarity and presentation issues**: Numerous typos and malformed sentences throughout. [Reviewer 5] Abbreviations (e.g., OS, DB, KG, DCG, LTP, HH, WS, WB) are not explained, making tables hard to read. [Reviewer 3] Figure (a) is not color-blind friendly. [Reviewer 3] Technical terms (“incompleteness,” “turn-taking”) are used imprecisely or outside their standard meanings. [Reviewer 5]
- **Specific questions and missing details**:
  - How is success rate calculated for runs that failed to complete? [Reviewer 2]
  - Which model does Table 4 correspond to? [Reviewer 2]
  - Is there a human expert score for these benchmarks? [Reviewer 3]
  - Why is there no benchmark for multiagent interaction between LLMs? [Reviewer 1]
  - How was the set of tasks chosen to comprehensively evaluate LLM-as-agent abilities? [Reviewer 1]
  - For the DB task, the paper claims few previous code evaluation frameworks consider multi-turn interactions, but DIAL-SQL and TPTU are both multi-turn. [Reviewer 4]

**Note on disagreement**: Two reviewers (1 and 5) are critical of the contribution and soundness (scores 3 and 6, soundness 2/2 and 2/4, contribution 2/2). Two reviewers (2 and 4) are very positive (scores 8,8), and reviewer 3 (score 6) is moderately positive but notes minor issues. The above weaknesses reflect the full spectrum of concerns.
