## Merged Review

### Summary
OmniKV reduces GPU memory usage for long-context LLM inference by exploiting observed similarity of important tokens across consecutive layers. It is a token-dropping-free, training-free method that offloads most KV cache to CPU and loads only important tokens per layer, achieving up to 75% GPU memory reduction and up to 1.87× speedup over a pipeline baseline, while preserving downstream accuracy on LongBench and InfiniteBench. The method extends Llama-3-8B’s maximum context on a single A100 from 128K to 450K.

### Strengths
- Addresses the timely and important problem of KV cache memory pressure during long-context LLM inference (Reviewers 1, 4).
- Simple yet effective core idea: cross-layer similarity of important tokens enables merging the CPU–GPU loading procedure for multiple layers, reducing memory transaction and identification overhead (Reviewers 1, 4).
- Preserves full context (no token dropping), reflected in strong needle-in-a-haystack and LongBench results (Reviewers 3, 4).
- Achieves better model quality preservation per speedup than other methods in this class (Reviewer 3).
- Evaluations include 70B-scale models and show impressive decoding speed (Reviewer 2). OmniKV can handle a 450K context with 7.52 tokens/s on a single A100 (Reviewer 4, from the abstract).
- Real performance gain shown with real workloads, not just synthetic benchmarks (Reviewer 1).

### Weaknesses
- No mathematical guarantee that the method is universally applicable to all LLMs; generalizability to larger models (e.g., Llama 3.1 405B) is unclear without intuition or guarantee (Reviewer 1; confidence 2, more positive but still raises this concern).
- The method introduces hyperparameters (filter layers) whose tuning is non-trivial; guidance is lacking (Reviewer 1).
- **Missing baselines:** Comparisons are needed with other dynamic KV selection methods such as Quest and Loki, and with static selection methods like H2O that also save total memory without CPU offloading (Reviewer 2). The only dynamic KV baseline shown is InfLLM, which is primarily designed for context extension (Reviewer 2). Comparison with MInference 1.0 (prefill acceleration) for both speed and quality preservation is also requested (Reviewer 3).
- The decoding speed baseline (dense) appears weak. For Llama-3-8B on A100 with sequence length 128K and batch size 1, TensorRT-LLM and vLLM take <20ms per token, but the paper’s dense baseline takes ~80ms (Figure 4). This raises concerns about the fairness of speed comparisons (Reviewer 4; soundness 2).
- OmniKV only accelerates the decoding phase; prefilling speed is not improved (Reviewer 4).
- In Figure 4, OmniKV with offloading is slower than the dense baseline until 128K context; even without offloading it lags behind the dense baseline for sequences <32K (Reviewer 4).
- **Serving compatibility issues:** The memory manipulation does not appear compatible with fundamental serving mechanisms like continuous batching and prefix caching, making real-world deployment questionable (Reviewer 3). Comparison with vLLM/SGLang using FlashInfer/FlashAttention backend for throughput and latency is needed, as well as compatibility with frameworks like vLLM (Reviewer 3).
- The method’s integration with tensor parallel (TP), pipeline parallel (PP), and context parallel (CP) – all essential in production – is unclear. Benchmarks for TP=4,8 on <10B models and TP=8,PP=4 on 70B models are requested, with latency/throughput for prompt lengths 128K, 256K, 512K (possibly needing context parallel) and output length 512, plus quality tests on needle-in-a-haystack at those contexts (Reviewer 3).
- The claimed 1.87× speedup over “original model running on three A100 GPUs in pipeline” is questioned: (a) inference-time pipeline parallelism within a single node is uncommon; a tensor-parallelism baseline should be provided (Reviewer 2). (b) The same reviewer asks what the latency would be with tensor parallelism instead of pipeline parallelism (Reviewer 4).
- **Novelty concern:** The idea of cross-layer KV cache selection similarity was introduced by InfiniGen; the paper lacks proper discussion of this prior work (Reviewer 2; contribution 2). Reviewer 2 stated they would raise their score if this is addressed.
- Reviewers 2, 3, and 4 express lower confidence in contribution (2/3) compared to Reviewer 1’s more positive assessment (contribution 3). Reviewer 4 rates soundness as 2, below the others (3).
