## Merged Review

### Summary
The paper introduces Coeditor, a CodeT5-based model fine-tuned for code auto-editing. It uses line-diff encoding of changes, block-sparse attention to extend context to 8K tokens, and static analysis to include relevant reference blocks (e.g. function signatures) from the codebase. A new dataset, PyCommits, is collected from 1650 open-source Python projects. In a single-round single-edit task, Coeditor (220M params) achieves 60.4% exact match accuracy, outperforming GPT-3.5 (text-davinci-003, 30.5%) and other general-purpose code infilling models. Multi-round iterative editing yields further improvements. Code, dataset, model weights, and a VSCode extension are open-sourced.

### Strengths
- **Contribution of a new dataset (PyCommits) and open-sourced resources** (code, model, VSCode extension) that facilitate future research on code editing (Reviewers 1,2,3).
- **Perspective shift to modeling edits** rather than code completion; a relatively small (220M) fine-tuned model beats far larger general-purpose models, demonstrating the value of task specialization (Reviewers 1,3,4).
- **Effective use of reference blocks and sparse attention** to handle long contexts; the “replace” performance is particularly promising (Reviewer 4).
- **Multi-round editing setting** shows substantial gains by conditioning on prior user edits, which is a realistic and practical workflow (Reviewers 2,3).
- **Writing quality is good** – clear and easy to follow, with minor grammar issues noted (Reviewers 1,4).

### Weaknesses
- **Unfair evaluation against baseline models.** Coeditor is fine-tuned and specialized for the edit task, while baselines (InCoder, StarCoder, text-davinci-003) are general-purpose; the prompting strategy used for these baselines is not clearly described, making it impossible to judge whether the comparison is equitable. Statements like “60.4% vs 30.5%” are misleading (Reviewers 1,4). One reviewer (R4) emphasizes that baselines were likely not given the same reference blocks or signature information, which are critical to Coeditor’s performance.
- **Impact of signature information (static analysis) is large but conceptually separate from the diff-based contribution.** Table 5 shows a substantial performance drop when signatures are removed, yet this technique is not part of the core “using diffs” idea and was not provided to baselines. This weakens the paper’s novelty and raises the question of how much of the gain is due to simple project-level context rather than edit history (Reviewers 3,4).
- **Large unexplained gap between Table 5 (42.1%) and Table 3 (60.4%).** Table 5 results are only halfway trained and on a validation set; the gap is suspicious and the relationship between these evaluations is unclear. Ablation effects might scale differently at full training (Reviewer 4).
- **Lack of diverse baselines.** The evaluation includes only large language models for code. No specialized code-editing models or tools (e.g., CodePlan, BluePencil) are compared, and multi-round results (Table 4) lack any baseline comparison (Reviewers 2,4). The PIE benchmark is suggested as another relevant test (Reviewer 1).
- **Manual edit-region selection limits automation.** Coeditor requires users to manually pinpoint the code region to edit, reducing its applicability for tasks such as automated refactoring (Reviewer 2).
- **Dataset bias from commit granularity.** The dataset is built from git commits, which may squash multiple intermediate changes, and edits can be overwritten; this introduces potential bias (Reviewer 3).
- **Delta/diff encoding is underexplored.** The paper does not investigate more granular edit events (e.g., IDE keystrokes, navigation events) that could provide richer side-channel information. The trade-off between context size and other factors is not fully analyzed (Reviewer 3).
- **Training details.** The model is trained with batch size 1 without gradient accumulation, which may be suboptimal for the 220M-parameter model on a 48GB GPU (Reviewers 1,4). It is also unclear whether the PyCommits projects all have permissive licenses (Reviewer 1).
- **Missing ablations with baselines.** Could signature information be exposed to pretrained models via prompting? Could a decoder-only LM or instruction-finetuned model be used for this task? The paper does not address these alternatives (Reviewers 1,4).
