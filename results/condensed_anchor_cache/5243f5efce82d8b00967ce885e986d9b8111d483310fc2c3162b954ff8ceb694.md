## Merged Review

### Summary
This paper proposes a neuro-symbolic pipeline (Sketch-Plan-Generalize, SPG) for learning inductive program representations of spatial concepts (e.g., staircase as a composition of towers) from a few demonstrations. The pipeline uses an LLM to generate a coarse function signature from language (Sketch), an MCTS planner grounded by a reactive policy to search over action sequences using available concepts and primitives (Plan), and the LLM to abstract the found plan into a reusable Python program (Generalize). Experiments in a simulated block-building environment show that SPG generalizes better than an end-to-end neural planner (StructDiffusion) and zero-shot LLM/VLM code generation on tasks testing induction, composition, and robustness to label change. Two reviewers (R1, R4) gave a score of 5, appreciating the originality of the inductive problem framing and the overall pipeline. Two reviewers (R2, R3) gave 3, raising major concerns about method clarity, evaluation narrowness, and reproducibility.

### Strengths
- **Originality of inductive concept learning**: The problem of learning inductive (recursive/compositional) spatial concepts from few demonstrations is timely and important. The paper takes a programmatic approach that differs from purely neural or LLM-only methods. (R1, R3, R4)
- **Formal problem representation**: Equation (1) providing a recursive decomposition (Induction ∘ Composition ∘ Base) is a useful conceptual compression. (R1)
- **Effective use of LLMs**: Using GPT-4 for natural language parsing and final code generation is well justified. (R1, R4)
- **Planning step with MCTS**: Generating action sequences for the LLM to abstract into a program has not been proposed before, to the best of the reviewers’ knowledge. (R2)
- **Relevant ablations**: The paper justifies the use of MCTS over an LLM planner, and ablates MCTS variants (concept library, pruning) in Figure 5. (R1)
- **Robustness to concept naming**: Dataset II (e.g., tower → rewot) shows clear advantage of SPG over zero-shot code generation (Table 3). This demonstrates that the method benefits from not relying on pre‑trained name knowledge. (R3)
- **Clarity of presentation**: Sections 1–3 clearly outline the problem and the gist of the method. Figure 2 and Supplementary Figure 12 are helpful. (R1, R4)
- **Potential for program synthesis**: The pipeline is generic and could be of interest to the learning community, especially for neuro-symbolic program synthesis. (R4)

### Weaknesses
- **Novelty and contribution placement**: The paper does not make its scientific contribution explicit relative to prior work (e.g., Code as Policies [Liang et al.], LILO [Grand et al.], Hypothesis Search [Wang et al.], Learning Planning Abstractions [Liu et al.]). Many components are existing; the authors should highlight what is new. (R1, R2, R4)
- **Unclear method details, especially the Sketch module**:
  * “Visual grounding module akin to” several papers – which one is actually used? What is the underlying pre-trained model (LLM or VLM)? What is a “quasi‑symbolic executor”? (R2)
  * The visual extractor is ResNet‑34; it is pre‑trained on some dataset and implies that the concept set is known in advance, severely limiting extension to unseen concepts. (R2)
  * “Disentangled representations” are claimed but not demonstrated – how are vector features associated with textual names? (R2)
  * The generalisation step’s prompt (Appendix, Listing 8) largely contains the correct answer and expected structure, making the LLM’s role trivial. (R2)
- **MCTS and action space**: Is the action space discrete? If continuous, how does MCTS handle it? If discrete, what discretisation and how large is the search space? (R2) The reactive policy used for primitive action pruning seems to limit search aggressively – would a simpler tree search without reward suffice? (R2) MCTS assumes a forward model exists; this should be stated up front. (R4)
- **What is learnable?**: The paper introduces parameters θ_S, θ_P, θ_G but does not specify which are actually trained. θ_P likely refers to MCTS counters/value function or the reactive policy (pre‑trained). θ_G is GPT‑4 (pre‑trained). θ_S is never defined. The formalization (Eq. 2) uses a Loss function (undefined) and an Exec function (undefined); the notation η_θ is undefined. (R2, R4)
- **Limited evaluation and narrow scope**:
  * The environment is custom (blocks and dices) and not a standard benchmark. No citation for the simulator; it is not open‑sourced. (R1, R3)
  * The task set is small (row, tower, staircase, etc.) and the method may not scale to more complex structures (e.g., 50 blocks, multiple control variables like a rectangle with height and width, composite objects). (R1, R4)
  * Important assumption: “there is only one unknown concept” (Appendix line 917) is not in the main text. (R4)
  * The curriculum used for all baselines is not clarified – were baselines exposed to the same sequence of tasks? (R1)
- **Missing baseline**: A GPT‑4 code generator that receives (1) task language, (2) visual grounding functions, (3) action primitives, and (4) the previously generated code in a curriculum (similar to Code as Policies) should be included. This would directly test whether MCTS+inductive programming is necessary. (R1)
- **Physical grounding claim not justified**: The paper claims physical grounding, but uses an oracle simulator and assumes primitive actions (“place object”, “move head”) are available off‑the‑shelf. It is unclear which components are learned from data vs. given. (R1, R2)
- **Reproducibility concerns**: No reproducibility statement. Insufficient details to replicate the evaluation protocol. No simulator source or release. (R3)
- **Language and presentation issues**: The writing has grammatical errors and convoluted sentences (e.g., page 5, Section 5). Many important details are relegated to the appendix; there are too many cross‑references. Notation inconsistency: **H** vs. **\mathcal{H}** in Figure 2. (R1, R2, R3)
- **Questions that overlap with weaknesses**:
  * “Do the authors use any off‑the‑shelf approach in the Sketch phase?” (R2)
  * “How sensitive is the mIoU metric to the demonstration representations?” (R3)
  * “Can the system handle composite inductive steps (e.g., five objects each of two cubes on a long block) or multiple control variables?” (R4)
  * “How is the reactive policy pruning not overly restrictive?” (R4)
  * “The ‘size’ parameter – could it refer to non‑physical sizes?” (R4)
- **Reviewer disagreement**: R1 and R4 (scores 5) found the pipeline novel and clearly presented despite these weaknesses; R2 and R3 (3) considered the method insufficiently described and the evaluation too narrow to support the claims.
