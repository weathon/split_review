## Merged Review

### Summary
The paper introduces AFlow, an automated framework that reformulates agentic workflow optimization as a Monte Carlo Tree Search (MCTS) problem over code-represented workflows. Workflows consist of LLM-invoking nodes connected by edges representing logic and dependencies. AFlow iteratively refines workflows using code modification, tree-structured experience, and execution feedback. Evaluated on six benchmarks (HumanEval, MBPP, MATH, GSM8K, HotPotQA, DRO), it achieves a 5.7% average improvement over state-of-the-art baselines and enables smaller models to outperform GPT-4o on specific tasks at 4.55% of its inference cost in dollars. The work aims to reduce human intervention in workflow design and provides a unified framework for future research.

### Strengths
- **Novel approach**: Integrates MCTS with code-represented workflows, reducing reliance on manual design and enabling efficient workflow discovery (Reviewers 1,2,4).
- **Comprehensive problem formulation**: Formalizes workflow optimization with a general mathematical framework that unifies prior approaches and establishes a foundational structure for future research (Reviewers 2,4).
- **Detailed critique of prior work**: Provides insightful analysis of existing methods, particularly identifying limitations of ADAS in information accumulation and search efficiency (Reviewer 2).
- **Strong empirical validation**: Rigorous evaluation across six diverse benchmark datasets with quantitative comparisons to multiple baselines, ablation studies on operators, and cost analysis (Reviewers 1,2,4). AFlow yields a 5.7% average improvement over SOTA (Reviewer 4).
- **Cost-performance Pareto improvement**: AFlow enables smaller, cheaper models to reach or surpass the performance of larger models (e.g., outperforming GPT-4o at 4.55% of its inference cost), which is significant for real-world applications (Reviewers 1,3,4). One reviewer specifically notes this lifts the cost/accuracy Pareto front (Reviewer 3).
- **Clarity and documentation**: Several reviewers find the paper well-organized with clear descriptions of the MCTS algorithm, node selection strategy, and LLM-driven node expansion, as well as detailed experimental setup and results (Reviewers 1,4). One reviewer notes the paper is logically rigorous (Reviewer 4).
- **Originality and significance**: Pioneers a new definition of workflow optimization as an MCTS search problem, providing a unified framework for future research and making up for shortcomings of previous approaches (Reviewer 4).

### Weaknesses
- **Lack of precision in methodology description (minority concern)**: One reviewer finds the presentation lacks precision and is at times handwavy, with specific confusions:
  - Unclear distinction between the tree structure of MCTS and the graph structure of the workflow search space; many parts do not specify which graph is being discussed (Reviewer 3).
  - The exact definition of the search space is unclear: what it means to have an edge between two nodes (sequential execution? decision point? parallel execution?), how output from one LLM invocation is passed to later nodes, and whether there is a root node (Reviewer 3).
  - The paper defines workflow as "a sequence of LLM-invoking nodes" but later discusses graphs with branching, loops, and parallel relations; terminology seems inconsistent (Reviewer 3).
  - Figure 2 is a DAG but the paper claims it can represent both sequential and parallel relationships; richer representations (e.g., workflow nets, BPMN) are typically required (Reviewer 3).
  - Claim that code offers "most precise control" is questioned, as other Turing-complete representations exist (e.g., Petri nets) (Reviewer 3).
  - Equation 2 passes three arguments to AFlow while Algorithm 1 takes five; the procedure is not well-specified (Reviewer 3).
  - What happens with an empty Operator Set is undefined (Reviewer 3).
  - Why the initial node is distinct from the root node in MCTS is unclear (Reviewer 3).
  - During expansion, it is not clear if the LLM generates new workflow code only or also modifies node contents (prompt, model, output format) (Reviewer 3).
  - This reviewer (score 6) contrasts with others who found clarity good (scores 8,8,8) (Reviewers 1,2,4).
- **Limited scope and generalizability**: The framework is demonstrated only on benchmark tasks with clear success metrics. There is limited discussion on applicability to open-ended or creative tasks (e.g., document generation, creative writing) where success criteria are not well-defined. The current prompts appear tailored to test-taking scenarios and may lack flexibility for exploratory outputs (Reviewer 2). One reviewer also questions whether the benchmark selection (six datasets) fully represents agent workflow optimization capability and would like more rationale (Reviewer 1).
- **Missing theoretical analysis**: The paper lacks theoretical analysis on convergence of the MCTS optimization process, completeness of the search space, and performance bounds, which are important for understanding robustness and scalability (Reviewer 2).
- **Insufficient implementation details for reproducibility**: The paper lacks sufficient detail on prompt handling, tool calling, and how workflows evolve with execution feedback. Specific examples of workflow changes during optimization and consistency maintenance across components would improve reproducibility (Reviewer 2). One reviewer asks for clearer examples of workflow evolution and how feedback informs changes in node structure, prompt design, or operator selection (Reviewer 2).
- **Limited comparative analysis**: The treatment of DSPy is brief, and Tree of Thoughts is only briefly mentioned despite its relevance. A more detailed comparison with these approaches would clarify AFlow's unique contributions and limitations (Reviewer 2). One reviewer also asks how AFlow's MCTS-based approach compares to DSPy's instruction optimization or ToT in handling complex, multi-stage tasks (Reviewer 2).
- **Missing cost analysis of the exploration phase**: The cost analysis in the paper shows the effectiveness and low consumption of the final workflow, but the early MCTS search stage is a huge process that consumes resources. This part is not experimentally accounted for. If the exploration cost is significant, the cost discussion should include it (Reviewer 4).
- **Insufficient experiments on model-specific workflow optimization**: The paper asserts that different language models require different workflows for optimal performance, but only provides one comparison (workflow found using DeepSeek-V2.5 performs notably weaker on GPT-4o-mini compared to the workflow found using GPT-4o-mini itself). At least one more comparative experiment is needed (e.g., generate a workflow via GPT-4o-mini then test on both GPT-4o-mini and DeepSeek-V2.5). Ideally, more model types (e.g., Llama series) should be compared (Reviewer 4).
- **Missing discussion on parameter choices and effects**: The paper fixes parameters such as model choice, temperature, and output format to reduce search space, but does not discuss the potential effect of these parameters on performance (Reviewer 1). MCTS parameters (e.g., λ=0.4 for balancing exploration vs. exploitation) are only mentioned in the appendix; key parameter values and rationale should be in the main paper (Reviewer 1). The reasoning for choosing specific models for executor vs. optimizer roles is not provided (Reviewer 1).
- **Questions about workflow representation and search space**: A reviewer asks how AFlow maintains context and coherence in longer workflows or workflows requiring memory across stages (Reviewer 2). Another asks how the scope of the search space is defined and controlled, how consistent results are across multiple runs with the same model and task, and what methods introduce variability (Reviewer 4). One reviewer requests examples of optimized workflows with explanations (Reviewer 4).
