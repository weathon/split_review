## Merged Review

### Summary
The paper proposes Tool Decoding, a training-free approach that enhances LLM tool-use by integrating constrained decoding (for format correctness, eliminating hallucinations) and order consistency (structured sampling with majority voting for parameter accuracy). Evaluated on API-Bank and BFCL V2 • Live across >10 models, it reports performance gains >70% for nearly all models; several 7B models surpass GPT-3.5 and two exceed GPT-4. The approach is plug-and-play and requires only API documentation.

### Strengths
- **Training‑free plug‑and‑play method**: No additional training is needed; easy integration into existing inference pipelines (R1, R2, R3, R4).
- **Significant accuracy gains**: Constrained decoding and order consistency substantially improve tool‑use accuracy over greedy/beam search baselines; gains >70% on both benchmarks for most models (R1, R2, R4).
- **Strong results against proprietary models**: Several 7B open‑weight models with Tool Decoding outperform GPT-3.5, and two exceed GPT-4 on key tasks (R1, R2).
- **Well‑structured error analysis**: Breakdown of errors into tool awareness, selection, and call stages across models, helping identify bottlenecks (R2, R4). The analysis uses the API-Bank and BFCL V2 • Live datasets appropriate for tool‑augmented LLMs (R2).
- **Compelling order‑consistency idea**: Generating multiple candidate parameter values by varying argument order and using majority voting is a novel and effective component (R4, R2).
- **Clear presentation**: Figures (e.g., constrained decoding workflow) effectively illustrate the method (R3).

### Weaknesses
- **Insufficient baseline comparisons**: Only greedy and beam search are compared. Many reviewers request comparisons with other existing methods: state‑tracked constrained decoding, reranking, in‑context learning, epsilon sampling, prompt engineering, and prior constrained‑decoding works such as those in [arXiv:2401.06201](https://arxiv.org/pdf/2401.06201), Domino, and TOOLDEC (R1, R2, R3, R4).  
  – A reviewer notes that novelty is limited because constrained decoding for tool calling has already been used in prior work (Domino, TOOLDEC); the primary novelty is order consistency, but Table 6 shows only a limited improvement from that component (R2).
- **Missing recent tool‑finetuned baselines**: More powerful and recent models like Hermes Function Calling and Gorilla are not included (R2). No technical reason is given for their omission (R2).
- **Latency / computational efficiency not reported**: The method involves structured sampling and majority voting, which likely increases latency. Reviewers request latency figures and a discussion of practical trade‑offs for real‑time use (R1, R3, R4).
- **Error analysis gaps**:  
  – Value errors *increase* in most scenarios after applying Tool Decoding; this trade‑off is not discussed as a limitation (R1).  
  – The analysis does not sufficiently acknowledge that similar error categorizations have been reported by prior work (e.g., API‑Bank paper, Section 7.3) (R1).  
  – No breakdown of success rate per stage (awareness, selection, tool call) with and without constrained decoding; it is unclear where the gains are most significant (R4).  
  – The change in awareness errors between configurations with and without Tool Decoding (Figure 6) is not explained (R4).  
  – Accuracy numbers for Gemma are missing from Figure 5 (R4).
- **Reporting choices**:  
  – Table 3 reports error reduction rather than absolute accuracy, making interpretation difficult; absolute accuracy would be more informative (R4).  
  – The statement in Section 2 that “tool call presents the greatest complexity, with even powerful models like Qwen1.5-72B achieving less than 60% accuracy” is misleading because the 32B model achieves ~70% accuracy; the wording should be rephrased (R4).
- **Limited model/task scope**:  
  – Models evaluated are mostly under 7B; discussion of larger models (30B, 70B) is limited, making it unclear whether the method scales (R3).  
  – The evaluation lacks stronger instruction‑tuned LLMs as base models (R4).  
  – Figure 2 uses UltraTool while Figure 3 uses API-Bank, but no reason for the choice is given (R4).  
  – It is unclear why the LLM generates optional parameters instead of supplying them directly (as is done with required parameters) (R4).  
  – The computation of accuracy is not explained in sufficient detail (R4).
