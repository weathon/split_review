## Merged Review

### Summary
The paper introduces SWE-bench Multimodal (SWE-bench M), an extension of SWE-bench that evaluates autonomous software engineering systems on fixing bugs in visual, user-facing JavaScript software. The benchmark contains 617–619 task instances from 17 JavaScript libraries (web UI, diagramming, visualization, syntax highlighting, mapping), each including at least one image in its problem statement or unit tests. Human validation shows 83.5% of tasks require images for resolution. The authors adapt three existing systems—SWE-agent, Agentless, and RAG (Moatless Tools)—to JavaScript and multimodal inputs. The best system (SWE-agent) resolves 12–12.2% of tasks; the next best achieves ~6%. The paper argues that current systems designed for Python struggle with cross-language generalization and visual reasoning.

### Strengths
- Introduces an important, forward-looking benchmark for multimodal autonomous software engineering, addressing a significant gap in existing evaluation.
- Thorough data collection and validation: extensive manual effort, human validation by three annotators, careful consideration of image necessity, licensing, and reproducibility.
- Diverse task instances (619 from 17 JS repositories) covering visual content types (UI fixes, diagram issues, map rendering bugs, etc.).
- Experimental comparison of existing models is thorough, clearly showing the benchmark remains challenging and unsolved.
- Reveals that more flexible, interaction-based systems (SWE-agent) outperform rigid, pipeline-based ones (Agentless) in multimodal settings.
- The dataset, adaptation methodology, and analysis provide a solid foundation for future research in this area.

### Weaknesses
- **Motivation and framing:** The paper claims SWE-bench M addresses Python-only limitation, but a truly “generalizable” benchmark should include multiple programming languages (Java, C++, Go), not just one new language (JavaScript). The incremental nature (SWE-bench was 0→1, this is 1→1.5) raises novelty concerns. Reviewers suggest the motivation should center on JavaScript’s dominant role in front-end development and its natural incorporation of visual elements, rather than positioning it as a language-coverage gap.
- **Inadequate baseline adaptation:** The adaptation of existing systems (Agentless, Moatless Tools) was oversimplified—merely swapping Python AST parsers for JavaScript parsers with no architectural changes to handle visual input. The low performance (e.g., Agentless 3.9% vs SWE-agent 11.5%) may reflect insufficient engineering effort rather than inherent limitations. The paper lacks documentation of failed adaptation attempts or rigorous attempts to strengthen baselines, undermining claims about generalization difficulties. Existing frameworks like HyperAgent (which handle multiple languages) are not referenced.
- **Missing comparisons:** Table 1 omits important related benchmarks (DevEval, CrossCodeEval, RepoExec). The paper does not compare model performance on multimodal issues vs. text-only issues within the same JavaScript repositories, nor does it compare against existing multimodal bug datasets (e.g., mobile app bug datasets). This limits assessment of image importance.
- **Unclear importance of visual data:** Performance drop when images are removed is only ~3% (Table 5), questioning whether visual elements are truly critical for these tasks. More rigorous ablation and analysis are needed.
- **Analysis of difficulty insufficient:** SWE-bench M is harder than SWE-bench Lite even on tasks that humans judged as not requiring images. The paper only attributes difficulty to multimodality; deeper analysis (e.g., root causes, localization complexity) is needed to inform the community.
- **Test quality and evaluation metrics:** The number of “Fail to Pass” test cases per task is limited (Figure 5, Table 9). Test augmentation or manual test writing could improve robustness. The benchmark uses only a binary pass/fail metric; intermediate metrics (root cause identification, code localization, test writing) would provide richer signal, especially given the high evaluation cost.
- **Criteria and generalizability:** Project and issue selection criteria are unclear (step 1: why 17 repos? what was the sample size after filters? step 5: how were conflicts resolved among the 3 annotators?). The focus on JavaScript limits generalizability to other visually-rich domains (game dev, mobile apps). There is already a rich body of work on multimodal bugs in mobile apps; the paper does not justify why JavaScript/front-end is uniquely important or different.
- **Practicality of benchmark design:** Simply increasing difficulty and adding visual elements may not be sustainable; the benchmark may be too challenging without providing granular insights. More nuanced design for incremental progress is suggested.
- **Concerns about benchmark quality:** A significant number of patches and test patches are reported as empty (reviewer 1 preliminary check). Evaluation methodology (pixel-level visual testing) is questioned for reasonableness.
- **Lack of representative examples:** The paper does not show a complete repair process or example outputs. It should showcase both successful cases (to demonstrate they are not trivial) and failed cases with root-cause analysis to clarify model limitations.
- **Missing human annotator details:** The paper only mentions 3 annotators with no further details (qualifications, inter-annotator agreement, how they were selected or resolved conflicts).
