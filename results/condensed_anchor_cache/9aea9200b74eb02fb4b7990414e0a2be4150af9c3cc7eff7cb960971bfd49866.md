- Decision: Reject
- Scores: 3, 3, 3, 3

## Merged Review

### Summary
The paper proposes G2T-LLM, a molecule generation method that converts molecular graphs into hierarchical text formats (JSON, XML) and fine-tunes an LLM with token constraining to produce valid structures. Experiments on QM9 and ZINC250k show comparable performance to state-of-the-art methods. Reviewers found the encoding idea interesting but raised major concerns about motivation, missing baselines, experimental rigor, presentation quality, and novelty.

### Strengths
- Novel approach converting molecular graphs into hierarchical text formats (JSON, XML) that LLMs can process, an area not extensively explored (Reviewers 1, 2, 4).
- Token constraining technique to guide generation of valid molecules (Reviewer 2).
- Comprehensive experiments and ablation studies on the impact of text encoding and supervised fine-tuning (Reviewers 1, 3, 4).
- Paper is clearly written (Reviewer 1).
- Various analyses support the results (Reviewer 4).

### Weaknesses
- **Motivation for JSON over existing representations is insufficient**  
  Molecules are naturally represented by SMILES, IUPAC, InChI, SELFIES, which are superior in readability, convenience, and complexity. The paper claims “SMILES may not tokenize effectively” but does not adequately explain advantages of JSON. Both serve a similar purpose, and SMILES is more informative (rings, aromatic rings, branches) (Reviewers 1, 4).  
  Contrast: Reviewer 1 notes that using SMILES, validity can exceed 99% and novelty >90% without token constraining [2], while the ablation shows the proposed method drops to 41.60% validity without constraining—suggesting JSON adds complexity without benefit.

- **Missing comparisons with sequence-based methods and related tree representations**  
  The paper does not compare with SMILES/SELFIES-based LLM generation, nor with graph-to-tree methods like HGGT (K2-trees) [3]. Previous works using XML/JSON for graph data in LLMs [1] and representing graphs in tree format [2] are not discussed. Including SMILES generation results (prompting or SFT) would partially address this (Reviewers 2, 3, 4).

- **Incomplete or unsound experimental setup**  
  – The evaluation focuses on unconditional generation, which is less practical for drug discovery. The paper should include goal-directed molecule generation benchmarks as recent works do [6,7] (Reviewer 3).  
  – Sequence-based molecular generation models are missing from baselines (Reviewer 3).  
  – Line 344 incorrectly calls QM9 a “real-world” dataset; most molecules are very small (up to 9 heavy atoms) and not real (Reviewer 3).  
  – The paper does not provide code to reproduce results (Reviewer 3).  
  – Performance is not strong: on QM9, validity 99.48 vs GraphDF 93.88, but novelty drops from 98.54 to 88.29; easy for graph-based methods to achieve 100% validity and high novelty [1] (Reviewer 1).  
  – No clear improvement over baselines, and results are not significant (Reviewers 2, 4).

- **Insufficient technical detail for algorithms**  
  – Token constraining: how are invalid node/bond types defined? How is valid JSON format enforced? How does this integrate with Llama’s decoding scheme? (Reviewers 1, 4).  
  – Random selection of starting component for the tree is not explained; why not train tree-to-graph directly? Any molecule containing the substructure could be valid, making loss function difficult (Reviewer 4).  
  – Duplicate edge representation (e.g., double bond repeated for (0,1) and (1,0)) is redundant for an undirected graph; no pruning technique is applied (Reviewer 4).  
  – The distinction between G2T-LLM and SFT-LLM is unclear and used interchangeably without definition (Reviewer 3).

- **Poor presentation quality**  
  – Figures 1, 2, 3 are poorly abstracted; raw code is pasted, not readable; diagrams with shapes would help understanding (Reviewer 3).  
  – Algorithms 1 and 2 are written with poor abstraction; variables/functions are not well explained (Reviewer 3).  
  – Typos: “Grum” → “GruM”, “SFT LLM” → “SFT-LLM”, “Zinc250k” → “ZINC250k” (Reviewer 3).  
  – One reviewer rated presentation 1 (soundness 1, contribution 1) citing these issues, while others rated presentation 2–3, indicating notable disagreement on clarity (Reviewers 1,2,4 vs 3).

- **Novelty concerns**  
  – Using XML/JSON for graph data in LLMs has been explored [1]; representing graphs in tree format is fundamentally similar [2]. The approach is closely related to HGGT [3], which also uses sequential tree representation and should be compared (Reviewer 4).

- **Missing references for key claims**  
  – No references support that JSON/XML are widely used in LLM training or that LLMs have demonstrated capacity to handle hierarchical data formats (Reviewer 4).  
  – The Introduction and Related Work only discuss rule-based and graph-based methods, omitting sequence-based methods that are a major branch. Need to list previous methods and state their limitations in detail (Reviewer 3).
