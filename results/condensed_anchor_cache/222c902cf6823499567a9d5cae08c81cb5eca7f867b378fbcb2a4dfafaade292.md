## Merged Review

### Summary
The paper introduces DataEnvGym, a testbed of teacher environments for data generation agents that iteratively improve student models. It frames data generation as sequential decision-making: an agent (data generation policy + engine) takes actions (data-generation plans) based on state feedback (student errors/weak skills) to improve the student. Environments are instantiated at three structure levels (open-ended, skill-list, skill-tree) across three tasks: mathematics, programming, and visual question answering (VQA). Baseline LLM-based policies are shown to improve student performance. The modular design and planned open-source release aim to facilitate further research.

### Strengths
- Novel problem and timely: automating data generation to improve models is a significant challenge with practical applications (Reviewers 1, 4).
- Well-defined framework: modular design with clear components (trainer, evaluator, policy, engine) and multiple structure levels makes the problem tractable and supports modular development (Reviewers 1, 2, 4).
- Multiple tasks and domains: experiments span mathematics, programming, and VQA, covering text and image modalities, demonstrating generalizability (Reviewers 2, 4).
- Promising initial results: student model improvement is shown across tasks and environments, including analysis of difficulty/rarity and training dynamics (Reviewers 1, 4).
- Novel perspective: framing data generation as sequential decision-making using RL concepts is insightful and clearly explained (Reviewer 2).
- Consideration of various data generation strategies (Reviewer 1).
- Well-designed experiments with insightful analyses (Reviewer 1).
- Commitment to open-source release of code and leaderboard (Reviewer 4).
- One reviewer found the paper clearly written (Reviewer 3), though another noted density issues (see Weaknesses).

### Weaknesses
- **Paper density and clarity (Reviewer 1, minority contrast from Reviewer 3):** Reviewer 1 finds the paper dense and difficult to follow, with excessive implementation details in the introduction and lacking a simple high-level intuition; suggests using a specific task example as a guide. Reviewer 3 found it clearly written. This disagreement indicates room for improvement in exposition.
- **Limited evaluation of agent architectures (Reviewers 1, 4):** Only baseline LLM-based policies are used. Reviewer 4 specifically calls for exploring more sophisticated agents (e.g., RL agents using policy gradient/Q-learning, agents with larger LLMs for planning) and a systematic comparison of agent architectures in terms of effectiveness, sample efficiency, and cost. Reviewer 1 questions whether a random policy (choosing naturally collected datapoints from a pool) can be implemented as a baseline, noting that the current “no-state” baseline may have LLM bias.
- **Incomplete experimental rigor (Reviewers 2, 3):** Reviewer 2 requests that a test set incorporating newly generated data be created and per-iteration evaluation results reported for each retrained model. Reviewer 3 notes the lack of repeated runs with confidence intervals, especially given high observed variance. Reviewer 2 also asks for evidence that student improvement is due to added data rather than insufficient training (fixed 10-epoch training; convergence unclear; does added data accelerate convergence?).
- **Fixed data-generation engine and neglect of engine quality (Reviewer 1):** The paper only addresses the data-generation plan, not a full end-to-end process; the engine is fixed and off-the-shelf. The engine’s quality can affect both student performance and the plan itself (e.g., poor engine output on a skill may cause the policy to avoid requesting more data for that skill), but this is not considered.
- **Over-reliance on LLMs for data generation and lack of alternatives (Reviewers 1, 4):** Reviewer 4 raises concerns about the quality and diversity of LLM-generated data and suggests exploring data augmentation, programmatic data generation, etc. Reviewer 1 asks for a comparison with active learning, where synthetic *labels* (but not synthetic inputs) are generated, effectively performing data selection.
- **Missing comparisons with existing methods (Reviewers 1, 3, 4):** Reviewer 1 suggests a comparison with active learning. Reviewer 4 calls for comparisons with curriculum learning (Bengio et al., 2009) and active learning (Settles, 2009) in terms of performance, data efficiency, and cost. Reviewer 3 lists specific missing related works ([1–4]) that use training feedback to generate training environments; their omission weakens the literature positioning.
- **Limited analysis of skill discovery quality (Reviewers 2, 4):** Both request more quantitative and qualitative results for the discovered skills. Reviewer 4 suggests measuring coherence, coverage, and relevance, and exploring alternative discovery methods (clustering, topic modeling) as well as comparing the proposed LLM-based method against them.
- **Scalability concerns (Reviewer 4):** Experiments use relatively small datasets and models. The paper lacks discussion of how DataEnvGym scales to larger datasets, more complex models, and the computational challenges (e.g., cost of LLM-based data generation, optimizing skill discovery and agent training).
- **Resource reporting (Reviewer 1):** The learning procedure can be resource-intensive; time, cost, and computing resources for experiments are not reported.
- **Typo and clarity issue (Reviewer 3):** Lines 460–465 likely contain a typo: “truncated once the performance consistently decreases” should probably say “increases”. Clarification needed.
- **Open questions on training protocol (Reviewers 2, 3):** Does performance plateau or continuously improve over longer iterations? Is the total training data allocation fixed or does it vary dynamically? The paper mentions rebalancing but lacks clarity on adaptive allocation.
