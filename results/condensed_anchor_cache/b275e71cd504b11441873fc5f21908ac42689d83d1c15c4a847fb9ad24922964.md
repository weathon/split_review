## Merged Review

### Summary

The paper introduces ZO-Offloading, a framework that fine-tunes large language models (LLMs) on a single GPU by combining zeroth-order (ZO) optimization with CPU offloading. ZO eliminates activation caching by using two forward passes, and the framework dynamically offloads model parameters to CPU memory, overlaps computation with H2D/D2H transfers, integrates low-bit precision (AMP mode), and supports asynchronous checkpointing. The key claimed result is fine-tuning OPT-175B on a 24GB GPU, which the authors present as a first.

### Strengths

- **Dynamic workload scheduling and overlap:** Devises a scheduler that overlaps computation and communication, including reusable block space and asynchronous checkpointing. (Reviewer 1 is positive; industrial value noted.)
- **Extension of offloading to ZO:** Tackles AI democratization by reducing hardware costs; extending system optimizations (e.g., offloading) to zeroth-order methods is empowering to model scientists. (Reviewer 2)
- **Claim of enabling 175B model on 24GB GPU:** If substantiated, this is a great feat and very useful to the community. (Reviewer 3; however, contested by Reviewers 2,3,4 – see Weaknesses.)
- **Intelligent integration of ZO features for offloading:** Utilizes ZO’s dual‑forward structure to reduce redundant transfers. (Reviewer 3)
- **Low-precision integration:** Demonstrated integration with FP8/FP16/BF16. (Reviewers 1,3,4)
- **Good ablation studies:** Breakup of performance from individual ideas. (Reviewer 3)
- **Clear presentation and logic flow.** (Reviewer 4)
- **Auto‑cast and AMP support** is a good thing to have for CPU offloading scenarios. (Reviewer 4)
- **Positive minority (Reviewer 1, score 8)** strongly endorses the industrial value of the scheduler and offloading mechanism, while three other reviewers rate the paper low (3,3,1) citing critical weaknesses.

### Weaknesses

**Novelty and Prior Work**
- The main weakness is that the paper appears to overlook critical prior work such as **ZeRO‑Infinity** (Reviewer 2). ZeRO‑Infinity already demonstrated overlapping parameter offloading with forward/backward pass, so the offloading approach here lacks clear novelty. Furthermore, ZeRO‑Infinity enables finetuning a **1T model with Adam using 32GB**, contradicting the claim that fine‑tuning OPT‑175B on 24GB is unprecedented. (Reviewer 2)  
  → *Suggestion*: Compare to ZeRO‑Infinity, highlight differences, and revise novelty/unprecedented claims.
- Other works also claim to run OPT‑175B on a single GPU, e.g., **FlexGen, LUT‑GEMM, OPTQ** (Reviewer 3). The paper should comment on these and modify the statement “for the first time it becomes possible to fine‑tune extremely large models … with just 24GB of memory”.
- The system design and implementation are very similar to **zero‑offload** (arXiv:2101.06840), including overlap of data memcpy with computation (Sec 5.1), dedicated memory block reuse (Sec 5.2), and AMP support (Sec 5.4 which is already present in Deepspeed’s zero‑offload). (Reviewer 4)  
  → *Request*: Provide a detailed comparison with zero‑offload and highlight specific novel aspects.
- Asynchronous checkpointing (Sec 5.5) is similar to more solid designs like **CheckFreq** (FAST'21) and **Check‑N‑Run** (NSDI'22). (Reviewer 4)
- No comparison with **HuggingFace Accelerate** (Reviewer 3).

**Evaluation and Comparisons**
- Table 1 lacks a breakdown of computation vs. communication (upload/download) time and the degree of overlap achieved by ZO‑Offloading compared to naive ZO baselines. The analysis should also separate parameter transfer and gradient transfer overheads. (Reviewer 1)  
  → *Requires*: Detailed timing data to assess the dynamic scheduler’s benefit.
- Asynchronous checkpointing is missing from the evaluation. (Reviewer 2)  
  → *Requires*: Results comparing async vs. sync checkpointing, e.g., training slowdown across model sizes.
- Given ZO requires only forward pass, comparisons with offloading inference works like **FlexGen** or **ZeRO‑Inference** are missing. (Reviewer 2)  
  → *Requires*: Comparative table/graph of forward‑pass throughput/latency vs. FlexGen and ZeRO‑Inference across model sizes.
- Only **OPT** models are used; results on **BLOOM** (another open‑source LLM family) are missing. (Reviewer 3)
- Only **one dataset** is used, whereas MeZO showed results with multiple datasets. (Reviewer 3)
- Table 3 shows no benefit from FP8 over FP16 (even for OPT‑6.7B); FP16/BF16 are only useful for OPT‑6.7B. This suggests CPU‑GPU transfer (communication) is **not** the bottleneck, and computational overhead inside the GPU is dominant. (Reviewer 3)
- Table 3 should have been shown all the way to OPT‑175B. (Reviewer 3)
- Evaluation reports only throughput (tokens/sec); no **convergence/accuracy tests** are reported, especially compared to first‑order methods. (Reviewer 4)  
  → *Request*: Include convergence comparisons with Adam/SGD (see also technical soundness).
- Ablation experiments on different CPU‑GPU interconnect bandwidths (PCIe generations) are missing. (Reviewer 3)
- No comparison of ZO‑Offloading with other techniques (e.g., zero‑offload) in terms of runtime and memory.

**Technical Soundness**
- **Figure 1** compares memory consumption of Adam vs. SGD without aligning model quality. Adam is dominant in LLM training because it yields higher convergence; comparing optimizers without quality results is unfair. (Reviewer 4)  
  → *Request*: Provide convergence results for Adam, SGD, and ZO methods.
- How were the memory usage numbers (e.g., 68 870 MB ≈ 68 GB) collected on a **24 GB** GPU? If empirically measured, how was such a high number measured on a device with only 24 GB? (Reviewer 4)  
  → *Request*: Explain the profiling methodology.
- The custom **lock mechanism** described (lines 295‑305) for synchronizing computation and offload is impractical. CUDA already provides multiple data transfer/compute sync techniques (async/sync memcpy, stream/event/block/thread synchronization). It is unnecessary to build a new lock without leveraging existing efficient functionality. (Reviewer 4)  
  → *Request*: Explain why a customized lock is needed over CUDA built‑ins.
- The supplementary material reports using “PyTorch **3.11**”. PyTorch has no 3.x version; even assuming a typo, the only version with “11” is **1.11.0**, which is quite old, making the experimental results outdated and unconvincing. (Reviewer 4)  
  → *Request*: Clarify the exact PyTorch version and why that version was selected.
- Zero‑order methods are not widely used for real large model training, as it is widely agreed that such gradient estimation methods can lead to model divergence. (Reviewer 4)  
  → *Request*: Provide citations or example applications of ZO in real‑world model training.
- The paper uses both “ZO” and “ZO‑SGD” inconsistently. (Reviewer 3)

**Implementation and Presentation Issues**
- Figure 1 uses “0” instead of “X”; caption could clarify that values are for a single GPU. It is unclear whether the figure shows GPU memory or CPU memory. (Reviewer 3)
- Figures 2, 3, 4 use white text that fades on color background when printed. (Reviewer 3)
- Incomplete phrase: “Since CPU resources can be combined and offloaded to expand the memory and computational capacity of a single GPU”. (Reviewer 3)
- “previously unattainable with conventional methods” is redundant. (Reviewer 3)
- Figures 5a and 5b (mentioned in introduction) should be in the main text, not appendix, because they are essential for understanding the difference between first‑order and zero‑order methods. (Reviewer 4)
- Figures 3 and 4 are ~90% identical; they should be merged, and the new part for AMP support should be highlighted. (Reviewer 4)
- The paper extends to too many minor contributions (e.g., async checkpoint); better to focus on a few major contributions. (Reviewer 4)
- Reviewer 1 requests a diagram of the “preemptive parameter updates” mechanism, especially how it halves interconnection bandwidth compared to two data transfer streams.
- Reviewer 2 asks: “Does the dual forward computation of block i occur before that of i+1? If so, how is block i updated based on loss information? (Figure 2)” and “What is the hardware environment of evaluation?”
- Reviewer 3 asks: “Can you theoretically state the largest OPT model your technique can run on a 24 GB GPU, assuming any OPT size is available?”
- Reviewer 4 asks: “What big/major LLM is pre‑trained/post‑trained using ZO?” and “How is higher memory usage (e.g., 68 870 MB) profiling conducted on a 24 GB GPU?”
