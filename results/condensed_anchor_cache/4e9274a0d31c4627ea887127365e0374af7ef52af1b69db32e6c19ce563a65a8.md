## Merged Review

### Summary
This work introduces LARM, a large auto-regressive model for long-horizon embodied tasks in Minecraft. LARM takes multi-view images and task text as input and directly predicts the next skill token in an auto-regressive manner, bypassing LLM outputs that require post-processing. The model is built on LLaVA with added Q-Former, LoRA, and projector modules. It uses a pre-prepared skill library generated by GPT-4 (based on Voyager's library) and a new data format, ARNTS, to capture dependencies between actions and observations. Experiments show LARM achieves 100% success on 14 of 15 skills, outperforming baselines like MineAgent and LLaMA-Rider, and is the first to craft an enchanted tool. Inference speed is reported as 6.8× faster than LLaVA-1.6-7B. Three reviewers gave a score of 5, while one reviewer (R3) gave 3, citing insufficient novelty, missing benchmarks, and lack of generalization evidence.

### Strengths
- Well-organized and detailed presentation; writing is clear and includes helpful figures (R1, R4).
- Introduces the ARNTS data format to model sequential dependencies between actions and observations (R1, R3).
- Provides a demonstration of LARM (R1).
- Fully embeddable model that does not require proprietary LLM API calls, reducing dependence on external services (R2).
- Inference speed is faster than LLaVA-1.6-7B (6.8× reported), and generally faster than LLM-based methods (R2, R3, R4). However, some reviewers question the reliability of this comparison (see Weaknesses).
- Reasonable architectural design with pre-training/fine-tuning phases (R2).
- Strong performance on the Minecraft benchmark: 100% success on 14 of 15 skills, outcompetes MineAgent and LLaMA-Rider, and achieves first-ever enchanted tool crafting (R2, R3, R4).
- Pinpoints the problem of lacking mutual dependency between actions and observations in previous work (R3).
- End-to-end subsequent skill prediction approach improves efficiency for local deployment (R4).

### Weaknesses
- Missing comparisons to important benchmarks in related work (R1, R3). The paper does not discuss generalization to other domains (e.g., ALFRED) and the method requires engineering adaptation to new domains (R1, R3, R4).
- No ablation studies are provided to show individual performance contributions or necessity of the many components: Q-Former, LoRA, projector, single skill token design (R1, R2, R3, R4). The use of Q-Former for visual token compression is not validated against alternatives (e.g., token sparsification, merging, pooling, convolution layers, mixture-of-experts) (R2). The effect of training LoRA and projector weights is unclear (R2).
- The choice of outputting a single skill token is not well justified; alternative strategies (e.g., multiple skill tokens with Hungarian matching) are not discussed or ablated (R2).
- Efficiency comparisons are not entirely reliable. Network latency can affect LLM API call baselines; the comparison should include wall-clock time under stable network conditions (R2). Also, the efficiency advantage over vanilla LLaVA (which LARM extends) is not clearly explained given additional modules (R4).
- Insufficient novelty: the model is a combination of existing foundation models (LLaVA, Q-Former, LoRA, GPT-4 skill library) without substantial new methodological contributions (R1, R3). One reviewer (R3) graded 3, noting the lack of novelty and missing generalization evidence as serious concerns.
- The paper does not provide detailed explanations of key components: the usage of GPT-4 for building the skill library, the exact format of environment feedback and "last skill position coordinate inventory list" (R2).
- The implementation of node dependency learning (blue dotted lines in Figure 3) is not described in enough detail (R4). There is a typographical confusion between ARNTS and ARTNS (R4).
- The skill library is pre-prepared based on Voyager; it is unclear whether LARM can adapt to new tasks or expand skills in a zero-shot manner as the library grows (R4).
- An ablation on the number of input views (multi-view vs. monocular) would be beneficial to refine training design (R4).
- The claim that LLM outputs are limited to sentences/code is questionable; prompt design could directly predict skill keywords for embedding matching, so additional analysis of Wiki-pretrained LLaVA in this role is recommended (R4).
- How skills are executed in Minecraft (hard-coded or deterministic) is not clarified (R3).
- The finite skill space may limit generalizability (R3).
