## Merged Review

### Summary
This paper introduces PLAY2PROMPT, an automated framework that iteratively refines tool documentation and generates usage examples for zero-shot tool use by LLMs. The approach uses beam search and self-reflection to explore tool input-output behaviors, generating candidate descriptions and demonstrations. It is evaluated on StableToolBench across LLaMA-3-8B, LLaMA-3-70B and GPT-3.5, reporting 3–6% improvements in solvable pass rate. Reviewers acknowledge the real-world importance of the problem and the creative “tool play” idea, but raise concerns about baseline sufficiency, benchmark limitation, computational cost, multi-tool support, and missing comparisons with other few-shot prompt optimization methods.

### Strengths
1. **Real-world problem, comprehensive approach.** Tackles the fundamental challenge of low-quality tool documentation that hinders zero-shot tool use, and presents a complete technique to refine descriptions and generate usage examples (R1, R2, R3). The “play” approach that lets LLMs explore tool behaviors without labeled data is creative and novel (R4, R5).
2. **Smart invocation-first sampling.** The method first samples tool invocations via rejection sampling, then generates corresponding queries and answers – a clever technique to introduce variance in the query distribution (R1).
3. **Empirical improvements across models.** Demonstrates 3–6% absolute gains on StableToolBench for both open-source (LLaMA-3-8B, LLaMA-3-70B) and closed-source (GPT-3.5) models, using a relatively small model (Llama-3-8B) for the optimization, highlighting practical applicability (R2, R3, R4).
4. **Clear presentation and thorough analysis.** The paper provides a structured breakdown of framework components (R2, R4) and includes comprehensive analysis of how tool documentation and demonstrations affect performance (R3).

### Weaknesses
1. **Multi-tool and multi-step limitation.** The method currently only supports single-tool scenarios; multi-tool, multi-step, or nested tool calls are not handled. The examples in Figures 2 and 3 are all single-tool, and the paper’s mention of “an API service represents a tool that contains multiple sub-tools” does not equate to true multi-step reasoning (R1, R4, R5). Specifically, nested tool calls (e.g., g_1(g_0)) and sequencing remain unsupported (R1 question 1).
2. **Benchmark choice and weaker results relative to SOTA.** Evaluation is limited to StableToolBench, a recently introduced benchmark that may contain specific problems (R2). Additional validation on other benchmarks such as BFCL, ToolQA, Mint, and APIBench is needed to demonstrate broader applicability (R2, R3). Moreover, the current reported results appear weaker than the SOTA on StableToolBench (e.g., GPT-3.5-Turbo-1106 achieves ~62.2±0.8 on the StableToolBench leaderboard, close to or above the reported PLAY2PROMPT gains) (R5).
3. **Insufficient novelty and baselines.** The baseline ReAct is well-established; the paper does not compare with existing few-shot example creation techniques such as ART or DSPy (R2). An ablation comparing the compute-intensive self-reflection query generation against a simpler 3-shot in-context prompt would help justify the computational cost (R1).
4. **Computational cost and search strategy concerns.** Beam search is computationally demanding, especially for larger models (R4). The ablation claims the MC variant fails to explore well, but a comparative analysis with Monte Carlo Tree Search (MCTS) – which has proven successful in LLM settings – would be valuable (R3). Alternative, more efficient search strategies should be tested (R4).
5. **Reward evaluation reliability.** The reward computation relies on LLM-based evaluation via prompting, which may introduce biases or inconsistencies in quality assessment (R3).
6. **Missing presentation details.** The paper would benefit from a high-level flowchart or algorithmic pseudocode before the Methodology section (R3). A visualization or quantitative analysis of how the reward r_t changes over iterations should be provided (R5).
7. **Metric scope too narrow.** The main metric, solvable pass rate, gives only a basic view of improvement and does not analyze specific failure types (e.g., tasks that consistently remain unsolved) (R4).
8. **Model size dependency.** Larger models benefit more from PLAY2PROMPT; smaller models may need tailored adjustments. It is unclear how much the framework relies on the base model’s initial understanding of tools (R4 and R4 question).
9. **Missing environment context in tool definition.** The definition v = (w, y, i) excludes the environment that the tool invocation is part of, potentially losing information needed to adjudicate whether the tool call is correct or incorrect (R1).
10. **Action selection justification.** In Line 172, the action a_t is determined by sampling from an optimization model M rather than a deterministic system; this choice requires explanation (R1 question 3).
