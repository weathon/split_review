## Merged Review

### Summary
The paper introduces CHASE-SQL, a framework combining multiple inference strategies for Text-to-SQL using closed-source LLMs (Gemini Pro 1.5, Claude). It employs three generators: (1) a divide-and-conquer approach that breaks complex queries into sub-queries in a single LLM call; (2) a query execution plan based chain-of-thought (Query Plan CoT); (3) an instance-aware synthetic few-shot generation technique (OS‑CoT). Generated SQL candidates are then fixed by a query fixer module. The final selection uses a fine-tuned pairwise comparator (trained on BIRD) that scores all pairs and picks the highest-ranked candidate. CHASE-SQL achieves state-of-the-art execution accuracy of 73.0% on the BIRD test set and 73.01% on the development set, also reporting competitive results on Spider. Three reviewers score 6/8/6; one scores 5. Confidence ranges from 4–5.

### Strengths
- **State-of-the-art performance**: Outperforms all published and undisclosed methods on the BIRD benchmark by a large margin, and also achieves competitive results on Spider, demonstrating generalizability.
- **Thorough evaluation and analysis**: Sufficient experiments including lower/upper bounds, ablation studies, and a detailed error analysis (per-database, per-difficulty, selection agent errors) that provides insights into why the framework works. The error analysis section is particularly informative and appreciated by the community.
- **Well-justified design**: Each component is clearly motivated and the overall framework is well-organized and easy to follow. The construction of few-shot examples (covering the full database and the specific database, balancing simple/complex SQL features) reduces overfitting risk.
- **Novel selection approach**: Fine-tuning a selector for pairwise comparison (rather than reranking a large pool) is a simple but effective task that yields robust results.
- **Solid presentation**: Detailed explanations of mathematical formulas, complete experimental details, and thorough comparisons.

### Weaknesses
- **Limited novelty of individual techniques** (score 5 reviewer strongly critical; others also note lack of novelty):
  - *Divide-and-Conquer*: Already used in DTS‑SQL, TKK, DEA‑SQL (see NL2SQL survey, Figure 6, “Decomposition” branch). The paper does not clarify how its decomposition avoids error propagation compared to multi-stage pipelines or how it differs from methods like TKK.
  - *Chain-of-Thought*: Extensively applied in CHESS, ACT‑SQL, COE‑SQL (survey Figure 6, “Chain-of-Thought” branch). The proposed Query Plan CoT is a variation of prompt engineering without fundamentally distinct reasoning steps.
  - *Instance‑Aware Synthetic Example Generation*: Few‑shot examples are already used in DIN‑SQL and CodeS. The paper does not justify why *synthesis* is superior to *selecting* existing examples from training data; it lacks empirical evidence or theoretical justification.
  - *Self‑consistency and self‑reflection methods* are already well‑studied in NL2SQL; the only novel component is the pairwise selector.
- **Missing cost and latency analysis** (raised by all reviewers):
  - No breakdown of API calls, token usage, or monetary cost per query. Prompt lengths are substantial (e.g., few‑shot prompt estimated >9,450 tokens). The reported token count (≈1,510 tokens per question for the financial database) appears inconsistent with a reviewer’s calculation (>13,319 tokens per question). End‑to‑end latency is not reported.
  - The high number of LLM calls (≥21 generator calls + O(n²) selector calls) makes interactive Text‑to‑SQL unlikely. Reviewers question the practical feasibility.
- **Lack of open‑source model experiments** (reviewers 1, 2, 4):
  - Experiments only use closed‑source models (Gemini Pro, Claude). Would the framework enhance performance when substituted with open‑source models (e.g., LLaMA‑3.1, Qwen‑2.5)? This limits generalizability and real‑world applicability. The paper would benefit from fine‑tuning an open‑source model for the selection agent.
- **Insufficient ablation and component comparison** (reviewers 2, 4):
  - No ablation on different LLMs, so unclear whether gains come from Gemini or the framework.
  - No systematic comparison of individual components (value retrieval, candidate generation, query fixing) against existing state‑of‑the‑art methods for each sub‑task.
  - No justification for the specific set of generators chosen; why not include even more off‑the‑shelf methods? The paper does not discuss the trade‑offs between method ensemble vs. fine‑grained module combination.
- **Query Fixer module under‑described** (reviewer 2): The algorithm is too brief; missing details on error types handled, correction strategies, and examples of execution results used in few‑shot prompts. Would covering diverse execution errors (e.g., Column Not Found, Data Type Mismatch) improve effectiveness?
- **Selection pairwise comparison** (reviewer 4, W7): Algorithm 3 requires comparing both (cᵢ, cⱼ) and (cⱼ, cᵢ). The paper does not explain why a two‑way comparison is necessary, whether it addresses order bias, or what impact it has on results.
- **Other missing analyses**:
  - Why schema union is especially effective for ranking query pairs (reviewer 1 question).
  - Some databases show zero correct samples for various methods; this should be combined with question difficulty for further analysis (reviewer 2 question).
  - The error analysis, though detailed, is placed mostly in the appendix; moving parts to the main text would benefit the community (reviewer 2 suggestion).
  - The abbreviation “CHASE” conflicts with a prior Text‑to‑SQL dataset (Chase, ACL 2021); consider a different name (reviewer 2 suggestion).
- **Ensemble vs. module combination** (reviewer 4): The paper does not discuss the pros/cons of coarse‑grained method ensembles versus fine‑grained module ensembles, nor does it reference “The Dawn of NL2SQL” work on automated architecture search.
