## Merged Review

### Summary

The paper introduces EcoAct, a method for selective tool registration in LLM agents to reduce token and computational costs. Instead of providing all tool details in context, EcoAct gives only tool names and a registration tool; the LLM must explicitly call the registration tool before using any other tool. This integrates registration into the reasoning process. Experiments on ToolBench using GPT-4o and GPT-4-turbo with ReAct and DFSDT demonstrate over 50% cost reduction while maintaining performance. Ablations include single-tool vs. multi-tool registration and providing descriptions alongside names.

### Strengths

- **Clear writing and presentation.** The paper is well-written, logically structured, and easy to follow. Motives, method, experiments, and results are clearly presented (all reviewers).
- **Explicit tool registration step reduces token costs.** The simple idea of having the LLM register tools only when needed effectively shortens context length without harming performance (reviewers 2,3,4,5,6). The step is generalizable to most agent frameworks (reviewers 4,5).
- **Comprehensive experiments and ablation studies.** The evaluation on ToolBench (G1, G2, G3) with multiple reasoning methods and ablations (single‑ vs. multi‑tool registration, with/without descriptions) provides solid empirical support (reviewers 2,3,4,5). The results clearly support the claim of cost reduction with minimal performance loss.
- **Originality.** The particular approach of dynamic registration via a dedicated tool call is novel and somewhat surprising in its effectiveness (reviewer 4). The idea is simple but effective and has practical implications for reducing API costs (reviewer 3).
- **Effective cost reduction.** The method achieves over 50% savings in token cost while maintaining pass rates, a clear practical benefit (reviewers 1,2,3,4,5,6). The effect is particularly strong when many irrelevant tools exist (reviewer 4).
- **Well-motivated experiments and fruitful discussions.** The research question, method design, ablations, and discussions (e.g., section 3.3.2) naturally follow from each other and add depth (reviewer 4).

### Weaknesses

- **Method is straightforward and lacks technical novelty.** Several reviewers note that the approach is merely adding a “register tool” step, making it a simple extension of ReAct rather than a deep innovation (reviewers 1,2,6). The changes from ReAct are minimal (see Tables 5 and 6) (reviewer 6).
- **No comparison with RAG-based tool selection or other alternative solutions.** The paper does not compare to Retrieval-Augmented Generation (RAG) methods that retrieve tool candidates by semantic similarity, which could similarly reduce token usage (reviewer 2). Also missing comparisons with other simple baselines, e.g., asking the LLM to filter the tool list first and then proceed (reviewer 4). Related works such as Seal-Tools, MTU-Bench, and ToolGen are not discussed or compared (reviewer 5).
- **Dependence on tool naming and lack of analysis of function name effects.** EcoAct relies on tool names being descriptive enough for the LLM to decide which tool to register. The paper does not examine cases where names are ambiguous, unintuitive, or very similar (e.g., “calculator” vs. “scientific calculator”) (reviewers 2,3). No experiments investigate robustness to different levels of descriptiveness.
- **No open-source model experiments despite code artifacts.** The evaluation only uses GPT-4o and GPT-4-turbo, yet the code contains files named “llama*” and “davinci*”. This omission limits the generality and applicability of the results, especially since the cost benefit hinges on API pricing (reviewers 1,2,3,5). Questions remain about how EcoAct would work with open‑source models run locally (reviewer 1).
- **Unexplained performance drop with descriptions in some settings.** In Table 4, models with descriptions (EcoAct‑Desc) perform worse on average than those without in G2 and G3‑Instruction. The paper offers no explanation for this behavior (reviewer 3).
- **Lack of qualitative analysis of tool registrations.** The paper does not provide examples or analysis of when and why specific tools are registered, making it harder to understand the decision‑making process and practical implications (reviewer 2).
- **Experimental setting may not be representative.** The experiments use ToolBench, which includes many tools (dozens to hundreds). Most real‑world agent workflows use fewer tools, so the cost savings may be less significant in practice (reviewer 4). The tasks themselves may reduce to tool choice rather than multi‑step reasoning with nuanced intermediate outputs (reviewer 4). The paper acknowledges this but does not address it experimentally.
- **Potential redundancy with prompt caching.** The economic motivation (reducing API cost) is less compelling given that prompt caching (available in OpenAI/Anthropic APIs) can reuse the static tool context across calls with negligible cost, which might be a more fundamental solution to the same problem (reviewer 4).
- **Missing evaluation protocol details.** The paper does not report model temperature, maximum tokens, or other generation parameters, making reproduction difficult (reviewer 3). The provided code is poorly written, hindering reproducibility (reviewer 3).
- **Visual inconsistency.** Figure 3 (a) and (b) use inconsistent y‑axis scales, making cross‑comparison harder (reviewer 3).
- **No analysis of error recovery or overhead.** The paper does not discuss how EcoAct recovers from a wrong initial tool registration, especially under tool name ambiguity (reviewer 2). It is not clear whether the registration step itself introduces extra latency or steps (reviewer 5). The maximum number of steps before failure is also not stated (reviewer 1).
- **Gpt4‑turbo cost anomaly.** In Figure 3(a), gpt4‑turbo with EcoAct shows higher cost than the baseline at difficulty level 1, which is not explained (reviewer 6).
- **Poor performance of multiple‑tool registration.** The ablation shows that allowing registration of multiple tools at once significantly degrades performance compared to ReAct and single‑tool EcoAct. The explanation (increased complexity) is not fully substantiated (reviewer 5).
- **Claim about tool space vs. action space may be false.** Section 2.1 states “the size of the tool space is equivalent to the size of the action space”, but tools can have infinite parameter combinations, making the action space infinite while the tool space is finite (reviewer 4).
- **Minor presentation issue.** Line 386 has a typo: “results” (reviewer 5).
