## Merged Review

### Summary
The paper introduces Effi-Code, a Python fine-tuning dataset and pipeline to improve both the efficiency and correctness of LLM-generated code. It aggregates and filters open-source data, then applies Self-Optimization based on Overhead Profiling (SOAP) to iteratively refine code samples by analyzing runtime performance. Models fine-tuned on Effi-Code (e.g., DeepSeek-Coder-6.7B-Instruct, Qwen2.5-Coder-7B) show absolute improvements on HumanEval and EffiBench: pass@1 of DeepSeek-Coder-6.7B-Instruct increased from 43.3% to 76.8%, and average execution time dropped by 30.5%. Five independent evaluations with mean and standard deviation are reported, along with ablations on training set size and model size. Reviewer opinions diverge: two (6,6) find the work important and novel, one (3) praises significance but questions novelty and scope, and one (1) considers the work repetitive and methodologically unsound.

### Strengths
- **Importance of the problem**: Code efficiency is less explored than correctness and is essential for performance-sensitive and resource-constrained environments.
- **Novel idea**: Iterative refinement of generated code via overhead profiling (SOAP) is a novel contribution (Reviewer 1).
- **Rigorous dataset curation**: The pipeline includes filtering risky operations, generating test cases, iterative optimization cycles, and runtime profiling, resulting in measurable improvements.
- **Thorough evaluation**: Five independent runs with mean/standard deviation; ablations on training set size and model size demonstrate robustness.
- **Significant absolute improvements**: Fine-tuned models outperform off-the-shelf baselines in Execution Time, Max Memory Usage, Total Memory Usage, and Correctness (pass@1).  
  Example: DeepSeek-Coder-6.7B-Instruct pass@1 from 43.3% → 76.8%; execution time reduction of 30.5%.
- **Comparison with prior work**: A comparison with PIE is included.
- **Open-source release**: Encourages reproducibility and broader research.

### Weaknesses
- **Novelty concerns** (minority reviewer 4 is strongly critical; reviewer 2 also questions novelty):  
  * The Self-Optimization process introduced in this paper is already published as SOAP (Huang et al., 2024, arXiv:2405.15189). The claim of introducing it is false.  
  * The test case generation technique is already present in EffiBench (Huang et al., 2024, arXiv:2402.02037); no novel contribution in that component.  
  * The pipeline consolidates existing methods (raw data sources from prior work, SOAP from prior work, EffiBench filtering). The primary novelty is the integration, not new methodologies.  
  * The use of LLM as a judge for constructing efficient solutions (DeepSeek-Coder) is not justified or backgrounded.

- **Limited comparison and ablation** (multiple reviewers):  
  * No comparison against baseline datasets or pipelines: what is the performance of models fine-tuned on the un-optimized version of the filtered data? On raw data directly optimized by SOAP without filtering?  
  * Relative improvements over existing methods focused on code efficiency are unclear; broader comparison is needed.  
  * Cross-evaluation: models fine-tuned on Effi-Code (Python) should be evaluated on PIE’s test set (C++) to assess generalization; PIE is currently evaluated only on EffiBench (Python), which is an unfair advantage.  
  * Table 3 shows pass@1 does not consistently increase as the proportion of Effi-Code training data grows; this inconsistency needs explanation.

- **Scope and generalizability** (reviewers 2 and 3):  
  * Effi-Code is exclusively Python; real-world performance-sensitive applications often use C/C++ (e.g., competitive programming). Expanding to C/C++ would enable finer-grained optimizations (I/O choices, data structures, variable initialization).  
  * Filtering out “non-algorithmic” tasks is questionable: non-algorithmic optimizations (e.g., switching from Python `list` to `numpy.array`, I/O changes like `cin` vs `scanf`) can yield substantial improvements without altering Big-O complexity. The claim that non-algorithmic tasks have no optimization potential is unsound.  
  * The paper does not address parallelizable or concurrent code patterns, which are important for multi-core and distributed systems.

- **Methodology concerns** (reviewers 1 and 4):  
  * Profiling metrics (execution time, memory usage) are highly sensitive to system noise and vary across platforms; given execution times are brief (seconds), they may not robustly demonstrate efficiency.  
  * Over-reliance on LLMs for filtering risky operations: static analysis would be more sound; there is no manual investigation of false positives/negatives.  
  * Test case generation relies only on GPT-3.5; should consider state-of-the-art test generators like CODAMOSA (ICSE 2023). Quality of generated tests (e.g., code coverage, branch coverage) is not evaluated.  
  * The method for analyzing correctness of GPT-3.5-generated test cases and the precise definition/criteria for filtering “non-algorithmic” tasks are not clearly specified.  
  * Discrepancy: the instruction says 8 data sources, but Section 3 says seven sources.

- **Presentation issues**:  
  * The paper is somewhat challenging to follow; criteria for filtering non-algorithmic and inefficient solutions are unclear (Reviewer 1).  
  * Some parts are poorly written (e.g., lines 73–76) (Reviewer 4).

- **Questions that overlap with criticisms** (missing experiments/ablations/justifications):  
  * What percentage of solutions improved efficiency but degraded correctness?  
  * How are test cases generated—conditioned on problem and solution or only problem and function signature? Number of tests per problem?  
  * How is test quality evaluated (assertions, invocation, line coverage)?  
  * What trade-offs exist between time and space optimization (e.g., Table 4 shows Max Memory Usage decreased while Execution Time decreased for DeepSeek-Coder-33b-base; is there any counterexample)?  
  * Why does pass@1 increase so dramatically (e.g., DeepSeek-Coder-6.7B-base from 7.3 to 59.8)? Could this be due to code quality independent of efficiency?
