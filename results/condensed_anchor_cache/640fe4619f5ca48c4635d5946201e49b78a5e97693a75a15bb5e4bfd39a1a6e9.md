## Merged Review

### Summary
The paper systematically investigates at which training stage (pre-training, instruction-tuning, or both) introducing code data improves LLM reasoning capability. Experiments on six reasoning tasks across five domains using a PanGu2.6B model (with limited comparisons on a 1.3B model) show that pre-training with mixed code+text significantly enhances general reasoning, while adding code at instruction-tuning yields little improvement and can hurt performance on some tasks. A dynamic text–code mixing strategy during instruction-tuning produces marginal gains, primarily on logical reasoning. One reviewer (score 5) is substantially more critical of the experimental controls and significance; three reviewers (scores 8) find the work valuable and well-executed but note several missing details and analyses.

### Strengths
- The research question – at which training stage code data helps LLM reasoning – is timely and well-motivated.
- The experimental design is comprehensive, covering six reasoning tasks across five domains and two model sizes, supporting the generalizability of the conclusions.
- The paper provides clear, in-depth analyses and insights: code in pre-training boosts general reasoning; code in SFT helps task-specific code reasoning; a dynamic mixing strategy enables progressive learning.
- The writing is mostly clear and results are well presented (though one reviewer found a grammar error and suggested table layout improvements).
- The dynamic mixing strategy is easy to follow and, in the view of two reviewers, effective.
- Code, model parameters, and other resources are open-sourced, supporting reproducibility.

### Weaknesses

**Experimental control and statistical significance**
- The code model is trained on more total tokens than the NL baseline. If it receives as many text tokens as the baseline plus code tokens, its better performance could be due to more data, not the nature of code. The study should control for total token count during pre-training. (R1; R1 increased score after rebuttal expecting such a control experiment)
- No statistical significance tests are reported. For example, Table 2 shows only a 0.13‑point gain on ScienceQA – it is unclear whether such differences are meaningful. (R1)

**Evaluation scope and dataset concerns**
- The evaluation omits mathematical reasoning, a domain where code data might yield large improvements. (R1, R2)
- Several datasets (e.g., Logic) are not well‑known; including more established datasets (especially for Tables 2 and 3) would strengthen the conclusions. (R2)
- For the Logic dataset, accuracy is exactly 40.9 across many model variants in Tables 2, 3, and 6, hinting at a possible dataset issue. (R2)
- Some datasets are not available in English; English examples would help readers gauge difficulty. (R2)

**Mixing-strategy experiment and instruction-tuning stage**
- The dynamic mixing strategy (ratios 7:3, 6:4, 5:5) shows only marginal improvements except on logical reasoning and actually hurts performance on three tasks. The paper does not thoroughly investigate why, and the choice of ratios and phases appears arbitrary. (R1, R2)
- Because adding code at instruction-tuning is already shown to be ineffective, testing the mixing strategy at that stage seems misguided; it would be more informative to test it during pre-training, where code helps. (R2)

**Insufficient experimental details**
- Key settings for data mixing strategies and decoding strategies are not reported in enough detail to support reproduction. (R3)
- The training corpus construction is unclear: data collection, cleaning, and fuzzy deduplication tools are not explained; the data are not open‑sourced. (R4)
- The model architecture (beyond size) is not detailed. (R4)

**Missing comparisons and related work**
- The paper does not discuss or experiment with recently released code foundation models such as CodeLlama, which are directly relevant to the research question. (R3)
- The related work section is weak and misses important papers (e.g., [1,2,3] from reviewer 3). (R3, R4)

**Contradictions in claims and results**
- Section 3.3.5 claims code data “has little negative impact” on other tasks, but Table 7 shows large drops on DuReader (already noted) and a decrease on CMNLI from 45.07 to 43.49 – a magnitude similar to some gains reported in Table 2. The language should be more consistent. (R2)
- Table 7 shows performance drops on four of five datasets, which could be interpreted as code not helping reasoning; the authors should provide valid reasons. (R4)

**Minor issues**
- Table 3 lists multiple equal numbers but bolds only one; Table 4 rows/columns should be reversed for consistency with other tables. (R2)
- Grammar error on page 8: “found” should be “showed”. (R4)
- Missing discussion of how the insights could be applied to real LLM products in different domains. (R4)
- The paper lacks a section on future work. (R4)

**Reviewer disagreement**: One reviewer (score 5, soundness 2, contribution 2) is notably more critical, emphasizing the lack of token‑count control, missing statistical significance, and the arbitrary design of the mixing strategy. The other three reviewers (scores 8, soundness 3–4, contribution 3) are positive overall but raise overlapping concerns about evaluation scope, missing experiments, and insufficient detail.
