## Merged Review

### Summary

This paper presents OSCAR, a generalist LLM+LMM-based agent for operating system control (desktop and mobile) that translates human instructions into executable Python code for mouse/keyboard input. Key components: GUI element recognition with Set-of-Marks (SoM) prompting, a state machine with error handling and task-driven re-planning, and code execution. Evaluated on three benchmarks—OSWorld, GAIA, AndroidWorld—OSCAR outperforms current SOTA baselines. The code will be open-sourced.

### Strengths

- **Generalist without fine-tuning**: OSCAR uses a general-purpose language model without any fine-tuning, relying on prompting and structured modules (Reviewer 1).
- **GUI grounding with SoM**: SoM techniques improve GUI element recognition reliability, addressing VLM difficulty reading raw screenshots (Reviewers 1, 3).
- **Many baseline comparisons and detailed implementation**: The paper provides comprehensive comparisons and implementation details (Reviewer 1).
- **Task-driven re-planning for real-time adaptation**: The re-planning strategy enables correction and state-aware reasoning, enhancing autonomy on complex tasks (Reviewer 2).
- **Diverse benchmarks demonstrate generalizability**: Superior performance across both desktop and smartphone environments (Reviewer 2).
- **Systematic state transition process**: The structured observation, planning, execution, verification phases support error recovery and adaptability (Reviewers 2, 4).
- **Strong quantitative results**: Achieves an average success rate of 28.7% and 13.5% on Level 3 tasks in GAIA (Reviewer 3).
- **Well-defined state machine for dynamic environments**: Clear formulation of states and transitions (Reviewer 3, 4).

### Weaknesses

- **Novelty and related work**: The proposed modules (task-driven re-planning, context memory, GUI observations, code actions) lack novelty. The paper omits closely related methods: Kim et al. (NeurIPS 2023), Sun et al. (NeurIPS 2023), Zheng et al. (ICLR 2024) (Reviewer 4).
- **Insufficient ablation of planning**: The ablation only compares with/without GUI observations and replanning. It does not isolate the impact of different planning strategies within OSCAR, nor explain how the planning module contributes to “fewer re-planning attempts” and “smaller steps” compared to baselines (Reviewer 4).
- **Performance regression on easy cases**: In Table 3, OSCAR underperforms baselines on easy cases. The paper provides no analysis of why the approach fails on simpler tasks, raising concerns about general applicability (Reviewer 4).
- **Unclear handling of real-time feedback**: It is unspecified how OSCAR leverages “real-time” OS feedback, including asynchronous signals. Additional experiments on environments like AgentStudio would help demonstrate robustness (Reviewer 4). A reviewer also questions whether plan→execute→error→re-plan is sufficient for complex tasks or whether sampling-based methods (e.g., evolutionary search) should be considered (Reviewer 1).
- **Missing safety discussion**: Given full OS control, the paper should discuss safety mechanisms (Reviewer 1).
- **No self-improvement mechanism**: OSCAR lacks a mechanism to learn from past failures beyond the current replan; representation of states (errors/failures) uses only pure text (Reviewer 1). A reviewer asks: will fine-tuned LMs eventually be needed for real-world robustness? What degree of user/expert supervision is required? (Reviewer 1).
- **Unclear [Verify] state**: The functionality of the verification step is ambiguous—what happens on a false positive? The paper needs an in-depth analysis of its failure modes and success rate (Reviewer 3).
- **Limited discussion of generalization**: More analysis is needed on how OSCAR fits into different OS environments and extends to more benchmarks and systems (Reviewer 2). A reviewer also notes the lack of any limitations discussion (Reviewer 4).
- **Missing details and analysis**: 
  - Detailed examples/cases of state transitions in action are lacking (Reviewer 2).
  - It is unclear how labels are added to elements in the dual-grounding observation approach (Reviewer 2).
  - The term “evaluation scripts” (Section 2.1) needs clarification—does it refer to OSWorld’s scripts? The evaluation process on each benchmark should be clearer (Reviewer 2).
  - The paper allows 4 attempts per run; it is not shown whether this is crucial for performance or whether failures are always learned from (Reviewer 2).
  - A detailed error analysis of step-limit failures is needed to improve error handling (Reviewer 2).
- **Typos**: Multiple formatting errors, e.g., line 300 “i.e. when” → “i.e., when”; line 332 “(e.g. Chrome)” → “(e.g., Chrome)”; missing spaces in Section 1 “(LLMs)(Ouyang …” and “(LMMs)(Li …”; Section 3 baselines “UFO(Zhang et al., 2024a)”; Table 1 caption “(i.e. GPT-4-turbo )” (Reviewer 4).

*Note on reviewer disagreement:* Two reviewers rated the paper 8 (high acceptance) emphasizing strong results and clear design, while two rated it 6 (borderline) focusing on novelty gaps, inadequate analysis, and missing details. The weaknesses above reflect concerns from both camps.
