## Merged Review

### Summary
The paper proposes AIDL, a solver-aided hierarchical domain-specific language (DSL) for enabling LLMs to generate CAD designs. AIDL offloads spatial reasoning to a geometric constraint solver and uses hierarchical constructs for modularity. Evaluated on 36 prompts using CLIP score and a perceptual study, AIDL outperforms OpenSCAD (which is in LLM training data) in the few-shot regime. Reviewers praise the novelty of the approach and the effective combination of LLMs with a solver, but raise concerns about limited evaluation, insufficient justification of innovation relative to tool learning and code generation, lack of error handling mechanisms, unclear scalability, and missing baselines or human evaluation. There is a split: two reviewers give a score of 5 (more positive but still noting limitations), while two give a score of 3 (more critical).

### Strengths
- First DSL for CAD modeling using LLMs, combining LLMs with a geometric constraint solver to generate complex CAD models without requiring the LLM to handle intricate spatial reasoning; enables more accurate and semantically rich designs.
- Incorporates hierarchical structures that facilitate modular design and align with designers' workflows, improving editability and management of complex models.
- In the few-shot regime, AIDL outperforms OpenSCAD in generating models closer to user prompts and more editable; this is significant because OpenSCAD is included in LLM training data whereas AIDL is not, highlighting the effectiveness of the language design.
- Introduces a novel application of LLMs for design tasks.
- Methodology is well-structured and clearly articulated; central idea is straightforward and accessible.
- Figures effectively illustrate the main contributions.

### Weaknesses
- **Innovation and contribution ambiguity**: The paper does not clearly differentiate AIDL from tool learning (where the solver is a tool) or from standard code generation in a particular domain. The LLM's role appears to be mostly compiling constraints for the solver; it is unclear what reasoning the LLM performs beyond code generation. As a result, several reviewers consider the technological depth insufficient and the work just another application of reformulating tasks with LLMs without significant new insights.
- **Limited and insufficient evaluation**: The approach is evaluated on only 36 prompts, which is too small to effectively evaluate LLMs. CLIP score may not accurately capture quality of CAD designs; a larger dataset with ground truth is needed. There is no baseline comparison with other code generation methods (only OpenSCAD is compared). No human evaluation is conducted, which is especially important given the difficulty of automatic evaluation in this domain. A few reviewers also note that only 2D designs are generated, which resemble images rather than true 3D CAD designs; scalability to complex 3D objects is questioned.
- **Lack of error handling and reliability analysis**: The paper does not discuss how to prevent or handle errors introduced by the LLM (syntactic or semantic errors in generated AIDL code). There is no mechanism (e.g., using an SMT solver for verification) to ensure the correctness of the generated constraints. Reliance on the LLM without fine-tuning or extensive training data raises concerns about consistency and reliability.
- **Missing performance analysis**: There is no benchmark or analysis of the computational overhead introduced by the external constraint solver, nor how solver performance scales with model complexity. This is crucial for assessing practical viability.
- **Scalability and realistic complexity**: The examples presented appear simpler than what OpenSCAD can already produce (e.g., see OpenSCAD demo); it is unclear whether the method scales to more complex or detailed designs. Some reviewers question the practical utility given that many examples could be easily done by direct human editing over a CAD object or with OpenSCAD.
- **Motivation and problem framing**: The motivation for requiring a language description to identify necessary objects is unclear. It is not obvious why an LLM is needed instead of, say, using an LLM to search for existing raw CAD files based on keywords. The discussion of limitations of existing methods could be rewritten to more clearly articulate the specific challenges faced.
- **Suggestions for improvement**: Use an SMT solver for constraint verification; evaluate with designer productivity metrics; include user studies to validate practical applicability; benchmark computational efficiency of the solver; create a larger dataset with ground truth; perform human evaluation; compare against more code generation baselines.
