## Merged Review

### Summary
The paper applies kNN-MT to code translation for error correction, proposing two methods: kNN-ECD (single round) and kNN-ECSₘ (multi-round with m sub-datastores), along with a unified name rule to reduce noise from rare identifiers. Experiments on Java→Python translation improve TransCoder-ST accuracy from 68.9% to 89.9% using functional equivalence instead of BLEU.

### Strengths
- Significant accuracy improvement (~20% absolute) over TransCoder-ST, achieved without retraining the model or re-sampling many times (as in self-repair). [R1, R3]
- Simple and extensible framework: both single and multi-round error correction are straightforward. [R2]
- The multi-round distributed structure (kNN-ECSₘ) with m sub-datastores is novel and further boosts performance; analysis varying the number of rounds is interesting and may inspire future work. [R1, R3]
- Extensive empirical analysis including ablation studies that decompose contributions of single vs multi-round correction, sub-datastore performance, and the unified renaming scheme. [R1, R2]
- The authors check for data leakage and show generalization of fixing patterns. [R2]

### Weaknesses
- **Limited technical novelty** – kNN-ECD is very similar to kNN-MT; the unified name rule is not particularly novel given existing related work. [R1, R3] Note: One reviewer rates the contribution as fair (2) while others rate good (3), indicating some disagreement. [R3 vs R1/R2]
- **Unclear motivation** – Why kNN-MT should be especially effective for programming languages rather than natural language is not justified. [R1]
- **Evaluation concerns** – (a) The unit tests used for evaluation are generated by the same TransCoder-ST model that the authors aim to correct; if the test generation itself is noisy, the evaluation is unreliable. (b) Only one language pair (Java→Python) is considered; reverse direction and other languages are neglected. (c) Table 1 lacks important baselines: no comparison to a retraining-based approach (e.g., fine-tuning TransCoder-ST on the same error-correction pairs), no results on state-of-the-art code models, and no latency measurements despite latency being discussed in related work. [R3] Additionally, the construction of error-correction pairs from 10 generated Python functions per Java function may pair a failed function with a successful function that was tested against a different test suite, so the “correction” may not be a true correction. [R3] Translation of PyTests from EvoSuite output has not been manually validated for correctness. [R2, R3] The assumption that the original Java version is bug‑free is also likely violated. [R2]
- **Interpretability is not convincingly demonstrated** – The claimed interpretability is left to the reader to infer; showing a mapping to a software engineer (as in S4.2) does little to explain the model’s decision or gain trust. [R2] Moreover, the key-value pairs in the datastore are still based on neural network representations, so why this is more interpretable than a standard transformer decoder is not explained (both attribute token predictions to source and partial target). [R1, R3]
- **Presentation issues** – Table 3 and Table 4 are hard to read; using figures with detailed numbers in the appendix would be better. [R1]
- **Generalizability to other models** – The datastore is built using errors specific to TransCoder‑ST; applying the same correction datastore to a different model (model B) may not fix its errors, potentially requiring a new datastore for each model, which limits applicability. [R1]
- **Lack of clarity on key design choices** – (a) It is not explained how variable/function names are identified and replaced for the unified name rule (automatic tool?). [R1] (b) Whether error correction is only applied to wrong translations (and how those are judged) is unclear. [R1] (c) In kNN-ECSₘ, does each subsequent ECD receive the mis‑corrected version from the previous module or the original wrong translation? If the former, do partial corrections build on each other? [R2] (d) The improvement of ECS over ECD is attributed to the distributed structure, but no multi-round experiments using a single large datastore repeated m times are performed; the advantage could come from iterative correction rather than distributedness. [R3] (e) Whether there is any fine‑tuning of TransCoder‑ST is not stated. [R1] (f) In Section 3.2, it is unclear how decoder hidden states can correspond to the failed Python function if that is passed to the encoder—or does the “partial Python function” only represent the target generated so far? [R3]
- **Minor** – “Uncorrect” should be “Incorrect.” [R1]
