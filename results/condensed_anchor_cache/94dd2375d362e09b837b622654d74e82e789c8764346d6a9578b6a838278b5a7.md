## Merged Review

### Summary
The paper proposes the Active Data Search (ADS) framework, where an LLM (optimizer) autonomously selects among three data acquisition APIs (Wikipedia Information Retrieval, Demonstration Generation, Question Answering) to collect training data for a policy LLM, using reinforcement learning (DPO) to balance performance gains and computational cost. The method is evaluated on 1,000 in-house tasks and three public benchmarks (AlpacaEval, MT-Bench, Arena-Hard) with Qwen-2-7B-Instruct and Gemma-2-9B-Instruct, showing performance improvements. Reviews show significant disagreement (scores 3,3,6,6,3). Lower-scoring reviewers raise fundamental concerns about the method’s actual implementation (in-context learning, not model training), insufficient baselines, scalability, and generality; higher-scoring reviewers acknowledge innovation and promising results but also note limitations.

### Strengths
- Tackles the important challenge of automating data acquisition for LLM self-improvement, potentially reducing human effort and enabling non-experts to tailor models. (All reviewers)
- Innovative framing of data collection as API calls with an RL-trained optimizer to dynamically select among them; the concept of LLMs developing self-awareness of strengths/weaknesses to guide data acquisition is compelling and original. (Reviewers 1, 3, 4)
- Robust empirical results: substantial and sometimes significant performance gains on 1,000 diverse in-house test tasks and three public benchmarks (AlpacaEval, MT-Bench, Arena-Hard) across two model families (Qwen-2-7B-Instruct, Gemma-2-9B-Instruct), at times matching larger models. (Reviewers 1, 3, 4)
- The framework and the complex training process of the optimizer are clearly explained. (Reviewer 4)
- Related work section is well-structured and positions contributions appropriately. (Reviewer 1)
- The approach incorporates iterative refinement (optimizer training with DPO) and a cost-penalty term, showing consistent improvements. (Reviewer 3)

### Weaknesses
- **Misleading claim: “training” vs. in-context learning.** The paper presents the method as letting the model “train” on collected data, but the actual implementation is in-context learning (adding data to the prompt) without updating model parameters. This is a significant overclaim of the title and main selling point. (Reviewer 5, strong criticism)
- **Insufficient baseline comparisons.** The paper lacks comparisons with:
  - Basic RAG (retrieval-augmented generation) and its variants. (Reviewers 1, 2)
  - Established data generation methods such as Self-Instruct, behavior cloning/distillation from a teacher LLM, and “Generate Rather than Retrieve”. (Reviewer 1)
  - Dynamic API selection vs. fixed single-API optimizers (e.g., Information Retrieval only, Demonstration Generation only, Question Generation only). (Reviewers 1, 3, 4)
  - An untrained LLM or a simple rule-based data collection strategy. (Reviewer 2)
  - Active learning or curriculum learning for data selection. (Reviewer 3)
  - “Question Answering for all instructions” baseline is only evaluated on the in-house test set, not on public benchmarks. (Reviewer 4)
  - No cost vs. quality comparison with relevant prior works. (Reviewer 5)
- **Limited to in-context policy improvement, not fine-tuning.** The method is only tested with data added to prompts, which restricts the amount of data to the context window. Its effectiveness for actual fine-tuning is untested; the RL reward estimation procedure would be prohibitively costly for fine-tuning, and scalability beyond a few examples is unclear. (Reviewers 1, 5)
- **Scalability and efficiency concerns.** Algorithm 1 requires O(N|A||T|) evaluations of the policy model, but computation cost is not reported. Feasibility for larger models, more API types, or practical deployment is not demonstrated. Sensitivity to different policy model architectures and sizes (e.g., Llama) is not systematically tested. (Reviewers 3, 5)
- **Missing ablation studies.**
  - Individual contribution of each API: no experiment removing one API or testing different combinations. (Reviewers 1, 3, 4)
  - Effect of iterative refinement (DPO iterations) not ablated. (Reviewer 3)
  - Impact of generated dataset size (scaling) not studied; the method is limited by context window. (Reviewer 1)
  - Impact of number of input task examples (currently only 5) not studied. (Reviewer 1)
  - Quality, diversity, and relevance of generated synthetic data not analyzed (e.g., perplexity, human evaluation). (Reviewer 1)
- **Optimizer generality and robustness concerns.**
  - Training tasks (MagPie) are similar to test tasks (AlpacaEval, etc.); generalization to unrelated benchmarks (Big-Bench-Hard, GSM8k, MMLU) not demonstrated. (Reviewers 1, 4)
  - Dependence on the MagPie dataset for optimizer training not investigated; sensitivity to training dataset not tested. (Reviewer 1)
  - The method relies on task clustering (grouping similar instances); robustness to different clustering strategies or random grouping not examined. (Reviewer 1)
  - The quality gains against the “Question Answering for all instructions” baseline are relatively minor. (Reviewer 4)
- **Missing analyses.**
  - No analysis of API call patterns (frequency, distribution) at test time. (Reviewer 1)
  - No qualitative analysis of the optimizer's self-reflections (weakness rationales) to gauge accuracy and depth. (Reviewer 1)
  - No discussion of failure cases or tasks where ADS underperforms. (Reviewer 3)
  - Lack of detailed exposition of the reinforcement learning component: reward function design, policy optimization algorithm, specific hyperparameters. (Reviewer 3)
- **Inconsistent use of Llama models.** Llama appears as a comparison point in Table 2 but is absent from Figure 2; rationale not explained. (Reviewer 2)
- **Minor issues.** Grammatical error in Line 50; incorrect citation format (\citet instead of \citep) in Line 58; typo “LLM-as-a judgment” in Line 138. (Reviewer 5)
