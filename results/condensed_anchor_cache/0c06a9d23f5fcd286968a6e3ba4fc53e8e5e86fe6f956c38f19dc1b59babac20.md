## Merged Review

### Summary
The paper proposes Wildflare GuardRail, a guardrail pipeline integrating SAFETY DETECTOR, GROUNDING (vector-database query enrichment), CUSTOMIZER (lightweight wrappers for user-defined protocols), and REPAIRER (hallucination correction based on explanations). The pipeline aims to enhance LLM inference safety and reliability by detecting unsafe input/output, hallucination, providing explanations, and fixing outputs.

### Strengths
- The pipeline systematically addresses safety from pre‑inference to post‑inference, breaking the lifecycle into modular, flexible, and adaptable components.
- The paper is well‑organized, clearly written, and experiments are easy to follow.
- It provides an open‑source attempt to replicate the safety/reliability ecosystem that proprietary models like ChatGPT may have in place.
- The authors developed their own models for safety detection, hallucination detection, and fixing, which can offer better accuracy, efficiency, and flexibility (Reviewer 4).
- Experimental results demonstrate that the proposed method outperforms baseline approaches in reducing toxic content and hallucinations.

### Weaknesses
- **Lack of novelty / minor contribution**: The pipeline is essentially a combination of existing techniques (safety detection, grounding, hallucination detection, repair); individual components are not novel (Reviewers 1, 2, 3, 4). Reviewer 3 and 4 consider the contribution minor (soundness 1–2, contribution 1). Training on existing datasets (e.g., safety detector) is straightforward (Reviewer 2).
- **Safety detection limitations**: The training set is not a full/realistic representation of real‑world jailbreak attempts (Reviewer 1). No comparison against safety‑specific models like LlamaGuard (Reviewer 1). Grouping all risky behaviors under a single “unsafe” category may cause over‑refusal (Reviewer 1). Reviewer 4 asks for justification of the claim that binary “safe/unsafe” classification is sufficient for LLM services given the complexity of AI safety definitions.
- **Hallucination detection weaknesses**:
  - Trained on only one dataset (HaluEval), inadequate for learning the task; classifier limited to that task scope (Reviewer 1). Detection accuracy is relatively low (0.78) (Reviewer 1).
  - The detector requires ground‑truth reference for judging hallucinations—an unreasonable assumption for out‑of‑distribution user queries (Reviewer 1).
  - Training data includes GPT‑4 annotations and explanations, which may introduce additional hallucinations, raising reliability concerns (Reviewer 2).
  - Only tested in‑distribution on HaluEval; out‑of‑domain performance unknown—need ablation (Reviewer 4).
  - Few details on hallucination evaluation; missing metrics such as false positive and false negative rates (Reviewers 1, 4).
  - Use of “Yes”/“No” tokens for detection output: unclear which tokens/whitespace variants are included when computing probability, and how probability is computed (Reviewer 4).
- **Grounding impracticality**: Requires creating vector indices for the entire database per task, not reasonable for general‑purpose LMs (Reviewer 1). Does not capture general retrieval settings where useful information comes from different sources (Reviewer 1). Grounding is essentially existing RAG models (e.g., Lewis et al., Min et al.) and should be compared against them (Reviewer 4).
- **Customizer issues**: Assumes API access for all prompts, impractical for open‑source pipelines (Reviewer 1). No discussion on practicality of defining which tools to use for which purposes (Reviewer 1). Little reporting on real‑time deployment performance (time delay) and scalability (Reviewer 1). Difference between customizer and repairer is unclear (Reviewer 3).
- **Repairer reliability**: Similar to hallucination module, the repairer’s reliability is questionable (Reviewer 1). In Experiment 5, the repairer’s fix rate is evaluated using another hallucination detection model (Vectara) instead of manual evaluation, which is less rigorous (Reviewer 2).
- **Insufficient quantitative evaluation**: Limited evaluation across the pipeline axes; many details missing (Reviewers 1, 3, 4). No supplementary material (Reviewer 1). Figures 5 and 6 lack baseline comparisons; Figure 4 shows similar performance to others (Reviewer 4). Need comparison of grounding with existing RAG models (Reviewer 4).
- **Missing technical details**:
  - Self‑trained model architecture, number of parameters, training procedure not specified (Reviewer 4).
  - No randomness analysis (sampling strategies, number of repetitions, confidence intervals) (Reviewer 4).
  - Line 193: “outputs are difficult to fix” lacks clear definition (Reviewer 4).
  - Line 219: “labels for hallucination” undefined; how obtained? (Reviewer 4).
  - Line 257: random selection from “15 public datasets” vague; no per‑dataset count, uniform sampling, deduplication, or total training set size (Reviewer 4).
  - Line 330: which tokens correspond to “Yes”/“No” (including whitespace variants)? How is probability computed? Is there a fallback if none of the candidate tokens are in top‑k? (Reviewer 4).
  - Different train/val/test splits for hallucination detector (8000/1500/500) and repairer (8000/1000/1000) on HaluEval—reason not explained (Reviewer 4).
  - Section 4.1: why randomly pick a small portion of data for detection training? (Reviewer 3).
  - Sections 6–7: few details on how the repairer corrects flawed output; model not introduced in depth (Reviewer 3).
- **Role of safety detector misleading**: Figure 1 suggests the safety detector handles both unsafe input detection and output hallucination detection, but later text treats them as separate fine‑tuned modules; clarification needed (Reviewer 4).
- **No justification for integrating all tasks in one system** (Reviewer 2). Request for positive/negative examples for each module (Reviewer 2).
- Over‑refusal rate on benign tasks (e.g., “how to kill a python program”) not assessed (Reviewer 1). Distribution of synthetic vs. real‑world jailbreaking prompts in the dataset not provided (Reviewer 1).
- Hallucinations with factual grounding errors in complex/domain‑specific contexts may not be detectable or repairable; lack of ablations on such tasks (Reviewer 1).
- URL experiment comparison with other models (Mistral, TinyLLama): unclear if all models have same API call access and how evaluation is conducted (Reviewer 1).
- Metric “Deployable on edge devices” unjustified; plausibly achievable with pruning/quantization (e.g., Li et al., 2024). “Explainable Results” may be unnecessary if the guard model fixes output (Reviewer 4).
