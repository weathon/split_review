## Merged Review

### Summary

This paper proposes Tool-Planner, a framework that clusters similar API tools into toolkits (via SimCSE embeddings and k-means) and uses tree search over these toolkits as nodes to improve LLM planning efficiency and robustness. Experiments on ToolBench and APIBench with GPT-4 and Claude 3 show higher pass and win rates versus several baselines, with ablations confirming the toolkit design. Reviewer scores vary: one strongly positive (8), two moderately positive (5, 5), and one moderately positive (6). The positive view appreciates the intuitive clustering and reduced decision space; the more critical reviewers note limited novelty (close to DFSDT), dependence on clustering quality, lack of theoretical justification, and missing comparisons (ToolChain*).

### Strengths

1. The idea of using toolkits (clusters of similar APIs) as nodes in tree search is novel and intuitive, providing a structured approach to handling API failures and reducing the LLM decision space. (Reviewer 2, 4; high confidence)
2. Comprehensive experiments across multiple datasets (ToolBench, APIBench) and against strong baselines (including DFSDT), with extensive ablation studies on the core toolkit component. (Reviewer 1, 2, 4)
3. Detailed appendix with experimental specifics and case studies; insightful error analysis. (Reviewer 1)
4. The method shows strong empirical pass rates and win rates, substantiating its effectiveness in improving LLM tool use efficiency and effectiveness. (Reviewer 1, 3)
5. The significance of simplifying planning with large action spaces: performance remains high regardless of many future tools. (Reviewer 2; high confidence)
6. The paper is clearly written and easy to follow, especially the methodology. (Reviewer 1, 2)

### Weaknesses

- **Novelty limited**: The method is derived directly from DFSDT by replacing API nodes with toolkits (Line 375), and the paper lacks clear distinction from this baseline. (Reviewer 1, 3) Reviewer 2 is more positive and considers the toolkit a novel contribution. (disagreement)
- **Missing comparison with ToolChain***: ToolChain* is compared in Table 1 but excluded from experiments, yet it is a relevant tree-based action-space method. (Reviewer 1, 2) This omission weakens the evaluation. (Reviewer 2 asks: Why is ToolChain* not included in experiments?)
- **Missing comparison with tree-based inference methods** (e.g., Language Agent Tree Search, AlphaZero-like tree search) mentioned in related work. (Reviewer 1)
- **Clustering quality dependence**: Performance heavily depends on the clustering model and algorithm. The paper lacks intermediate metrics to evaluate clustering quality beyond end-to-end performance (Table 5). (Reviewer 4; high confidence) Also, the choice of k for k-means requires exploration and is impractical for new datasets (Figure 3); more sophisticated adaptive methods (e.g., DBSCAN) are not tested. (Reviewer 3, 4)
- **No theoretical justification** for why clustering tools improves planning; similar benefits might be achieved by simply prompting the LLM to prefer similar APIs when handling failures, without explicit clustering. (Reviewer 4; high confidence)
- **Methodology clarification needed**: In Section 3.2, “the model will choose any API within the toolkit for invocation” oversimplifies API selection; each API has a specific parameter structure, and the selection process lacks clear decision-making beyond randomness. (Reviewer 3)
- **Replanning stage lacks quantification**: Paper does not count how many tasks reach the “Task Replanning Across Toolkits” stage, nor report token consumption or computational time for those tasks. Also unclear what criteria trigger cross-toolkit replanning. (Reviewer 3)
- **Efficiency evaluation insufficient**: Tool-Planner runtime is significantly higher than most baselines except DFSDT. The paper should provide number of LLM invocations and token usage statistics per method, and analyze how the number of clusters affects execution efficiency. (Reviewer 3)
- **Ablation baseline (Toolkit Integration) not fully specified**: How is the integration achieved? What criteria select the toolkit before invoking a specific API? (Reviewer 3)
- **Figure 2 misleading**: It looks like DFSDT or ToolChain* because search appears over single APIs rather than toolkits; more emphasis on toolkit nodes would improve clarity. (Reviewer 2)
- **Table 1 feature categories vague**: “Tool Integration” is unclear; “Tool Clustering” distinguishes Tool-Planner from DFSDT better. (Reviewer 2; Reviewer 2 asks: What does “Tool Integration” refer to? How were the “Explainable Planning” and “Tool Integration” categorizations decided?)
- **Adaptive clustering not explored**: No experiments with DBSCAN or other automatic clustering methods; need guidelines for selecting k optimally for new datasets. (Reviewer 3, 4; Reviewer 4 asks: Have the authors considered more sophisticated clustering methods that don’t require pre-specifying k?)
- **Handling dynamic APIs unclear**: How does Tool-Planner perform when APIs change frequently? Is reclustering needed, and if so, how often? (Reviewer 4)
- **Name suggestion**: Rename to ToolkitPlanner to better reflect the method. (Reviewer 1)
