## Merged Review

### Summary
This paper proposes AuPairs, a method for self-repair in code generation. It synthesizes a set of golden pairs (problem, initial guess, fix) from a dataset, selects complementary pairs at inference time, and uses each as a 1-shot in-context example to generate a repaired solution; the highest-scoring fix among N attempts is selected. Experiments on 7 competitive programming datasets with Gemma and Gemini models show improvement over a best-of-N baseline. Reviewers agree the problem is important and the approach is interesting, but they raise significant concerns about evaluation rigor, scope, and practical applicability. Reviewer 4 (score 1, high confidence) is much more negative than the other three (scores 5,5,6), questioning the evaluation, practicality, and claims of generality.

### Strengths
- **Interesting and relevant problem**: The paper tackles an important task of self-repair in coding (R2, R4). The focus on improving LLM responses via in-context learning without extra training is well-chosen (R3).
- **Experimental breadth**: Effectiveness is demonstrated across a wide range of datasets (7 competitive programming datasets) and models (Gemma 9B, 27B; Gemini 1.5 Flash, Pro), including in-domain and out-of-domain generalization (R1, R2, R3).
- **Controlled compute budget**: The method is designed to use exactly N LLM calls (best-of-N style), which alleviates concerns about uncontrolled compute growth (R2). 
- **Ingenious design**: The approach of reusing imperfect fixes as guesses in pair generation and the complementary selection via score subtraction are innovative (R3). 
- **Presentation**: The paper is easy to follow (R4). Multiple reviewers find the empirical comparison interesting (R1) and the analysis comprehensive (R3).

### Weaknesses
- **Overclaim of generality/domain-independence**: The paper claims (lines 079–081) a general-purpose, domain-agnostic algorithm but is only evaluated on code repair. R1 and R4 find this confusing and unsubstantiated. R1 notes that unit tests (essential to the pipeline) are absent in hallucination detection or VLM settings; R4 states the method is only evaluated in one domain. Without a second use case or clear adaptation, the claim is misleading.
- **Unrealistic reliance on test cases**: The method assumes test cases are available during generation (to score guesses and fixes). R2 argues this “reveals the answer” and enables test-driven development, which is unrealistic in real-world coding where test cases are unknown. R1 similarly asks how the framework could apply to domains without unit tests. This significantly simplifies the task and inflates performance.
- **Weak baseline and missing comparisons**: The only baseline is best-of-N (R1, R2, R3, R4). R3 notes that prior work (e.g., Self-Repair [1]) explores different feedback/repair budgets, and methods that provide execution results before resampling are not compared. R4 adds that other RAG-based approaches and standard pass@k metrics are missing, and the best-of-N configuration is unclear (zero-shot? what prompt?). The comparison is insufficient to demonstrate the method’s advantages.
- **Incomprehensive model selection**: Only Gemma and Gemini models are used. R2 points out that coding-specific models (CodeGemma, CodeLlama, DeepseekCoder) are omitted, and the paper should either evaluate them or clarify the method only applies to text-oriented LMs. R4 also notes missing results for other models.
- **Evaluation metric issues**: The evaluation metric (apparently “number of unit tests passed”) is not clearly defined (R2, R4). R2 argues that number of tests passed does not correlate with program correctness (all tests must pass) and that test case distribution/sufficiency is not analyzed. R4 notes the absence of standard pass@k metrics. R3 adds that the experimental datasets are overstated: six of seven are subsets of CodeContest, and code repair benchmarks (e.g., LiveCodeBench self-repair, xCodeEval APR) are missing.
- **Practicality and computational cost**: R4 notes that for each test problem, the method requires |C| LLM calls (to rank all candidate pairs), which is extremely expensive. R2 asks how the N LLM call compute budget is controlled, since using N AuPairs plus N fixes would be 2N calls. R4 questions whether alternative ranking (e.g., by sequence similarity) could reduce cost.
- **Lack of algorithmic detail**: R1 finds Figure 1 too high-level; the extraction process is unclear. R4 points out that parameters are unspecified: when does generation stop (Section 2.1)? what is the size of C relative to D? what is k (number of random samples)? Is generation controlled for balanced representation? R1 and R2 also ask for a clear list of required inputs (the validation set is mentioned later but not in the initial description).
- **Diversity vs. performance trade-off not substantiated**: R3 observes that Figure 7(b) shows performance scores of AuPairs declining as diversity increases (from Gemini-1.5-flash to Gemma-9B to Gemma-27B), contradicting the claim that diversity comes without performance cost.
- **Validation set requirement**: The method requires a held-out validation set. R2 asks how it applies when no such set is available. R1 notes this requirement is not stated in the initial problem setup.
- **Minor concerns**: Title is confusing: the paper solves text-to-code, not code repair where a broken program is given (R4). Figures could be annotated better (R1, R2, R4) – e.g., explain colors in Figures 1 and 3, annotate with numbers, explain scores in Figure 2. R3 suggests optimizing information density in figures. R4 questions why one-shot is limited to 1 (can larger k be used?) and why there may be fewer than 32 AuPairs from large datasets.
