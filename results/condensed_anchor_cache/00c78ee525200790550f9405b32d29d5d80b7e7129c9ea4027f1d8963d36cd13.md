## Merged Review

### Summary
The paper presents MUSTARD, a framework for automatically generating informal and formal theorem-and-proof data by prompting an LLM with mathematical concept seeds and using the Lean prover to filter valid formal proofs. The resulting dataset, MustardSauce, contains 5,866 validated data points (the abstract states 5,866; the reviews sometimes mention 7,335—likely including unfiltered versions). Fine-tuning Llama 2-7B on this data yields a 15.41% average relative gain in automated theorem proving and 8.18% in math word problems. The three reviewers (scores: 8, 6, 8) all consider the topic significant and the dataset valuable, but one reviewer (score 6) is more critical about the magnitude of improvements, statistical robustness, and scalability.

### Strengths
- The problem is important: producing high-quality reasoning step data at low cost is a key challenge for the community. (R1, R2)
- The proposed pipeline (LLM generation of problems and informal proofs, then formalization and verification by Lean) is conceptually simple and technically innovative. (R2, R3)
- The resulting dataset is diverse (elementary to undergraduate level) and contains step-by-step reasoning, which is useful for chain-of-thought training. (R1, R3)
- The dataset is a valuable benchmark for the research community. (R1)
- The paper includes a thorough analysis of the generated data, including an expert user study—something rarely done and which validates data quality. (R1)
- Clear writing and easy-to-follow experiments. (R2)
- The evaluation is rich: two models (Llama 2-7B, GPT2), multiple fine-tuning strategies, and different training data splits. (R2)
- Fine-tuning on MustardSauce leads to considerable performance gains on GSM8k and Mathlib. (R1, R3)
- The formalization step shows validated effectiveness: a simple filtering of valid formal statements improves downstream performance. (R3)

### Weaknesses
- The LLM used for informal data generation is not specified. This is a crucial omission for assessing data quality, bias, and limitations. (R1, R2)
- The approach is inherently limited by the capability of the LLM used for generation. If that LLM is already near GPT-4 level, it is unclear how generating data with it can further improve the best models. (R1, R2 mention scalability)
- The improvement from involving the theorem prover for filtering is relatively minor (see Table 4: $\texttt{in}$, $\texttt{ra}$, $\texttt{va}$). It is not clearly shown that filtering outperforms simply using the entire generated dataset. A more detailed trade-off analysis between data quantity and quality is needed. (R2)
- The manual verification sample is very small (only 88 data points). Given the variance across problem types, this may not be statistically robust. A larger, more diverse sample and a power analysis are required. (R2)
- Scalability is unknown: only 7,335 data points were generated (a small number for LLM fine-tuning), results after fine-tuning are described as "mediocre" by one reviewer, and no experiments were run on larger models (e.g., 34B, 70B, GPT-3). (R2)
- Inconsistencies between the natural language reasoning and the formalized language (e.g., the final result computed by the `#reduce` statement) may go undetected because the theorem prover does not report an error. The paper does not explain how such inconsistencies are handled. The filtering strategy in Table 13 does not cover this case. (R2)
- There is a misalignment between the generated data and the test sets. For example, the dataset includes undergraduate-level problems (e.g., alternating series convergence) whereas GSM8k contains only elementary-school-level problems; using `#reduce` in Lean is suitable for word problems but inconsistent with the style of proofs in Mathlib. The paper should explain how the generated data applies to different types of math problems. (R2)
- The low value of D3 in Table 3 is unclear and not adequately explained. (R1)
- The "valid" rate of the generated formal statements and proofs is not reported. (R3)
- Data contamination from using an LLM to generate training data is a risk; the paper should present evidence that no serious contamination occurred. (R3)
