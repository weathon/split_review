## Merged Review

### Summary
The paper introduces Conveyor, an LLM serving system that reduces request completion latency by parallelizing text generation (decoding) and external tool execution. Conveyor uses a parser within the prompting interface to identify tool execution commands, allowing partial execution of tools before full decoding finishes. Evaluated on code generation, search, planning, and validation workloads, the authors report up to 38.8% latency improvement compared to sequential execution.

### Strengths
- The concept of separating tool execution from LLM decoding and running them in parallel is interesting and timely, addressing an important problem in compound AI systems.
- [Minority: Reviewer 4] The paper touches on a very timely and important matter as inference optimization becomes increasingly important with broader adoption.
- The background introduction to LLM serving and the tool execution workflow is correct and provides a comprehensive breakdown of the workflow for LLMs with external tool augmentation.
- Evaluation covers diverse workloads—code generation, search, planning, and validation—demonstrating Conveyor across various scenarios. [Minority: Reviewer 4 considers the experimental pipelines well-chosen, representing a good range of practical use cases.]
- [Minority: Reviewer 4] The theoretical framework is intuitive.
- The paper involves engineering effort in prompt design.
- [Minority: Reviewer 3] The method addresses a problem for which satisfactory solutions are currently lacking and offers a reference for future research.
- [Minority: Reviewer 3] The writing of the paper is good.

### Weaknesses
- **Unrealistic assumption about tool calls**: The paper implicitly assumes each request triggers only one tool execution exactly once. This oversimplification (visible in Figure 4, Section 3.4, and evaluation) deviates from real-world workloads where multiple tools or multiple invocations per request are common. [Reviewer 1; also echoed in Reviewer 2's question about how results would change with multiple tools/invocations.]
- **Theoretical analysis is weak or trivial**: Section 3.4's bounds assume a single tool call per request and remain loose (latency improvement ranges widely). [Reviewer 1] Reviewer 4 notes that the difference between $\sum_i^n\max(g_i, t_i) + g_{n+1}$ and $L_{new}$ is identical in the best case, missing an optimization criterion and a clear worst-case penalty for inefficiency. Reviewer 2 adds that the analysis omits overhead from token passing and does not account for dependencies that could delay tool execution.
- **Imprecise terminology / limited system contribution**: The so-called "serving system" is actually just a prompting interface; it does not address model-, algorithm-, or system-level optimizations. "Parallel execution" is merely separate prompt calls, not multi-threading or hardware-level parallelism. [Reviewer 1] Implementing the solution in a real serving system such as vLLM would strengthen the case. [Reviewer 1 question: "Can you implement this into the current mainstream serving system, such as vLLM?"]
- **Overhead and applicability concerns**: The optimization benefits only long, independent tool calls; it could increase latency when overhead outweighs gains. A dynamic hybrid approach that enables/disables partial execution based on predicted tool and system properties would be more effective. [Reviewer 2] The system's ability to recognize partial execution triggers requires adaptation per new capability (e.g., triggers tied to specific programming language delimiters), limiting generalization. [Reviewer 2] Reviewer 4 also questions whether rule-based triggers (like newlines) are practical for potentially hundreds or thousands of tool types, suggesting learning from tokens would be more appropriate.
- **Lack of rigorous overhead analysis**: The parser is claimed to be "efficient" but no specific metrics are provided to substantiate this. [Reviewer 2] The theoretical analysis omits the latency of token passing and the probability of dependency failures. [Reviewer 2]
- **Insufficient evaluation / baselines / datasets**: 
  - Only a single experiment per workload is conducted; multiple trials are needed to demonstrate representativeness and generalizability to other tasks within the same workload. [Reviewer 3]
  - No comparison to state-of-the-art external tool augmentation methods such as INFERCEPT. [Reviewer 2]
  - Although the authors note a lack of realistic datasets, ToolBench provides data for external tool augmentation and should be used. [Reviewer 2]
  - Evaluation does not compare Conveyor's scheduler to dynamic or continuous batching. [Reviewer 4]
  - An appendix with more experimental details would be helpful since the work is largely empirically based. [Reviewer 4]
  - The number of code lines is not a good measure of human effort; complexity and adaptability matter more. [Reviewer 2]
- **Related work is insufficient**: The paper lacks discussion of methods like LLM-dCache and APIServe that also improve efficiency of LLM external tool utilization. [Reviewer 3] The approach is straightforward and relies on predefined rule-based scheduling without incorporating feedback (e.g., as in ReAct), limiting adaptability and generalizability. [Reviewer 3] No demonstration of integration with caching or memory techniques. [Reviewer 3]
- **Minor issue**: Citation style missing brackets makes the paper hard to read. [Reviewer 4]
