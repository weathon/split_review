- Scores: 3, 3, 5, 3

## Merged Review

### Summary
Reviewers agree that the paper addresses an important problem—providing LLMs with a complete yet non-redundant set of tools—and that the introduced RecTools dataset and TRACC metric are useful contributions. The PTR approach is intuitive and shows effectiveness on three datasets. However, the majority of reviewers (scores 3,3,3) raise significant concerns about missing experimental validation, insufficient comparisons, lack of clarity, and the dataset’s reliability. One reviewer (score 5) is more positive, emphasizing that PTR dynamically adjusts the toolset and that the comprehensive experiments validate the approach. Across all reviewers, the main weaknesses center on: (i) the lack of evidence that tool redundancy actually harms LLM performance, (ii) the failure to measure downstream task improvements, (iii) missing baseline comparisons (especially recent tool retrieval works), and (iv) computational cost not being reported.

### Strengths
- The paper tackles a highly relevant problem: providing LLMs with a tool set that is simultaneously complete and non-redundant. (Reviewer 1, Reviewer 3)
- The new RecTools dataset and the TRACC evaluation metric are valuable contributions specifically designed for tool recommendation/retrieval in LLMs. (Reviewer 1, Reviewer 2, Reviewer 3, Reviewer 4)
- The proposed PTR method is intuitive and demonstrates promising results across three datasets (ToolLens, RecTools, and another). (Reviewer 2, Reviewer 3)
- The code is publicly available, enhancing reproducibility. (Reviewer 2)
- The paper is well-organized and easy to follow. (Reviewer 2)

### Weaknesses
- **Missing validation of redundancy harm.** The paper claims that redundant or missing tools degrade LLM problem-solving, but does not provide any quantitative experiments to support this claim. For example, the concept of “oversolving” (line 233) is not backed by experiments showing its actual impact on performance. (Reviewer 1, Reviewer 2, Reviewer 4)
- **No downstream evaluation.** The experiments only evaluate retrieval metrics; there is no verification that improvements in tool recommendation translate into better LLM-generated responses on the downstream task. As an intermediate step, tool retrieval should be assessed by its effect on final LLM output. (Reviewer 1, Reviewer 2)
- **Insufficient baseline comparisons.** The evaluation omits several recent state-of-the-art tool retrieval methods, e.g., [1] “Enhancing Tool Retrieval with Iterative Feedback…”, EMNLP 2024; [2] “Re-Invoke: Tool Invocation Rewriting…”, EMNLP 2024; [3] “Towards Completeness-Oriented Tool Retrieval…”, CIKM 2024. A more thorough comparison with a wider range of existing methods is needed. (Reviewer 1, Reviewer 3)
- **Lack of clarity in method description.** The paper does not explain how vector representations of tool bundles are obtained, nor does it specify the ordering of tools within bundles when computing metrics. (Reviewer 1) Also, the two-step evaluation process (random tool removal for “Partial Solving” after “Oversolving”) is confusing and needs clarification. (Reviewer 4)
- **Dataset concerns.** The necessity of proposing RecTools is not well motivated; ToolBench [ToolLLM] appears to encompass all the same characteristics. The construction of RecTools relied solely on GPT-4 to determine “Exact Solving” without actually invoking the tools, which reduces confidence in the labels. Additionally, the metrics on RecTools are significantly higher (NDCG@K ~0.9) than on ToolLens, suggesting the dataset may be less challenging. (Reviewer 2, also echoed by Reviewer 1 asking about differences from ToolBench)
- **Computational and memory overhead not discussed.** PTR involves multiple LLM calls; the paper should report token consumption, model complexity, and the trade-off between performance gains and computational cost. (Reviewer 3, Reviewer 4) Also, an analysis of the efficiency and cost associated with using different LLMs (e.g., those in Table 2) and an “without LLM” baseline would strengthen the evaluation. (Reviewer 4)
- **Terminology and definition issues.** The use of “tool recommendation” instead of “tool retrieval” seems unnecessary, as the formulation is identical to prior retrieval work. (Reviewer 2) Additionally, one reviewer notes that unlike traditional recommendation (where different users may prefer different items), here there is only one ground truth per query, making it more like “prediction” than “recommendation”. (Reviewer 3) Moreover, Definition 1 is redundant: when the recommended set equals the ground truth set, the cardinality constraint is automatically satisfied. (Reviewer 2)
- **Metric justification.** The TRACC metric uses the absolute difference in tool counts (\(|n_2 - n_1|\)). The paper does not sufficiently explain why traditional metrics like F1-score (which already consider precision and recall) are insufficient for this task. (Reviewer 2, Reviewer 4)
- **Reliance on semantic analysis only.** Selecting suitable tools based solely on LLM-based semantic analysis of tool descriptions may be ineffective, especially when many tool descriptions are “No description available”. The paper does not consider using past interaction information or feedback from the LLM after actually invoking tools. (Reviewer 2)
- **Lack of ablation on the tool-bundle step.** In Table 3, performance appears to improve even without the Tool Bundle Acquisition step (i.e., using random selection), yet outperforms BM25 and Contriever for initial bundle acquisition. The paper does not explain why this is the case. (Reviewer 1)
- **Missing comparison with decomposition-first paradigms.** The paper does not discuss how the proposed method compares to first decomposing a task into subtasks and then retrieving tools for each subtask. (Reviewer 1)
