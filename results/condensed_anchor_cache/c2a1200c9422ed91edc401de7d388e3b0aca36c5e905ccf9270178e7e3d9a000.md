## Merged Review

### Summary
The paper studies the relationship between task complexity (approximated by a Kolmogorov complexity proxy using compressed minimal Python code) and the minimum transformer size required to learn arithmetic tasks from ListOps. It finds a power-law (cubic) scaling between KC and parameter count, reports that sum mod 10 is harder than max/median but easier when trained alongside them, and analyzes embeddings to infer that single-task models (sum-only) memorize while joint models learn numeric-like representations.

### Strengths
- **Learning mechanisms and embedding analysis** (Reviewer 1, 3): The paper attempts to understand how small transformers acquire arithmetic abilities, using Kolmogorov complexity rigorously. The analysis of learned embeddings via cosine similarity and PCA is interesting, especially evidence that the model learns sorting and parity as intermediates for SUM mod 10. Reviewer 3 notes the thorough study of embedding weights revealing circular patterns in cosine correlations.
- **Fresh perspective on task complexity and scaling** (Reviewer 2): Offers a fresh perspective on how task complexity influences scaling laws, which traditionally are considered independent of tasks. Connecting Kolmogorov complexity to the scaling law is new.
- **Rigorous derivation of approximate KC** (Reviewer 2): The process of deriving approximate Kolmogorov complexity is rigorous.
- **Gzip for KC characterization** (Reviewer 3): Using gzip and Kolmogorov complexity to characterize task complexity is a strength.
- **Presentation** (Reviewer 4): The presentation is well done; the paper is well-focused on the specific setting and fairly attempts to answer the described problem.

### Weaknesses
- **Kolmogorov complexity proxy is problematic and not generalizable** (Reviewer 1, 2, 3, 4):
  - (R1) Using compressed size of minimal Python code is problematic; the rules in Appendix C seem arbitrary and compressed sizes for the three algorithms are likely similar.
  - (R2) KC is extremely difficult to compute for any practical task, limiting practical implications of the scaling law.
  - (R3) The proposed measure has two parts (symbolic KC and numerical KC) that are inconsistent and not generalizable. It only works for ListOps and is not scalable (e.g., how to define minimal implementations for large codebases?).
  - (R4) The justifications of how KC affects learning are incomplete; the arguments for ListOps are not convincingly relevant to general language model use cases.

- **Insufficient data to support scaling law** (Reviewer 1, 3, 4):
  - (R1) The fitted cubic scaling law (KC ≈ 18n_p^{0.34}) is based on too few data points to be reliable.
  - (R3) Figure 1 right panel fits a line to only 3 algorithms; too few for any scaling law indication.
  - (R4) The relationship is weak; Figure 2 shows many tasks cluttering around the same number of parameters.

- **Lack of novelty and insufficient support for key claims** (Reviewer 2, 3, 4):
  - (R2) Beyond the KC connection, the paper lacks novelty. For example, the sum-only operation maps 100 to 10 classes, making memorization easier than understanding; models trained on max/min/median map 1000 to 10 classes, making understanding more likely. Thus the observed embedding differences are expected.
  - (R2) The claim that multitask learning accelerates learning of harder tasks is not adequately supported. The benefit from MAX, MIN, MED to SUM may only be due to learning numeric representation. To support the claim, experiments should show that, e.g., MAX only does not help MIN, MED, SUM, but MAX and MIN together help MED and SUM.
  - (R3) Section 3.2 assumes “MAX+MIN+MED” has higher task complexity than “SUM” without proof.
  - (R4) The finding that joint training improves performance is not new and has been explored extensively (citing Xie et al., Doremi, NeurIPS 2023; Xie et al., Importance Resampling, NeurIPS 2023; Miranda et al., Beyond Scale, arXiv 2023). The main claim is not convincingly relevant to general LMs.

- **Incomplete analysis of learned algorithms** (Reviewer 3):
  - The paper categorizes models as learning only symbolic or numeric algorithms, but neural networks may discover mixed algorithms. A systematic circuit analysis (e.g., as in the cited paper) is needed.
  - Section 3.3: The conclusion that the SUM algorithm “has not developed a structured representation of numbers” is based only on embedding inspection; other parts of the model should be examined. There is no evidence that the SUM algorithm memorizes the numeric table.

- **Presentation and completeness issues** (Reviewer 1, 2, 3):
  - (R1) Plots are hard to read (font too small, legends difficult to parse).
  - (R1) Accuracy is defined only testing the first character after ‘=’; a strict accuracy measure is missing.
  - (R1) Total number of possible equations in the default setting (max nesting 3, num_operands 3) is unclear; what fraction of examples is the model seeing during training? The 1k test set seems too small to be representative of the full universe of examples up to max nesting and num_operands. (R1 question: is the number around 50k?) Need to check if accuracy on the test set is representative.
  - (R1, R3) Incomplete sections: missing Appendix C.1, B (“Designing solution algorithms”), K (“Ablation Studies”); placeholders like “[insert number]” and missing parentheses remain.
  - (R1) Notation inconsistency: “SUM” vs “sum”.
  - (R1) Line 135: “representing the” → “representing them”.
  - (R2) Some sentences appear LLM-polished (e.g., “As we push the boundaries of AI capabilities...”) and should be made more natural.
  - (R2) Appendix content should be in the main body; the main body has verbose sentences and large spaces.

- **Experimental design and data concerns** (Reviewer 1, 4):
  - (R1) The naive solution for max may not require large memory; it could be a 10x10 table for ListOps. (R1 question)
  - (R1) The attention output/input ratio metric needs definition; it is referenced before being explained. (R1 question)
  - (R1) Does using for loops in Appendix C assume comparisons even though the paper tries to avoid them for symbolic algorithms? (R1 question)
  - (R4) The length of examples affects difficulty and should be considered in experimental results.
  - (R4) Could have used alternative complexity measures (e.g., decision problems in formal language) or a simpler transformer with vocabulary restricted to relevant symbols for a more controlled experiment.

- **Methodological concerns about KC estimation** (Reviewer 1, 3):
  - (R1) The naive solution for max may not require large memory; it could be a 10x10 table for ListOps. (Also listed above)
  - (R3) The proposed task complexity measure is not consistent; it has two parts (symbolic and numerical) and is not generalizable.
