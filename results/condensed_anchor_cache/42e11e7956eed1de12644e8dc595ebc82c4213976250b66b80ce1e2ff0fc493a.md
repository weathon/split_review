## Merged Review

### Summary
This work proposes SELF-DEBUGGING, a few-shot prompting approach that enables LLMs to debug their own generated code by investigating execution results and generating natural language explanations (rubber duck debugging). The method achieves state-of-the-art performance on Spider (text-to-SQL), TransCoder (C++-to-Python translation), and MBPP (text-to-Python generation). The authors systematically evaluate multiple feedback variants (Simple, UT, Expl, Trace) across models and tasks.

### Strengths
- Proposes a novel approach, SELF-DEBUGGING, that teaches LLMs to self-debug via few-shot demonstrations, inspired by rubber duck debugging (Reviewer 1, 2).
- Achieves state-of-the-art results on Spider (2-3% improvement overall, 9% on hardest level), TransCoder, and MBPP (up to 12% improvement) (Reviewer 1, 2, 3).
- Provides a systematic, thorough evaluation of self-repair across multiple models, tasks, and feedback methods (Reviewer 4).
- The method is simple, effective, and can be applied to any LLM (Reviewer 3); the intuition and introduction are clear (Reviewer 3).
- Discusses ethical considerations of using LLMs for automated code generation (Reviewer 1).

### Weaknesses
- **Unfair comparison with baselines (major concern from one reviewer):** The self-debugging pipeline uses an oracle (test execution success) to decide whether to enter the repair round. Existing baselines and reranking methods do not have access to this oracle during inference; thus the reported improvements may be meaningless. This reviewer suggests either letting the model self-decide correctness (without oracle) or giving baselines access to the oracle via resampling to ensure a fair comparison (Reviewer 4).
- **Statistical significance unclear:** The 2-3% improvement on Spider (and code-explanation-only gains on TransCoder/MBPP) are not tested for statistical significance and could be accidental results of prompt changes. Self-debugging without unit test execution shows very limited, possibly insignificant improvements (Reviewer 2).
- **Missing comparison with related self-reflection method:** The paper does not compare with Reflexion (Shinn et al., 2023), a similar self-reflection approach (Reviewer 3).
- **Logic error handling not demonstrated:** It is unclear whether self-debugging can fix logic errors, where the code is correct but does not actually solve the problem. The paper only shows fixes for grammar and semantic errors (Reviewer 3).
- **Inference latency not reported:** The additional computational cost and latency from multiple rounds of explanation and debugging is not discussed, which is a concern for practical use (Reviewer 1).
- **Methodology clarity:** Although the intuition is clear, the methodology section (Figure 1) is not sufficiently detailed. A concrete example in the main text would help understanding of the multiple components (code execution, explanation, correctness inference) (Reviewer 3).
- **Sample efficiency claim needs better justification:** The claim of improved sample efficiency is questionable because self-debugging generates many more tokens per problem. A fairer comparison would be average number of tokens generated for solving each problem (Reviewer 3).
- **Presentation inconsistencies in results:** In Table 1, the line "Codex" appears under the "Self-Debugging (this work)" section but its meaning is unexplained and the results differ from other self-debugging variants. Also, Codex results for Spider and MBPP are inconsistent between Table 1 and Table 2 (Reviewer 2).

Note: Initial presentation issues (Section 4 readability and table formatting) were fixed by the authors and are no longer considered weaknesses (Reviewer 2).
