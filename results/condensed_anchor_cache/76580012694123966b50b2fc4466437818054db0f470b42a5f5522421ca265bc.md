## Merged Review

### Summary
The paper introduces Eureka, an LLM-powered method for automatically generating reward functions for reinforcement learning tasks. Eureka uses GPT-4's zero-shot code generation and in-context improvement to perform evolutionary optimization over reward code, without task-specific prompting or pre-defined templates. It iteratively improves initial reward proposals by feeding back policy evaluation text and environment source code. Evaluated across 29 Isaac Gym environments with 10 robot morphologies, Eureka outperforms human-designed rewards on 83% of tasks (average 52% improvement). A case study demonstrates a simulated Shadow Hand performing pen spinning via curriculum learning. The approach also incorporates human feedback for reward safety/quality without model updating.

### Strengths
- Novel and clever approach: using LLMs for zero-shot reward code generation and iterative improvement, exploiting LLM code-writing and in-context improvement capabilities. The idea is simple but yields surprisingly good performance, reflecting a well-structured system.
- Removes dependency on expert demonstrations for reward design; LLMs serve as a cheap alternative for acquiring domain-specific task knowledge.
- General pipeline for reward design without task-specific templates, showing generalization across diverse tasks. Potentially saves significant human effort in reward shaping.
- Effective combination of LLM with evolutionary search, with potential for other areas.
- Clear presentation; authors provide all prompts and code.
- Demonstration of challenging pen spinning task that had not been solved before.
- Approach can incorporate human feedback (RLHF) without model updating.
- Well motivated; could lead to interesting advances in RL.

### Weaknesses
- **Lack of limitations discussion**: No section or extended discussion on limitations. Claims of generality are overstated given evaluation on single simulator (Isaac Gym) and fixed RL algorithm. Missing discussion on applicability to more complex environments (e.g., exceeding LLM context window), real-world scenarios, or different simulators.
- **Unfair human comparison**: Human-designed rewards were zero-shot and not tuned over many RL trials; equal cost (evolutionary search) might change results. Comparison may be unfair.
- **Assumption of environment source code access**: Method critically depends on having full source code (observation portion) as LLM context. This is unrealistic for many RL setups (black-box simulators, real-world systems, compiled interfaces). May be restricted to simulated environments only.
- **Strong assumption on fitness function**: Evolutionary search requires a fitness function F(.) that implicitly accesses ground-truth reward to evaluate policies. This presumes a pre-existing notion of task success, which is what reward design aims to define. Limits applicability to tasks with known ground-truth rewards (often sparse), not real-world unpredictable tasks.
- **Missing technical details in main paper**: Core aspects like exact input/output of evolutionary search, what "reward reflection" does, how RL method choices affect it, are unclear. Details in appendix/code are insufficient for understanding the main approach.
- **Lack of clarity on environment context**: What level of environment detail is needed? For simulators other than Isaac Gym, what information must be provided? The "environment as context" is not fully defined.
- **"Zero-shot" classification unclear**: LLM may have seen similar environments during training; it is unknown if generation is truly zero-shot.
- **Time and compute resource cost not addressed**: Each iteration samples tens of reward functions, each requiring multiple policy training runs. No details on total time, compute resource requirements, how many environments per reward sample, termination criteria, or whether insufficient training could miss effective rewards.
- **Pen spinning demonstration clarity**: Unclear what drives success (reward design vs. unspecified engineering). Section 4.3 leaves questions: How was pre-trained policy obtained? Is curriculum learning using same or different reward functions? If same, dual-stage optimization may be the cause, not reward design. If different, how are multiple reward functions generated and how many are needed?
- **Missing generalization questions**: Can method handle tasks with diverse objects? If task requires image input (hard to run many environments simultaneously), will method still work? Would only initial success reward lead LLM to find more optimal reward?
- **Issue with leaking simulation internals**: Using environment code may leak internal simulation details beyond intended sensing/acting interface. Automatic extraction of observation portion does not guarantee no leaks.
- **Figure contrast/font sizes**: Figure 2 and 3 could be improved for readability.
- **Reviewer 4 (most positive, score 8)** raises distinct weaknesses on time cost, resource requirements, and applicability to image-based tasks; these are preserved as they overlap with missing experiments/ablations.
- **Reviewer 3 (most negative, score 5)** emphasizes the unrealistic assumptions about source code access and fitness function; these are kept as distinct minority viewpoints.
