## Merged Review

### Summary

The paper introduces Learning to Presolve (L2P) for Mixed Integer Programming (MIP), a supervised learning framework that uses simulated annealing (SA) solutions as training labels to predict instance-specific presolving parameters (priority, max rounds, timing). This is a novel area—the first work to apply learning to the presolving stage of MIP solvers. The proposed neural net first predicts the priority order, then uses that prediction to predict max rounds and timing. L2P is orthogonal to learning-based improvements within the B&B stage. Evaluated on diverse real-world datasets (sustainable corridor optimization, maritime inventory routing, load balancing, item placement), L2P yields consistent solving-time improvements with negligible per-instance overhead (<0.5s) compared to default presolving and other hyperparameter tuning methods. The authors release their code. All four reviewers consider the work novel and the results strong, but they flag missing procedural details and certain reporting choices that limit reproducibility and interpretation.

### Strengths

- **Novel research direction.** Tackles an understudied aspect of MIP solving by learning instance-wise presolving parameters. This is a pioneering application of deep learning to presolving. (R1, R2, R3, R4)
- **Well-conceived framework.** The L2P framework is systematic, includes a KRL-based decomposition for label collection, and could serve as a benchmark for future research. (R1)
- **Strong and consistent empirical results.** L2P shows performance improvements over baselines (FBAS, SMAC3, default) across multiple real-world problem families, especially on hard instances. (R1, R2, R3)
- **Extensive evaluation.** Includes ablation studies, sensitivity analysis of components (KRL, dynamic loss averaging), and investigation of individual hyperparameter effects. (R3)
- **Practical applicability.** The method is fast at inference (<0.5s) and directly usable with existing MIP solvers. (R4)
- **Clear writing and useful code release.** The paper is easy to follow and provides code to benchmark and extend the approach. (R2, R3)
- **Real-world impact.** Datasets include practically relevant domains (sustainable corridor, maritime inventory, load balancing, item placement). (R3)

### Weaknesses

- **Missing methodology details.** The main text does not define the loss functions, the range/nature of label values for priority, max-round, and timing tasks, or the PD-integral metric mathematically (these are only in the Appendix). The graph embedding aggregation mechanism is not described. The dynamic loss averaging weighting is not explained. Default parameters (“42x3”) are not listed. (R1, R4)
- **Incomplete reporting of metrics.** Arithmetic mean is used for solving times; the MIP community standard is geometric mean (robust to outliers). Presolving time is only reported for L2P, not for FBAS or SMAC3, obscuring possible overhead. The number of instances used in Table 1 and the metric and instance count per problem family in Table 4 are not stated. (R1, R3)
- **Lack of training data details.** Training/test set sizes, number of epochs, training time, and wall-clock time to generate SA solutions are not reported. No rule of thumb is given for required training data size. (R4)
- **Insufficient ablation of key components.** The impact of KRL and dynamic loss averaging is not fully isolated. (R1, R2) An ablation showing performance versus increasing training data size is missing. (R4)
- **Counterintuitive result not discussed.** L2P outperforms SA on “Hard: Load Balancing” and “Hard: Anonymous” instances. This is unexpected (L2P is trained to mimic SA) and could indicate a flaw; it warrants investigation. (R4)
- **Limited comparison scope.** Experiments only use SCIP; gains with other solvers (GUROBI, CPLEX) are not tested. (R2) Modern architectures (e.g., graph-formers) are not considered as replacements for GCNN backbones. (R2) A relevant paper on learning to presolve for LP (“Accelerate Presolve in Large-Scale Linear Programming via Reinforcement Learning”) is not cited. (R2)
- **Approach does not go beyond hyperparameter tuning.** L2P only tunes existing presolver parameters; it does not explore learning new presolving methods (e.g., which constraints to preprocess, new propagation rules) or instance-specific strategies beyond a single model. (R3)
- **Underutilized SA data.** The many parameter settings explored during SA are discarded; contrastive learning or re-using performant settings across instances could improve data efficiency. (R3)
- **Minor clarity issues.** Section 4.2 has a grammatical error and Section 4.3’s privacy discussion is vague. A paragraph is repeated in Appendix A.1. The meaning of Δ_y in Equation 4 (Appendix A.2) is ambiguous—it should refer to solving time. (R1)
- **Formatting inconsistency.** In Table 4, for “Hard: Anonymous” the 55% is bolded while other methods also achieve 55%, which is misleading. (R3)
