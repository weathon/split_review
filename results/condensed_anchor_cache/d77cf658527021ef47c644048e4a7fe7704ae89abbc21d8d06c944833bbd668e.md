## Merged Review

### Summary
This paper proposes a neural solver selection framework for TSP and CVRP that allocates each instance to the most suitable solver from a pool, using feature extraction (graph encoder, hierarchical), selection model, and selection strategies (Greedy, Top‑k, Rejection‑based, Top‑p). The framework achieves better performance than individual solvers with little extra time cost. However, the approach is seen as similar to existing algorithm selection methods (e.g., Bai et al. 2021; [1] for TSP algorithm selection) and the components are standard. The idea is interesting and practically significant, but novelty and necessity are questioned, and several important comparisons and analyses are missing.

### Strengths
- The paper addresses the important observation that a single neural solver cannot capture the entire problem structure; different solvers have complementary strengths, motivating solver selection. (R1, R2, R3)
- The framework is flexible, combining hierarchical graph encoders with multiple selection strategies. (R2)
- Experimental results on TSP and CVRP demonstrate improved performance over individual solvers and show generalization ability across problem distributions and scales. (R1, R2, R3)
- The paper is well‑written, well‑structured, easy to follow, and the presentation is clear. (R2, R3, R4)
- The work is a timely contribution to the emerging area of neural combinatorial optimization, where algorithm selection has not yet been well studied. (R3)

### Weaknesses
- **Limited novelty and insufficient connection to existing algorithm selection.** The proposed framework is agnostic to NCO: it does not leverage solver‑specific features (architectures, training dynamics) and extracts features only from problem instances. The idea of ranking solvers for individual instances is not technically innovative. The method is similar to existing algorithm selection methods (e.g., Bai et al. 2021; [1] for TSP algorithm selection), and the paper does not adequately compare with these methods, either in methodology or performance. The key components (GNN feature extraction, training loss, selection strategies) are standard and not specifically tailored for NCO. (R3, R4, R2)
- **Missing comparisons and baselines.** A detailed comparison with existing learning‑based and non‑learning‑based algorithm selection methods is absent. It is unclear how the proposed method performs when applied to classic solvers, or how existing methods perform on NCO solvers. Experiments only provide a single summary table; separate results for different instance sizes (e.g., TSP‑20, ‑50, ‑100; CVRP‑20, ‑50, ‑100) are missing, which is standard in NCO papers. (R3)
- **Evaluation issues.** The use of “OPT” in the optimality gap computation is misleading; the paper should use exact solvers or powerful heuristics (e.g., Gurobi, LKH3, HGS) as reference solutions, as is common in prior work. Including such heuristics in the solver selection zoo would further strengthen the significance. The paper should also report the original objective (e.g., tour length) in addition to the gap. (R4)
- **Training cost and necessity.** Training the selection model requires executing multiple solvers on the training set, which is time‑consuming. Given this overhead, it is not clear why one would not simply run all solvers sequentially on the target dataset and select the best result, making the framework’s necessity questionable. (R4)
- **Limited scope and scalability.** The framework is only evaluated on TSP and CVRP with relatively small scales; results on large instances (e.g., N ≥ 1000, and specifically TSP‑10000 (R1)) are missing. Can the framework be applied to more complex combinatorial problems? At larger scales, most neural solvers struggle compared to traditional heuristics, which undermines the significance. (R1, R4) Additionally, it is not clarified whether training instances for the selection model come from the same distribution as testing instances. (R1)
- **Selection strategy choice unclear.** It is not clear when to use which selection strategy (e.g., Top‑k vs. Top‑p); there is no guidance on how to choose based on instance characteristics or computational budget. Is the Top‑p threshold set adaptively based on instance features? (R2)
- **Lack of interpretation of hierarchical features.** The hierarchical encoder is claimed to capture hierarchical structural features, but it is unclear what these features correspond to in problems like TSP or CVRP. The added complexity of the hierarchical encoder needs quantitative efficiency analysis (trade‑off between complexity and performance). (R2)
- **Missing solver‑specific features in the selection model.** The selection model does not incorporate solver‑specific features, which may limit generalization to new solvers. How exactly does the MLP relate to different solvers, and how are solver features reflected? Would the absence of these solver‑specific features limit the selection model’s generalization ability? (R2, R3)
- **Need for more comprehensive solver pool and datasets.** More mainstream neural solvers should be included (e.g., supervised, reinforced, unsupervised, meta‑reinforced, divide‑and‑conquer, neural‑heuristic approaches). The evaluation should use conventionally used uniform TSP datasets (e.g., test files from prior works) for better comparability. (R4)
- **Generalization analysis insufficient.** Although empirical generalization is shown, the paper does not provide an in‑depth analysis of why the method generalizes well across problem distributions and scales. The underlying mechanisms are not explained. (R3)
