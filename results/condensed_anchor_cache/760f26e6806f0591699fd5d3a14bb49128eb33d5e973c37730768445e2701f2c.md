## Merged Review

### Summary
SpecFuse ensembles LLMs by iteratively generating and ranking segments in parallel. In each round, candidate segments from each base model are scored via average log-probabilities across all models; the top-ranked segment is broadcast to all models for the next round. A Model Exit Mechanism dynamically drops underperforming models to reduce calls. Evaluations across six benchmarks (instruction-response, reasoning, commonsense, instruction-following) using five 7–9B LLMs show consistent gains (e.g., +3.1 RougeL on Chinese, +3.0 on English human-computer interaction benchmarks), often outperforming 70B models. The exit mechanism reduces the average number of models invoked per round from 5 to 2.4 with only a slight performance drop. Scores: 6, 5, 5 (Reviewer 1 is more positive; reviewers 2 and 3 are more cautious, with confidence 3–5).

### Strengths
- Novel ensemble framework that enables cooperative segment-level generation among LLMs without training any additional modules – works plug-and-play with any set of models.
- Empirically effective across a diverse set of benchmarks (six datasets covering different task types), showing significant and consistent improvements over individual models.
- The methodology is clearly articulated, with diagrams effectively illustrating the workflow.
- Model exit mechanism is a practical addition that substantially reduces computational overhead while maintaining most of the performance (average model calls per round drop from 5 to 2.4).

### Weaknesses
1. **Logit dependence** – SpecFuse requires access to logits from all models, which limits applicability to models that only expose API-based interfaces, thus constraining its usability (R1, R2, R3).
2. **Lack of computational cost analysis** – The framework demands substantial extra compute (multiple models queried per round, plus additional verification passes), yet the paper provides no systematic discussion of time, resource consumption, or latency. It is unclear whether the observed gains justify the added cost, especially for long responses (e.g., math CoT) and larger models (e.g., 70B). “First token latency” is not clearly defined (R1, R2, R3).
3. **Insufficient comparisons with other ensemble methods** – Only one post-hoc ensemble baseline is included. No pre-selection / router-based methods are compared, nor is “Best-of-N” (which might require an extra reward model). This limits the ability to contextualize SpecFuse’s advantages (R1, R2, R3). Even after the authors’ response, the comparison remains limited to instruction-following tasks, and a broader set of benchmarks (e.g., GSM8K, MMLU, ARC-C, real-world datasets) is expected (R3).
4. **Exit mechanism analysis is superficial** – The mechanism receives little empirical scrutiny. The paper only reports a slight average performance drop, but does not analyze how the number of active models varies per task/query, which models are dropped, or the impact of different threshold choices. A comprehensive ablation and justification of the heuristic design is needed (R3).
5. **Practical necessity questioned** – Given the complexity of the multi-round, multi-model process, one reviewer doubts whether such a complicated ensemble procedure is genuinely needed in practice (R3).
6. **Missing details on benchmark evaluation** – For multiple-choice datasets (MMLU, ARC-C), it is unclear what sequence is being decoded and how long the generations are; the evaluation protocol should be clarified (R1, R3).
