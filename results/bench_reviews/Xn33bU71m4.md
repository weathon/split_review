## Summary

This paper presents a systematic empirical evaluation of nine open-source, mid-sized LLMs on two binary reverse engineering tasks: name recovery and type inference. The evaluation covers four architectures (x86-64, x86-32, ARM, MIPS) at four compiler optimization levels using a dataset of 40,000 functions. The main finding is that all LLMs perform poorly in zero-shot settings (F1 < 0.1 on nearly all tasks) and improve only modestly and inconsistently after LoRA fine-tuning. The paper also includes experiments on assembly code, real-world firmware, and analyses of model size, CodeWordNet impact, and prompt template effects.

## Strengths

- **Comprehensive and systematic experimental scope**: The paper evaluates 9 LLMs across 4 architectures and 4 optimization levels, totaling 40,000 function samples. This breadth is unusual in the reverse engineering literature and gives the findings high coverage across different compilation settings.

- **Addresses a genuine, under-explored gap**: As the paper documents, prior work in reverse engineering selects LLMs without systematic justification (e.g., SYMGEN uses CodeLlama-34B, RESYM uses StarCoder-3B). This paper provides the first rigorous multi-model comparison on these tasks, offering evidence-driven guidance for future model selection.

- **Clear negative result on assembly-level name recovery**: All models, both original and fine-tuned, achieve 0.00 F1 on function name recovery from assembly code across all architectures (Tables 5, 12). This is a crisp, unambiguous finding that underscores the difficulty of extracting semantics from raw instructions.

- **CodeWordNet ablation validates metric choice**: Figure 1 demonstrates that removing semantic matching causes a sharp drop in F1 scores, justifying the use of CodeWordNet-based evaluation over strict string matching for name recovery. This is a well-motivated methodological choice.

- **Practical operational observations**: Findings about DeepSeek-R1's chain-of-thought behavior interfering with task completion, and prompt-template sensitivity affecting fine-tuning time by up to 4× (Table 7), provide actionable guidance for practitioners.

- **Multi-architecture appendix adds transparency**: Detailed per-architecture tables (Tables 9–12) allow readers to examine consistency of trends across ISAs.

## Weaknesses

### Fatal

- **Factually incorrect claim in the abstract**: The abstract states that after fine-tuning, "DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." No table in the entire paper reports an F1 of 0.37 for any model on any task. DeepSeek-R1's best fine-tuned score is 0.17 (Table 3, variable name recovery, O0). The highest score for any model is 0.33 (Table 3). This is not a typo or rounding error — the claimed number simply does not exist in the paper's own results. This misrepresents a headline finding and erodes trust in the evaluation.

### Major

- **Fine-tuning protocol is inadequately described and likely under-trained**: The paper reports "200 fine-tuning steps" (Table 7 caption) on a training set of 160,000 functions. No batch size, learning rate, LoRA rank, or number of epochs is reported. Two hundred gradient updates is an extremely small training budget for a dataset of this size. The paper draws conclusions about fine-tuning (Findings 1, 2; abstract claims about fine-tuning benefits) without demonstrating that models converged or that additional training would not yield further improvements. The paper cannot distinguish between "fine-tuning does not help" and "fine-tuning was not given sufficient budget to help."

- **No baseline comparison with specialized non-LLM tools**: The paper cites numerous specialized systems for name recovery and type inference (SYMLM, Debin, Osprey, StateFormer, RESYM, VARBERT, DIRTY) but never evaluates any of them on the same dataset. Without a reference point, the absolute F1 scores are difficult to calibrate. While the paper's primary contribution is LLM-to-LLM comparison, the conclusion that LLMs are "fundamentally limited" (§5) requires knowing what "reasonable" performance looks like. An F1 of 0.05 could indicate LLM failure or simply an extremely difficult benchmark where even specialized tools score similarly low.

### Minor

- **Auxiliary LLM extraction fidelity is unevaluated**: The paper uses an auxiliary LLM to normalize heterogeneous model outputs into a consistent format (§3.2). The accuracy of this extraction step is never validated. If the extraction model makes errors, reported F1 scores are a lower bound on true LLM capability. This should at least be acknowledged as a limitation.

- **Placeholder-to-ground-truth matching lacks validation**: The procedure for matching variables across stripped and unstripped binaries by stack layout and registers (§3.1, Appendix A) is described but its accuracy is not quantified. While the approach is deterministic and standard, any matching errors would introduce noisy labels that artificially depress F1 scores.

- **No confidence intervals or significance testing**: With 2,500 samples per configuration, many of the small numerical differences between models (e.g., F1 differences of 0.01–0.02 in Tables 2–4) could be noise. Without variance estimates, the ranking of models is unreliable. Finding 4 ("larger model size does not guarantee better performance") and Finding 6 may be conceptually sound but the data supporting them could vanish with resampling.

- **Finding 7 (prompt template influence on training time) lacks controlled experiment**: The observation about DeepSeek-V2's outlier training time being attributed to template design is anecdotal — no controlled experiment (varying only the template while keeping model fixed) is performed.

- **Selective qualitative case study**: Table 8 shows cases where fine-tuned Qwen2.5 succeeded while the original failed. A balanced view would also show cases where fine-tuning made predictions worse (the paper itself notes this happens, e.g., DeepSeek-V2 under O1 in Table 3), to give readers a complete picture of fine-tuning's reliability.

### Trivial

- The paper describes 8 LLMs in the model list (Table 1) but the abstract and introduction say 9 — this is a minor accounting inconsistency.
- Model naming is inconsistent: Table 1 lists "Deepseek-R1-Qwen (14B)" while elsewhere it is "Deepseek-R1" — the paper should clarify it uses the Qwen-distilled variant throughout.
- The text says DeepSeek-R1 is "built on Qwen2.5" — while the distilled variant is, this should be explicit to avoid confusion with the full DeepSeek-R1 model.

## Nice-to-Haves

- Re-running fine-tuning with a proper training budget (multiple epochs, learning-rate schedule, early stopping on a validation set) and reporting convergence curves would substantially strengthen the fine-tuning conclusions.
- Including at least one specialized non-LLM baseline (e.g., SYMLM for function names) on the same dataset would calibrate the absolute F1 scores and make the "fundamentally limited" claim credible.
- An error analysis categorizing model failures (e.g., how often the model generates a semantically plausible but wrong name vs. a completely nonsensical one) would reveal whether LLMs have partial understanding or are purely guessing.
- Reporting extraction accuracy of the auxiliary LLM on a manually verified subset would bound post-processing errors.
