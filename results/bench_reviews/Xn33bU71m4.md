## Summary

This paper presents a systematic evaluation of nine open-source mid-sized LLMs (13B–16B) on two core reverse engineering tasks: name recovery (function and variable names) and type inference from stripped binaries. The authors build an automated pipeline using placeholder normalization and an auxiliary LLM for output standardization, evaluate across four architectures (x86-64, x86-32, ARM, MIPS) and four optimization levels, and also test fine-tuning via LoRA. The central finding is that all evaluated models perform poorly — most F1 scores are below 0.1 on zero-shot inference, with fine-tuning yielding modest improvements (up to 0.33 on variable name recovery) that are inconsistent and task-dependent.

## Strengths

- **First systematic multi-model evaluation spanning both name recovery and type inference.** The paper benchmarks nine LLMs across two complementary tasks, filling a gap identified in prior work that focused on only one task or a single model (Section 2). The consistently low F1 scores across all models (e.g., most below 0.1 in Tables 2–4) provide direct evidence supporting the paper's main claim that current mid-sized open-source LLMs are not yet capable of performing these tasks reliably.

- **Comprehensive benchmark across architectures, optimizations, and real-world firmware.** The dataset covers four architectures (x86-64, x86-32, ARM, MIPS) and four optimization levels, totaling 40,000 functions (Section 4.1). Evaluation on real-world firmware with two decompilers (Table 6) further reinforces the main finding by showing near-zero performance in a realistic setting, strengthening the generalizability of the conclusion.

- **Fine-tuning analysis revealing inconsistent and task-dependent gains.** The paper demonstrates that while fine-tuning can improve name recovery (e.g., WizardCoder variable name recovery from 0.01 to 0.33 in Table 3), it sometimes degrades performance (DeepSeek-V2 under O1 drops from 0.10 to 0.05). Finding 1 explicitly notes this inconsistency, providing a nuanced insight beyond a simple "fine-tuning helps" conclusion.

- **Finding that model size does not guarantee better performance.** The comparison of CodeLlama 7B, 13B, and 34B (Figure 2) shows negligible differences in F1 scores. DeepSeek-R1 (fine-tuned from Qwen2.5) underperforming Qwen2.5 (Section 4.4) further supports the finding that training data quality and architecture matter more than parameter count.

## Weaknesses

### Fatal
None.

### Major

- **The auxiliary LLM used for response extraction is not identified or validated.** The paper relies on an auxiliary LLM to normalize heterogeneous model outputs into a standard format (Section 3.2), but never specifies which model serves this role, evaluates its accuracy, or reports how often outputs were lost or corrupted by this post-processing step. Given that all models achieve near-zero scores, a plausible alternative explanation is that the auxiliary LLM systematically fails to parse correct predictions. The paper reports that LLMs "often miss some" requested names and sometimes produce multiple candidates — the auxiliary model's handling of these cases is critical but unexamined. This is a significant uncontrolled confound.

- **No comparison to dedicated non-LLM approaches or prior work under original task definitions.** The paper extends the name recovery task to require predicting all callee function names (Section 2), which is fundamentally harder than prior work that only predicted the current function's name. Without evaluating models under the original (simpler) task definition, it is impossible to tell whether the low scores reflect LLM inability or an unreasonably difficult task formulation. Similarly, the paper does not benchmark against dedicated tools like SYMLM (Jin et al., 2022) or Debin (He et al., 2018) that were designed specifically for these tasks. The conclusion that LLMs are "fundamentally limited" requires comparison to the state of the art, not just to each other.

- **Exclusion of frontier API-based models limits the scope of the conclusions.** The paper evaluates only mid-sized open-source models (13B–16B) and explicitly excludes ChatGPT and GPT-4 due to cost and model size mismatch (Section 4.2). While this is a stated scoping decision, the paper's title and framing ask the general question "LLMs as Reverse Engineers?" — which cannot be answered by testing only models in this size range. Even a small-scale evaluation on 100 samples with GPT-4 or Claude would substantially strengthen the paper's claims. The paper should either include such results or more carefully limit its claims to "mid-sized open-source LLMs."

- **The strict type inference metric conflates partial correctness with failure.** The paper uses "strict equality checks" for type inference (Section 3.4), meaning a model that infers `int` instead of `int32_t`, or a struct type with fields in a different order, gets zero credit. The paper acknowledges this is "challenging" but does not justify it as appropriate or report results under a more lenient metric. This makes the type inference results difficult to interpret — they may reflect metric harshness rather than model inability.

### Minor

- **The expanded name recovery task (predicting all callee names) is not compared against the original single-function-name formulation.** While the paper acknowledges extending the scope (Section 2), it does not ablate this choice. A model that correctly predicts the main function name but fails on 8 callee function names would get a low F1 score despite being partially useful. An ablation comparing the two formulations would clarify how much of the poor performance stems from the harder task definition.

- **The placeholder normalization removes information that would exist even in stripped binary decompilation.** Replacing all identifiers with VAR1, VAR2, etc. (Section 3.1, Figure 3) eliminates naming conventions that carry semantic signal (e.g., `local_10` vs `param_1` in decompiler output). While the paper frames this as "minimizing noise," it also removes structure that helps inference. The results do not distinguish between "LLMs cannot infer meaning from code" and "LLMs cannot infer meaning from code where all decompiler-generated naming hints are removed."

- **Finding 4 about model size is drawn from a single model family (CodeLlama) without controlling for other factors.** The comparison of CodeLlama 7B/13B/34B (Figure 2) is informative but limited. The paper does not test size variants from other families (e.g., Qwen2.5 7B vs 14B vs 72B) to see if the pattern generalizes.

- **The fine-tuning time analysis (Table 7) attributes 3× longer training for DeepSeek-V2 to "prompt template design" but this is speculative.** The paper reports that modifying CodeLlama's template produced a similar increase, but does not provide controlled experiments isolating the template effect from other factors (e.g., model architecture, tokenizer efficiency).

## Novel Insights

The reviews surface a tension that the paper itself does not fully address: the evaluation design simultaneously makes the task harder than prior work (predicting all callee names, strict type matching, placeholder normalization) while testing weaker models (mid-sized open-source only) and using an unvalidated measurement pipeline. This means the paper's negative result is overdetermined — there are multiple plausible explanations for the near-zero scores, and the experimental design cannot disentangle them. The most valuable insight from the reviews is that the paper would be substantially stronger if it isolated these factors: compare against the original task definition, validate the auxiliary LLM, test at least one frontier model, and use a more lenient type metric. Without these controls, the paper's central claim ("LLMs remain fundamentally limited") is a reasonable hypothesis but not a proven conclusion.

## Suggestions

1. **Identify and validate the auxiliary LLM** used for response extraction. Report its accuracy on a labeled set of model outputs to rule out the possibility that near-zero scores are artifacts of the post-processing step.
2. **Add an ablation comparing the original (single-function-name) task formulation** against the expanded (all-callee-names) formulation. This would clarify how much of the poor performance stems from the harder task definition.
3. **Include a small-scale evaluation of at least one frontier API-based model** (GPT-4, Claude) on 100–200 samples. This would bound the question of whether the failure is specific to mid-sized models or general.
4. **Report type inference results under a more lenient metric** (e.g., allowing partial type matches, handling `int` vs `int32_t` equivalently) alongside the strict metric, to distinguish metric harshness from model inability.
5. **Benchmark against at least one dedicated non-LLM approach** (e.g., SYMLM for name recovery) to contextualize the LLM results against the state of the art.
