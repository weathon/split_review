## Summary

This paper presents the first systematic, large-scale evaluation of nine mid-sized open-source LLMs on two core binary reverse engineering tasks: name recovery (function and variable names) and type inference. The authors evaluate across four CPU architectures, four compiler optimization levels, and 40,000 unique functions, with both zero-shot and LoRA fine-tuned settings. The key finding is that current LLMs — with or without fine-tuning — achieve very low F1 scores (most below 0.1, with the best fine-tuned result reaching ~0.33 for variable names), demonstrating they are not yet viable reverse-engineering tools.

## Strengths

- **Comprehensive, large-scale benchmarking**: Evaluates 9 LLMs across 4 ISAs (x86-64, x86-32, ARM, MIPS) and 4 optimization levels using 40,000 unique functions (Section 4.1, Tables 2-4, 9-12). This systematic design provides robust evidence for the paper's central negative result.

- **Real-world corroboration**: Evaluation on stripped firmware binaries decompiled with both Ghidra and IDA Pro (Table 6) confirms near-zero F1 scores, validating that laboratory findings translate to practical settings.

- **Automated evaluation pipeline**: The LLM-based response normalization (Section 3.2, Figure 4b) addresses a real engineering challenge in benchmarking diverse models with heterogeneous output formats.

- **Genuinely useful findings**: Several conclusions are actionable for the community — (a) training data quality matters more than parameter count (Finding 4, Figure 2), (b) CodeWordNet-based semantic matching substantially inflates scores compared to strict matching (Figure 1), and (c) LLMs consistently fail to follow output formatting without fine-tuning or post-processing (Finding 8).

- **Clear negative-result contribution**: The paper provides concrete, large-scale evidence that LLMs are not yet capable of binary reverse engineering in their current form — a valuable data point for researchers deciding whether to invest in this direction.

## Weaknesses

### Fatal

None.

### Major

- **Abstract contains a factual error that misrepresents results.** The abstract (line 50-51) states: "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." This value appears nowhere in any table in the paper. The highest F1 for DeepSeek-R1 across all architectures, tasks, and optimization levels is 0.18 (ARM, variable name recovery, O0, fine-tuned, Table 10). On x86-64, its highest is 0.17 (Table 3). The 0.37 figure is unsupported and, more importantly, contradicts the paper's own conclusion that fine-tuning gains remain insufficient. This quantitative misrepresentation in the most-read section of the paper damages credibility and must be corrected.

### Minor

- **Fine-tuning hyperparameters are not reported.** The paper adopts LoRA fine-tuning (Section 3.3) but omits rank, alpha, learning rate, optimizer, number of epochs, batch size, and target output format. While the fine-tuning results are supplementary to the main benchmarking contribution, these details are necessary for reproducibility. This is not fatal because the paper's primary claim (LLMs perform poorly at zero-shot) does not depend on fine-tuning results.

- **Auxiliary LLM normalization quality is not validated.** The post-processing pipeline uses an auxiliary LLM to normalize heterogeneous model outputs (Section 3.2), but its accuracy is never evaluated — e.g., how often does it mis-extract or alter predictions? Without this check, systematic errors could affect reported scores. The pipeline is a pragmatic engineering solution, but a brief validation on a hand-annotated subset would strengthen confidence.

- **Dataset diversity limitations are acknowledged but not discussed.** The dataset is drawn "mostly from GNU software" (line 244). While 4 ISAs and 4 optimization levels provide breadth, the code domain is homogeneous. The paper should discuss whether GNU-style C code is representative of the broader binary RE landscape (embedded firmware, proprietary applications, diverse coding idioms).

- **The "established reverse engineering prompt" citation is weak.** The prompt (Figure 4a) is attributed to a GPT-3.5-era blog post (citation "gpt, 2023"). This is thin justification for a scientific study. The prompt design itself is reasonable, but the citation should be replaced or supplemented.

### Trivial

- **DeepSeek-R1 prompt modification is noted but under-discussed.** The paper suppresses DeepSeek-R1's chain-of-thought reasoning via prompt template modification (Section 4.5, lines 587-588). While this is acknowledged, it means DeepSeek-R1 is evaluated in a non-standard configuration. This should be more explicitly flagged as a limitation when discussing DeepSeek-R1's results.

- The paper states it evaluates "eight" models in Section 4.2 but Table 1 lists nine models — a minor counting inconsistency.

## Nice-to-Haves

- A validation of the auxiliary LLM normalization accuracy on a small hand-annotated subset would substantially strengthen confidence in the automated pipeline.
- Qualitative examples (beyond Table 8) showing common failure modes — e.g., near-miss synonyms vs. nonsensical outputs — would help readers understand the nature of LLM errors.
- An analysis of why fine-tuning sometimes *hurts* performance (e.g., DeepSeek-V2 drops from 0.10 to 0.05 on variable names at O1, Table 3) would add depth.
