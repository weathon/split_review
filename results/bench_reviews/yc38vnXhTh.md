## Summary

This paper introduces ACTOR, an LLM-powered agent for simulating human behavior in 3D indoor scenes through a perceive-plan-act cycle with value-driven tree search (MCTS). It also introduces BehaviorHub, BehaviorHub, a large-scale dataset of ~10k human behavior samples across ~1.5k 3D scenes, automatically generated by distilling LLM knowledge and aligning motion resources with scene geometry. The paper evaluates ACTOR against LLMaP and HuggingGPT on planning and simulation metrics, conducts ablations validating the architecture components, and demonstrates that BehaviorHub provides useful training data for downstream motion generation tasks.

## Strengths

- **Value-driven behavior planning architecture with clear ablative support**: The paper proposes a genuinely novel combination of LLM-guided tree search with customizable value functions (real-valued + language-based). Table 3a provides clean ablative evidence that each component—active search, hierarchical prior, and value functions—contributes positively when added incrementally to the same GPT-4 backbone (GSR improving from 0.07 → 0.42 → 0.56 → 0.73). This ablative validation is the strongest evidence for the architecture's merit and survives scrutiny independent of the baseline comparison confound.

- **BehaviorHub dataset is a substantial resource with validated downstream utility**: At 10k samples across 1.5k scenes with 2k unique activities, BehaviorHub is an order of magnitude larger than ActivityPrograms. More importantly, Table 4 demonstrates that pre-training on BehaviorHub improves performance on two distinct downstream tasks (scene-aware motion generation on PROX and language-conditioned generation on HumanML3D) across all reported metrics, providing independent evidence that the dataset captures useful motion-scene alignments.

- **Dynamic adaptation capability**: The Dynamic subset and qualitative examples (Figure 4) convincingly illustrate that ACTOR can handle environment state changes (e.g., occupied bathroom) and language-specified preferences—capabilities that standard ungrounded LLM planners lack by design. The human evaluation (Table 2) independently confirms ACTOR outperforms baselines on completeness and rationality.

## Weaknesses

### Fatal
None.

### Major

- **Headline baseline comparison is confounded with LLM backbone**. The paper claims ACTOR "nearly doubles the overall success rate" (Table 1), but the paper specifies that ACTOR uses GPT-4 (§4.3) while never stating which LLM powers LLMaP and HuggingGPT. Since LLMaP (2022) predates GPT-4 and HuggingGPT typically uses GPT-3.5, the comparison conflates architecture improvements with a stronger base model. Additionally, ACTOR's motion generation models are fine-tuned on BehaviorHub (§4.3: "fine-tune them on BehaviorHub") with no indication that baselines receive comparable fine-tuning. The motion simulation metrics (GSR, SSR, FID) therefore reflect a compound advantage of stronger LLM + fine-tuned motion models + architecture. The ablations in Table 3a do partially mitigate this by showing improvements over the same GPT-4 backbone, but the headline result as stated is not interpretable as an architecture-only improvement.

- **Planning evaluation metrics are partially circular with data generation**. The planning metrics (Sentence-BLEU, BERTScore) compare against BehaviorHub's ground-truth plans, which were themselves generated by GPT-4/3.5 through an LLM pipeline (§5.1). This rewards agents for producing plans similar to the LLM's own output distribution rather than for planning quality in any absolute sense. The paper does not clarify whether the "Human" baseline in Table 2 represents independently written plans or post-processed seed data, nor does it specify who the "three verifiers" (§5.2) are (crowdworkers? experts? the authors themselves?). The human evaluation (Table 2) provides some independent validation, but the automatic metrics central to Table 1 suffer from this circularity.

- **The perception module is a black box with no evaluation or reproducibility**. The perception phase (§4.1) uses "readily available models" and "heuristic functions" to convert scene geometry into linguistic descriptions, but no specific models are named and no accuracy is measured. The example description appears to be a manually crafted template. Without any evaluation of perception correctness or even an ablation that bypasses perception, the entire perceive-plan-act loop is uninterpretable: failures could stem from perception errors, planning errors, or both. This makes the system non-reproducible as described.

### Minor

- **Value function calibration is arbitrary and unanalyzed**. The language-based value functions map qualitative responses ("sure/more-likely/less-likely/impossible") to probabilities (1.0/0.7/0.3/0.01) with no sensitivity analysis. The product formulation \( p_v = \prod_n p_{v_n} \) assumes conditional independence across value functions (e.g., "neat person" and "shortest path" may correlate). The large gain from adding value functions (Table 3a: GSR 0.42→0.73) could be partly driven by the specific mapping rather than the semantic content. A sensitivity study varying these values would strengthen the claim.

- **The "three verifiers" used for data quality (§5.2) are not identified**—are they crowdworkers, domain experts, or the authors themselves? Their identity critically affects the perceived quality of BehaviorHub's ground truth.

- **MCTS implementation details are sparse**: No exploration constant (UCT), number of simulations, or rollout policy is specified (§4.2–4.3). With window size=5 and depth=3 the search space is small, and MCTS may behave similarly to beam search. Reproducing the exact algorithm requires this information.

- **The Dynamic subset creation method is vaguely described** (§6.1): "we carefully configure the agent's environment state-aware triggers" — this is underspecified and the triggers could be cherry-picked. The human evaluation uses only 5 participants, which is small for drawing general conclusions.

### Trivial
- Table numbers are referenced inconsistently in the text (Table 3 vs Table 4b in §6.2).

## Nice-to-Haves
- A controlled experiment evaluating all methods (including ACTOR's components) with the same LLM backbone (e.g., GPT-3.5-turbo) for planning, at minimum, the planning-only metrics would make the headline claim interpretable.
- An evaluation of perception accuracy (e.g., comparing the linguistic scene description against ground-truth scene labels on a held-out subset) or an ablation that removes the perception module would clarify the system's dependency on this component.
- Sensitivity analysis for value function probability mappings (e.g., testing multiple calibration schemes) or replacing the product assumption with weighted summation would increase confidence in the value-driven planning results.

## Suggestions
1. **Run a controlled planning experiment**: Compare ACTOR (with minimal value functions), LLMaP, and HuggingGPT all using GPT-3.5-turbo with no fine-tuned motion models. Report only planning metrics (BERT-S, Sentence-BLEU) for this controlled comparison. This would isolate the architecture's contribution from the LLM backbone confound.
2. **Specify and evaluate the perception module**: Name the models used, report accuracy on a held-out perception test, or at minimum run an ablation where ground-truth scene descriptions are fed directly to the planner to measure the perception bottleneck.
3. **Add value function sensitivity analysis**: Report how GSR changes under at least 2-3 alternative probability mappings (e.g., 0.9/0.6/0.2/0.01 or 1.0/0.5/0.2/0.0) to verify that the gains are driven by semantic content rather than the specific numbers.
4. **Identify the verifiers and clarify the Human baseline**: Describe who the three verifiers are (expert annotators? crowdworkers?) and how the "Human" row in Table 2 was constructed.
