## Summary

YOLO-MARL proposes a framework that leverages a single, pre-training interaction with an LLM to generate a high-level assignment planning function, which is then used to compute reward/penalty signals during MARL training. The key innovation is the one-time LLM cost: after generating the planning function, no further LLM calls are needed during training, and the trained policies are normal-sized neural networks independent of the LLM. The method is evaluated across three environments (LBF, MPE, SMAC) with three MARL algorithms (QMIX, MADDPG, MAPPO).

## Strengths

- **One-time LLM interaction eliminates costly online queries**: The framework requires only a single LLM call per environment before training begins (Algorithm 1, Section 4.4). This is a clear practical advantage over methods like ELLM or SayCan that repeatedly query LLMs during training, and the paper demonstrates that the approach works without any LLM involvement during the actual MARL training loop.

- **Compatibility across multiple MARL algorithms**: YOLO-MARL is demonstrated to work with QMIX, MADDPG, and MAPPO in the same framework (Section 5.2.1, Table 1). The ablations verify that the same generated planning function provides benefits across all three algorithm families, supporting the claim of strong generalization.

- **Significant performance gains in sparse-reward cooperative tasks**: In the LBF environment (2-player, 2-food), YOLO-MARL achieves up to a **105% improvement** in mean return and **2× faster convergence** compared to baselines (Section 5.2.1, Table 1, Figure 2). This is concrete evidence that LLM-generated planning functions can substantially guide policy learning where standard MARL algorithms struggle.

- **Ablation studies validate the necessity of each module**: The paper systematically ablates the Strategy Generation module (Section 6.1, Figure 6), the State Interpretation module (Section 6.2), and compares against a reward-generation-only variant (Section 6.3). These ablations demonstrate that each component contributes meaningfully to the overall performance.

## Weaknesses

### Fatal
None.

### Major

- **The abstract overclaims "outperforms" while SMAC results only show comparable performance.** The abstract states "YOLO-MARL outperforms traditional MARL algorithms" and the conclusion says "outperforms or achieve competitive results." However, the SMAC section (line 240) honestly acknowledges that the method "still achieves comparable results on certain maps" with a very coarse assignment space of just {Move, Attack, Stop, None}. The paper's own discussion (commented out in lines 243-244) notes "it is challenging for an LLM-generated planning function to determine the appropriate enemy to attack or the optimal position to move to." The claim in the abstract is inconsistent with what the SMAC experiments actually demonstrate, and the paper does not analyze which maps underperform or why. This needs to be corrected: either present SMAC as a limitation or redesign the planning function to provide more informative assignments.

- **The mapping from LLM-generated assignments to concrete actions is underspecified, impairing reproducibility.** Algorithm 1 checks `if a_i ∈ T_i` to determine the reward signal, and Section 4.3 defines the assignment set `T` "over the action space such that an action can belong to multiple assignments and vice versa." However, the paper never specifies how this membership check is implemented. The descriptions in Sections 4.3 and 5.2.1 are illustrative (e.g., "taking the action 'UP' can be associated with both assignments") but not operational. Without knowing whether this mapping is (a) generated by the LLM as part of the planning function, (b) hand-coded per environment by the user, or (c) derived from a geometric rule (e.g., check if the action moves toward the assigned target), readers cannot assess whether improvements come from LLM planning or from manually engineered heuristics. The paper's claimed "easy adaptation to various game environments" hinges on this detail being clarified. This is the single most significant technical gap in the paper.

### Minor

- **The state interpretation function requires manual effort that is under-acknowledged.** Section 4.2 states "we implement a Python function that processes the vector observation and restructures each component." This function must be written by the user and requires detailed knowledge of the environment's observation structure (which indices correspond to positions, velocities, etc., and how they are encoded). The paper's framing suggests that the framework "requires only basic background understanding of a new game environment from the users," but writing a correct interpretation function for complex environments like SMAC is non-trivial. The paper would benefit from acknowledging this effort and providing concrete examples of interpretation functions.

- **Hyperparameters r' and p' (reward and penalty signals) are listed in Algorithm 1 but never specified or ablated.** These two constants control the strength of the LLM's influence on the policy. Their magnitude relative to the environment's reward scale could significantly affect performance, but the paper provides no guidance on how to set them or whether they are environment-dependent. An ablation or sensitivity analysis is needed.

- **Only one LLM (Claude 3.5 Sonnet) is tested.** The Limitations section (line 356) acknowledges this but does not address it concretely. The paper does not analyze the quality, variability, or failure rate of the LLM-generated planning functions (e.g., how often does the LLM produce buggy/invalid Python code across different random seeds or prompt variations?). This limits confidence in the robustness of the approach.

- **MPE improvements are modest for one setting and marginally meaningful in another.** The 4-agent QMIX result shows only a 2.4% improvement. While the 18.09% improvement with MADDPG is stronger, the paper does not discuss which factors drive the variance across algorithms and agent counts.

### Trivial

- The paper uses a Markov game formulation (Section 3) but has a commented-out `\iffalse` block containing a Dec-POMDP formulation (lines 56-68). While this does not affect the content, it is a minor presentation issue that could confuse readers.

## Nice-to-Haves

- A direct comparison to more sophisticated LLM-based reward-shaping methods (e.g., adapting EUREKA's iterative refinement with detailed execution traces to the MARL setting) would strengthen the positioning of the planning-function approach relative to existing work. However, the paper's existing reward-generation ablation (Section 6.3) is a reasonable internal control for its stated purpose.
- Concrete examples of the prompts, the generated planning function code, and the state interpretation function for at least one environment (ideally LBF) would greatly improve reproducibility and allow readers to judge where the LLM's contribution begins and ends.

## Removed Points

- **Criticism about reward generation comparison being a "straw-man" baseline**: The paper tests both reward generation without feedback AND with iterative refinement (Section 6.3). The comparison is a valid internal ablation to justify the planning-function design choice vs. direct reward generation. While a comparison to EUREKA/Text2Reward would be interesting, the paper's existing comparison is not a straw-man and is appropriate for its stated purpose. This is moved to Nice-to-Haves.
- **Criticism about the Dec-POMDP vs. Markov game formulation causing confusion about partial observability**: The paper clearly uses the Markov game formulation (Section 3). The commented-out block is a parser artifact. The paper also states it uses "global states" during training (Section 4.2), which is consistent with centralized training in CTDE frameworks.

## Suggestions

1. **Reconcile the abstract's claims with the SMAC results.** Either redesign the SMAC planning function to produce more informative assignments (e.g., "attack the nearest low-health enemy") and demonstrate gains, or honestly limit the scope of the outperformance claim to settings where the LLM's planning can be effectively grounded.
2. **Specify the assignment-to-action mapping.** Provide the actual Python logic (whether LLM-generated or hand-coded) that determines whether an action "belongs to" an assignment. This is essential for reproducibility and for assessing the LLM's genuine contribution.
3. **Report and ablate the hyperparameters r' and p'**, at minimum their chosen values and a sensitivity analysis.
4. **Include concrete examples** of the prompt template, an example of a generated planning function, and the state interpretation function for at least one environment.
