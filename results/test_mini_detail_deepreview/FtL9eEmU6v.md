## Summary

EditBench introduces a benchmark for instructed code editing built from real-world user data collected via a VS Code extension. It comprises 540 problems (109 unique, translated across 5 natural languages and 2 programming languages) that require models to integrate user instructions, code context, highlighted code, and cursor position. The paper evaluates 40 LLMs, finding that only one model exceeds 60% pass@1, and shows that performance varies substantially across edit categories and context configurations.

## Strengths

1. **Real-world data collection from actual developers in their natural workflow.** The paper develops a VS Code extension (Section 3.1) and gathers 2,672 accepted responses from 458 users performing day-to-day coding tasks. This is a genuine differentiator from prior edit benchmarks (CanItEdit, EditEval, Aider Polyglot) that rely on annotator-written or educational problems, as explicitly shown in Table 1.

2. **First benchmark to require all four contextual signals (instruction, code context, highlighted code, cursor position) together.** Table 1 shows EditBench is the only benchmark with highlighted code. The ablation study (Table 3) confirms that adding highlighted code improves pass@1 for 5 of 7 top models by up to 3.52%, demonstrating that these signals matter for performance.

3. **Multilingual and multi-language coverage.** EditBench provides problems in 5 natural languages (English, Spanish, Russian, Chinese, Portuguese) and 2 programming languages. It achieves 74 unique import libraries in Python — more than three times the diversity of comparable benchmarks (Figure 3). The translation pipeline with native-speaker validation is methodologically sound.

4. **Broad and systematic model evaluation.** 40 models spanning multiple families (GPT, Qwen, Llama, Mistral, Sonnet, Gemma, Grok, DeepSeek, Gemini, Kimi, GLM) are evaluated with consistent methodology, providing a useful snapshot of current code-editing capabilities.

5. **Transparent problem curation and per-category analysis.** The filtering from 2,672 raw responses to 109 core problems is documented step-by-step (Section 3.2). The categorization into feature addition, modification, bug fixing, and optimization (Table 2) enables more granular analysis of model strengths, e.g., finding that models perform best on bug fixing and struggle with optimization (Section 5.1).

## Weaknesses

### Fatal
None.

### Major

1. **Potential bias in test harness design from model-generated solutions.** Section 3.3 states that annotators were given example solutions generated by GPT-4o and Sonnet 3.7 "to give insight into possible solutions." This is a methodological concern: annotators may anchor on what those specific models produce, potentially biasing test cases toward solution patterns of the very models being evaluated. The paper does not describe mitigation (e.g., a subset of test cases written without model examples and compared for agreement). While the second-review step adds quality control, it does not directly address this anchoring concern. The paper's central claim — that EditBench measures real-world editing ability independent of prior model behavior — is weakened by this ambiguity.

2. **No representativeness analysis of the filtering pipeline.** The 2,672 accepted responses are filtered to 109 unique problems — a 96% reduction. The paper describes the filtering steps (Section 3.2) but does not compare the distribution of the final 109 problems to the original pool on dimensions such as task category, instruction length, code complexity, or domain breadth. Without this diagnostic analysis, it is unclear whether the benchmark captures a representative slice of real-world edits or a narrow subset biased toward "interesting" or "challenging" problems. The limitations section acknowledges this only briefly ("it is unclear to what extent our problems encapsulate all real-world use cases") without quantification.

3. **Reliability of test harness creation is not demonstrated.** The annotation process involves a two-reviewer system (Section 3.3), but no inter-annotator agreement metric is reported. How often did the second reviewer reject or modify test cases? Were edge cases resolved consistently? Given that the core contribution is transforming raw user data into a testable benchmark, the absence of any reliability measure for this transformation is a notable omission.

### Minor

4. **Weak correlation with existing benchmarks is discussed without appropriate caution.** The Pearson correlation with Aider Polyglot is $r=0.24$ ($p=0.06$), which is not statistically significant at conventional thresholds. The $r=0.11$ ($p=0.01$) correlation with Chatbot Arena coding is significant but very weak. The paper attributes this to differences in input/output modality, interaction mode, and real-world intent. However, the weak correlation could equally reflect higher noise from the small problem set (109 unique problems). The discussion (Section 5.2) acknowledges these factors but does not adequately weigh the noise hypothesis.

5. **No confidence intervals or variance estimates for pass@1.** With only 109 unique problems, the standard error on pass@1 is potentially substantial. Reporting confidence intervals would help assess whether differences between closely ranked models (e.g., positions 2–5 in Figure 4) are meaningful.

6. **No breakdown of performance by natural language.** The paper highlights 5 natural languages as a key differentiator and validates translations with native speakers, but reports no per-language performance analysis. This is a missed opportunity to evaluate whether language affects model editing behavior.

### Trivial

7. The ablation interpretation (Table 3) is slightly mismatched: the paper states "models perform best when given highlighted code, but not cursor position" as an overall finding, but two of seven models (o3-mini, qwen3-coder) perform worse with highlighted code. The individual-level variation is acknowledged in the text but the summary statement could be more precise.

## Nice-to-Haves

- A contamination analysis showing that the 109 core problems are drawn from user code not present in common training corpora would strengthen the "in-the-wild" claim.
- Reporting whether the second-review step identified systematic disagreements in test harness design would increase confidence in the annotation process.
- Discussing potential behavioral effects of users knowing their data is being collected (Section 3.1) would improve the limitations section.

## Novel Insights

The harsh critic's note about the potential alignment between model-generated example solutions during test harness creation and the model ranking itself is an insightful meta-point that the paper does not address. If annotators were implicitly guided toward solutions that resemble GPT-4o or Sonnet 3.7 outputs, then models that follow similar coding patterns may be systematically advantaged. This interacts with an observation from the ablation study: highlighted code improves most models but hurts o3-mini and qwen3-coder, suggesting that different models use contextual information differently — a pattern that could be confounded with test harness design choices. A straightforward addition of a bias analysis (e.g., having a subset of tests written blind to model outputs and comparing rankings) would substantially strengthen the paper's validity claims.

## Suggestions

1. **Address the test harness bias concern directly:** Have a subset of problems annotated by experienced programmers *without* showing any model-generated examples, then compare the resulting test suites. If the test suites agree on model rankings, this concern is eliminated.
2. **Add a representativeness study:** Compare the 109 core problems against the full 2,672-response pool on instruction length, code context length, domain/task type distribution, and difficulty profile. Report whether filtering shifted the distribution.
3. **Report inter-annotator agreement** for the second-review step on test harness creation (e.g., percentage of tests modified or rejected).
4. **Add confidence intervals** for pass@1 scores, particularly given the 109-problem core.
5. **Report per-language performance** for the 5 natural languages to validate translation quality empirically and identify language-specific patterns.
