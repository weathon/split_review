## Summary

This paper introduces ToolLLM, a comprehensive framework for tool-use with LLMs encompassing (1) ToolBench — a large-scale instruction-tuning dataset with 16,464 real-world REST APIs, 126,486 instances, and 469,585 real API calls spanning both single-tool and multi-tool scenarios, (2) DFSDT — a depth-first search-based decision tree algorithm that improves LLM planning and reasoning over ReACT, (3) ToolEval — an automatic evaluator using GPT-3.5-turbo with reported 87.1%/80.3% agreement with humans, and (4) ToolLLaMA — a fine-tuned LLaMA-2 7B model with a neural API retriever. Experiments show that ToolLLaMA+DFSDT performs comparably to ChatGPT+DFSDT and surpasses Claude-2 and Text-Davinci-003.

## Strengths

- **Massive-scale, real-world, multi-tool dataset (ToolBench).** With 16,464 APIs, 126,486 instances, and 469,585 real API calls (Table 1), ToolBench far surpasses prior datasets in scale (APIBench: 1,645 APIs, 0 real calls; ToolAlpaca: 400 APIs, 0 real calls) and is the first to cover multi-tool scenarios with real API execution. This is a significant engineering contribution that has enabled substantial follow-up work.

- **DFSDT clearly and dramatically improves over ReACT.** On ChatGPT, DFSDT achieves 63.8% average pass rate vs. 35.3% for ReACT and 44.5% for ReACT@N with matched cost (Table 3). The improvement is largest on multi-tool instructions (I3: 62.8% vs. 27.6%), demonstrating that the method genuinely expands what LLMs can accomplish during inference.

- **Effective neural API retriever.** The Sentence-BERT retriever achieves 84.9% NDCG@5 average vs. 45.4% for Ada and 17.0% for BM25 (Table 2). When integrated with ToolLLaMA using retrieved APIs, it even improves pass rate slightly over the oracle API set (67.3% vs. 66.7%), suggesting the retriever can identify more appropriate APIs than the ground-truth set.

- **Well-designed three-level generalization evaluation.** The paper tests on unseen instructions (Inst.), unseen tools within seen categories (Tool), and unseen tools in unseen categories (Cat.) — a thoughtful evaluation design that goes beyond standard held-out splits.

- **ToolEval shows reasonable correlation with human judgment.** The reported 87.1% agreement on pass rate and 80.3% on win rate with human annotators, while not perfect, provides evidence that the automatic evaluator is a useful proxy.

## Weaknesses

### Major

- **The central claim conflates model contribution with reasoning method contribution.** The paper's headline claim that "ToolLLaMA matches ChatGPT" rests on the ToolLLaMA+DFSDT setting. However, with ReACT (both models using the same reasoning strategy), ToolLLaMA achieves only 29.0% average pass rate vs. ChatGPT-ReACT's 40.2% (Table 4). DFSDT is a prompt-based search algorithm applicable at inference time to any LLM, so the comparison ToolLLaMA+DFSDT vs. ChatGPT+DFSDT primarily evaluates DFSDT's benefit, not the fine-tuning data's contribution to model capability. The paper lacks a controlled ablation isolating the training data effect (e.g., ToolLLaMA+ReACT vs. base LLaMA+ReACT), leaving the contribution of ToolBench itself underdetermined.

- **Evaluation via ChatGPT for models trained on ChatGPT-generated data creates a systematic bias risk.** ToolEval (GPT-3.5-turbo) evaluates all models, but the training data was also generated by GPT-3.5-turbo. This raises a validity concern: the evaluator may systematically favor solution paths that resemble the teacher model's output patterns, independent of actual task quality. While the paper reports human agreement (87.1%/80.3%), the subset size, annotator count, and inter-annotator agreement are deferred to the appendix, and the gap itself (especially 80.3% for win rate) is non-trivial. The paper does not discuss this evaluation circularity.

- **Missing direct open-source baseline on the core setting.** Gorilla (Patil et al., 2023) — the closest open-source model specifically trained for tool use — is only evaluated in the OOD experiment (Table 5) and never in the main ToolBench evaluation. The paper argues Gorilla cannot handle multi-tool settings, but a comparison on single-tool (I1) instructions would provide a fair open-source baseline for the core contribution. Without this, the improvement over Vicuna and Alpaca (general chatbots that achieve 0%) merely confirms that task-specific training helps — a low bar.

### Minor

- **OOD generalization claims are overstated for the realistic setting.** ToolLLaMA+Our Retriever achieves only 16.77% AST accuracy on HuggingFace (Table 5). While this beats Gorilla-ZS+BM25 (10.51%), it is very low in absolute terms and far below the oracle-retriever results (88.80%). Claiming "remarkable OOD generalization" for this setting overstates what the evidence supports. The strength is in generalization with the oracle retriever, but the practical retriever results are modest.

- **The retriever outperforming the oracle API set is not analyzed.** The paper notes that using the retriever improves pass rate over ground-truth APIs (e.g., 64.0% vs. 57.0% on I1-Inst.). The explanation offered (the retriever finds "better" APIs) raises a question about the quality of the ground-truth API labels used during instruction generation. This deserves deeper analysis — e.g., how many instructions have this issue and whether it indicates noisy training data — but receives only a single sentence.

- **DFSDT vs. Tree-of-Thought distinction is undersupported.** The paper distinguishes DFSDT from ToT by noting "infinite" vs. "simple" decision spaces, but provides no quantitative comparison (e.g., branching factor, node counts, cost). This claim would benefit from empirical grounding.

## Suggestions

1. **Disentangle model and method.** Add an ablation comparing LLaMA-base+ReACT vs. ToolLLaMA+ReACT to isolate the training data contribution. Reframe the headline claim accordingly (e.g., "ToolLLaMA with DFSDT achieves comparable performance to ChatGPT with DFSDT").
2. **Add Gorilla on I1 instructions.** A direct comparison on single-tool instructions would ground the improvement in the open-source landscape.
3. **Address evaluator bias.** Either (a) report ToolEval's agreement broken down by model type to check for systematic bias, (b) validate key results with GPT-4 as an alternative evaluator, or (c) discuss the circularity explicitly as a limitation.
4. **Temper OOD claims.** The "remarkable" generalization language should be reserved for the oracle retriever setting, with the practical retriever results described more modestly.
5. **Analyze the retriever-vs-oracle discrepancy.** A qualitative analysis of cases where the retriever outperforms the oracle would clarify whether the ground-truth API labels are noisy or simply incomplete.
