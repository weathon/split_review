## Summary

This paper presents a systematic, large-scale evaluation of nine open-source LLMs on two core binary reverse engineering tasks: name recovery (function and variable names) and type inference from stripped binaries. Using a dataset of 40,000 functions across four architectures (x86-64, x86-32, ARM, MIPS) at multiple optimization levels, the authors evaluate both zero-shot and fine-tuned (LoRA) performance. The central finding is that current LLMs achieve uniformly low F1 scores (mostly below 0.1) on these tasks, with fine-tuning producing inconsistent gains that do not fundamentally solve the problem.

## Strengths

- **First systematic large-scale evaluation across LLMs for these RE tasks.** The paper evaluates 9 models on 40,000 functions from 4 architectures and multiple optimization levels, directly addressing the gap that prior work (e.g., SYMGEN, ReSYM) selected models without clear rationale. The uniformly low F1 scores (Tables 2–4) provide concrete evidence supporting the claim that current LLMs are not yet capable of reliable reverse engineering.

- **Demonstration that fine-tuning gains are inconsistent and do not solve the problem.** The paper shows fine-tuning helps some cases (e.g., WizardCoder from 0.01→0.33 on variable names at O0) but can also hurt performance (DeepSeek-V2 under O1 halves its score), and type inference remains below 0.1 for all models even after fine-tuning (Table 4). Findings 1 and 2 articulate these patterns clearly.

- **Evidence that model size does not guarantee better performance.** Figure 2 compares CodeLlama 7B, 13B, and 34B on the same tasks and shows negligible differences, challenging the common assumption that larger models are automatically better for these tasks. Finding 6 states this explicitly.

- **Real-world firmware evaluation with two decompilers (Ghidra and IDA Pro).** Table 6 provides a more grounded assessment, revealing that most models perform slightly better on IDA Pro outputs, which highlights the role of decompiler quality — a dimension prior work largely ignored.

## Weaknesses

### Major

- **Unclear relationship between Figure 1 and Tables 2/3 F1 scores.** Section 3.4 states that CodeWordNet-based evaluation (SYMLM) is used for name recovery. However, Table 2 reports function name recovery F1 scores (e.g., CodeLlama O0: 0.04) that are 3–20× lower than Figure 1's "w CodeWordNet" values (CodeLlama O0: ~0.15). Meanwhile, Figure 1's "wo CodeWordNet" values (CodeLlama O0: ~0.05) are closer to Table 2 but still do not match for several entries (e.g., Llama2 O0: 0.06 vs 0.01; DeepSeek-V2 O0: 0.07 vs 0.01). The paper does not clarify whether Tables 2/3 use exact-match F1, CodeWordNet-based F1, or a different variant, nor does it explain why the "wo CodeWordNet" ablation values do not precisely match the main table values. This ambiguity makes it difficult to interpret the main quantitative results or reproduce the evaluation. The paper should explicitly state which F1 variant each table uses and reconcile any differences.

### Minor

- **Auxiliary LLM post-processing pipeline is not validated.** The paper uses a separate LLM to normalize model outputs into a consistent schema (Section 3.2) but provides no accuracy evaluation of this extraction step, no comparison with rule-based parsing or human judgment, and no statistics on how often the auxiliary LLM had to intervene (e.g., percentage of malformed responses). Since the zero-shot results depend on this pipeline, a basic validation (even a small hand-labeled sample) would substantially strengthen confidence in the reported scores. (This concern is partly mitigated because fine-tuned models "consistently adhered to the required output format" per Section 4.5.)

- **No analysis of why O0 is dramatically easier than O1/O2/O3 for variable name recovery.** Table 3 shows fine-tuning improves variable name recovery at O0 to 0.22–0.33 across models, while O1–O3 improvements are much smaller (0.02–0.10). This pattern is mentioned in passing but never analyzed — understanding why could inform future RE-specific fine-tuning strategies.

- **Real-world firmware test set details omitted.** The number of functions, how they were selected, and what specific firmware targets were used are not reported for Table 6. This information is important for assessing the reliability and representativeness of the real-world evaluation.
