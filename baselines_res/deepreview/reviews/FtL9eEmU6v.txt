## Summary:

This paper introduces EditBench, a novel benchmark designed to evaluate the code editing capabilities of large language models (LLMs) in a realistic setting. Unlike existing benchmarks that primarily focus on code generation from scratch, EditBench is grounded in real-world usage data, collected from 458 developers using a custom VS Code extension. This approach allows for a more ecologically valid assessment of LLMs' ability to perform code edits based on authentic user instructions and code contexts. The benchmark comprises 540 problems, spanning five natural languages (English, Spanish, Russian, Chinese, and Portuguese) and two programming languages (Python and JavaScript). The problems cover a diverse range of real-world use cases, including bug fixing, feature addition, and code refactoring. The authors evaluated 40 diverse LLMs on EditBench, finding that only one model achieved a pass@1 score above 60%, highlighting the challenging nature of the benchmark. The study also investigates the impact of different levels of contextual information, such as highlighted code and cursor position, on model performance, revealing that these factors significantly affect task success rates. The authors also analyze model performance across different categories of user instructions, demonstrating that models exhibit varying levels of proficiency depending on the type of edit required. Overall, the paper makes a significant contribution to the field by providing a much-needed benchmark for evaluating LLMs in code editing scenarios that closely mirror real-world software development tasks. The findings underscore the limitations of current LLMs in handling complex code edits and emphasize the importance of considering contextual information when evaluating these models. The benchmark is publicly available, offering a valuable resource for future research in this area.

## Strengths:

The primary strength of this paper lies in the introduction of EditBench, a benchmark that addresses a critical gap in the evaluation of LLMs for code editing. Unlike many existing benchmarks that focus on code generation, EditBench is specifically designed to assess code editing capabilities in a realistic setting. This is a significant contribution, as it moves beyond synthetic or educational datasets and towards a more ecologically valid evaluation. The use of a VS Code extension to collect real-world code edits from developers is a novel and effective approach. This methodology ensures that the benchmark reflects authentic editing tasks, enhancing its relevance for evaluating LLMs in practical scenarios. The inclusion of 540 problems across five natural languages and two programming languages (Python and JavaScript) makes EditBench a versatile and comprehensive benchmark. This multilingual support is crucial for evaluating LLMs in a global software development context. The paper also provides a thorough evaluation of 40 diverse LLMs, offering valuable insights into the current state of LLM code editing capabilities. The analysis of how different levels of contextual information (e.g., highlighted code, cursor position) affect model performance is insightful and can guide future model development. The authors' analysis of model performance across different categories of user instructions further highlights the nuanced capabilities of these models. ## Weaknesses:

While EditBench represents a significant advancement in evaluating LLMs for code editing, several weaknesses warrant careful consideration. First, the process of manually creating test cases by human annotators introduces subjectivity and potential inconsistencies. As described in Section 3.3, the annotators were instructed to create test cases that adhere to the user's intent and are generalizable, but the lack of a formalized specification for test case generation could lead to variations in difficulty and coverage. This subjectivity could result in test cases that are not uniformly challenging or aligned with real-world testing practices, potentially favoring models that are better at exploiting specific test case structures rather than demonstrating genuine code editing proficiency. For example, some annotators might focus on boundary conditions while others might prioritize functional correctness, leading to a non-uniform distribution of test case types. This lack of standardization could affect the reliability of the evaluation. My confidence in this weakness is high, as the paper explicitly states the manual nature of test case creation and the absence of a formal specification. Second, the benchmark's focus on only two programming languages, Python and JavaScript, limits its applicability and relevance for a broader range of software development contexts. As stated in Section 4, these languages were chosen because they comprise the majority of in-the-wild instructed edits collected, but this selection limits the benchmark's ability to assess the generalization capabilities of LLMs across different programming paradigms and syntax. This could bias the results towards models that are specifically trained on Python and JavaScript code. For instance, languages like C++ with its manual memory management or Java with its strong typing system could reveal different strengths and weaknesses in LLM code editing capabilities. This limitation is explicitly stated in the paper, giving me high confidence in its validity. Third, the paper lacks a detailed analysis of the types of errors that LLMs make when editing code. The evaluation primarily relies on the `pass@1` metric, which indicates whether all test cases passed but doesn't provide insights into the nature of the failures. As I observed in Section 5.1, the results focus on overall performance and comparisons across models and problem categories, but there is no breakdown of error types. This lack of error analysis makes it difficult to understand the specific challenges that models face and to guide future research efforts to address these limitations. For example, are models struggling with understanding the context of the code, or are they making syntactic errors? Are they failing to correctly interpret the user's instructions, or are they generating code that is semantically incorrect? Without this detailed error analysis, it is difficult to pinpoint the specific weaknesses of current LLMs in code editing. My confidence in this weakness is high, as the paper clearly lacks this type of analysis. Fourth, the paper does not compare the performance of the models on EditBench with their performance on other code-related tasks, such as code generation or bug fixing. While the paper compares EditBench to other benchmarks in Section 5.2, it does not show how the *same* models perform on those other benchmarks. This makes it difficult to assess the relative strengths and weaknesses of LLMs in code editing compared to other tasks. For example, how do models that perform well on code generation tasks fare on EditBench? Are models that are specifically trained for bug fixing more effective on EditBench compared to general-purpose LLMs? This comparative analysis would help to identify the specific strengths and weaknesses of LLMs in code editing relative to other code-related tasks. My confidence in this weakness is high, as the paper's comparison focuses on benchmark performance rather than model performance across different tasks. Fifth, the paper does not discuss the potential biases that may be present in the collected data. While the data is collected from real-world usage scenarios, there is no explicit discussion of potential biases inherent in the data. Factors like the demographics of the users, the types of projects they work on, and the specific IDE extensions they use could introduce biases. As I noted, the paper describes the data collection process in Section 3.1, but there's no explicit discussion of potential biases. This lack of discussion is a significant oversight, as these biases could affect the generalizability of the benchmark. My confidence in this weakness is high, as the paper lacks any discussion of potential data biases. Finally, the paper does not provide a detailed analysis of the computational resources required to run the benchmark. This information is crucial for researchers who want to use the benchmark, especially those with limited computational resources. ## Suggestions:

To address the identified weaknesses, I recommend several concrete improvements. First, to mitigate the subjectivity in test case generation, the authors should develop a formal specification for test case creation. This specification should include guidelines on the types of tests to be generated (e.g., boundary conditions, functional correctness, performance), the level of difficulty, and the expected behavior of the code after editing. This specification should be used to train the annotators and ensure consistency across the dataset. Furthermore, the authors could explore techniques like automated test case generation tools to supplement the manual process, which could help in creating a more diverse and objective set of test cases. For example, symbolic execution or fuzzing techniques could be used to generate test cases that are more likely to expose bugs or edge cases in the edited code. This would not only improve the reliability of the evaluation but also make the benchmark more robust and representative of real-world scenarios. Second, to enhance the benchmark's applicability, the authors should prioritize expanding the range of programming languages included. This could be done by leveraging the existing data collection methodology through the VS Code extension, focusing on repositories and projects that use languages like Java, C++, or Go. The authors could also consider a phased approach, starting with one or two additional languages that are widely used in different domains. This would allow for a more comprehensive evaluation of LLMs' code editing capabilities across different programming paradigms and syntax. For example, including a language like Rust, with its focus on safety and concurrency, could reveal different aspects of LLMs' ability to handle complex code editing tasks. The authors should also consider the specific challenges posed by each language, such as memory management in C++ or concurrency in Go, and ensure that the benchmark includes tasks that test these capabilities. Third, the authors should conduct a more detailed error analysis, categorizing the types of mistakes made by LLMs during code editing. This analysis should go beyond simple pass/fail metrics and delve into the specific reasons for failure. For example, are models struggling with understanding the context of the code, or are they making syntactic errors? Are they failing to correctly interpret the user's instructions, or are they generating code that is semantically incorrect? A breakdown of error types, such as incorrect logic, syntax errors, or failure to adhere to coding style guidelines, would be beneficial. Furthermore, the analysis should investigate whether certain types of edits are more challenging than others, such as bug fixes versus feature additions. This detailed error analysis would provide valuable insights into the specific weaknesses of current LLMs in code editing and guide future research efforts to address these limitations. Fourth, to better contextualize the performance of LLMs on EditBench, the authors should compare their results with performance on other code-related benchmarks. This comparison should include tasks such as code generation, code summarization, and bug fixing. For example, how do models that perform well on code generation tasks fare on EditBench? Are models that are specifically trained for bug fixing more effective on EditBench compared to general-purpose LLMs? This comparative analysis would help to identify the specific strengths and weaknesses of LLMs in code editing relative to other code-related tasks. It would also help to determine whether the challenges posed by EditBench are unique to code editing or whether they are shared with other code-related tasks. This analysis should also consider the types of contextual information used in different benchmarks, as this can significantly impact model performance. Fifth, the authors should provide a more detailed discussion of the potential biases in the collected data. The authors should analyze the distribution of code edits across different programming languages and identify any potential biases towards specific languages or types of code. They should also analyze the distribution of edit types (e.g., bug fixes, feature additions) to ensure that the benchmark is representative of real-world code editing tasks. Finally, the authors should provide a detailed breakdown of the computational resources required to run the benchmark, including the time taken to run the tests, the memory usage, and the hardware requirements. This information is crucial for researchers who want to use the benchmark, especially those with limited computational resources. The authors should also discuss the scalability of the benchmark and whether it can be used to evaluate larger models or more complex code editing tasks.
